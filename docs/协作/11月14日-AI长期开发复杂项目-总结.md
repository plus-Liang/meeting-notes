## 一、一句话结论

**AI 长期开发一个项目，失控不是"某次写错"，而是五类腐化在几十次迭代里累积出来的**：
样式/组件各自造、硬编码、重复逻辑、废弃 fallback 残留、文档过期。
作者的做法不是"写更好的提示词"，而是**在流程上装六道闸**：调研与拆解 → 方案（人要看得懂）→ 独立 review（四目标）→
测试分层 → 项目治理（规则/交互/文档巡检）→ 发布门禁与回滚。**人主要花时间在"治理流程"，不是写功能。**

## 二、五类腐化（为什么"不加束缚地让它自己叠"一定会烂）

| # | 腐化 | 原文要点 | 后果 |
|---|---|---|---|
| 1 | **样式/组件各自实现** | 每个地方单独实现一套，不复用已有的样式与组件；缺标准化文档 | 每次加功能"长得和上个月不一样"，产品没有统一感 |
| 2 | **硬编码** | 固定数值不维护成变量/常量 | 可维护性差：改个样式要改很多处；换个设备展示完全不同、兼容性差 |
| 3 | **重复逻辑实现** | AI 写新功能时不知道你以前写过，又实现一遍；两处复杂逻辑还不一致 | 浪费；两套不一致的逻辑后期必炸 |
| 4 | **废弃代码残留** | 迭代改了几版后，旧实现被留作 fallback（"GPT 很喜欢写 fallback"） | 项目没上线就有好几套 fallback；占上下文、浪费 token、后续读一堆无用代码 |
| 5 | **文档不断累积且过期** | AI 爱写方案、人也要求写；不清理就越攒越多；框架/业务改了，旧文档没人改 | **AI 采纳旧文档的旧消息 → 后续功能埋坑**（详见 §3.6） |

> **本文最值钱的一句**：**错误的文档比没有文档更可怕**——因为 AI 会以旧文档为标准去实现，而人很难发现。
> 文档相当于"精简版代码/目录"，是 agent 快速理解业务的高速入口，所以它必须**被巡检、被删减、被更新**。

## 三、六步治理（他的实际流程，按时间顺序）

### 3.1 动手前：技术调研与拆解（先别写功能代码）

- 让 AI 先调研：同类开源项目/框架用了什么技术？**能否直接基于它二开**。
- **开源协议是硬门槛**（他专门讲了一段）：
  - `MIT` / `Apache` 等宽松协议 → **可以改、可以商用**；MIT 二开后**要保留原作者版权声明**；
  - `GPL` / `AGPL` → **传染性**：二开后你的项目也必须开源 → **不能拿来做商业化闭源**。
- **有好的开源项目就不要重复造轮子**：存量项目经年维护，很多"看起来对 AI 反直觉、但为了兜住某种特殊场景"的写法，
  是 AI 从零写不出来的；用它能显著降低新分支的负担。
- 选型依据是**自己的实际业务**（长期维护 + 性能指标），不是"新不新"；**不熟的语言也能用 AI 开发**，
  但他会**直接问 AI 自己对该语言的掌握程度**作为选型输入（本项目对应：选型三原则 + 原则 V 复用权威）。

### 3.2 方案：怎么判断一份方案能不能用

- 用**沟通/产品设计强**的模型写方案；**同时让另一个模型交叉 review**（一个写、一个挑刺，**达成共识才可信**）。
- **方案必须人看得懂**。AI 写方案两种烂法（本项目直接对应"规划四问"的失效形态）：
  1. 堆技术细节 → 你不懂这门语言就完全看不懂；
  2. 把你的需求**换个说法重述一遍** → 没有对业务需求的判断、没有风险提示、没有具体做法，等于没写。
- **一份合格方案必须让人知道 5 件事**：UI 怎么改 / 大概什么思路实现 / 改哪块代码 / 特殊情况怎么处理 /
  **哪些地方需要人做决定** + **怎么验收**（是跑性能测试，还是人点一下看体验）。

### 3.3 执行：主对话保持干净，执行派给"便宜且能跑"的模型

- 写方案/交流用一个模型（额度贵、要干净上下文），**执行**派给另一个额度宽松、执行强的模型；
  主 agent 只做判断与派发（他用 skill + CLI 派发）。
- 效果：可以**非常频繁地**用强模型 review（方案 review、代码 review），因为 review 开销远低于写代码。

### 3.4 代码 review：四个目标（本次配图原文）

> 「就算我们自己不熟悉底层语言、不逐行读代码，也可以明确要求负责 Review 的模型**围绕四个目标检查并汇报**」——

| # | 目标 | 具体要求 |
|---|---|---|
| 1 | **业务是否真的跑通** | 功能有没有真正跑通、有没有对应测试、有没有**端到端测试**（模拟用户从输入到看到最终结果的完整流程）；**不是写一堆没用的单测** |
| 2 | **代码实现是否优雅** | 有没有冗余代码、有没有自己维护的**很绕/维护成本很高**的算法、有没有"有现成框架却自己造一套" |
| 3 | **有没有写完全没用的测试** | 没有实际意义的测试只会浪费后续跑测试的时间 |
| 4 | **有没有充分复用已有基建** | 项目里已写好的通用组件、工具函数等基础能力有没有拿来用，而不是重复写一套 |

- review 模型给**结论 + 建议** → 主 agent 判断派给谁修 → **发现问题直接打回继续改，全部通过再合分支**。
- 作者补充："AI 做的端到端测试只是**兜底**（确保业务能跑通）；**产品设计是否优雅、交互是否舒服，现阶段只有人能判断**"。

### 3.5 测试：分层 + 提速（别让模型过度防御）

- **测试分层**：运算逻辑抽成独立测试模块 → **改哪个区域就跑哪部分**，不做无脑全量；
  UI 相关抽离出来（UI 测试必须模拟人的操作，快不起来）；**改动与 UI 无关就不跑 UI 测试**。
- **别在改代码途中反复跑长测试**：改一小时里跑 10 次 × 2 分钟 = 20 分钟全花在测试上；
  应当"局部只跑模块测试，**功能完成后再跑重型回归**（端到端全流程）"。
- **性能测试交给 AI**（采集指标、火焰图、定位链路它非常快）；但**别让它钻牛角尖**追不切实际的指标，否则越改越烂。
- **把常用调试链路封装成 CLI/脚本**（传一个参数就跑），下次不用再模拟人工点击；
  桌面端可做后台静默运行，避免抢屏幕、能并行。
- **定期删无意义的单测**（"1+1=2"式断言）：它不仅浪费跑测试时间，改需求时还得同步改测试，浪费 token。

### 3.6 长期治理：规则沉淀 / 交互统一 / 文档巡检

- **规则沉淀（高频踩坑）**：同一个位置反复出问题，或**两个不同功能都出现同一个问题** → 立刻写进
  `AGENTS.md`/`REVIEW.md`，让后续**开发和 review 都重点看**这个位置。
- **交互标准统一**：同一产品里卡片选择器和下拉框混用 → 用规范把颜色/间距/通用组件收敛到**唯一文档来源**；
  否则"不同页面交互逻辑完全不同"，用户体验和品牌感都会烂。
- **文档巡检**：定期让 AI **通读当前代码** → 删过时文档 / 改成正确的 / 凝练。
  "错误文档比没文档可怕"：AI 读了旧文档又读了代码，最多浪费一次时间；**读了旧文档却没读代码，就会按旧标准实现**，
  而且人很难发现。

### 3.7 复杂 bug 排查与止损（人怎么介入）

- 修了很久/好几轮没修好 → **人介入，先让 AI 判断"核心问题在哪"，人来定方向**。
- 让**两个强模型各自定位**并给**自信度**：≥90% 才有信心；**两个都 <60 分 → 这功能可能真的很难实现**。
- 此时的选择（本项目 D-032 已有同款思路）：**直接砍掉这个功能**，或**换个方式满足用户需求**（曲先救国）；
  不要硬交付——AI 都定位不了的 bug，上线后维护成本极高、交付给用户不可靠。

### 3.8 发布：文档化流程 + **程序化硬限制** + 回滚

- 发布流程要文档化：怎么提交/建分支/合并/走什么测试/本地执行什么/更新官网更新日志。
- 更好的方式：**用程序硬限制 agent 的行动**——没在本地跑过测试**不许推送**；官网版本号没更新也**不许推送**。
- **保留上一版配置**，线上出问题能快速回滚。
- 桌面端案例：新版客户端一打开就崩，用户不会想到去官网下新版 → 他做了**安全模式**兜底（崩溃时退回安全模式，
  提示装新版）；且要保证"安全模式自己不会再崩"。

## 六、一句话给未来的自己

> **AI 长期开发的好坏，不取决于它某次写得多漂亮，而取决于你有没有"治理"它**：
> 五类腐化每天都会长（样式/硬编码/重复/残留/过期文档），
> 你要做的是把它们变成**可判定的闸门**（review 四目标、测试分层、规则沉淀、文档巡检、发布硬门禁、回滚兜底），
> 而不是每次出问题都重新想一遍。

## 2. 发现（都不阻塞）

### F-1（观察 + 提醒，低风险）`SimpleClientHttpRequestFactory` 默认缓冲整个请求体
`setBufferRequestBody` 默认 `true` → 上传给 ASR 的 multipart 请求体会先进内存。我用 javap 确认：**Spring 6.2 里
`setBufferRequestBody` 已标 `Deprecated: true`**，以后不能靠它关缓冲。
实测 108MB 请求体时内存平稳（735→740MiB，可能被 GC 吸收），**这次没出问题**；但最坏情况 = 200MB 上限 + ASR 并发 2 → 堆上最多 +400MB。
判定：**不返工**。等 T2.6（并发控制）或发布前，把工厂换成 `JdkClientHttpRequestFactory`（JDK HttpClient，天然流式，connectTimeout 可在 HttpClient 上设）更稳。已写进 T2.6 的备注。

### F-2（残留风险，接受）"纯 DNS 解析挂起"理论上不完全由 connectTimeout 兜住
我的黑洞实验证明的是 **TCP 连接阶段**被 5s 掐断；作者也说这次没复现 78s 那次的 DNS 挂起。
判定：接受。若以后真实用户环境复现（挂 >10s），用数据再定（可选项：预解析/探活/换 JDK HttpClient）。

### F-3（作者交办的 docs 债，我已补）
① `配置清单.md` §2 的 `$appKeys` 快照 34 → **35**（加入 `app.asr.connect-timeout-sec`）；

③ `接入指南.md` §3.2 补"ASR 不可用时的时延语义"（约 3–7s 进 RETRYING、约 8s 内 DEAD）。

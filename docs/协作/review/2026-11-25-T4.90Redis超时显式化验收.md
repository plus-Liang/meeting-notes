> **立即/短停 ≤10s 恢复；长停（≥60s）后 30s 内最终恢复，且恢复后队列可正常消费。** 容器侧容忍度：healthcheck `retries: 30 × interval: 10s` = 300s，恢复窗远在其内。

## 六、建议（不阻塞）

- **S1（恢复时间要写进运维口径）**：长停恢复 14–19s 属 Lettuce 退避，不是缺陷。建议在 `运维-监控与告警.md` 的健康检查段补一句「redis 长停后 ≤30s 自行恢复，容器 healthcheck 300s 容忍窗内不会误判」，避免运维把恢复延迟当成新故障。若要更快，另出小卡加 `ClientOptions`（固定 1s 重连），需 Java 白名单。
- **S2（日志噪声放大 ~10×）**：120s outage 期间本卡镜像产生 `Redis 不可用` **92** 条 + `RedisCommandTimeoutException` **35** 条，基线镜像同期只有 **8** + **9** 条——因为失败更快、重试更频繁。建议另出小卡做「依赖故障日志去抖」（仅在状态翻转时打 WARN，其后降为 debug/每 N 分钟一次），否则生产 Redis 维护窗口会刷屏。
- **S3（`.env.example` 行内注释的隐性依赖）**：本次 `WORKER_POLL_TIMEOUT_SEC=2  # 必须 < REDIS_TIMEOUT` 依赖 compose-go 剥离行内注释——我实测 `docker compose config` 解析为 `WORKER_POLL_TIMEOUT_SEC: "2"`（正确）。但这是**环境依赖**，应写进 `配置清单.md` 注一句「行内注释依赖 Compose v2 解析；其它解析器（如自写脚本）可能把注释当值的一部分」，防止将来有人手写解析踩坑。
- **S4（升级兼容要进 Release note）**：老部署 `.env` 若保留 `WORKER_POLL_TIMEOUT_SEC=10`，升级后 10s 的 BLPOP 会被 3s 命令超时切断 → 每次收队异常 + 空转（**契约测试只守 yml 默认值，守不住用户的 `.env`**）。建议 Release note 明示「升级需把该值改为 < `REDIS_TIMEOUT`」；长期应在 worker 启动时做运行期守卫（`poll >= timeout` → WARN 并强制回退），属 Java 改动，另卡。

## 7. 建议项

格式：`S编号｜文件:行号｜事实｜证据｜影响｜修法`。全部为非阻塞。

**S1（R3，中）清扫器的 `stale-minutes` 阈值没有测试钉住**
`StalePendingSweeperTest.java:40` 用 `ReflectionTestUtils.setField(sweeper, "staleMinutes", 2L)` 直接绕开 `@Value` 默认值，`:46/:57/:79` 用 `ArgumentMatchers.any()` 接住 cutoff。证据：变异 M7 把 `StalePendingSweeper.java:43` 的 `:2` 改成 `:0`，`StalePendingSweeperTest` 仍 4/4 全绿（`artifacts\T4.66\review\mut\mutations2.txt`）；对照 M8 同样改启动路径常量会让 `StartupRecoveryDbTest` 变红。影响：阈值退化成 0/1 时，每轮清扫会把"刚创建、还没入队"的行也重投，队列里出现大量无谓副本、WARN 噪声上涨，而 CI 不红、真栈也不报错。修法：`ArgumentCaptor<Timestamp>` 接住 cutoff 并与 `now()-2min` 比对（或断言 `cutoff` 单调），并在 `StalePendingQueriesTest` 补一条"阈值 0 时刚插入的行也入选"的反向用例。

**S2（R2，中）「tryPublish 永不抛」的契约比代码宽**
`StartupRecovery.java:84-85` 的方法注释与 `QueuePublisher.java:24-25` 的类注释都写 `tryPublish`「永不抛」，但实现只 `catch (ApiException e)`（`QueuePublisher.java:58`、`:79`），而 `publish` 只把 `DataAccessException` 转成 `ApiException`（`:46-49`、`:68-71`）——其它 `RuntimeException` 会直接穿出。影响：`StartupRecovery` 是 `ApplicationRunner`（`StartupRecovery.java:27`），穿出的异常会让**应用启动失败**；T4.62 之前这里是 `catch (RuntimeException e)`（宽），收窄后这条兜底消失了，注释却没变。修法：`pushBack` 里恢复 `catch (RuntimeException)` 兜底（一行），或把两处注释改成"仅 DataAccessException 不抛"。

**S3（R2/运维，中）三个清扫器配置键未进任何配置清单**
`app.queue.pending-sweep.{enabled,stale-minutes,interval-ms}`（`StalePendingSweeper.java:39/43/52`）在 `app/src/main/resources/application.yml` 与 `.env.example` 里都没有；`git grep pending-sweep` 只命中代码 3 处 + T4.61/T4.62 验收文档 + 任务清单 + 决策记录 D-201；`docs/项目/录音纪要平台/配置清单.md:184-192` 的 41 键 `$appKeys` 快照也没收录，而该文件第 203 行明写「新增配置项时必须同步加进这个列表」。影响：`APP_QUEUE_PENDING_SWEEP_ENABLED=false` 是故障止血开关（T4.61/T4.62 的验收全靠它关掉清扫来保证归因唯一），运维从配置清单里找不到它，出问题时只能读代码。修法：补 `application.yml` 三个键（带默认值与注释）+ `.env.example` + 配置清单同步。

**S4（R1/R2，中）陈旧阈值两套真相**
`StartupRecovery.java:32` `static final long STALE_PENDING_MINUTES = 2` 与 `StalePendingSweeper.java:43` `@Value("${app.queue.pending-sweep.stale-minutes:2}")` 是两个独立来源，而 `StalePendingSweeper.java:42` 的注释写「与 StartupRecovery.STALE_PENDING_MINUTES 的 2 分钟口径一致」。影响：运维把 `APP_QUEUE_PENDING_SWEEP_STALE_MINUTES` 调成 10（想减少重投）后，启动路径仍是 2 分钟，`/actuator` 与日志都没有任何提示；两个路径对"陈旧"的定义会静默分叉。修法：`StartupRecovery` 也读同一属性（`@Value` 注入），或把常量搬进 `StalePendingQueries` 作为唯一来源。

**S5（R2，低）`requeuedPending` 记的是"扫到的行数"，不是"成功入队数"**
`StartupRecovery.java:74` `requeuedPending = stale.size()`，与 `pushBack`（:86-94）里每条 `tryPublish` 是否成功无关；而同一次启动里 `recovered`（:79）也是"尝试数"。影响：Redis 不可用时日志会打印 `requeuedPending: 5`，实际入队 0 条，排障时误判为"已经恢复了"；T4.62 验收证据 `b1-startup-evidence.json` 里 0/1 两个数字恰好也是成功值，无法从格式上区分两种含义（对比 `StalePendingSweeper.java:72/80` 的 `requeued` 是精确成功数）。修法：`pushBack` 返回 `int` 成功计数，`requeuedPending = pushBack(stale)`。

**S6（R2，低）清扫器空库/查库失败静默返回，零日志**
`StalePendingSweeper.java:58-63` `catch (DataAccessException e) { /* 注释 */ return; }`，没有 `log`；而同一场景在启动路径是 `log.warn`（`StartupRecovery.java:57-61`、`:75-77`）。影响：若 `task` 表结构变更、权限收紧或连接池配置错，运行期清扫会**永久静默失效**，症状只是"任务一直排队中"，任何日志里都找不到线索（M9 也印证这条分支完全没有测试覆盖）。修法：保留不抛，但补一行 `log.warn("陈旧 PENDING 清扫跳过（可能空库/无表）：{}", e.getMessage())`。

**S7（R2/性能，中）阻塞式清扫占用唯一调度线程，会拖停 Webhook 扫描**
`MeetingNotesApplication.java:20` `@EnableScheduling`，`application.yml` 未设 `spring.task.scheduling.pool.size`（Spring 默认 1 线程），全仓只有两个 `@Scheduled`：`StalePendingSweeper.java:52`（60s）与 `WebhookDeliveryService.java:118`（`fixedDelay = 1000`）。`StalePendingSweeper.java:25-26` 的注释自陈"每条投递等待 Lettuce command-timeout（默认 60s）"。影响：Redis 半死（TCP 通、命令不响应）且陈旧行有 N 条时，一轮清扫最长占住调度线程 `N×60s`，期间 Webhook 到期扫描完全停摆（只延迟、不丢，但重试节律会漂）；这个边界只写在注释里，没有任何配置或隔离保障。修法：`spring.task.scheduling.pool.size: 4`（最小改动），或给清扫器单独的 `TaskScheduler`。

**S8（R2，低）恢复批量按 id 顺序 `leftPush`，落队后是倒序**
`StartupRecovery.java:63/73` 与 `StalePendingSweeper.java:68-72` 都是 `for id in list { publish(id) }`，而 `publish` 是 `leftPush`（`QueuePublisher.java:45`）。影响：Redis 长时间故障后积压 100 条陈旧任务，恢复后它们全部排在队头、且顺序完全颠倒（最后一条最先被处理、最早卡住的最后处理），与"先来先服务"相反；对用户表现为"越早提交的越晚出纪要"。修法：`StalePendingQueries` 的 SELECT 加 `ORDER BY updated_at DESC` 让倒序翻正（一行），或批量 `leftPushAll(list.reversed())` 并加注释说明。

**S9（R2，低）用户自愈路径不刷新 `updated_at`，会被清扫器再投一次**
`TaskRequeueSupport.java:67-70` 的 `publishPending` 只 `publish` + `log.info`，不 `touch`；而同一行的自愈场景（用户重提一个停在 PENDING 的旧任务）之后 60s 内，清扫器仍会把它当"陈旧"再投一遍（判据是 `updated_at < cutoff`，`StalePendingQueries.java:33`）。影响：队列多一份必然被跳过的副本（`TranscriptionWorker.java:136-138`），且清扫日志会打出 `swept:1 requeued:1`，把"用户重提"记成"清扫自愈"，归因变模糊。修法：`publishPending` 成功后 `stalePendingQueries.touch(id)`（或直接复用"先投后 touch"口径），使自愈路径对清扫器可见。

**S10（T4.65/R4，低）`-Repo` 只归一了分隔符，相对路径仍让 allowlist 失配**
`tools/check-maintainability.ps1:23` 只做 `$Repo = $Repo.Replace('/', '\')`，而 `RelPath`（:37）是 `$p.Replace($Repo + '\', '')`。实测 `-Repo '.'`（CWD=仓库）→ 阻塞 0 / **提示 4**，四条 M12 打印绝对路径（§0 #4，`maint-rel.txt`）；推而广之，尾部分隔符 `-Repo 'D:\new\projects\meeting-notes\'` 会拼成双反斜杠同样失配。同时 T4.65 验收文档 `docs/协作/review/2026-11-22-T4.65门禁分隔符验收.md` §1 只有「无参 / 反斜杠 / 正斜杠」三跑，没有相对路径用例。影响：门禁在人手/脚本传相对路径时输出假提示（当前两仓默认都无参跑，所以不阻塞发布）。修法：归一化改成 `[IO.Path]::GetFullPath($Repo).TrimEnd('\')`，并在 `RelPath` 里 `TrimEnd('\')` 后再拼；验收文档补一行相对路径用例。

**S11（R3，低）两处无效断言 + `tryX` 的 WARN 丢异常对象**
`QueuePublisherTest.tryVariantsReturnFalseOnRedisFailure` 的 `:82` `assertTrue(true, "两处均未抛出（走到断言即证明）")` 是恒真断言，真正起作用的是它上面的 `:80-81` `assertFalse`；`QueuePublisherTest.nullQueueKeyBehavesAsCurrentImplementation:87-93` 把「key 为 null 时仍然 `verify(listOps).leftPush(null, "7")` / `rightPush(null, "7")`」写成**期望行为**，等于给未定义行为上锁（M1 里它随方向变化一起红，说明它其实在测方向而不是 null 语义）。另：`QueuePublisher.java:59`/`:80` 的 `log.warn` 不带异常对象（`publish` 已在 :47/:69 记过带栈的 error，但 WARN 与 ERROR 是两条独立记录，排查"是哪条命令超时"时只剩一行无栈 WARN）。影响：测试语义噪声 + 排障信息不足，均不改变正确性。修法：删掉恒真断言、把 null key 用例改成"拒绝/抛 IllegalArgumentException"或删除；`tryX` 的 WARN 补 `e`（或降为 debug 并注释"栈在上一条 error"）。

**S12（R2/多实例，中）清扫器注释里的"多实例安全"论证不成立**
`StalePendingSweeper.java:27-29` 写「多实例假设：重投后 updated_at 刷新 + worker 按 status 认领（非 PENDING/RETRYING 直接跳过），重复入队的多余副本会被安全跳过（单实例部署为当前口径，D-061）」。但 worker 的认领是**两步非原子**：`TranscriptionWorker.java:133-134` 先 `SELECT status`，`:140` 再 `UPDATE ... SET status='RUNNING' WHERE id = ?`（无 status 谓词、不校验影响行数）。两个实例各 pop 到同一任务的两份副本时，都会在 SELECT 阶段看到 `PENDING`，于是双双置 RUNNING、双双处理（双倍 ASR 成本 + 双份终态写 + 可能双发 Webhook）。影响：当前单实例部署（D-061）下不出现，但注释把"重复副本安全"写成已论证的结论，会诱导下一次扩容直接开两副本；这是"注释承诺 > 代码实现"的典型。修法：把注释改成"重复副本在单实例下无害；多实例前必须先把认领改成 `UPDATE ... WHERE id=? AND status IN ('PENDING','RETRYING')` 并校验影响行数"（或顺手把认领改原子）。

**S13（文档同步，低）任务清单仍描述被 T4.62 改掉的测试形态**
`docs/项目/录音纪要平台/任务清单.md:398` 写「StalePendingSweeperTest（121 行，真 H2 MODE=PostgreSQL）」；实际 `StalePendingSweeperTest.java` 现为 90 行（含注释）、全 mock，真 H2 的 SQL 语义已迁到 `StalePendingQueriesTest.java`。影响：下一轮 review/接手者按文档去找"真 H2 的清扫器测试"会找不到，误判 R3 退化（我这轮就先怀疑了一次）。修法：更新该行描述 + 在 T4.62 段落补一句"SQL 语义迁至 StalePendingQueriesTest"。

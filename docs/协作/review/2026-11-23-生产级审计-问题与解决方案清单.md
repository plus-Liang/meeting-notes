## 3. 逐条详解

> 每条格式：**现象 / 假设 / 触发 / 后果 / 修法（取舍）/ 验证**。证据行号以当前 HEAD 为准。

### P-01 启动恢复把「所有 RUNNING」无条件回收（Blocker·多实例）

- **现象**：`StartupRecovery.run()` 先 `SELECT id FROM task WHERE status='RUNNING'`，再 `UPDATE task SET status='PENDING' WHERE status='RUNNING'`，然后逐条重新入队。
  证据：`worker/StartupRecovery.java:54`、`:57`、`:66`、`:81-84`；类注释自认单实例假设 `:17-19`（「多实例部署时别人的 RUNNING 会被误回收，须改为按 updated_at 阈值判僵尸」）。
- **假设**：应用是唯一会写 `RUNNING` 的进程，且启动时库里的 RUNNING 一定是上次自己崩掉留下的。
- **触发**：① `docker compose up -d --scale app=2`；② 滚动重启（新副本启动时旧副本仍在跑任务）；③ 将来把 worker 拆成独立 Deployment。
- **后果**：同一个音频被两个实例同时转写（ASR CPU ×2、配额/时长/成本双计，`task_result` 互相覆盖，摘要可能比上一次短）；同时 `attempts` 不动，失败计数被清零语义打乱。
- **修法**：
  1. **必须**：加 `heartbeat_at`（P-06），恢复条件改 `status='RUNNING' AND heartbeat_at < now() - interval '5 min'`；
  2. 可选：实例号 `instance_id` 列，只回收「自己上次的」（需要实例稳定标识，容器里不稳，故不推荐单独使用）；
  3. 取舍：心跳需要 worker 每 30s 一次 `UPDATE`，与 P-35 的写放大同一类成本；把心跳与 `last_used_at` 分开表/分开频率可控制。
- **验证**：真 PG + 两副本隔离栈；A 副本跑一个 8 分钟音频，期间 `docker restart` B 副本，断言库中该任务 `status` 不变、`attempts` 不变、最终只产生一次 `task_result`（对比 `webhook_delivery` 或 `updated_at` 次数）；负向：把心跳阈值改成 0 必须让测试红。

### P-02 Redis List 没有 ACK / 可见性超时（High）

- **现象**：worker 用 `leftPop(queueKey, POLL_TIMEOUT)` 取任务（BLPOP 语义：取走即从 List 移除），取到后先更新 DB 为 RUNNING 再干活；崩溃即丢「这条消息已取走」的信息。
  证据：`TranscriptionWorker.java:102-130`（`leftPop` 在 **`:106`**；`start()` 日志 `:88` 自述「BLPOP 阻塞取，超时 300s 仅用于优雅停机」）；`QueuePublisher.java:46-53`（push 端）、`:68-75`（尾插）。
- **假设**：任务状态在 DB 里是权威，消息只是「提示」，丢了还能靠清扫补。
- **触发**：worker 被 SIGKILL/OOM/节点重启，或 `docker stop` 超时被强杀。
- **后果**：任务停在 `RUNNING`；要等「应用重启」才会被 P-01 的恢复逻辑捞回。**单实例下能自愈，但自愈入口只有启动**（这是设计取舍，不是遗漏）；容器平台未必重启进程，多实例下更不能靠它。
- **修法（三档，按成本）**：
  1. 最小改动：加心跳 + 清扫同时扫「RUNNING 且心跳超时」（把 P-06 一起做），恢复从「启动时」扩展到「运行期」；
  2. 换 `Redis Stream` + 消费组（`XREADGROUP`/`XPENDING`/`XCLAIM`），天然有 ACK 与可见性超时，代价是引入新的客户端 API 与幂等要求（任务认领已幂等，兼容）；
  3. 换 DB 队列（`FOR UPDATE SKIP LOCKED` 直接取任务行），彻底去掉对 Redis 的强依赖，代价是轮询压力（可用 `LISTEN/NOTIFY` 缓解）。
- **验证**：隔离栈停 worker（`docker stop app`），期间提交任务，再 `docker start app`，断言任务被自动重投且只处理一次；配合 P-06 阈值调小观察 30s 级自愈。

### P-03 硬崩溃不计 attempts ⇒ 毒丸任务无限重试（High）

- **现象**：`markFailure` 只有在 Java 能捕获异常时才 `attempts = attempts + 1`；进程级崩溃（SIGKILL/OOM/`System.exit`）不经过它。
  证据：`TranscriptionWorker.java:247-274`，**`:252`** 是唯一自增点（`UPDATE … RETURNING attempts`）；`:271-273` 的 catch 只记 ERROR「可能卡在 RUNNING」。
- **测试有效性缺口**：`:252` 用的是 `RETURNING`（`StartupRecovery.java:52-53` 注释明说「RETURNING 是 PG 专用语法，H2 跑不了」），而 `TranscriptionWorkerTest` 的 `jdbc` 是 mock ⇒ **这条 SQL 在单测里从未被执行**，测的只是「有没有调用 `jdbc.update`」。真库路径仅靠 smoke/E2E 兜着。
- **假设**：所有失败都能被 try/catch 捕获。
- **触发**：某条音频让 ffmpeg/ASR 进程 OOM 或让 JVM 被杀；每次恢复后同一个任务再次把进程搞挂 = 崩-重启-崩的循环。
- **后果**：整个服务被一条任务反复打崩（可用性事故），且不容易定位（日志只有 error）。
- **修法**：恢复/心跳超时时 `attempts+1`（同一套 `markFailure` 语义），达到上限进 `DEAD`；再做 quarantine（隔离表）保留证据。取舍：恢复正常任务会多算一次尝试，需要把「心跳超时」阈值设得比最长任务更长（8 分钟音频约 60s 转写，阈值 5 分钟足够）。
- **验证**：单测构造「RUNNING 且心跳超时」的行，跑恢复两次，断言第二次进 DEAD；负向：去掉自增，测试必须红。

### P-04 ffmpeg 抽音轨「先读流再等进程」⇒ 超时永不生效（High）

- **现象**：`extract()` 先 `p.getInputStream().readAllBytes()`（阻塞到进程关闭 stdout），之后才 `p.waitFor(10, TimeUnit.MINUTES)`。
  证据：`worker/MonoWavExtractor.java:31-37`。
- **假设**：ffmpeg 一定会在有限时间内结束并关闭 stdout。
- **触发**：坏容器/超大文件/需要联网的输入让 ffmpeg 卡住且不再输出。
- **后果**：`readAllBytes` 永久阻塞 → **单线程 worker 永久卡死** → 队列全部任务排它后面（整站转写停摆），且 10 分钟超时**根本走不到**。
- **修法（仓库里已有现成范本，但要抄对结构）**：`fetch/ProcessMediaFetcher.java:72-140` 已经解决过同一个问题。**要抄的是它的三条结构，不是「先读流还是先 waitFor」这个动作顺序**：① `:72` `redirectErrorStream(false)` + `:79` `drainStderr(...)` 起**旁路线程**把 stderr 排空（否则管道写满照样死锁）；② `:86` 独立 **watchdog**（`Thread.sleep(timeoutMs)` + 超时 `destroyForcibly()`）而不是把超时挂在读流之后；③ 失败路径 `:135/:139` 抛 `FETCH_FAILED`。**`MonoWavExtractor:28` 现在是 `redirectErrorStream(true)`，必须同时改成 `false` 并接上排空线程**，否则只挪动作顺序等于没修。实现时外加 `-nostdin`，避免 ffmpeg 等待 stdin 而阻塞。
- **验证**：假 ffmpeg 不能只 `sleep`（sleep 不写管道，测不出写满死锁），要写一个**持续向 stderr 输出且不退出**的脚本，断言 10s 内进程被杀、任务进 RETRYING、下一任务继续被处理。

### P-05 清扫一次拉全量，积压时缺批量治理（Low-Medium）

- **现象**：`SELECT id FROM task WHERE status='PENDING' AND updated_at < ? ORDER BY updated_at ASC`，一次拉全量，然后逐条 `publishToTail` + `touch`。
  证据：`worker/StalePendingQueries.java:48-52`；调用方 `StalePendingSweeper.java:59`、`:70-71`。
- **索引不缺**（v1.0 写错，已删）：`V1__init.sql:22` `ix_task_status(status, updated_at)`、`:86` `ix_webhook_due(next_retry) WHERE next_retry IS NOT NULL` 都在，查询计划不会是全表扫。
- **不是一致性问题**（v1.0 表述过重，已修正）：多实例同时清扫只会**重复入队**（队列里两条同 id），worker 侧的原子认领（`TranscriptionWorker.java:134-141`，`WHERE status IN ('PENDING','RETRYING')` + 校验影响行数）保证**只处理一次**；代价是 `swept/requeued` 计数虚高与日志噪声。
- **仍然值得改的**：一次把几万行读进内存 + 逐条 Redis 往返，会长时间占用调度线程（`spring.task.scheduling.pool.size: 4`，P-25 的其它定时任务被挤）。改法：`LIMIT 200` + `FOR UPDATE SKIP LOCKED`，一次一批，下轮继续。
- **验证**：造 5000 条陈旧 PENDING，断言单轮处理量 = 200、总任务最终全被处理、调度线程无长阻塞。

### P-06 没有心跳字段 ⇒ 「僵尸 RUNNING」无法与「正在跑」区分（High）

- **现象**：`RUNNING` 期间除了认领与终态，没有任何 `updated_at` 刷新。
  证据：`TranscriptionWorker.java:134-141`（认领时写）、`:214`（DONE）、`:252`（attempts+1）。
- **假设**：进程活着 = 任务在跑。
- **触发**：P-02/P-03 的崩溃场景；或任务耗时超过运维设定的任何「陈旧阈值」。
- **后果**：判断任务死活只能靠“重启”（P-01），多实例无法安全清扫。
- **修法**：`heartbeat_at` 列 + worker 处理线程每 30s 刷新（或用 `pg` 的 `pg_stat_activity` 无法映射到 task，不可取）；阈值 = 最大任务时长 × 2（可配）。取舍：多一次写；可用批量/低频（60s）降低影响。
- **验证**：跑真实任务时观察 `heartbeat_at` 变化间隔 ≤ 60s；杀掉 worker 后 5 分钟内清扫把任务重新入队。

### P-07 结果落库 / DONE / webhook 三者无事务边界（Medium）

- **现象**：`finalizeResult` 顺序：`saveTranscript`（upsert `task_result`）→ 结构化/标点 → `UPDATE task DONE` → `webhookService.onTerminal`。
  证据：`TranscriptionWorker.java:209-216`；注释 D-069 明确「顺序即契约」。
- **假设**：中间不会崩。
- **触发**：在 `saveTranscript` 之后、`DONE` 之前崩溃（如 OOM）。
- **后果**：DB 里有转写结果但状态仍 `RUNNING`（随后可能被恢复成 PENDING 重跑；重跑会再 upsert，结果被覆盖——如果重跑失败，用户看到旧结果但状态是 DEAD）。
- **窗口有多大（v1.2 更正）**：`saveTranscript(:209)` 之后还要跑 `runAiStep("结构化")`（LLM，超时 `app.llm.timeout-sec:120`）与标点（ollama 路径 `:180` 秒级），最后才 `:214 DONE` ⇒ 窗口是**秒到分钟级**，不是我 v1.1 写的「毫秒级」。仍判 Medium 的理由改为：结果写入是 upsert，最坏是**结果被重跑覆盖**而不是丢数据；与 P-02/P-03 的「任务永久卡住」不同量级。
- **修法**：① 结果 + DONE 放同一事务（最小改动，webhook 仍在事务外）；② 更彻底：事务内写 outbox 表，webhook 由 outbox 消费（顺带解决 P-10/P-13 的顺序与重试语义）。
- **验证**：用 `kill -9` 在 `DONE` 前打断（可用测试钩子/断点），断言库里状态与结果自洽（要么都有要么都没有）。

### P-08 复活重投不是原子操作（Medium）

- **现象**：`reviveDead`（清 attempts/状态/死信）+ `publish`（Redis）+ `touch` 分三步，两次 DB 写不在同一事务。
  证据：`TaskRequeueSupport.java:42-48`、`:57-68`、`:73-77`。
- **假设**：中间失败可被清扫兜底。
- **触发**：DB 正常但 Redis 不可用；或进程在两步之间退出。
- **后果**：任务回到 PENDING 但没进队列 → 依赖清扫（最多 2 分钟 + 清扫可用性）才恢复；`dead_letter` 已被删，证据丢一半。
- **修法**：DB 两写放同一事务（`TransactionTemplate`），Redis 失败则保持 DEAD 并返回 503（已有 `...OrRollback` 版本可复用）；或改为 outbox。
- **验证**：注入 Redis down，调用重传，断言返回 503 且任务仍是 DEAD、死信行仍在。

### P-09 上传事务里做 S3 写（Medium）

- **现象**：`transactionTemplate.execute` 内先 `INSERT task`、`INSERT task_result`、`quotaService.consume`，再 `putObjectEnsuringBucket(200MB)`。
  证据：`task/TaskService.java:127-160`、`:150-158`。
- **假设**：对象存储写入快且稳定。
- **触发**：MinIO 慢（大文件/磁盘忙）。
- **后果**：数据库连接被长时间占用（Hikari 默认 10 个连接，未调整 → §7），高并发上传会打满连接池，其它接口排队。同时上传失败要回滚已写 DB。
- **修法**：先算 hash/时长 → 预生成 taskId（序列或 UUID）→ 先写对象 → 再开短事务写 DB + 扣配额；失败删孤儿对象（定时对账）。取舍：需要清理逻辑，但把长事务换成短事务，收益更大。
- **验证**：并发 10 个 200MB 上传，观察连接池占用与 P99 时延；断言事务时长 < 1s。

### P-10 Webhook 扫描无 LIMIT + 无界队列（High）

- **现象**：`scanDue` 每秒查「`next_retry <= now()`」全量行，逐条 `dispatcher.submit(...)`；dispatcher 是单线程无界队列（LinkedBlockingQueue 默认容量 `Integer.MAX_VALUE`）。
  证据：`webhook/WebhookDeliveryService.java` 扫描段（约 `:120-140`，含 `for (Long id : due) dispatcher.submit(...)`）、`attempt()`（`:148-185`）。
- **假设**：到期行数量小。
- **触发**：对端挂 1 小时后恢复（1s 内几万行同时到期）。
- **后果**：内存暴涨（每个提交是一个任务对象 + 闭包）+ 投递队列排队几小时 + 每秒重复扫描重复提交（`attempt` 的 `next_retry IS NOT NULL` 认领会挡住重复处理，但无谓的提交仍占队列）。
- **修法**：扫描 `LIMIT 100` + `ORDER BY next_retry`；有界队列 + `ThreadPoolExecutor.CallerRunsPolicy` 或直接丢弃并依赖下轮扫描；扫描间隔自适应（有积压时缩短）。
- **验证**：造 5000 条到期行，观察堆与 queue size；断言一次提交 ≤ 100。

### P-11 Webhook 投递单线程 ⇒ 队头阻塞（High；若确认只有单端点可降 Medium）

- **现象**：`dispatcher` 单线程，每条投递最长 10s 超时（`webhook.timeout-sec`）。
  证据：`WebhookDeliveryService` 的 dispatcher 初始化；`application.yml:217-221`。
- **假设**：端点都是快响应。
- **触发**：一个慢端点（挂起的对端 + 10s 超时）。
- **后果**：其它webhook 端点被连带延迟（10s × N 条排队）；任务完成通知不实时。
- **修法**：小线程池（如 4）+ 每 URL 并发信号量；或按 URL 分片；顺带加 jitter 退避（P-12）。
- **级别说明（R2 裁决）**：`callback_url` 全仓无写入点 ⇒ 现状只有**一个**全局端点，单线程只是「慢」，故可降 Medium；一旦开放 `callback_url` 或接入方多端点，则升回 High。**P-10（无界队列）在任何情况下都维持 High。**
- **验证**：一个端点用「睡 10s」的 stub，另一个正常端点；断言正常端点通知延迟 < 1s。

### P-12 退避无 jitter、无端点熔断（Medium）

- **现象**：`nextBackoffSec` 固定 1/10/60 秒。
  证据：`WebhookDeliveryService.nextBackoffSec`（`:188-190`）、`recordAttempt`（`:193-202`）。
- **触发**：对端恢复瞬间。
- **后果**：重试风暴（同秒并发），对端二次被打挂。
- **修法**：`backoff × (0.5 + random)`；端点连续失败 N 次后进入「冷却」，冷却期只记不投。
- **验证**：模拟 100 条同时失败，断言下次到期时间分散在区间内。

### P-13 `webhook_delivery` 只增不减（Medium）

- **现象**：终局行 `next_retry=NULL` 保留，无清理任务。
  证据：`recordAttempt`（`:193-202`）只改状态；无 `@Scheduled` 清理。
- **后果**：表无限增长，扫描变慢（无合适索引时更明显）。
- **修法**：每天清理 `next_retry IS NULL AND created_at < now()-30d`；或按月分区。
- **验证**：插入 10 万行后观察扫描耗时；清理后表大小回落。

### P-14 Webhook 签名无时间戳（Low）

### P-15 `occurred_at` 用投递时刻（Low）

### P-16 状态迁移散落各处、无单一入口（Medium）

- **现象**：`UPDATE task SET status=...` 至少 8 处（创建、认领、重试、DEAD、DONE、恢复回收、恢复重投、删除）。

### P-18 DEAD 无分类视图与批量重试（Low）

- **现象**：`application.yml` 无 `server.shutdown`、无 `spring.lifecycle.timeout-per-shutdown-phase`；worker `stop()` 只置标志 + `interrupt()`，不等当前任务、不记录在飞任务。
  证据：`application.yml`（全文未见）；`TranscriptionWorker.java:91-95`。
- **后果**：`docker compose restart` / 滚动升级时正在转写的任务被腰斩（且打断后是 P-02/P-03 的场景）；用户看到「任务消失又重跑」。
- **修法**：`server.shutdown: graceful` + `timeout-per-shutdown-phase: 30s`；worker 实现 `SmartLifecycle` 的 `stop()` 等待当前任务（或超时后主动 `markFailure` 记录），并 `stop()` 前不再取新任务。
- **验证**：跑一个 8 分钟音频，`docker compose restart app`，断言任务不丢（要么完成要么明确 RETRYING），且没有 `attempts` 因腰斩而丢。

### P-20 compose 只有 asr 有 restart 策略（High）

- **现象**：`docker-compose.yml` 里 `restart: unless-stopped` 只在 asr 服务（`:56-79`）；app/postgres/redis/minio 都没有。
  证据：`docker-compose.yml:9-133`。
- **后果**：宿主机重启/OOM 后除 asr 外全部不自愈（生产要人肉起）。
- **修法**：四个服务都加 `restart: unless-stopped`；OOM 类再叠加内存上限 + `oom_score_adj` 策略。
- **验证**：`docker kill` 各服务后等待，断言自动恢复。

### P-21/P-22 临时文件与磁盘无守卫（Medium）

- **现象**：`Files.createTempDirectory("mn-job-")`、`mn-upload-*`，`finally` 删除；SIGKILL 则残留；处理前不查磁盘余量。
  证据：`TranscriptionWorker.java:132-201`（临时目录/下载/抽音轨都在 `process()` 内）、`TaskService.java:111-113`、`:190-192`。
- **修法**：启动清理残留前缀；处理前检查 `usable space > 3 × 输入大小`；给 `/tmp` 挂独立卷并设配额。
- **验证**：模拟 SIGKILL 后重启，断言残留被清；填满磁盘时任务以明确错误码失败而不是写坏文件。

### P-23 扩容前置条件没有成文清单（Medium·范围边界）

- **现象**：单实例假设散落 P-01/P-02/P-06/P-19/P-29/P-30，但没有一页「要扩容先做什么」的清单；`asr.max-concurrency` 属于**已登记的 P2 计划配置**（见 §2），不是缺陷。
- **修法**：把「扩容前置条件」写成一页清单（无状态化 → 幂等认领 → 心跳 → 限流 → 多副本验收），按 P-01/06/19/29/30 顺序落地。
- **验证**：`--scale app=2` 跑 100 条任务，断言每条只处理一次、无任务丢失。

### P-25 Prometheus 指标缺失（Medium·建设项）

- **现象**：只暴露 `health,info,metrics`，无 `micrometer-registry-prometheus`、无 `/actuator/prometheus`。
  证据：`application.yml:228-235`（`exposure.include: health,info,metrics`）；`app/pom.xml` **已核实**无 `micrometer-registry-prometheus` 依赖（v1.0 曾标「未核实」）。
- **修法**：加依赖 + `management.endpoints.web.exposure.include: health,info,metrics,prometheus`；自定义指标：`tasks_queue_depth`、`task_duration_seconds`、`tasks_dead_total`、`webhook_delivery_lag_seconds`。
- **验证**：`curl /actuator/prometheus | grep tasks_`。

### P-26 无请求关联 ID（Medium）

- **现象**：只有 worker 设置 `MDC taskId`（`:117`），HTTP 入口无 `X-Request-Id`。
- **修法**：Filter 生成/透传 request id 写 MDC，worker/webhook 从任务行带到日志。
- **验证**：一次 API 调用 → 一次转写 → webhook，三处日志同一 id。

### P-27 无业务告警（Medium·建设项）

- **现象**：只有 health 探针；没有「队列积压」「DEAD 增速」「webhook 连续失败」告警。
- **修法**：Prometheus 规则 + Alertmanager；最少 3 条（队列深度 > 100、最老 PENDING > 10min、DEAD 5 分钟 > 10）。
- **验证**：注入故障触发告警（用 `amtool`/邮件 stub）。

### P-28 health 细节外泄（Low·部署注意项）

- **现象**：`management.endpoint.health.show-details: always`。
- **修法**：外网部署设 `when_authorized`，内网保留 always。
- **验证**：未带 token 请求 health，断言不含依赖细节。

### P-29 无接口限流 / 无登录防爆破（High）

- **现象**：无失败计数、无锁定、无限流过滤器；登录与注册都是免费尝试。
  证据：全仓 `git grep -i "ratelimit\|RateLimiter\|failedAttempts"` 无命中（见 §7 校验）；`AuthService` 登录只校验密码。
- **后果**：密码爆破（PBKDF2 让每次尝试昂贵，反而可被用来打满 CPU——DoS 放大）；接口被刷（提交任务消耗 ASR）。
- **修法**：登录失败计数（Redis `INCR` + TTL）+ 锁定；令牌桶（`Bucket4j` 或自写 Redis 计数）按用户+IP；`/tasks` 提交限速（如 10/min）。
- **验证**：连续错误登录 10 次，断言第 6 次起 429/423 且响应时间恒定；压测 `/tasks` 断言被限。

### P-30 无并发任务上限（High）

- **现象**：只有每日配额（120 分钟 / 50 任务），没有「同时在跑/在队列」上限。
  证据：`QuotaService.java:30-51`；`application.yml:213-215`。
- **触发**：一个用户提交 50 个 1 小时音频。
- **后果**：单线程 worker 要 50 小时（RTF 0.13 也要 ~6.5 小时），其它用户全部排队（饥饿）。
- **修法**：每用户 `PENDING+RUNNING+RETRYING` 计数上限（如 5），超限 429；或按用户公平调度（多 worker + 优先级队列）。
- **验证**：用户 A 提交 50 条，用户 B 提交 1 条，断言 B 在 5 分钟内完成（公平性）。

### P-31 配额不退（Medium，策略）

- **现象**：创建即扣，失败/删除不退；429 有 `Retry-After`（`ApiExceptionHandler.java:34`，按 JVM 本地日到零点）。
- **修法**：显式策略：要么文档写清「不退」，要么失败退一半/全退（需要 `quota` 记流水，不只是当日聚合）。
- **验证**：失败任务后查配额；按策略断言。

### P-32 默认 `API_TOKEN` 弱口令且等价 ADMIN（High）

- **现象**：默认 `change-me-api-token`，命中即 `ADMIN_USER_ID=1`，能删所有人任务；`.env.example` 也是同值。
  证据：`application.yml:200-201`；`ApiTokenFilter.java:118-120`。
- **修法**：启动时检测默认值/长度 < 32 → 拒绝启动（或强制首启生成随机值写入 `.env`）；文档把「必须改」提到第一步。
- **验证**：用默认 token 启动，断言启动失败并给出明确提示。

### P-33 Webhook 出站不经 SSRF 防护（Medium）

- **现象**：`WebhookDeliveryService.post(:254-264)` 直接 `HttpRequest.newBuilder(URI.create(url))`（`:255`）发给 `resolveUrl(:267-274)` 得到的地址；`fetch/UrlGuard` 的引用清单里**没有** `webhook/`（`git grep -l UrlGuard -- app/src/main/java` 只有 `fetch/` 的 5 个类 + `task/LinkTaskService` + `web/LinkPreviewController`）。
- **触发**：把 `WEBHOOK_URL` 配成内网地址（`http://169.254.169.254/…`、`http://postgres:5432`），投递时请求会真的打过去；签名头 `X-MeetingNotes-Signature` 也随请求外带（`:260`），等于把签名能力提供给被指向的主机。
- **为什么只判 Medium**：`callback_url` 全仓**无写入入口**（只有 `:268` 读），所以 URL 目前完全由运维配置决定——能改配置的人本来就能进容器，SSRF 的「外部输入驱动」前提不成立。
- **修法**：`post()` 前过 `UrlGuard.verify(url)`（解析 + 连接层双重校验，防 DNS rebinding）；顺带把 secret 只用于签名、不外带（现状是签名值外带，可接受，但需要文档说明「签名不等于 secret」）。
- **验证**：把 `WEBHOOK_URL` 指向 `http://127.0.0.1:8080/api/v1/version`，断言投递被拒并在日志里给出「目标地址不允许」；再用公网回环（ngrok 之类）断言正常投递。

### P-34 登录响应时序可枚举用户名（Medium）

- **现象**：`AuthService.login(:130-146)`；用户名不存在时 `:142` 直接 `throw unauthorized()`，用户名存在则 `:145` 才跑 `passwordHasher.verify(password, …)`（PBKDF2-HMAC-SHA256，120,000 次迭代）⇒ 两条路径耗时差一个数量级。
- **证据**：`web/AuthService.java:142`（查无此人立刻 401）与 `:145-146`（查到人才验hash）；`web/PasswordHasher.java:22-25`（120k 迭代）。
- **后果**：攻击者可对用户名做计时枚举，把「爆破密码」降级为「枚举账号 + 定向爆破」；`registration-enabled=false` 时更明显（没有注册噪声）。
- **修法**：无论用户是否存在都跑一次**等价开销的假哈希**（用固定 salt 的 dummy hash），失败响应与文案完全统一；再加登录失败计数（P-29 一起做）。
- **验证**：对「存在用户 / 不存在用户」各打 200 次，断言 p50/p95 差值在噪声范围内（如 <10ms）。

### P-36 分享链接过期行无清理（Low）

- **现象**：`task/ShareService.java:48-49` 只负责插入；读取处靠**查询条件**过滤——`ShareService:68` 与 `web/ShareController:96` 都是 `WHERE … revoked_at IS NULL AND expires_at > now()`；全仓没有定时清理。
- **后果**：`share_link` 表只增不减（每分享一次一行），一年后表变大、索引变脏；不影响正确性。
- **修法**：`@Scheduled` 每天删「过期超过 7 天或已撤销且超 7 天」的行（保留窗口便于排查）；或按 `expires_at` 月分区。
- **验证**：插一条 `expires_at = now() - 1 day` 的行，跑清理任务，断言被删；再断言未过期行不受影响。

## 5. 面试讲法（问题 → 证据 → 修法）

**① 为什么「单实例」是技术债（P-01/P-06/P-02）**
问题：早期为了简单，启动时把 `RUNNING` 全量回收，靠「进程重启」当唯一恢复手段。
证据：`StartupRecovery.java:54/57` 的无条件 UPDATE，类注释自己写了单实例假设；`TranscriptionWorker` 取消息是 BLPOP，没有 ACK。
修法：加 `heartbeat_at` 把「RUNNING」变成「有租约的 RUNNING」，恢复判据从「状态」改成「心跳超时」，多实例才安全；恢复从启动期扩展到运行期。

**② 一条坏音频如何打垮整站（P-04/P-03）**
问题：抽音轨先读流后等进程，超时是死代码；单线程 worker 一卡全停。加上崩溃不计 attempts，坏任务会无限次把进程搞崩。
证据：`MonoWavExtractor.java:31-37`；`TranscriptionWorker.java:88-100` 单线程循环、`:251-253` 唯一的 attempts 自增点。
修法：超时与流消费并行 + 强制 kill；恢复时对心跳超时的任务计 attempts，达上限进 DEAD + 隔离。

**③ 队列选型为什么不一开始就上 Kafka（D-009）**
问题：v1 要在单机零成本跑，且要能看见每条消息的去向。
证据：`QueuePublisher` 用 Redis List + DB 状态为权威；`503 QUEUE_UNAVAILABLE` 明确失败。
代价与补救：Redis List 无 ACK，所以补了「清扫 + 启动恢复 + 幂等认领」三件套；真要规模化，迁移路径是先 Stream 消费组再 DB 队列，Kafka 是最后选项（运维成本 > 收益）。
面试落点：能讲清「我明确知道这个选择缺什么、补了什么、以及什么时候该换」。

**④ Webhook 交付的可靠性（P-10/P-11/P-12/P-13）**
问题：一开始只追求「能发出去」，扫描无 LIMIT、单线程、固定退避。
证据：`WebhookDeliveryService` 的 scan/attempt 两段；`nextBackoffSec` 只有 1/10/60。
修法：限量扫描 + 有界队列 + 小线程池 + jitter + 终局清理；再进一步是 outbox 模式（与 P-07 一起）。
面试落点：至少一次投递 + 消费端幂等（`delivery_id` 去重）+ 可观测（lag 指标）。

**⑤ 安全默认值（P-32/P-29）**
问题：默认 `API_TOKEN` 是公开已知值且等价管理员；登录无失败计数（PBKDF2 反而被拿来放大 CPU）。
证据：`application.yml:200`；`ApiTokenFilter.java:118-120`；`PasswordHasher` 120k 迭代。
修法：默认值拒绝启动、强制随机生成；失败计数 + 锁定 + 恒定响应时间。
面试落点：「安全默认值」比「文档里写必须改」靠谱。

**⑥ 吞吐上限与公平性（P-30/P-23）**
问题：单线程串行是 v1 的明确取舍（D-061），但没有「每用户并发/排队上限」，一个用户可以饿死所有人。
证据：`TranscriptionWorker` 单线程；`QuotaService` 只有按日聚合。
修法：每用户 PENDING+RUNNING 上限 → 用户级公平调度 → 多 worker + 心跳，三步走。
面试落点：先讲清「为什么先串行」（确定性、无并发 bug、零成本），再讲「怎么平滑扩容」。

## 2. 阻塞项

### B1（阻塞）`LinkTaskService.java:166-182` / `TextTaskService.java:154-170`：幂等命中 PENDING 不自愈，link/paste 用户仍会永久卡 PENDING
- **事实**：`TaskService.java:182-187` 新增了 `if ("PENDING".equals(existing.status())) { enqueue(existing.id()); }`；`LinkTaskService` 与 `TextTaskService` 的同构幂等分支**只有 DEAD 分支**，非 DEAD 直接 `return new TaskCreatedResponse(existing.id(), existing.status(), ...)`（`LinkTaskService.java:182`、`TextTaskService.java:170`）——没有 PENDING 重投。
  证据命令：`git -C D:\new\projects\meeting-notes grep -n 'equals(existing.status())' -- app/src/main/java/com/meetingnotes/task`（PENDING 分支只出现在 `TaskService`）。
- **影响**：Redis 停机期间 `POST /api/v1/tasks/link`（或 `/tasks` 的文本/字幕提交）→ 503（但行已提交 PENDING，见 `LinkTaskService.java:185` 在事务外入队）→ Redis 恢复后用户重提同一链接/同一段文本 → **200/201 `reused=true, status=PENDING`，队列仍 0 条** → 删除被 `409 TASK_BUSY` 挡、批量重试被 `NOT_DEAD` 跳过、重传不自愈。这正是 T4.50 卡面 §1 第 4 点列的"用户自救全堵死"，只是换了两个端点。任务清单 T4.50 的验收语是"幂等重传能让卡住的 PENDING 自愈"（未限定端点），卡面 §3 第 2 条虽只点名 `TaskService.java:182`，但缺陷族相同、修法 4 行。
- **复现**（需隔离栈；我按约束没跑）：
  ```powershell
  docker stop mn-t450-redis-1
  curl -sS -X POST localhost:18080/api/v1/tasks/link -H "Authorization: Bearer <token>" -d '{"url":"https://host/a.mp3"}'   # 503 QUEUE_UNAVAILABLE，DB 行已 PENDING
  docker start mn-t450-redis-1
  curl -sS -X POST localhost:18080/api/v1/tasks/link -H "Authorization: Bearer <token>" -d '{"url":"https://host/a.mp3"}'   # 期望重新入队；实际 200 reused=true status=PENDING
  redis-cli -p 16379 LLEN meetingnotes:task-queue    # 期望 1；实际 0
  ```

### B2（阻塞）`TaskRetryService.java:79-86`：批量中途入队失败 → 该 id 变"PENDING 且不在队列"，重试端点随后 200 报成功（假成功搬家）
- **事实**：`retry()` 逐条"改 PENDING（79-82）→ 删死信（83）→ enqueue（84）"，`enqueue` 抛 503 时循环中断、`retried` 列表整体丢弃（`TaskRetryService.java:97`）。此时**当前 id 已是 PENDING、死信已删、队列没投**，而重试端点只处理 DEAD（`TaskRetryService.java:74-77`）。
- **影响**：客户端重发同一批 ids → 全部落到 `NOT_DEAD` 分支 → **HTTP 200 `{retried:[], skipped:[{id:8, reason:"NOT_DEAD"}]}`**，用户看到"成功"，任务永远 PENDING（只能靠重启 app 且 `updated_at` 已刷新过、还要再等 2 分钟——见 S3）。这与 T4.50 判定的 P1 现象（"看起来成功、永远排队、自救全堵死"）完全同形，只是从 `POST /tasks` 搬到了 `POST /tasks/retry`；且 503 响应体不带明细，客户端连"哪几条复活了"都不知道。
- **复现**（不跑栈也能证，建议补成失败用例）：
  ```java
  // ids=[7,8] 均为 DEAD；leftPush("8") 抛 DataAccessResourceFailureException
  assertThrows(ApiException.class, () -> service.retry(List.of(7L, 8L)));   // 8 已被 UPDATE 成 PENDING
  when(jdbc.query(... eq(8L), eq(1L))).thenReturn("PENDING");               // 回查 8
  RetryOutcome again = service.retry(List.of(8L));                          // => retried=[], skipped=[(8,"NOT_DEAD")]
  ```
- **要求修法**：enqueue 失败时把该 id 回退成 `DEAD`（`status='DEAD'`，可保留 error_code）并继续/或抛 503 时在 body 带 `{revived:[...],failed:[...]}`；不允许留下"PENDING 但不在队列"且重试端点不可达的状态。

## 3. 建议项

### S1（R4/重复实现）把入队收敛成一个组件
`TaskService.java:203-210`、`LinkTaskService.java:251-258`、`TaskRetryService.java:92-99`、`TextTaskService.java:190-197` 是同一段代码 4 份；`StartupRecovery.java:76-87` 是第 5 份变体（吞异常版）。本次 copy 时已经漂移一次（B1），如果不抽 `QueuePublisher { void publish(long taskId) throws ApiException }` 放进 `common/` 或 `task/`，下一次改口径必然再漏一处。**只修 B1 不抽公共类 = 下一张卡继续付同样的钱。**

### S2 重复入队没有去重，leftPush 还会插队
`TaskService.java:185`（重传自愈）与 `StartupRecovery.java:64`（陈旧 PENDING 清扫）都会无条件 `leftPush`，同一个 id 可以进队列 2 次以上。单实例下靠 `TranscriptionWorker.java:137-141` 的"状态不是 PENDING/RETRYING 就跳过"兜住，不会双跑；但代价是：(a) 队列里出现重复条目、`LLEN` 不再可信；(b) `leftPush` + `leftPop` 是**头进头出**，重投的 id 会**插到正常排队任务前面**（长音频排队时尤为明显）。建议入队前做一次轻量判重（如 `SETNX task:{id}:queued` 或入队后清标记），或至少把重复入队写进运维口径。

### S3 `StartupRecovery.java:56-57` 的注释与实现不符：没有"下个周期"
注释称"投递失败的等下个周期（≥2 分钟）再兜底"，但 `run()` 只由 `ApplicationRunner` 在**启动时**执行一次，全项目没有定时清扫。实际语义是"**下一次重启**，且距上次扫描 ≥2 分钟"，Redis 一直不可用时下一次重启仍会刷新 `updated_at` 再失败，等于无限顺延。运维按注释理解会误判（T4.50 交接里也写了"只在 app 重启时回收"，代码注释请对齐）。

### S4 `StartupRecovery.java:64-65` `requeuedPending` 计的是"扫到的行数"，不是"成功入队数"
`pushBack(stale)` 内部逐条吞异常（`76-87`），之后 `requeuedPending = stale.size()`。Redis 挂掉时日志仍打 `"requeuedPending":3`，实际 0 条投递成功——排障时会沿着错误的数字查。建议 pushBack 返回成功数，日志拆成 `requeuedPending` / `failedToEnqueue`。

### S5（M-1/M-4）2 分钟阈值外置
`StartupRecovery.java:62` 的 `interval '2 minutes'` 建议改成 `app.worker.pending-recovery-age`（`@Value` 注入 + 拼参数化 SQL，或读 `Duration` 再传 `?::interval`），同步 `application.yml:130-135`、`.env.example`、`配置清单.md`。说明：卡面 §3 第 3 条**逐字给了**这个字面量，所以不追究写码方；但按 M-1/M-4 它是硬编码，建议 Lead 在收口时补成配置项，否则下一个人照卡面抄。

### S6 第 5 处入队口径不一致：`TranscriptionWorker.java:268` 失败会让任务永久卡 RETRYING
`markFailure()` 先 `UPDATE ... status='RETRYING'`（266）再 `rightPush`（268），push 抛异常被外层 `catch (RuntimeException)`（271-273）记日志吞掉 → 任务停在 RETRYING 且不在队列。而 `StartupRecovery.java:22` 明确写"不碰 RETRYING（本就在队列里）"——这个假设在 push 失败时**不成立**，新的 PENDING 清扫也只认 PENDING（62）。结果：RETRYING 任务永久卡死，批量重试又只认 DEAD。这是与 T4.50 同族的洞，本次没覆盖；建议出卡（先 push 再改状态，或清扫时把 `status='RETRYING'` 且 `updated_at` 超阈值的也纳入）。

### S7 多实例下的重复处理窗口（现在是"单实例假设"，但 T4.50 把重复入队变多了）
`TranscriptionWorker.java:135-142` 是"SELECT status → 判 PENDING → UPDATE 置 RUNNING"，无 `WHERE status IN ('PENDING','RETRYING')` 条件、不看影响行数。单实例单线程无碍；一旦多开（或将来水平扩），两个 worker 可同时通过检查 → 同一任务跑两遍 ASR（真金白银）。本次让重复条目变多，建议顺手把置 RUNNING 改成条件更新 + 影响行数为 0 就跳过，成本 3 行。

### S8 503 没带 `Retry-After`
`ApiExceptionHandler.java:32-34` 只给 `QUOTA_EXCEEDED` 加了 `Retry-After`。`QUEUE_UNAVAILABLE` 是明确可退避重试的码（接入指南里 `ASR_UNAVAILABLE` 也写"退避重试"），接入方拿不到退避建议只能拍脑袋。建议给 503 加 `Retry-After: 5`（或统一在文档里给固定退避）。

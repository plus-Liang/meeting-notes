### P-33 Webhook 出站 SSRF（High，新增）

- **现象**：`WebhookDeliveryService.post():254-264` 直接 `HttpRequest.newBuilder(URI.create(url))`，`url` 来自 `resolveUrl():267-274`——优先 `task.callback_url`（`:268`），否则全局 `app.webhook.url`（`application.yml:218`）。**两条来源都不过 `UrlGuard`**。
- **假设**：webhook 目标 URL 可信。
- **触发**：① 若有任何入口能写 `callback_url`（当前实现全仓 `git grep callback_url` **只有读取点**，V1:17 建表列、`:268` 读取——**当前不可从 API 写入**，这是缓释因素）；② 运维/部署时把 `WEBHOOK_URL` 配成不可信地址；③ 未来加「每任务回调」功能时忘记校验。
- **后果**：服务端代攻击者访问内网（SSRF），可打云元数据 `169.254.169.254`、内网服务；且 webhook secret 会随请求发给该目标（HMAC 用的是全局 secret，见 `:260` / `:291-299`）。
- **定级理由**：当前写入口不存在，故不判 Blocker；但「URL 未校验 + secret 外带 + 未来必加 callback 写入」三条叠加，够 High。
- **修法**：`resolveUrl` 返回前调用 `UrlGuard.verify(url)`（复用现成 SSRF 防护，`fetch/UrlGuard.java:85-132`），失败记 WARN 并跳过该 delivery；或在 `onTerminal:93` 记账前拦。取舍：`UrlGuard` 默认拦内网，`WEBHOOK_URL` 若指向内网自建接收端需用 `allow-hosts` 白名单（该配置现有语义，`:30-31/:103-105`）。
- **验证**：单测注入 `url=http://127.0.0.1:8080/` 断言不投递；真栈设 `WEBHOOK_URL=http://169.254.169.254/` 断言无出站且日志有拦截记录。

### P-34 登录响应时序可枚举用户（Medium，新增）

- **现象**：`AuthService.login:141-142`——用户不存在（`rows.isEmpty()` 或 `password_hash='!'`）**直接抛 401，不做 PBKDF2**；存在则 `:145` 调用 `passwordHasher.verify`（120k 迭代，`:22`）。对外文案统一（`:282-284`），但**响应时间差达数十毫秒级**。
- **假设**：文案统一 = 无用户枚举。
- **触发**：攻击者批量试用户名，测响应时间分布。
- **后果**：可枚举已注册账号，为 P-29 的爆破提供目标清单；与 P-29 叠加放大。
- **修法**：用户不存在时用固定 dummy hash（启动时算一次）跑同样的 `verify`，再统一抛 401；取舍：每次失败登录都付 120k 成本（正是 P-29 的 DoS 放大），因此**必须与登录限流一起做**，否则顾此失彼。
- **验证**：压测 1000 次存在/不存在用户名，断言 P50/P99 时延差 < 阈值（如 10%）。

### P-35 多实例清扫重复入队（Medium，新增）

- **现象**：`StalePendingSweeper.sweepStalePending:58-89` 与 `StartupRecovery:71-76` 都查同一 `findStalePending`（`StalePendingQueries.java:48-52`），查询无 `FOR UPDATE SKIP LOCKED`，多副本会各自拿到同一批 id 并各自 `publishToTail`。
- **假设**：单实例（类注释 `:31-35` 明确这样写）。
- **触发**：`--scale app=2`，或滚动重启期间新旧副本并存。
- **后果**：与 P-05 叠加——队列里同一 id 出现多份；worker 原子认领（`:135-141`）挡住**重复转写**，但队列膨胀、清扫写放大（每份都 touch）。

- **验证**：两副本隔离栈，造 100 条陈旧 PENDING，断言队列长度增量 = 100 而非 200。

### P-36 分享链接过期行无清理（Medium，新增）

- **现象**：`ShareService.java:49` INSERT share_link，`ShareController.java:96` 读取时判 `expires_at > now()`；`ShareService.java` 与全仓**无任何 DELETE/清理任务**（实核 `git grep`）。`ttl-days` 默认 7（`application.yml:126`）。
- **后果**：表随分享数无限增长；`ix_share_link_token`（V5:15）膨胀。
- **修法**：`@Scheduled` 每日 `DELETE FROM share_link WHERE expires_at < now() - interval '7 days'`（保留余量便于审计）；或按期分区。
- **验证**：插入过期行，跑清理后断言消失、未过期行不受影响。

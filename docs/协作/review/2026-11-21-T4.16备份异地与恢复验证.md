### 2.2 对象存储（这里第一次失败，是本次最重要的发现）

按现有 `scripts\restore.ps1:70-71` 的口径清空 + 解包：

```sh
rm -rf /data/* ; tar xzf /backup/minio-data.tar.gz -C /
```

结果：

- `docker compose ps` → minio **healthy**；`/actuator/health` → `minio: UP`；
- 但**任何上传 → `500 STORAGE_ERROR 对象存储写入失败，请检查 MinIO 服务是否可用`**；
- minio 日志：

```
Error: Following error has been printed 3 times.. UUID on positions 0:0 do not match with,
expected 772c5d2f-4073-4753-807b-5216092a5638 got 13b1a7dd-dc63-4b4b-b4cb-551f2399037a:
(inconsistent drive found) (*fmt.wrapError)
```

根因：`rm -rf /data/*` **不匹配隐藏项**，新建的 MinIO 实例写的 `.minio.sys`（drive UUID `13b1a7dd-…`）留在卷里，随后被备份里的 `.minio.sys`（UUID `772c5d2f-…`）覆盖 → MinIO 判定 "inconsistent drive found"，元数据只读、写入全失败。

**健康检查盲区**：`/actuator/health` 的 minio 项只看「bucket 能否列出」，UUID 不一致时它仍然 UP —— 也就是说**监控会说"一切正常"，而用户上传全失败**。

修正口径（我手工重跑验证）：整卷清空**含隐藏目录**：

```sh
find /data -mindepth 1 -delete ; tar xzf /backup/minio-data.tar.gz -C /
```

→ MinIO 正常启动、无 UUID 报错。

2. **恢复链路可用，但脚本在灾难场景有 P1 缺陷** → 出卡 **T4.51**（`restore.ps1` 整卷清空含 `.minio.sys` + 解包后校验 `format.json`）。

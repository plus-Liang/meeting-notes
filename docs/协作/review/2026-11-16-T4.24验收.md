## 3. 缺陷与观察

### P3-1（真缺陷，**不阻塞但要求下一张卡开工前置修**）：`q` 为超长纯数字 → 500

- 复现（真实容器，只读）：`q=99999999999999999999`、`q=9223372036854775808`、`q=123456789012345678901234567890` 均得到 **500 `{"code":"INTERNAL_ERROR"}`**；而 `q=9223372036854775807` 与 `q=007` 正常 200。
- 根因：`TaskQueryService.list()` 里 `q.matches("\\d+")` 成立后直接 `Long.parseLong(q)`，超出 `long` 范围抛 `NumberFormatException`，没人接 → 500。
- 影响：违反文档"参数非法 → 400"的对外契约；任意接入方用 20+ 位数字即可打出 500 与错误日志噪音。概率低（正常任务 id 不会这么大），无数据损坏/无越权 → **P3**。
- 处置：见 `任务卡.md` 新增的 **T4.24b 收尾小修卡**（下卡前置，含单测/E2E/文档/验证口径）。

### P3-2（观察，同 T4.24b 顺手修）：搜索框没有 `maxlength`，101 字输入会走到 `renderFallback()` 的「服务暂时不可用」

- 后端按契约返 400，但前端 `loadFirst` 对任何非 200 一律 `renderFallback()` → 用户会看到"服务不可用 + 本机缓存列表"这种误导性错误（不是数据错误）。

### P3-3（记录不修）：搜索请求没有"响应序号守卫"

- 连续两次搜索若响应乱序（本地服务 <50ms，概率极低），后到的旧响应可能覆盖新结果；属既有 `getJson` 无 abort 的通病，记入 backlog 观察。

### P3-4（记录不修）：`counts` 与列表是两次独立请求

- 极端时点两者可能差一条（30s 轮询会对齐）；不影响"计数与 DB 一致"的判据。

### 观察（性能）：`source_uri ILIKE '%q%'` 无索引

- 当前 135 行 seq scan 无感；行数上万后再考虑 `pg_trgm` GIN（记入发布后性能备注，不做）。

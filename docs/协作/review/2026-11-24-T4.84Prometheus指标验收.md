## §3 代码审查（要点）

1. **Gauge 强引用**：`Gauge.builder("meetingnotes.task.count", bucket, value -> {...})` 以 `AtomicLong bucket` 作为 state 对象持有（注释写明「Micrometer Gauge 只弱引用 lambda，不弱引用 holder」）——这条容易踩，写对了。
2. **单条 SQL**：`refreshIfStale()` 内只有 `jdbc.query("SELECT status, count(*) FROM task GROUP BY status", collector)` 一次查询，`for (STATUS_BUCKETS)` 只做内存赋值（禁止项 4 满足）。
3. **节流**：`lastRefreshMillis` 是 `volatile long`，`now - last < cacheSeconds*1000` 判断；**初值为 `0`（启动即过期）**，注释明确记录了「不能 `Long.MIN_VALUE`——`now - MIN_VALUE` 会 long 溢出为负、节流恒真、指标永不刷新」，即写码方自曝的 bug 与修法都留在代码里。
4. **异常口径**：`catch (RuntimeException)` 内 `failureWarned.compareAndSet(false,true)` 只 WARN 一次、保留缓存旧值、不外抛（`/actuator/prometheus` 不会 500）；成功刷新时 `failureWarned.set(false)` 复位。
5. **无后台线程**：`grep @Scheduled` 在新增文件为 0；类 javadoc 写明「抓取驱动」与「单实例口径」。
6. **测试与实际同源**：4 例覆盖「首次装载 / 窗口内不重查（改库后仍旧值）/ `cacheSeconds=0` 立即重查 / 表被删保留旧值且 `assertDoesNotThrow`」。

## §7 建议（S1–S4）

- **S1（文档口径，建议下一轮小改）**：`TaskMetrics` javadoc 写「多实例各报各自视角的同一 DB 计数（值相同，无聚合问题）」——对**单值读取**成立，但 PromQL 里 `sum(meetingnotes_task_count{status="DONE"})` 跨实例会**重复累加**（每实例各报一次）。运维文档的告警表达式若用 `sum(...)`，多实例部署时会翻倍。建议文档明确「按 status 取值请用 `max by (status)` 或先固定 `instance`」，或将来给指标加 `instance` 说明。
- **S2（并发）**：`refreshIfStale()` 无锁，两个并发抓取可能同时刷新（多一次查询，无害）。若要严格，可在 `lastRefreshMillis` 上用 `AtomicLong.compareAndSet`。
- **S3（阻塞语义）**：刷新发生在**抓取线程**上，DB 慢时抓取也会慢；`cacheSeconds=15` 已限频，但文档应写明「指标抓取超时 = DB 慢」的排查指向。
- **S4（配置可见性）**：`app.metrics.cache-seconds` 不在 yml，用户无法从 yml 发现；README/运维文档已提，但 `配置清单.md` 未收录（本卡未改该文件）。建议后续统一「@Value-only 键也要登记进配置清单」。

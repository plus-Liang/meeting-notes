## 2. 深挖发现（P1，已出卡 T4.50）：Redis 不可用时提交「假成功 201」，任务永久卡 PENDING

演练里 S3 最初是 FAIL，查下去发现两件事，**一件是我的断言口径错，另一件是真缺陷**。

### 2.1 口径修正：401 不是「依赖挂导致的鉴权失败」，而是令牌轮换

`web/TokenService.java:11-15` 的口径是「同一用户仅保留一个有效令牌，重新登录即轮换（旧令牌立即失效）」。
我第一版 S3 在停机期间先调 `login`（轮换）再用旧 token 提交 → 401。**这是我自己的测试顺序造成的**，不是 Redis 依赖问题。校准探针 `probe-s3b.py` 证明：**Redis 停机期间**，未轮换的令牌

- `POST /api/v1/tasks` → **201 `PENDING`**（提交被接受）
- `GET /api/v1/tasks` → **200**（列表正常）
- `POST /api/v1/auth/login` → **200**（认证走 DB，不依赖 Redis）

### 2.2 真缺陷：任务行提交了，队列没投进去，且没有任何机制补投

证据链（隔离栈 mn-drill，两个用户两次提交）：

| 检查 | 结果 |
|---|---|
| 停机期间提交 | `201 {"task_id":13,"status":"PENDING"}` |
| Redis 恢复后队列 | `llen transcriptions` = **0** |
| DB 任务行 | id 11 / 13 **仍是 `PENDING`**，`updated_at` 停在提交时刻（6 分钟后复查未变） |
| 重启 app（触发 StartupRecovery） | 日志 `启动恢复：回收 RUNNING 僵尸任务重新入队`、**`"recovered":0`**；11/13 仍 PENDING |
| 用户能否自救 | 删除 → `409 TASK_BUSY`（`task/TaskDeleteService.java:127`）；批量重试 → `NOT_DEAD` 跳过（`task/TaskRetryService.java:74`）；重传同一文件 → 幂等命中直接返回 `PENDING`、**不重新入队**（`task/TaskService.java:182`） |

代码位置：`task/TaskService.java:196-202` 的 `enqueue()` 用 `catch (DataAccessException e)` **只打日志不上抛**，注释声称「由 T2.3 的恢复机制兜底」，但 T2.3 = `worker/StartupRecovery.java:42-57` **只回收 RUNNING**，不碰 PENDING。同款 `enqueue` 还在 `LinkTaskService.java:250-255`、`TaskRetryService.java:91-96`、`TextTaskService.java:193`。

**后果**：Redis 抖一下（甚至只是重启），这段时间提交的用户会看到「已提交、排队中」，然后**永远排队**，且删不掉、重试不了、重传也没用。对比 S4：MinIO 挂时正确返回 `500 STORAGE_ERROR` —— 同一套系统里两种依赖故障的处理口径不一致，这才是本缺陷的本质。

修法要求见 `artifacts/T4.15-drill/card-T4.50-pending-stuck.md`（① 入队失败抛 503；② 幂等命中 PENDING 时重新入队；③ 启动恢复扩展到陈旧 PENDING）。

## 3. 顺带得到的运维结论（可直接写进文档）

1. **依赖挂时 app 的健康检查会「阻塞到超时」而不是立刻 503**：Redis 停机时 `/actuator/health` 要 **~60 s** 才返回 503（`RedisReactiveHealthIndicator` 阻塞），Postgres 停机时直接超时。做健康探针要给够超时（≥70 s），否则会把"慢"误判成"死"。
2. **asr / minio 停机时 app 健康检查如实变 DOWN**（503），不会假 UP —— 这条是好的，可写进运维文档。
3. **网络分区恢复不是瞬时的**：app 与整个 docker 网络断开后重连，连接池重建约 **50 s**（Hikari + S3 客户端），期间提交会 500/连接失败。运维需要知道"恢复后等 1 分钟再判定失败"。
4. **内容去重会影响"重试验证"**：同一用户重复上传同一音频会幂等命中既有任务（响应带 `reused`），因此做故障演练/压测时必须**每个场景换新用户**，否则会误判成"任务没在跑"。

## 4. 演练脚本自身的 5 次返工（教训，已进 K-105）

| 轮次 | 症状 | 根因 |
|---|---|---|
| v1 | S1「PASS」但 asr 其实没被杀 | 容器名单少了 compose 加的 `-1` 后缀，`docker kill mn-drill-asr` 报 `No such container`，而脚本**没断言 rc** → kill 变空操作 = **假 PASS** |
| run2 | S2 `recovered=0`、S3 看不到日志 | S2 中途 `login()` 换了新用户（用别人 token 轮询旧任务）；`logs()` 只取尾部 3000 字把启动期证据切掉 |
| run3 | S6/S7 FAIL | `docker network disconnect` 断的是**整网**（不止 asr），重连 5 s 就提交撞 `500 STORAGE_ERROR`；实测 50 s 后才自愈 → 断言窗口太短 |
| run4 | S3 FAIL（`日志命中=0`） | worker 每 10 s 才写一次日志，采样窗口只等了 10 s；且停机期间先 `login` 造成 401 误判 |
| run5 | **10 PASS / 0 FAIL** | 逐条修正：显式容器名 + `must()` 断言每个 docker 命令 rc=0；每场景新用户、场景内复用 token；日志用全量 `docker logs` 过滤 + 轮询；S3 先提交后登录并给 70 s 超时；S6 重连后轮询 6×20 s 记录自愈耗时 |

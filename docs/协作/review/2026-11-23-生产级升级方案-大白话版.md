# 从 demo 到生产级：方案与依据（大白话版）

> 给不需要读代码的人看。想知道每条问题在哪一行、怎么验，看 `docs/协作/review/2026-11-23-生产级审计-问题与解决方案清单.md`（v1.3，34 条）。
> 本文回答三件事：**现在到哪一步、接下来按什么顺序做、为什么这么选、依据从哪来。**

## 一、现在这个项目是什么水平

一句话：**能自己用、能发给朋友部署，但还不敢多开一台机器、也不敢给陌生人用。**

已做到（都有可点验的证据）：

| 事 | 证据 |
|---|---|
| 功能闭环 | 需求文档里的 11 条完成定义，10 条做到（第 11 条「陌生人 30 分钟跑通」只有脚本模拟，没有真人） |
| 自动化测试 | 单测 551 条全过；CI 两条流水线全绿 |
| 真跑过 | 你机器上现在就是 179 条任务、真实模型、5 个容器全健康 |
| 出过事能扛 | 故障注入 10 种场景全过（硬杀转写服务 2 秒进失败、整站断网 50 秒自愈） |
| 数据能救 | 备份 + 恢复演练过（数据库 197KB、对象存储 473MB，恢复后任务还在） |

所以它不是玩具，也不是可以直接卖给别人的产品——中间差的是「不顺利时怎么办」。

## 二、demo 和生产的真正差别

demo 心里假设三件事：**一路顺利、只有一台机器、没人恶意**。
生产必须假设：**随时会崩、随时要扩容、随时有人攻击**。

这次审计干的事，就是把代码里所有这类"心里假设"翻出来，一条条写成「什么条件下会炸、炸了什么样、怎么修、怎么验」。翻出 34 条。

## 三、34 条按「会怎么坑你」分成四堆（不按技术分）

| 堆 | 会有多疼 | 典型条目 |
|---|---|---|
| **A. 会丢活 / 卡死** | 用户看到任务永远转圈，或者整站转写停摆 | 进程崩了没心跳、重启把别人正在跑的任务抢回来、转写超时永远不生效、webhook 堆在一个线程里排队 |
| **B. 会被人打穿** | 别人能拿到管理员、能爆破、能让服务器去打内网 | 默认口令等于公开管理员、登录不限制次数、时间差能猜出用户名、webhook 地址没做内网拦截 |
| **C. 出事看不见 / 起不来** | 挂了没人知道、机器重启后要人手动拉 | 没有监控指标、没有告警、没有优雅停机、容器没有重启策略 |
| **D. 脏数据 / 隐性成本** | 越跑越慢、账对不上 | 清扫一次拉全表、对象存储写在数据库事务里、失败不退配额、分享链接表只增不减 |

还有一类是**明确不修**的，也写清了理由：多租户、Kafka、自动扩缩容、DRM 等——自托管单机场景下，收益不抵成本。

## 四、从 demo 到生产级：四步走，每步为什么必须在这个位置

### 第一步 · 一天内能做完，但事故成本最高（4 张卡）

「默认口令必须拒绝启动」→「优雅停机」→「容器重启策略」→「转写超时」。

为什么排最前：这四件事都是**改动几个字符到几十行**，但对应的是「管理员被接管」「停机丢任务」「机器重启后全站不自愈」「一个坏文件把整站转写卡死」——都是当天就能炸、炸了最难受的。

### 第二步 · 三天到五天，一组三张卡必须一起验收

「任务心跳（谁还活着）」→「重启恢复只看僵尸」→「队列可见性超时（取走没确认的自动重投）」。

为什么必须绑在一起：单独上线「心跳」而不改「恢复逻辑」，会出现"心跳写进去了、但重启还是把别人正在跑的任务抢回来"，**比不改更危险**。所以这三张卡同批验收，不允许中间态进生产。

### 第三步 · 两三天，攻击面收口（4 张卡）

「接口限流」「登录失败锁定」「webhook 出站拦截内网」「登录时间差抹平」。

为什么在扩容之前：多开一个实例，攻击面就翻倍；先把"谁能打进来、打进来能干什么"收干净，再谈扩容。

### 第四步 · 三到五天，让它"出事能看见、能补"（3 张卡）

「关键指标暴露」「业务告警」「webhook 改成先落库再发（outbox）」。

为什么最后：前三步解决"跑得对"，这一步解决"出事我知道、我还能补"。指标和告警要建在已经稳定的行为上，否则就是给一个还在抖的系统装报警器。

### 什么时候算"生产级"了

四条硬门槛 + 两条演练，全部有证据才叫到：

1. 默认口令启动不起来；
2. `docker stop` 时正在跑的任务不丢/不脏；
3. 机器重启后容器自己回来、任务自己续上；
4. 单个坏输入不会把整站卡死；
5. 双副本跑一遍故障注入，同一任务只被转写一次；
6. 指标页能看到队列深度、最老待处理任务年龄、失败率。

## 五、为什么选这些方案（每条一句话，外加"没选什么"）

| 要解决的问题 | 选的方案 | 为什么不选另一个 |
|---|---|---|
| 任务怎么排队 | 数据库存任务 + Redis 做队列 | 不上 Kafka：要三节点集群、要专人运维；而且 Kafka 的消息在系统里看不见，做不了「死信列表」这种运维界面 |
| 多个实例怎么不抢同一个任务 | 一条带条件的 UPDATE，看影响行数（**已经做了**） | 不加分布式锁：数据库自己就能保证原子，少一个组件、少一类死锁 |
| 清扫任务时怎么不重复 | 数据库行锁 + 跳过已被锁的行（`FOR UPDATE SKIP LOCKED`） | 不用 Redis 锁当主方案：锁会过期、要续租，是新的坑；Redis 锁只用来"少扫一点" |
| 取走的消息丢了怎么办 | 定期重投 + 原子认领 + 结果幂等（可见性超时） | 不追求"消息绝不丢"：Redis 队列没有确认机制，硬做要换成专业消息队列，成本翻倍 |
| webhook 怎么不丢、不乱序 | 先写"待发送表"再发（outbox） | 不在业务事务里直接发 HTTP：网络一抖就丢，还拖慢事务 |
| 怎么知道实例活着 | 干活期间定期刷新任务行的更新时间当心跳 | 不加新表、不引注册中心：复用已有字段，代价一条 UPDATE |
| 为什么不支持多租户 | 写进"明确不做"清单 | 自托管单机用户场景用不上，做了就是给自己加复杂度 |

## 六、依据从哪来（四类，都能点验）

1. **代码行号**：每条问题都写 `文件:行`，并且从这一轮起强制「行号只用 python/read 工具复核」——因为用 PowerShell 取行号曾连错 6 处，被外部审查抓到。
2. **真栈实验**：停 Redis、停数据库、硬杀转写服务、双副本并发、停应用……每个数字（多少秒自愈、几条被重投）都来自我自己的隔离环境，不是推算。
3. **项目自己的决策记录与坑库**：216 条决策（当时为什么这么选）+ 147 条踩坑（踩过什么）——比如「单线程串行消费」是 D-061 明确取舍，不是疏忽。
4. **三轮外部审查**：另一个 AI 连续三轮逐条挑错（抓出我 6 处行号错误、1 处误报），我逐条核实后**对的改、错的举证反驳**。这一来一回本身就是"这个结论被别人挑过"的证明。

## 5. 阻塞项

### B1 失败重投从队尾变队头，与类注释契约相反，且回归被测试一并改掉

- 位置：`app/src/main/java/com/meetingnotes/worker/TranscriptionWorker.java:262`（调用）→
  `app/src/main/java/com/meetingnotes/task/QueuePublisher.java:39`（`leftPush`）；契约注释在
  `app/src/main/java/com/meetingnotes/worker/TranscriptionWorker.java:23`；消费端 `TranscriptionWorker.java:106`（`leftPop`）。
- 事实：父版本该处是 `redis.opsForList().rightPush(...)`（`git show 3ac0c58:.../TranscriptionWorker.java` 可验），
  T4.52 改为 `queuePublisher.tryPublish(taskId)`，而 `QueuePublisher.publish` 用的是 `leftPush`。
  消费者从左侧 `leftPop`，所以：**原语义=排到队尾让位给已排队任务；新语义=插到队头，立刻被自己取回重跑。**
  类注释 `:23` 仍写「RETRYING 重新入队（队尾，FIFO 不插队）」。
- 影响：失败任务在**同一个 worker 线程里立刻重跑**，没有任何退避；ASR 瞬时故障（连接拒绝、超时）时，
  单任务可在数秒内烧完 `max-retries`（默认 3）直接进 DEAD——本该是"换时间换机会"的重试变成"连续撞墙"。
  同时它插到队头，队列里其他 PENDING 任务被反复插队（单线程下即饥饿）。
  更糟的是 `TranscriptionWorkerTest.java:238` 把断言从 `rightPush` 改成 `verify(...).tryPublish(9L)`，**行为回归被测试固化了**。
- 复现（静态，3 条命令即可确认方向反转）：
  ```
  git -C D:\new\projects\meeting-notes show 3ac0c58:app/src/main/java/com/meetingnotes/worker/TranscriptionWorker.java | Select-String rightPush
  git -C D:\new\projects\meeting-notes show 3ac0c58:app/src/main/java/com/meetingnotes/worker/TranscriptionWorker.java | Select-String '队尾'
  Select-String -Path D:\new\projects\meeting-notes\app\src\main\java\com\meetingnotes\worker\TranscriptionWorker.java -Pattern 'leftPop|tryPublish'
  ```
  第 1 条有输出、第 2 条有输出、第 3 条显示 `:106 leftPop` + `:262 tryPublish`（→`QueuePublisher.java:39 leftPush`），
  三条一起就是"注释说队尾、代码走队头"。
- 建议修法：给 `QueuePublisher` 补 `publishToTail/tryPublishToTail`（`rightPush`），worker 重投用尾插；
  或明确取消"不插队"语义并改掉 `:23` 注释 + 在 `:262` 写清"头插=立刻重试"。二选一，但不能注释说队尾、代码做队头。
  同时把 `TranscriptionWorkerTest.java:238` 的断言改成验证**尾插**（例如验证 `rightPush` 的包装或 listOps 调用方向）。

## 6. 建议项

### S1（P1）S6 退回 PENDING 后，运行中的实例没有任何重投机制——"不卡 RETRYING"只是换了卡住的状态名

- 位置：`app/src/main/java/com/meetingnotes/worker/TranscriptionWorker.java:266`、
  `app/src/main/java/com/meetingnotes/worker/StartupRecovery.java:29、49、81-83`。
- 事实：`PENDING` 的自愈只有两条路——`StartupRecovery.run()`（`ApplicationRunner`，进程启动才跑一次）和客户端重提
  （`TaskService.java:177-181` 等）。运行中的进程没有周期性扫描：`git grep -n '@Scheduled'` 只命中
  `WebhookDeliveryService.java:118`。
- 影响：Redis 抖一下导致重投失败 → 任务退 PENDING；Redis 恢复后 worker 的 `leftPop` 空转，任务**无限期**不执行，
  直到下次重启或用户重传同一内容。用户视角是"提交成功但永远不出结果"。
- 复现：`git -C D:\new\projects\meeting-notes grep -n '@Scheduled\|@EnableScheduling' -- app/src/main/java`
  → 只有 webhook 一处；对比 `StartupRecovery.java:49` 只有 `run()` 入口。
- 建议修法：加一个低频 `@Scheduled(fixedDelay = 120000)` 的 sweep（复用 `StartupRecovery` 的陈旧 PENDING 查询与 `pushBack`），
  或让 worker 在 `leftPop` 超时时顺手扫一次陈旧 PENDING。已有 `@EnableScheduling` + Webhook 的 drain 先例，成本很低。

- 位置：`app/src/main/java/com/meetingnotes/worker/StartupRecovery.java:52-58`（注释 `:53`）。
- 事实：`TranscriptionWorker` 是 `SmartLifecycle`（`TranscriptionWorker.java:30`），`start()` 在 `:83-88` 开线程；
  Spring 在 context refresh 的 `finishRefresh` 阶段启动 lifecycle bean，**早于** `ApplicationRunner`
  （`StartupRecovery.java:29`）。所以 `run()` 执行时 worker 线程已在 `leftPop`。`:54` 的 SELECT 与 `:57` 的全表
  `UPDATE ... WHERE status='RUNNING'` 之间，worker 完全可能把某个任务置为 RUNNING。
- 影响：那个"活任务"被 `:57` 改回 PENDING 且 `updated_at=now()`；worker 跑完会置 DONE，一般自愈，
  但它若在跑完前崩溃，留下的 PENDING 因 `updated_at` 很新，**下一次启动的 2 分钟阈值兜不住**（要等再下一次重启，或用户重提）。
  另外日志 `recovered=stuck.size()` 统计不到它。
- 复现：静态证据即可——`StartupRecovery.java:53` 注释 vs `TranscriptionWorker.java:30`（`implements SmartLifecycle`）+
  `:83-88`（`start()` 内 `workerThread.start()`）。
- 建议修法：`UPDATE ... SET status='PENDING' WHERE status='RUNNING' AND updated_at < ?`（真正的僵尸判据，顺带解决多实例误回收），
  或把回收改成 `... WHERE id = ?` 逐条 + 条件仍为 RUNNING，避免全表扫。

### S3（P1）`requeuedPending` 是"选中数"不是"入队成功数"，且先刷 `updated_at` 再投递

- 位置：`app/src/main/java/com/meetingnotes/worker/StartupRecovery.java:76-80、91-101`。

  ② 失败行的 `updated_at` 已被刷成 now，**下次启动（哪怕 1 秒后）也扫不到它**，等于把"投递失败"变成"2 分钟内不可再兜底"，

- 复现：
  ```

  ```
- 建议修法：`pushBack` 返回成功条数；`requeuedPending = pushBack(stale)`；把 `updated_at` 刷新挪到"投递成功后"，
  或对投递失败的 id 单独再写回旧时间。

## 2. 两个裁决：**都批准**（D-055）

### 2.1 `DROP INDEX ux_task_hash` —— 批准

V1 的 `CREATE UNIQUE INDEX ux_task_hash ON task (content_hash)` 是**跨用户全局唯一**：用户 B 上传与 A 相同内容会被当成重复 → 与 D-040（查询必须带 `user_id`）/ 多用户语义矛盾。V2 先查重、再 `DROP INDEX IF EXISTS`、再建 `(user_id, content_hash)` 唯一索引，**方向正确**。
我核过：没有任何代码/迁移依赖全局索引（`grep ux_task_hash` 只出现在 V1/V2 与注释里）。唯一"损失"是同内容跨用户不再天然去重——那本来就不该去重。

### 2.2 不用 catch `DuplicateKeyException`，改 `INSERT … ON CONFLICT DO NOTHING RETURNING id` + 判空回查 —— 批准

**这是作者纠正了我的卡**：在 PostgreSQL 里，同一事务内约束冲突后事务进入 aborted 状态，catch 之后再回查会报 `current transaction is aborted`；我卡里写的"捕获 `DuplicateKeyException` 后回查"**在事务内根本跑不通**。
作者方案语义等价且更稳：幂等权威仍是唯一约束（**没有** SELECT-then-INSERT 的 TOCTOU），冲突后回查在事务外做（干净快照）。
**教训已记**：以后卡里不写具体 SQL/异常模式，只写约束——"幂等权威必须是数据库唯一约束；禁止先查后插；事务边界自己定"。

## 3. 我新查出来的问题

### F-1（真实缺陷，已立项）复活成功后 `dead_letter` 残留 → 死信列表里会出现"已 DONE 的任务"

证据（我清理数据前抓的）：
```
task 11 status=DONE
dead_letter rows for task 11: 1     -- 复活成功，但死信行还在
```
后果：T4.x 的失败/死信视图会把 task 11 列成"永久失败"，与实际 DONE 矛盾；若再失败一次，会写**第二条** dead_letter（同一任务多条）。
处理：**D-056** + 新增 **T2.11**（复活时 `DELETE FROM dead_letter WHERE task_id = ?`；单测覆盖）。

### F-2（真实缺陷，已立项）上传路径的存储故障响应**不合对外契约**

证据：停 MinIO 后上传 → HTTP 500，响应体是 Spring 默认体：
```json
{"timestamp":"...","status":500,"error":"Internal Server Error","path":"/api/v1/tasks"}
```
**没有 `code` 字段**。而 `ApiExceptionHandler` 只处理 `ApiException` 与 4 类 multipart 异常，**没有兜底 `@ExceptionHandler(Exception.class)`**。
后果：接入方（US-10 那条"接进自己系统"的卖点）拿到 500 时无法按码分支；且 `STORAGE_ERROR` 这个既有错误码只存在于 worker 侧，上传侧的存储故障没有归口。
处理：**D-056** + **T2.11**：S3/MinIO 异常 → `500 STORAGE_ERROR`；其它未捕获异常 → `500 INTERNAL_ERROR`（统一 envelope）；`接入指南.md` §3.3 补一行兜底说明。

### F-3（观测，非缺陷）ASR 不可用时"多慢才发现"

我这次测到**78s** 才走完 3 次尝试到 DEAD（T1.5 那次是 9s）。日志显示原因不是本项目逻辑：
```
I/O error ... "http://asr:8000" : asr: No address associated with hostname   ← 卡在 DNS 解析超时
```
`docker compose stop asr` 后容器 DNS 记录消失，Java 侧 DNS 查询会一直等到系统超时（~70s），后续重试才是 2s。
**这不是 T2.1 引入的**，但暴露两点：①用户看到的是"任务卡在 RUNNING 一分多钟"；②`app.asr.timeout-sec` 至今**没有消费方**（D-054 已登记）。
处理：并入 **T2.2**（重试/超时/死信）——用 `app.asr.timeout-sec` 给 ASR 调用设上限，并考虑"提交时快速失败"。

### F-4（接受）V2 去重删除遇到"重复任务已 DEAD"会失败

V2 的 `DELETE FROM task a USING task b ...` 删重复行时，`task_result` 有级联、**`dead_letter` 没有**级联；若重复任务里有一条 DEAD（写过 dead_letter），迁移会因外键失败。
判定：**接受**。当前库无存量数据（自托管首发是全新库）；V2 不能改（Flyway checksum），将来真遇到就出 V3。作者已在迁移注释里写明"需人工处理"，属于诚实处理。

### F-5（建议项）`scripts/test.ps1` 的 `ASR_SMOKE_AUDIO` 兜底默认是本机路径 `D:\datasets\...`

`.env` 已定义该键，兜底几乎不触发；但它和 D-054"不许本机绝对路径"的精神相悖。建议改成"未设置就打印用法并退出 3"（T2.11 里顺手一行）。

## 11. 验收后追加（同日 15:30，回答"全量 E2E 为什么吃 3 个任务 / 失败为什么要等"时发现）——F-23

- **触发**：用户问"为什么全量 E2E 一次正好吃 3 个任务配额、为什么失败一次就要等明天"。我去核对账目时顺手验了日切口径，发现 **D-067 的时区修正并没有真正生效**：
  - `docker inspect` 显示 postgres 容器 `TZ=Asia/Shanghai`；容器内 `date` 也显示 **CST**；但 `SHOW timezone` = **UTC**，来源 `configuration file`
    （`/var/lib/postgresql/data/postgresql.conf`）——数据卷是 UTC 时期 initdb 的，`TZ` 环境变量改不动已写死的 PG GUC。
  - 所以 `CURRENT_DATE` 仍按 UTC 日 → 配额实际在**北京时间早上 08:00** 重置；而 `Retry-After` 用 JVM `LocalDate.now()`（app TZ=Asia/Shanghai），
    在 **00:00–08:00** 窗口两者语义不一致（`/settings` 的"今日"也按 UTC 日）。
- **运维修正（0 任务，已执行）**：`ALTER DATABASE meetingnotes SET timezone TO 'Asia/Shanghai';` → 重启 app 让连接池重连。
  验证：`SHOW timezone` = **Asia/Shanghai**、`CURRENT_DATE = (now() AT TIME ZONE 'Asia/Shanghai')::date` = **t**；配额行 `day=2026-11-15`（80/47）未变。
  证据 `D:\new\artifacts\T4.8\tz-fix\before.txt` / `after.txt`。
- **定性**：**F-23**（"配置写进去了 ≠ 配置生效"的层间不一致），记 **K-51**，决策 **D-097** 并补正 D-067 的判据；
  **遗留进 T4.12**：启动预检（DB GUC 与 `TZ` 不一致要可读报警）+ 新装/新卷验证（临时空卷验 `SHOW timezone`）+ `Retry-After` 与计费日语义核对。

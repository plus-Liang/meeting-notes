## §6 阻塞 B1：队列脏数据打死 worker，且永不复活（真栈实证）

我在 A5 栈上注入一条脏队列项（模拟「Redis 里混入非数字成员」——运维误操作、旧版本遗留、手工 LPUSH 都可能）：

```text
docker exec mn-t479l-redis-1 redis-cli RPUSH meetingnotes:task-queue "not-a-number"
8 秒后日志：
Exception in thread "transcription-worker" java.lang.NumberFormatException: For input string: "not-a-number"
	at java.base/java.lang.NumberFormatException.forInputString(Unknown Source)
```

- 根因：`TranscriptionWorker.java:133` `handleOne` 第一行 `long id = Long.parseLong(taskId.trim());` 在 `try` **之外**（`:137` 才是 `try`）；异常逃出 `loop()` 的 while 体，而 `loop()` 没有外层 catch ⇒ 线程死亡。
- 危害：`running` 字段仍是 true（`isRunning()` 依旧返回 true、`/actuator/health` 只 UP），**此后队列再没有任何消费者**——我这轮后续的 `POST /api/v1/tasks` 任务全部停在 `PENDING`、`LLEN` 涨回 0/无进展（我为了让脏项被取走，队列已被取空，但线程已死）。也就是说：P-02 把「任务不丢」做到了，但「消费者自己死了没人拉起来」仍是敞口。
- 与 T4.77-fix B1 同族（那次是 `claim()` 在 try 外），**这次换了个位置**：T4.77-fix 只搬了 `claim`，把同一函数最前面的 `parseLong` 留在外面。
- 建议修法（3 行级）：把 `parseLong` 移进 `try`（catch `RuntimeException` → `log.error` + 清回执 + 继续下一条），或给 `loop()` 的 while 体包一层 `catch (RuntimeException)`；并加回归用例「坏成员不打死 worker、下一条照常」，A 项补一条真栈注入。

## §7 建议（不阻塞）

- **S1（中）**：`markProcessing` 失败后仍继续 `handleOne(taskId)`——ZADD 失败 → 回执没写、任务已被退回队尾，本轮却又照常认领处理。单线程下「队尾那份」随后会因为状态已变而 `claimed==0` 跳过，危害有限；但语义上是「同一任务在队列里两次 + 本轮处理」，建议 `markProcessing` 返回 boolean，失败即 `continue`（并补一条单测）。
- **S2（低·可读性）**：为压 300 行硬闸，本卡把大量语句合并成一行、并删了若干有信息量的 javadoc（如「崩溃恢复属 T2.3」「三档级联降级」「RETRYING 无机制回收」）。行数闸的初衷是控制复杂度，靠删注释/合并语句过关会让后来者少掉关键线索。建议后续把 `process()` 里「S3 拉文件/ffmpeg/ASR」抽成包级 helper（顺带留出再加逻辑的余量）。
- **S3（低·证据口径）**：`zombieReceipts` 把「行已删 / DONE / DEAD 只清回执」也算进去了，单看这个数字说不出「回收了几条」。建议验收证据固定要求**同时**贴 `requeued`，或把计数拆成 `cleaned`/`reclaimed`。
- **S4（低·回报准确性）**：回报写「8 文件 +383/−58」，实际 **9 文件 +405/−58**（漏了 `StalePendingQueriesTest.java`，插入数也差 22）。K-130 同类：落点/范围一律以 `git diff --stat` 原文为准。

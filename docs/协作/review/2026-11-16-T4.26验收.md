### P2-1（契约缺陷）：真并发 = 500，不是 409

- **复现**：对同一任务同时发两个 `POST /restructure`（两个独立线程）→ 稳定得到 **200 + 500**（不是 200+409）；500 body `{"code":"INTERNAL_ERROR","message":"服务器内部错误，请稍后重试…"}`。两轮复现一致。
- **服务端根因**（我抓 app 日志）：`SELECT status FROM task WHERE id=? AND user_id=? FOR UPDATE NOWAIT` 在 PostgreSQL 报 `SQL state [55P03]`（could not obtain lock on row），Spring 抛出的是 **`org.springframework.jdbc.UncategorizedSQLException`**，而代码只 catch 了 `CannotAcquireLockException` → 未被识别 → 冒泡成 500。
- **为什么单测没抓到**（K-79）：`RestructureServiceTest.lockConflictReturns409TaskBusy` 直接 mock 抛 `CannotAcquireLockException`——生产里这个类型根本不会出现，**测试绿但生产红**（K-40 同类：假绿）。
- **影响**：卡面明确要求"并发第二请求 409 快速失败"；现在客户端（多标签页/脚本重放/双击绕过 UI 禁用）会收到 500 与"服务器内部错误"误导文案。无数据损坏（锁查询阶段即失败，未写库），故定 **P2**。
- **处置**：**T4.26b 微修**（下一张开工前置）：按 SQLState `55P03` 识别锁冲突（catch `DataAccessException`→取 most specific cause 的 SQLState），并补"真并发生 409"验证（不允许只用 mock）。

## 二、代码复核要点

- `RestructureService`：`TransactionTemplate` 包裹 → `SELECT … FOR UPDATE NOWAIT` 锁任务行 → 状态校验（404/409）→ `transcript` 校验（400）→ `structuringService.structure(taskId, transcript, explicitTemplate)` → 读 `ai_tier` 返回；任何异常回滚，旧结果保留。**语义正确，唯异常识别面窄（P2-1）**。
- `StructuringService`：`structure(taskId, transcript, null)` 保持 worker 原行为（读落库模板）；`persist` 改为写 `template`（worker 写回同值、重跑写显式值）——T3.9 旧不变量"persist 不碰 template"**有意变更**，测试同步改名重写，我核对 diff 确认不是误删。
- `task.html`：`bindRestructure` 只在 `status === 'DONE'` 分支绑定（DEAD 无入口、不报错——我 UI 探针实测）。
- 文档：权威 `接入指南.md` §3.6c 与实现一致（含失败不写半截、并发口径）。
- 注意：LLM 调用在事务内持行锁（v1 单用户可接受，注释已写清）；并发修复后仍是"快速失败"语义，不排队。

## §5 非阻塞建议（不影响本轮通过）

- **S1** 「同一入队语义两处实现」：`StartupRecovery.java:94` 仍直接 `redis.opsForList().leftPush(...)`（`QueuePublisher` javadoc 已说明启动期 Redis 未就绪、刻意不走该 Bean）。卡面允许既有实现保留，但这意味着「入队方向」由两处代码各自保证——若将来启动恢复要改成尾插，容易漏。
- **S2** 陈旧判据 `SELECT id FROM task WHERE status='PENDING' AND updated_at < ?` 现在**逐字出现两次**（`StalePendingSweeper.java:62` 与 `StartupRecovery.java:74`）。可抽到 `TaskRequeueSupport` 旁边一个 `findStalePending(Timestamp)`，本次不做。
- **S3** 半死 Redis（TCP 通、命令不应答）下，每条重投要等 Lettuce command-timeout；我实测「停机期提交」的 503 延迟 = **~60s**（客户端超时必须 ≥ 服务端，见 §6）。串行清扫在调度线程，不影响 worker/HTTP，但一轮可能被拖长——已写进 javadoc。
- **S4** 多实例并发清扫（同一批行被两个实例同时投递）未注入验证；当前单实例口径（D-061）。

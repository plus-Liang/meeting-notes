## 4. 阻塞 B1：认领异常打死 worker 线程（静默）

**复现**（同一隔离栈，任务 1 已 `DONE`）：

1. `redis-cli RPUSH meetingnotes:task-queue 999999`（库里不存在该 task 行）；
2. worker 取到后进入 `claim(999999)` → `jdbc.queryForMap(...)` 抛 `EmptyResultDataAccessException`；
3. 日志：

```
Exception in thread "transcription-worker" org.springframework.dao.EmptyResultDataAccessException: Incorrect result size: expected 1, actual 0
	at com.meetingnotes.worker.TranscriptionWorker.claim(TranscriptionWorker.java:137)
	at com.meetingnotes.worker.TranscriptionWorker.loop(TranscriptionWorker.java:118)
```

4. 再提交一条**内容不同**的 PASTE 任务（`task_id=3`）：15s 后仍 `PENDING`、`attempts=0`、队列 `LLEN=1`（无人消费）；
5. `GET /actuator/health` 仍 `{"status":"UP", ...}`（没有 worker 组件，看不出线程已死）。

**根因**：`loop()` 里 `var claimed = claim(...)`（`:118`）写在 `try` **之外**，而 `claim()` 的第一句就是 `queryForMap`；异常穿出 `while (running)` 循环、`loop()` 无外层 catch ⇒ 线程终止、`running` 仍为 `true`。

**为什么是回归**：改造前 `queryForMap` 在 `process(long)` 内，而 `process` 被 `try { … } catch (Exception e) { log.error; markFailure(...) }` 包着——同样的异常只会让该条任务失败，worker 继续消费。本卡把认领抽成 `claim()` 时把它挪出了保护伞。

**危害**：单实例部署下这是一次性、永久、静默的「转写停摆」——没有日志告警（只有一条 `Exception in thread` 栈）、健康检查全绿、任务在队列里堆积直到磁盘/队列爆掉。触发面不只是「任务被删」：任何一次 `queryForMap` 的瞬时异常（连接池耗尽、DB 重启窗口、迁移锁）都会踩中。

**修法（写进 T4.77-fix）**：把 `claim()` 纳入 `try`，认领失败只记 error 并 `continue`（**不**调 `markFailure`——那会把不存在的行也走一遍 `UPDATE … RETURNING`，返回空还会 NPE）；`finally` 里 `hb` 的关闭与 `inflightTaskId` 归零保持不变。

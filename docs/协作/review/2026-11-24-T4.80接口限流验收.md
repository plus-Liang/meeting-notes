## 2. 代码审查要点（我逐行看过）

- **计数原子性**：`windows.compute(key, (k, old) -> ...)` 整条替换不可变 `Window`，无锁且不会丢计数；窗口滚动条件 `old.windowEndMillis() <= now`。
- **身份隔离**：`LOGIN/REGISTER` 用 `getRemoteAddr()`；`TASKS` 用 `UserContext.current()`，未设置时 `IllegalStateException` 被捕获后**放行**（不误伤），与卡面意图一致。
- **路径判定**：只认 `POST` + 四条精确 URI（`/api/v1/auth/login`、`/api/v1/auth/register`、`/api/v1/tasks`、`/api/v1/tasks/batch`），其余方法/路径与 `OPTIONS` 一律放行——不是全局限流。
- **Retry-After**：`remainingSeconds` 向上取整且至少 1；`ApiExceptionHandler` 从请求属性读，缺省 `"60"`，`QUOTA_EXCEEDED` 分支原封不动。
- **异常能否被 `@RestControllerAdvice` 接住**：拦截器 `preHandle` 抛的是 `ApiException`，`DispatcherServlet` 交给 `HandlerExceptionResolver`（全局 advice 生效）——真栈 429 带正确 JSON 体与头，**实证成立**，不是推演。
- **内存上界**：`map.size() > 10000` 时 `removeIf` 清过期，无 `@Scheduled`、无新依赖。

## 5. 我发现的 1 处缺陷（已由 Lead 修）+ 3 条建议

**F1（文档缺陷，Lead 直修 `f8f8066`）**：README「常见问题 / 故障排查」表里，新加的 429 行后面多了一行 `|---|---|` 分隔行 ⇒ GFM 会把 429 行当成**新表头**、其余行降级为该表数据，渲染直接错乱。已删除该行并核对「表头 + 分隔行 + 连续数据行」（`README.md:275-282`）。

**S1（建议，Medium）配置 ≤0 的语义分裂**：`limits <= 0` 会让第一个请求就 429（全锁死）；`window-sec <= 0` 让 `windowMillis <= 0`，每个请求都滚动重置 ⇒ 限流**静默失效**。建议在构造器里做 `WARN + 回退默认`（与 T4.78 的 `stale-running-minutes`、T4.79 的 `visibility-timeout-sec` 同一口径）。

**S2（建议，Medium）反代后按 IP 限流会变成「全站共用一个桶」**：`getRemoteAddr()` 在 nginx/Cloudflare 后面恒为代理 IP，10 次错误登录就锁死**所有人**。建议 README 补一句：反代部署时设 `server.forward-headers-strategy=framework`（或由运维把登录桶上限按客户端数放大）。

**S3（建议，Low）成功登录也计数**：桶统计的是「请求次数」而非「失败次数」，脚本化登录 10 次/分钟就会被限。当前阈值足够宽松，仅需在 README 里说清「这是频率限流，不是失败锁定」（失败计数 + 锁定是 P-29 后半那张卡）。

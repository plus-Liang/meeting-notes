## 1. 背景：CI 首跑抓到的真 bug

`CI` run 44725089031（commit `a30d56d`）：`compose-config` ✅ / `unit` ❌ **493 用例 1 失败**。

```
[ERROR] ProcessMediaFetcherTest.nonZeroExitReportsFetchFailedWithStderrTail:106
  文案带 stderr 末尾：外部工具异常退出（exit 2）；stderr 末尾：ls: cannot access '/nonexistent-t432b/nothing': ...
  ==> expected: <true> but was: <false>
```

根因：用例按平台分支，Windows 分支 `cmd.exe /c echo this-tool-failed-badly ... 1>&2 & exit 3` 的 stderr 带断言要找的 marker；**非 Windows 分支用 `ls {url}`**，stderr 是 `ls: cannot access ...`，断言必败。本地只在 Windows 上跑过，从未暴露 → **CI 的第一个直接价值**（不是文档口号，是真抓出来）。

## 3. 修法评估（我独立读了实现与 diff）

写码方的关键前置判断正确：**`ProcessMediaFetcher` 按空格拆 argv、不过 shell**（ProcessBuilder 直接 exec），所以 `sh -c "…"` 的引号会被拆散 —— 必须走脚本文件方案：

```java
Path script = tmpDir.resolve("fail.sh");
Files.write(script, "#!/bin/sh\nprintf 'this-tool-failed-badly\\n' >&2\nexit 3\n".getBytes(UTF_8));
Files.setPosixFilePermissions(script, PosixFilePermissions.fromString("rwxr-xr-x"));
cmd = "sh " + script + " {url}";
```

- 脚本内容确定性：stderr 只有 marker 一行、exit 3；不依赖 `ls` 的本地化文案。
- `@TempDir` 路径无空格，且脚本路径作为**单个 argv token** 传入；`{url}` 仍是独立 token（注入防线未破）。
- `setPosixFilePermissions` 只在非 Windows 分支执行（`if (isWindows())` 守卫），Windows 上不会抛 `UnsupportedOperationException`。
- 新增 `throws Exception` 与方法签名一致，无其他调用点。

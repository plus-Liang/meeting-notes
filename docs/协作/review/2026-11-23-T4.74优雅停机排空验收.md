## §7 裁决与建议

**写码方提出的三处「断言 vs 平台语义」冲突：全部采纳，扣我的卡面错误。**

- **R-1 exit code**：`docker stop` 下 JVM 对 SIGTERM 的退出码是 **143**，卡面要求「容器退出码 0」**不可达**。采纳其替代断言：143 + `OOMKilled=false` + 排空日志链完整。
- **R-2 排空窗口算术**：RTF≈0.13 ⇒ 8 分钟音频本身就要 ~62s，卡面「60s 窗口 + ≥8min 音频 + DONE」三者互斥。采纳：**默认 60s 用短音频验 DONE**（本报告 §2 即此路径）、长音频只在显式调大 drain 时验排空。
- **R-3 中断后短暂 RUNNING**：interrupt 后 `markFailure` 未及跑完、shutdown 收尾，任务停在 RUNNING 是「交启动恢复」的设计路径。采纳：断言改为「`up` 后最终 DONE」。

**一处实现偏差（`@Value` 字段注入）**：接受。理由成立——加构造器参数会连带改 `TranscriptionWorkerTest`（不在本卡白名单）；且它保留了 `= 60` 初始化器（纯 `new` 时可用），yml 键与默认值一致，语义等价。

**建议（不阻塞）**：

- **OBS-1**：`drainTimeoutSec=0` 的语义（「不等待」）没有任何测试；建议后续加一条「0 → 立即 WARN 并 interrupt」用例。
- **OBS-2**：排空期间若 HTTP 请求也在收尾，`spring.lifecycle` 120s 与 drain 60s 是串行还是并行、预算是否够，未压测；建议写一条运维口径（当前注释已说明层级，够用）。
- **OBS-3**：`TranscriptionWorker.java` 已顶到 **300 行**上限，构造器被压成多参数单行。下一张动这个文件的卡（P-04 就在 `MonoWavExtractor`/同族）建议先抽 `WorkerDrain`（或把排空逻辑搬进独立小类），否则很快会被 M3 挡住。

**我自己的三处卡面错误（记 K-151）**：① 断言 `exit 0`；② 排空窗口与音频时长的算术；③ 断言 `HostConfig.StopTimeout`（实际字段是 **`Config.StopTimeout`**）。

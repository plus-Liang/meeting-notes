## 1. 两个设计决策我认同（不只是"能跑"）

### 1.1 D-035 用 `EnvironmentPostProcessor + spring.ai.model.chat=none`，比替代方案都干净

| 方案 | 评价 |
|---|---|
| 填一个假 base-url 让它能启动 | ❌ 一调用就 5xx，更糟（D-035 已排除） |
| 用 `@SpringBootApplication(exclude=OpenAiChatAutoConfiguration.class)` | ❌ 跟"将来有 key 要启用"冲突，得写条件排除，更容易错 |
| **EPP 在配置加载后、条件求值前算 `app.llm.enabled`，用官方 `spring.ai.model.*` 开关关掉** | ✅ **采用**：不动自动配置类、不写假值、显式配置优先（`putIfAbsent` 不覆盖用户设置） |

排序值 `HIGHEST_PRECEDENCE + 20` 也选对了（晚于 `ConfigDataEnvironmentPostProcessor` 的 +10，否则读不到 `application.yml` 里的 `app.llm.enabled`）。

### 1.2 `NoKeyStartupTest` 的隔离方式是**真的隔离**

它没有靠"改环境变量后重启 JVM"这种假做法，而是用 `@SpringBootTest(properties = {"LLM_API_KEY=", ...})`：
Inlined 属性源优先级高于系统环境变量 → EPP 读到空串 → 判定关闭。**在 `.env` 里有真 key 的情况下也成立**，我用真实 key 环境复跑验证了（见上）。

> 唯一 fragility：这份隔离依赖"EPP 读的键名 = 测试里写的键名"。将来若改键名，测试会静默失效（仍绿但没验到东西）。建议 T1.x 在 EPP 里加一行启动日志打印"当前 LLM 档位/为什么"，人一眼能看出来。

## 2. 顺手修的 `V1__init.sql`（`right` 保留字）——**我自己在真实 PG16 上验过了**

它说"不修就无从验证启动不崩"，这是对的；但 `NoKeyStartupTest` 用的是 **H2 + `flyway.enabled=false`**，所以**Flyway 脚本本身并没有被任何自动化测试覆盖**。我补做了：

```text
docker run -d --name pg-verify -e POSTGRES_PASSWORD=verify -e POSTGRES_DB=meetingnotes postgres:16-alpine
docker cp V1__init.sql pg-verify:/tmp/V1.sql
docker exec pg-verify psql -v ON_ERROR_STOP=1 -U postgres -d meetingnotes -f /tmp/V1.sql
→ psql exit=0，7 张表全部建成
→ \d glossary 显示列：id | user_id | wrong | right | hits | priority | created_at
```

**结论：引号写法在 PG16 上有效。**

### ⚠️ 环境坑（不是项目缺陷，但要写进文档）

我在复核中亲测到 3 个本机坑：

1. **宿主注入 `SERVER__PORT`** → 被宽松绑定成 `server.port`，与宿主监听端口冲突（它遇到的）；
2. **curl 本机端口需 `--noproxy "*"`**（本机有代理环境变量）；
3. **`docker run -v D:\...\db\migration:/mig:ro` 会让 PG 容器起不来**（状态卡在 `Created`、无日志）；
   去掉挂载或改用 `docker cp` 就正常 —— 我最终用 `docker cp` 完成验证。**Windows Docker Desktop 的文件共享偶发问题**。

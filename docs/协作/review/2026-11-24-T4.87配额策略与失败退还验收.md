## 三、静态与代码审查（我逐行读）

1. **`QuotaService.refundForTask`（`:78-98`）**：单事务两段 SQL——`UPDATE task SET quota_refunded = TRUE WHERE id = ? AND quota_refunded = FALSE RETURNING user_id, duration_sec, CAST(created_at AS DATE)`，0 行即返回 `false`（幂等，不抛）；分钟数用 `ceilMinutes`（`:101-103`，`<=0` 归 0），`minutes > 0` 才 `UPDATE quota SET used_minutes = GREATEST(0, used_minutes - ?) … AND day = ?`。**不变量成立**：翻转标志与扣减在同一事务；`consume()` 的守卫 SQL 一字未改（`:36-57`）。
2. **`task/DeadTaskRecorder.java`**：`markDead` 单事务内 ① 置 DEAD+error_code ② 插 `dead_letter` ③ 委托 `refundForTask`；退款结果只作为返回值，**不影响 DEAD/死信落库**（与卡面 C3 一致）。

4. **`TranscriptionWorker`（`:265`）**：原 3 行 UPDATE+INSERT 收敛成一行 `deadTaskRecorder.markDead(...)`，`webhookService.onTerminal(taskId,"DEAD")` 顺序未变；`:160` 认领 SQL 的 `COALESCE(request_id,'')`（T4.86）保留。

## 六、建议（0 阻塞）

- **S1 断言换主人要盯住**：worker 的两条 SQL 断言迁到 `DeadTaskRecorderTest` 后，worker 侧只剩 `verify(markDead)`。语义没丢，但「谁保证 DEAD 的 SQL 长什么样」从两个文件变成一个——建议在本类 javadoc 顶部写明「DEAD 的 SQL 断言只在 `DeadTaskRecorderTest` 维护」，防未来误删。
- **S2 `QuotaService.consumeForTask` 目前没有生产调用点**：`reviveDead` 直接调 `consume(userId, ceilMinutes(...))`（它自己 `UPDATE … RETURNING` 拿到了 user_id/duration_sec），于是 `consumeForTask` 只被单测调用，是**死代码**。建议二选一：删掉它，或让 `reviveDead` 改用它（但那样会多一次 `SELECT`，与「单事务一次 RETURNING」的设计相反）。我倾向前者。
- **S3 `markDead` 不校验当前状态**：重复调用会对同一任务再插一行 `dead_letter`（原实现亦如此，非本卡引入）。建议后续卡改成「`INSERT … SELECT … WHERE NOT EXISTS (SELECT 1 FROM dead_letter WHERE task_id = ?)`」或按 `status <> 'DEAD'` 守卫，让 DEAD 也幂等。
- **S4 文档与实现写法不一致**：`接入指南.md` 写 `created_at::date`，实现是 `CAST(created_at AS DATE)`（为 H2/PG 通用）。语义相同，但接入方照文档手写 SQL 时可能以为我们用了 PG 专有写法——建议文档改成同一写法。
- **S5 历史任务与新不变量**：`quota_refunded` 不回补（卡面决定），于是**升级前**的 DEAD 任务满足 `status='DEAD' AND quota_refunded=false`，任何按不变量做的监控/校验会把它们全报出来。建议在 `接入指南.md` / `运维-监控与告警.md` 补一句限定：**不变量对 V13 之后创建的任务成立**。

## 四、代码与卡面核对（我读了实现与测试）

- `AudioStreamService`：签名 = **HMAC-SHA256(key=`API_TOKEN`, `taskId+"\n"+exp`)**（复用现有键、不新增 secret；卡面允许的第一种）；验签用 `MessageDigest.isEqual` **常量时间比较**；`exp` 形状/长度/过期/与 taskId 不匹配一律 false（调用方统一 404）；签发闸：不存在/非本人 **404**，PASTE/无 source_uri/非 DONE **400**（PASTE 的 s3 文本对象显式拒，不 500）。
- `AudioStreamController`：验签在**读 MinIO 之前**，失败统一 404；Range **在打开 MinIO 前解析**（416 不留半截响应）；`GetObject(range=…)` + `ResponseTransformer.toInputStream()` **流式转发不整文件进内存**；`Accept-Ranges/Content-Length/Content-Range/Content-Type` 都正确；MinIO 侧 416 有兜底（置 416 + `Content-Range: bytes */size`）。
- `ApiTokenFilter`：新增豁免 = **GET 且正则精确 `^/api/v1/tasks/\d+/audio$`**；`/tasks`、`/tasks/{id}`、`/tasks/{id}/audio-token` 匿名仍 401，`/tasks/{id}/audio` 的其它方法（非 GET）不豁免——测试有 `nearbyPathsAreNotExempt`/`audioPathNonNumericOrWrongMethodNotExempt` 断言。
- 配置三处一致（yml / `.env.example` / `配置清单`：`AUDIO_TOKEN_TTL_SEC=600`）；文档 **§3.10** 覆盖签发/播放/Range 语义/错误码/安全边界，且明确"本端点无 401（没 Bearer 且没签名 → 要么 404 要么被 filter 401）"。
- 测试非空壳：签名矩阵（正确/改 taskId/改 exp/过期）+ Range 矩阵（三形态/越界/非法）+ 签发拒绝 + Content-Type + 豁免面。

## 五、残余风险（P3，接受不阻塞）

| 编号 | 说明 |
|---|---|
| P3-1 | **音频 GET 未按 user_id 校验**（当前单用户 D-040；签名只绑 taskId+exp）→ **T4.37 多用户时必须把 userId 一起绑进签名/校验**，否则任一用户拿到他人签名 URL 即可听（签名 URL 本身就是"可分享只读"，但对多用户要重新定义） |
| P3-2 | PASTE 保护依赖"签发闸拒绝"；若持有 API_TOKEN 的人手算签名，理论上能拉到 PASTE 的 `paste.txt` 对象（API_TOKEN 泄露=全权限，影响低；T4.37 一并收） |
| P3-3 | `HEAD /audio` 未实现（`<audio>` 只用 Range GET，足够）；多段 Range 显式 416（浏览器 seek 均单段） |
| P3-4 | 416 的 MinIO 兜底分支（响应体为空 JSON）未注入故障实测；`size_bytes` 与对象实际大小若不一致（历史脏数据）会由 MinIO 416 兜底 |
| P3-5 | 签名 TTL 只做"过期 + 上限"校验，不做单次使用/吊销（无状态签名，v1 接受） |

## 2. 我发现的问题（按严重度）

### P1-1：响应字段与错误码 **不符合 `接入指南.md` 已承诺的契约**

`接入指南.md` §3.1/§3.3 写得很硬（"**错误码必须固定，否则接入方无法处理**"），但实现是另一套：

| 位置 | 接入指南（承诺） | 实现（实际） | 影响 |
|---|---|---|---|
| 响应字段 | `task_id` / `content_hash` / `reused` | `taskId` / `contentHash` / `duplicate` | 接入方按文档写的解析代码全空 |
| 超大文件 | 400 `SIZE_EXCEEDED` | **413** `TOO_LARGE` | 接入方按文档判 400+`SIZE_EXCEEDED` 会漏判 |
| 超时长 | 400 `DURATION_EXCEEDED` | 400 `TOO_LONG` | code 字符串对不上 |

**我的判定**：以文档为准改代码（文档里 webhook 契约、`task_id`、`ai_tier` 全是 snake_case，全项目一致；
错误码用 `SIZE_EXCEEDED`/`DURATION_EXCEEDED`）。HTTP 状态码我**保留 413**（HTTP 语义正确，且浏览器/代理友好），
同步把文档那一行拆成 413 `SIZE_EXCEEDED` / 400 `DURATION_EXCEEDED`。已记 **D-041**。
→ 这是 T1.5 前的第一个动作（现在没有接入方，改是免费的）。

### P2-1：幂等命中时返回**假状态**（硬编码 `PENDING`）

`TaskService` 幂等分支直接 `return new TaskCreatedResponse(existing, "PENDING", …)`，不看库里真实状态。我构造证据：

```
$ psql: update task set status='DONE' where id=1
$ curl -F file=@a_e91acf.wav → {"taskId":1,"status":"PENDING",…,"duplicate":true}   ← 任务其实是 DONE
```

T1.5 让任务真能跑到 DONE 后，这个 bug 立刻对外可见（前端/接入方以为还在转写，无限轮询）。
→ 改法：`select status from task where id=?` 带出真实状态返回。

### P2-2：幂等查询**没有 user_id 条件**（认证上线即越权）

`findIdByHash` 只按 `content_hash` 查。现在固定 `user_id=1` 无影响，但 T4.6 接上 `API_TOKEN` 认证后，
**B 用户上传与 A 用户相同内容会拿到 A 的 taskId**，之后 `GET /api/v1/tasks/{id}` 就能读到别人的转写结果。
单行成本：`WHERE content_hash = ? AND user_id = ?`。现在修，别等 T4.6。

### P3（不阻塞，记录）

1. `QuotaService.consume` 返回 `{usedMinutes, tasksPerDay}`——第二个元素应该是 `usedTasks`（当前无人使用返回值，但命名会坑下一个读代码的人）。
2. `AudioDurationProbe` 先读完 stdout 再读 stderr：理论上存在管道缓冲区互锁（ffprobe `-v error` 输出极小，实际风险低）；真要稳就 `redirectErrorStream(true)`。
3. `spring.servlet.multipart.max-request-size` 与 `max-file-size` 都等于 `TASK_MAX_SIZE_BYTES`：正好卡在上限的文件会因 multipart 边界开销先被 servlet 413（边界场景，建议 request-size 留 1MB 余量）。
4. MinIO `putObject` 成功但随后 `UPDATE task SET source_uri` 失败 → 对象孤儿（无对账机制；T2.x 备份/巡检再管）。
5. `content_hash` 还没有唯一约束（T2.1 计划）→ 同文件**并发**上传仍可能双插；WorkBuddy 已在风险里自述，我确认为真，留给 T2.1。
6. 配额消息在 `QUOTA_TASKS_PER_DAY=0` 时显示"0 个任务"（语义对、观感差，P3-3 同类，T3.3 一起）。

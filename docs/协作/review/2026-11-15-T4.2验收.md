## 4. `NoKeyStartupTest` 的 `@MockBean`（额外改动，我认可 + 保留意见）

- **它发现的问题是真的**：`NoKeyStartupTest` 是**完整 `@SpringBootTest` 上下文**（真实 `application.yml` + 真实 Spring AI 自动配置，只把 DB 换 H2），
  因此会装配**真实的 `TranscriptionWorker`**，而它的队列键取自真实配置 → 测试 JVM 会 `BLPOP` **真实 Redis 队列**，与容器内 worker 抢任务；
  被抢走的任务在本测试里写进 H2、真实任务卡 `PENDING` → E2E 轮询超时假红。这解释了他们看到的"test JVM 里出现 `PASTE 文本已读取`"。
- **我核对过竞品面**：两个冒烟测试用的是 `MinimalContext`（不装配 worker），所以**只有这一个**上下文存在抢队列问题——修复面判断正确。
- **修复方式**：`@MockBean TranscriptionWorker`（在卡面允许的 `app/src/test/**` 内）；`NoKeyStartupTest` 的断言对象是"无 key 时 ChatModel 数量=0 / 应用能起来 / 健康 UP"，mock 掉 worker 不影响这些断言。
- **保留意见（不阻塞）**：mock 掉 worker 后，本类**不再覆盖 worker 的真实装配**（构造参数/`@Value` 绑定错误在这里不会暴露）。当前由
  ①`TranscriptionWorkerTest`（纯 Mockito 覆盖 worker 逻辑）②容器实机（5 服务跑真实 worker，T4.1/T4.2 的 139/141… 都走真实队列）共同兜底。
  更"忠实"的替代做法是**给测试上下文指定独立队列键**（`app.worker.queue-key=test:isolated`，不 mock 任何 bean）；我判断本卡改 mock 已经足够，
  但把它记为**T4.12 死配置体检时**可顺手评估的一项（若那时发现 worker 装配无其它覆盖，再换成独立队列键）。

## §2 我的静态对账与代码审读

落点：

- `application.yml:133` `ffmpeg-timeout-sec: ${FFMPEG_TIMEOUT_SEC:600}`（`:132` 注释说明预算与强杀语义）；
- `.env.example:38` `FFMPEG_TIMEOUT_SEC=600`（`:36` `FFMPEG_BIN` 既有）；
- `MonoWavExtractor.java`：`:36-40` 构造器 `@Value("${app.media.ffmpeg-bin:ffmpeg}")` + `@Value("${app.media.ffmpeg-timeout-sec:600}")`；`:43-48` `ProcessBuilder(...).redirectErrorStream(false).start()`；`:50` stderr drain（`StringBuilder` 尾部累积）、`:51` stdout drain（排空即弃）；`:54-64` `ffmpeg-watchdog` 守护线程（`sleep(timeoutSec*1000)` → `timedOut.set(true)` → `destroyForcibly()`）；`:67` `p.waitFor(timeoutSec, SECONDS)`；`:75-83` 收尾（interrupt watchdog、未完成强杀、join 两 drain、超时抛异常）；`:91-109` `drain(InputStream, StringBuilder)`；`:111-117` `joinQuietly`。
- `MonoWavExtractorTest.java`：`:24-25` 平台判断；`:31-40` 假脚本（POSIX `chmod rwxr-xr-x` / Windows `.bat`）；4 例 `normalExitReturnsQuietly` / `hangingWithOutputTimesOutAndKillsProcess`（断言 `<3000ms`、消息含「上限 1 秒」）/ `hangingSilentTimesOut` / `nonZeroExitReportsStderrTail`；`assertNoResidualProcess`（`:47-58`）用 `ProcessHandle.allProcesses()` 轮询 8×250ms，属「等待条件」而非对 sleep 的行为断言。

**死锁是否真被消除（我逐条看代码）**：① stderr 由独立线程持续排空 ⇒ 子进程不会因管道写满而卡住；② 主线程只 `waitFor(timeout)`、不碰无界读 ⇒ 超时预算真实生效；③ watchdog 到点 `destroyForcibly()` 让所有管道 EOF ⇒ 即使子进程无视 TERM 也能收敛。三条合起来，P-04 的根因（先阻塞读、后 waitFor）已被移除，而不是「把 waitFor 挪到读之前」的表面修法。

## §6 建议（非阻塞）

- **S1（低，内存）**：`:51` stdout 的 drain 虽然「排空即弃」，但仍 append 进一个无界 `StringBuilder`；若某个异常输入让 ffmpeg 往 stdout 狂写，这里没有上限（stderr 那条有 2048 截断）。建议 stdout 传 `null` 或复用同一限长缓冲。
- **S2（低，边界）**：`:97-99` 的截断发生在 append **之前**，因此 `stderrTail` 最终可能达到 `2048 + 4096` 字符（而非严格 2048）；`tail(…, 300)` 后无影响，但注释「只留尾部 2048」与实现略有偏差。
- **S3（低，测试面）**：`hangingSilentTimesOut` 在 Windows 用 `:loop / goto loop` 空转，CPU 占用较高；CI 三平台并行时不至于超时，但可改成 `ping -n 60 127.0.0.1 > nul` 更省资源。

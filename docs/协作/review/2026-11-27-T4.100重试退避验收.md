## 三、静态与代码审查（逐行）

- `RetryBackoff.delayFor(attempts)`：`max(1,attempts)`；`attempts>=31` 直接返回 max（防溢出）；循环内先比 `max/2` 再乘 2 ⇒ 无 long 溢出；`base<1 || max<base` WARN 回退 30/300。
- `RetryDueSweeper`：`DUE_SQL` 含 `deleted_at IS NULL AND next_retry_at IS NOT NULL AND next_retry_at <= now()` + `ORDER BY … LIMIT 50`；`CLAIM_SQL` 条件 UPDATE（`status='RETRYING' AND deleted_at IS NULL AND next_retry_at <= now()`），影响行数 1 才投递 ⇒ 多实例/并发不重复入队；投递失败恢复 RETRYING + 原到期值（守住 C7 不变量）；整轮 `catch (RuntimeException)` 只 ERROR。
- `TranscriptionWorker.markFailure`：`bump → read → attempts>=maxRetries ? markDead(+onTerminal DEAD) : UPDATE status='RETRYING', next_retry_at=Timestamp(now+delay)`；**不再立即 tryPublish、不再退回 PENDING**；SQL 无 `interval`（时间在 Java 算）。
- `StalePendingSweeper`：僵尸回执分支新增「RETRYING 且 `next_retry_at` 未到 → skipped + ZREM，不投递」——正确堵住「退避被清扫器打穿」。
- `DeadTaskRecorder.markDead` 清 `next_retry_at`（C7 单一出口）；`WorkerSupport` 抽出 `abbreviate`/`sleepQuietly`（行为逐字不变，为压 300 行）。

## 六、建议（S1–S5）

- **S1（中）调度器每轮都打 INFO**：`RetryDueSweeper.sweep()` 空轮也 `log.info("重试调度完成：到期=0 入队=0 失败=0")`。本栈 1s 一轮，20 分钟产生 **354 行**；生产默认 5s ⇒ 每天约 1.7 万行。建议 `enqueued+failed==0` 时降到 DEBUG（或只在有到期时打）。
- **S2（中）`RetryBackoff.scanIntervalMs()` 是死代码**：`@Scheduled(fixedDelayString="${app.retry.scan-interval-ms:5000}")` 直接读原始配置，所以 C3 承诺的「scan<500 回退 5000」在生产**不生效**（配 100ms 就按 100ms 跑），且该回退没有 WARN。根因是**卡面 C3 与 C5 给了同一配置两个来源**（我的锅）；建议下卡二选一：要么让调度器读 `RetryBackoff.scanIntervalMs()`，要么删掉该方法并补 WARN。
- **S3（中）成功后 `task.error_code` 残留**：任务 1 最终 `DONE` 但 `error_code=ASR_ERROR`（上一次失败写的）。前端只在 DEAD/RETRYING 展示，但 `/api/v1/tasks` 消费者会看到「DONE + ASR_ERROR」的矛盾组合。建议成功落库时清 `error_code=NULL`。
- **S4（低）卡面 A6 口径不准**：我写「DONE attempts=3 自愈」，实际 `attempts` 记的是**失败次数**，第三次尝试成功时 `attempts` 仍为 2。判据应改为「DONE 且 `next_retry_at` 为 NULL 且调度日志出现 `到期=1 入队=1`」。
- **S5（低）`RetryDueSweeper` 只捕 RuntimeException**：PG/Redis 抖动都是 RuntimeException，够用；但 `Error`（OOM 等）会终止调度线程。可接受，登记即可。

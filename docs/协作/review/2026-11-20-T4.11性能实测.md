**方法要点**（避免污染既有证据）

1. 用「追加 128 字节 ID3v1 尾块」生成同音频、不同 `content_hash` 的副本，绕过 `(user_id, content_hash)` 幂等复用，三份副本音频内容与时长完全不变。
2. 通过公开 REST API（`POST /api/v1/tasks` multipart + `GET /api/v1/tasks/{id}` 轮询）驱动，与真实用户路径一致，不直接改库。
3. 并发期间每 2 秒采样 `docker stats --no-stream`（app/asr/postgres/redis/minio 的 CPU% 与内存）。
4. 结束后用 `POST /api/v1/tasks/delete` 删除任务（同时清 MinIO 对象），并删除当日 `quota` 行，核对基线。

## 3. 测试 B：并发 2 任务（480 s + 377.5 s 音频）

| 指标 | 实测 |
|---|---|
| 提交 | 2 个任务在同一秒内提交（创建耗时合计 **0.3 s**） |
| 任务 845（480 s 音频） | DONE，墙钟 **27.58 s** |
| 任务 846（377.5 s 音频） | DONE，墙钟 **117.13 s**（其中前 27.6 s 等待前一个任务让出） |
| 总墙钟 | **117.13 s** |
| 音频总量 | 857.5 s |
| 聚合 RTF | **0.137** |
| 串行理论预期（按 RTF 0.105） | ≈ 90.0 s |
| 并行理论预期（按 RTF 0.105） | ≈ 50.4 s |

**观察**：两任务同时进入 RUNNING，但完成时间呈**排队**特征（846 在 845 结束后才开始出结果）——说明当前 worker 对 ASR 的实际并发利用是"任务级串行 + ASR 侧并发能力有限"，`ASR_MAX_CONCURRENCY=2` 并未带来 2 倍吞吐。这是**已知取舍**（本机 14 核 CPU 跑 int8 whisper 已吃满 4 线程、且 app 内存无压力），不是缺陷；要提速的正解是换更强模型/GPU 或加 ASR 副本（README 生产化路线图已写）。

## 7. 局限（必须如实写进材料）

1. **单次测量**，云 LLM 段受网络与供应商波动影响；因此对外只给区间与均值，不给"保证值"。
2. 并发结论建立在"本机 14 核 / ASR 单容器"前提上，**不代表多副本水平扩展**（未测）。
3. 未做故障注入类破坏性实验（停 asr 的 9 秒死信路径来自 T1.5 历史实测，未在本次复跑，避免污染基线）。
4. 测试 A/B 使用的 8–10 分钟音频为合成/编辑样本，语音密度与真实会议录音不同，RTF 与 T4.16 的 0.160 有正常差异。

# AI 开发提示词模板（可复用 · 任何项目/任何 agent 通用）

> 来源：2026-11-13 音频「用 AI 做项目的三准备 + 四规则」+ 6 张提示词卡，见 `11月13日-音频总结.md`。
> **用法**：按下面的"什么时候用哪张"查表 → 复制模板 → 把 `<>` 里的占位符换成当前项目的真实路径/命令。
> 每个模板都配了「本项目（录音纪要平台）定制版」，可以直接对比着改。
> **判据是硬要求**：模板不是让你把话说漂亮，而是让输出**可客观判断过没过**。

---

## 0. 速查：什么时候用哪张

| 时机 | 用哪张 | 一句话作用 |
|---|---|---|
| 新需求还很模糊 | **模板 1 需求澄清** | 把模糊需求压成可验证的验收标准 |
| 要动架构/选型/加依赖 | **模板 2 选型与架构** | 逼出"为什么不用 X"，防止追新技术挖坑 |
| 换会话/换 agent/上下文快满 | **模板 3 三份短文档** | 让新 agent 30 秒接上，不重复踩已排除的坑 |
| 复杂任务开工前 | **模板 4 规划四问** | 改哪里·复用什么·影响什么·怎么验证 |
| 任务会碰到公共组件/公共逻辑 | **模板 5 扩范围先确认** | 防止"顺手优化"改坏别处 |
| 测试跑完 / 要提交 / 要合并 | **模板 6 测试三问** | 交代清楚"还有哪些没验证" |
| 出了 bug、AI 越改越乱 | **模板 7 证据链报错** | 先给证据、先分析，确认后再实现 |

**两条附则（比模板更重要）**：

- **同一问题连续两轮没有实质进展 → 停止追问**，改用模板 7。
- **范围限制不能只靠提示词**：AI 自查改动（`git diff --stat`）+ 版本管理（commit/快照），人再收口看 diff。

## 模板 1 · 需求澄清（先不要写代码）

**什么时候用**：用户描述是"我想做个 X"级别，还没有验收标准；或需求方给的是一段愿景而不是行为。

```text
先不要写代码。你的任务是通过多轮对话，帮我把模糊需求整理成明确、可验证的验收标准。

规则：
1. 区分【已明确的需求】和【待确认的问题】，不要替我做决定；拿不准就问我。
2. 根据我的回答持续完善需求，不要重复问我已经回答过的问题。
3. 只问影响功能与验收的问题，不要过度追问实现细节。
4. 当每条需求都有【触发条件 + 预期行为 + 可检查的结果】时，停止提问。

输出：一份简洁的验收标准列表，每条都能客观判断是否通过（不要写"体验流畅"这类无法判定的描述）。
另外单独列一节【本轮未确认的问题】，明确写出还缺什么信息。
```

**本项目定制版**：需求结束后落成 `docs/项目/录音纪要平台/spec.md` 的 US-x / N-x 编号 + DoD（每条 DoD 必须带命令或可检查的数值），
并同步 `需求确认单.md`。**示例**：US-1 场景② 的 DoD 不是"能处理坏文件"，而是"改名 `.exe` → 400 `INVALID_MEDIA`"。

**检查点**：每条验收标准都能被一条命令/一次点击判真假；不能判的退回去改。

## 模板 2 · 技术选型与轻量架构（选型别全靠 AI）

**什么时候用**：项目起步、要加新依赖、要换框架/存储、要拆服务之前。

```text
我要做 <一句话产品>。请帮我做技术选型与架构建议，但遵守以下约束：

选型原则（按优先级）：
1. 可维护性：小团队/单人能否长期维护，出问题是否容易定位。
2. 可查阅资料的丰富程度：社区案例、文档、报错可搜索性（我们要靠它让 AI 帮忙排错）。
3. 是否有与我这个业务相似的落地场景（不要选只在 demo 里出现的技术）。

输出要求：
- 给出 2–3 个候选方案，每个都写【为什么不用它】（排除项比选择项更重要）。
- 明确版本号（不要写 latest），并说明版本组合是否互相兼容。
- 产出【轻量架构一页纸】，必须回答 4 件事：
  ① 页面/组件放在哪里 ② 接口请求放在哪里 ③ 核心数据有哪些字段（表/字段/约束）
  ④ 哪些事由前端处理、哪些必须由服务端处理（含权限、校验、敏感数据）。
- 架构文档控制在 1 页内，不要写成八股文。
```

**本项目定制版**：选型结论进 `decisions.md`（六字段：ID｜日期｜结论｜依据｜已排除项｜决策人）；
架构一页纸在 `plan.md` §5–§10；版本组合事实在 `AGENT.md` §4.1（Boot 3.5.16 / Spring AI 1.1.8 / Java 21 / AWS SDK BOM）。

**检查点**：每个候选都写得出"为什么不用"；版本号是查过官方而不是背出来的。

## 模板 3 · 三份短文档（换会话/换 agent 前必须齐）

**什么时候用**：会话快满、要换 agent（Codex/Claude/WorkBuddy…）、要换机器、或新开一个会话继续。

```text
请帮我把当前状态沉淀成三份短文档（总量控制在 2 页内），写到 <项目目录> 下：

1. 项目总览：已有功能清单 + 主要模块之间怎么配合（不要贴代码）。
2. 架构方案：技术栈与版本、目录结构、编码约定、部署方式。
3. 进度记录：当前做到哪一步、哪里还有 bug、**试过哪些方案、哪些方案没解决问题**（这条最关键）。

硬要求：
- 每条都写"证据在哪"（文件路径 / 命令 / commit）。
- 不要写"已完成，应该可以了"这类无证据结论。
- 未决问题单独列出，并标注"卡在谁/什么条件"。
```

**本项目定制版**：`docs/项目/录音纪要平台/` 下 `00-先看这个.md`（总览）+ `plan.md`（架构）+
`state.md`（现在，≤40 行）+ `handoff.md`（交接，4 段 ≤25 行）+ `decisions.md`（已排除项的家）。
`handoff.md` §2「别踩的坑」就是"试过什么没解决"的沉淀位。

**检查点**：新会话只读 4 个文件就能开工（AGENTS.md + 该项目 state/handoff + 一份 rules）。

## 模板 4 · 规划四问（复杂任务开工前）

**什么时候用**：一个任务要改 >3 个文件、要碰公共组件、或你无法一眼看出影响面。

```text
先不要改代码，先给我计划。计划里必须回答四件事：
1. 改哪里：要新增/修改哪些文件（列全路径）。
2. 复用什么：项目里已有的哪些类/函数/配置可以直接用（不要重复造）。
3. 影响哪些功能：这次改动会让哪些已有行为发生变化（含接口契约、数据库、配置项）。
4. 怎么验证：给出可执行的验证命令与期望结果（含反例：什么样的输入应该被拒绝）。

然后等我确认你的计划，再动手。
```

**本项目定制版**（任务卡固定段，见 `tasks-starter.md`）：

```text
【规划四问】改哪里：… ｜ 复用什么：… ｜ 影响哪些功能：… ｜ 怎么验证：命令 + 期望输出 + exit code
【范围声明】本次只改 <目录/文件>，不改 <明确列表>；若需扩范围先问我（模板 5）
```

**检查点**：review 计划时**先看范围有没有跑偏**，再看实现细节。

## 模板 5 · 扩大改动范围前先确认（防"顺手优化"）

**什么时候用**：任何时候都可能触发——只要 AI 想动公共组件、公共配置、公共样式、别人负责的模块。

```text
【范围约束】本次任务只做 <X>。
- 必须保留的现有行为：<列表>。
- 如果要修改公共组件/公共配置，或需要扩大改动范围：先说明【原因 + 影响面 + 替代方案】，等我确认后再继续，不要直接改。
```

**本项目定制版**：公共面 = `application.yml` 配置键、`docker-compose.yml` 服务定义、`V1__init.sql` 之后的迁移、
`AGENT.md` 规则、任何 `/api/v1` 的响应字段（对外契约，改动要同步 `接入指南.md`）。

**检查点**：`git diff --stat` 里出现计划外文件 = 违规，先回滚再问。

## 模板 6 · 测试三问（测试跑完 / 提交前 / 合并前）

**什么时候用**：每次"我做完了/测试过了"之后。这是**防止 AI 口嗨**的核心模板（对应 11月7日音频的 P5）。

```text
在你把任务标记为完成之前，逐条回答（每条都要带证据）：
1. 检查了哪些场景？——列出你实际验证过的场景，以及对应的输入（含反例：什么样的输入会被拒绝）。
2. 实际运行了哪些测试？——贴命令 + 实际输出 + exit code；不要只说"全绿"。
3. 还有哪些没有验证？——明确列出没验证的部分、原因、风险等级（高/中/低）。
另外：涉及 <权限/数据写入/资金/删除> 的关键逻辑，指出哪几段需要人工 review，并说明为什么。
```

**本项目定制版**：回报格式（`AGENT.md` §5）已含"验证命令/实际输出/exit code/剩余风险"，
本模板把"剩余风险"升级为**结构化的"未验证清单 + 风险等级"**；review 报告（`docs/协作/templates/review.md`）同样必填。

**检查点**：第 3 条永远是**非空**的——一句"全部验证完毕"就是可疑信号。

## 模板 7 · 证据链报错（AI 越改越乱时）

**什么时候用**：同一个问题**连续两轮没有实质进展**（或它开始"换一种写法试试"）。先停，再发这个。

```text
先不要改代码。请先基于我给的证据分析原因，并明确说明【还缺什么证据】，然后再提最小修改方案。

【错误场景】（具体步骤，不要只说"X 坏了"）
1. …
2. …
3. 期望：…；实际：…

【完整报错与实际结果】
- 报错原文（整段贴，不要截断）：
- 出错位置（文件:行 / 接口 / 容器）：
- 核心日志（时间范围内）：
- 我原本期望看到的结果：

【最近的改动】
- 改了哪些文件（git diff --stat 或 commit）：
- 改了之后才开始出现的现象：

要求：
1. 先列出可能原因并排序，每条都要说"用什么证据能排除它"。
2. 说明当前证据还缺什么（要我去拿什么）。
3. 等我确认分析对得上，再做【最小修改】，然后按原步骤重测。
```

**本项目定制版**：贴 `docker compose logs <svc>` 片段、`docker compose ps` 健康状态、失败命令原文；
证据链沉淀到 `docs/协作/review/*.md` 或 `handoff.md` §2（"试过什么、什么没解决"）。

**检查点**：AI 的分析里出现了"我猜是因为…"却没有验证方法 = 退回重来。

## 附：换项目 / 换 agent 时怎么用这套模板

1. **只改占位符**：`<项目目录>`、`<命令>`、`<公共面清单>` 三处；模板骨架不用动。
2. **agent 适配**：Codex/Claude Code/Gemini 等把这份文档放进它们会自动读的位置（`AGENTS.md`/`CLAUDE.md` 里加一行指针），
   或在开工时手动贴对应模板。
3. **项目若没有"三份文档"**：先用模板 3 生成，之后再谈其他——没有状态沉淀，后面所有模板都会失效。
4. **小改动（<10 分钟）不要全套上**：只保留模板 5（范围）+ 模板 6（三问）两句即可，别把流程变成负担。

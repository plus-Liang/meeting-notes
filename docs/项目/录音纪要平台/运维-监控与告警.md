# 运维 — 监控与告警（T4.84 / 审计 P-25）

本文档面向「想给 meeting-notes 接一个外部 Prometheus」的自托管用户：给出抓取配置、指标清单、可执行的告警规则、与手工对账的口径，以及**安全边界**。项目本身不内置 Prometheus/Grafana/Alertmanager 容器（自托管最小集原则）——你只需要一个能抓 HTTP 的 Prometheus，一切指标都在 `GET /actuator/prometheus`。

## 1. 抓取配置

把下面这段粘进你的 `prometheus.yml`（`<host>` 换成部署机器地址；容器内互抓用服务名）：

```yaml
scrape_configs:
  - job_name: meeting-notes
    scrape_interval: 15s
    metrics_path: /actuator/prometheus
    # T4.89/P-28：actuator 需 Bearer；credentials_file 内容 = API_TOKEN（单行，勿带换行/引号）
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/meeting-notes.token
    static_configs:
      - targets: ['host:8080']
        labels:
          application: meeting-notes
```

（指标自带全局标签 `application="meeting-notes"`，由 `application.yml` 的 `management.metrics.tags` 注入；这里再写一份 targets 级标签是冗余保险。）

## 2. 指标清单

| 别名（PromQL） | 含义 | 看它想发现什么 |
|---|---|---|
| `http_server_requests_seconds_count / _sum`（`uri`/`status`/`exception` 标签） | HTTP 请求延迟直方图与计数 | 接口延迟突增、5xx 比例、某 uri 被打爆 |
| `jvm_memory_used_bytes{area="heap"}` | JVM 堆/非堆内存用量 | 内存泄漏、堆逼近上限（Xmx） |
| `jvm_gc_pause_seconds_*` | GC 暂停分布 | GC 频繁/长暂停（转写大文件时堆压力大） |
| `hikaricp_connections_active / pending / max` | DB 连接池活跃/排队/上限 | 连接池打满（pending>0 持续即异常） |
| `meetingnotes_task_count{status=...}` | 任务按状态计数（PENDING/RUNNING/DONE/DEAD/RETRYING 五档） | 失败堆积（DEAD 增长）、卡住（RUNNING 不动）、积压（PENDING 增长） |
| `meetingnotes_queue_depth` | Redis 转写队列深度（待取条数） | 队列积压——worker 死了或转写吞吐跟不上 |
| `meetingnotes_pending_oldest_age_seconds` | 最老一条 PENDING 距今秒数（0 = 无 PENDING） | 入队无人消费（worker 卡死/掉线，T4.85） |
| `meetingnotes_task_duration_seconds{quantile="0.5"/"0.95"}` | DONE 任务时延分位（秒；近 1h、最多 500 条样本）。**quantile 标签是我们自算的 p50/p95（最近秩法），不是 Prometheus summary——不要用 histogram_quantile 处理它** | 时延劣化（模型慢/资源紧张，T4.85） |

另有 JVM 线程/文件描述符、`logback_events_total`、`system_cpu_usage` 等标准指标，随 `micrometer-registry-prometheus` 自动暴露。

## 3. 告警规则（可执行）

把下面粘贴进你的 Prometheus rules 文件（阈值是自托管单实例的合理起点，按你的量级调整）：

```yaml
groups:
  - name: meeting-notes
    rules:
      - alert: WebhookQueueBacklog
        expr: meetingnotes_queue_depth > 100
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "转写队列积压 {{ $value }} 条，持续 10 分钟——worker 死亡或吞吐不足"

      - alert: PendingOldestAge
        expr: meetingnotes_pending_oldest_age_seconds > 600
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "最老 PENDING 已等待 {{ $value }} 秒——worker 死亡或消费停滞（T4.85）"

      - alert: DeadTaskDelta
        expr: delta(meetingnotes_task_count{status="DEAD"}[10m]) > 3
        for: 0m
        labels:
          severity: warning
        annotations:
          summary: "10 分钟内 DEAD 净增超过 3 个（转写彻底失败，需人工排查）"

      - alert: TaskDurationP95
        expr: meetingnotes_task_duration_seconds{quantile="0.95"} > 300
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "DONE 任务 p95 时延超过 300 秒（模型变慢/资源紧张，T4.85）"

      - alert: TasksStuckInRunning
        expr: sum(meetingnotes_task_count{status="RUNNING"}) == sum(meetingnotes_task_count{status="RUNNING"} offset 30m)
          and sum(meetingnotes_task_count{status="PENDING"}) > 0
        for: 0m
        labels:
          severity: warning
        annotations:
          summary: "RUNNING 数 30 分钟无变化且仍有排队——疑似 ASR 卡死或进程假死"

      - alert: HighHttp5xxRatio
        expr: sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          / sum(rate(http_server_requests_seconds_count[5m])) > 0.05
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "HTTP 5xx 比例超过 5%（持续 5 分钟）"

      - alert: JvmHeapHigh
        expr: jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"} > 0.85
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "JVM 堆使用超过 85%（持续 10 分钟）"

      - alert: InstanceDown
        expr: up{job="meeting-notes"} == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "meeting-notes 实例不可抓取（进程死亡或网络不通）"

      - alert: DbConnectionPoolSaturated
        expr: hikaricp_connections_pending > 0
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "DB 连接池出现排队等待（活跃连接打满）"
```

## 4. 手工核对口径

指标值必须与下面两条手工命令的输出一致（不同即指标有 bug，优先查本文件第 5 节的时序偏差）：

```sql
-- task 按状态计数 ↔ meetingnotes_task_count{status=...}（五档之和 = 总行数）
SELECT status, count(*) FROM task GROUP BY status;

-- 最老 PENDING 年龄 ↔ meetingnotes_pending_oldest_age_seconds（秒差由 app 在 Java 侧计算）
SELECT min(updated_at) FROM task WHERE status = 'PENDING';

-- 时延分位 ↔ meetingnotes_task_duration_seconds（app 只统计近 1h、最新 500 条 DONE，Java 侧排序取最近秩 p50/p95）
SELECT created_at, updated_at FROM task WHERE status = 'DONE' AND updated_at > now() - interval '1 hour' ORDER BY updated_at DESC LIMIT 500;
```

```bash
# 队列深度 ↔ meetingnotes_queue_depth
docker exec meeting-notes-redis-1 redis-cli LLEN meetingnotes:task-queue
```

两个注意点：①`meetingnotes_task_count` 与 SQL 之间有**最多 cacheSeconds（默认 15s）的时序偏差**，对账时以「抓取后 15 秒内不提交新任务」再比；②`RUNNING` 归属本机视角——`task.task_heartbeat` 的僵尸回收（T4.78）与可见性超时回收（T4.79）会把死实例的 RUNNING 扳回 PENDING，指标随后跟上。

**依赖故障时的健康检查时延预算（T4.90/S1）**：`spring.data.redis.timeout=3s`（命令）/ `spring.data.redis.connect-timeout=2s`（连接）/ 容器 healthcheck `timeout: 5s`——Redis 半死时带 token 的 `/actuator/health` 在 **3s 内**返回 503（此前 Lettuce 默认 60s，实测阻塞 60.04s）；任何依赖探测**超过 5s 会被容器健康检查判失败**（curl 超时），依赖抖动即容器 flapping。调参必须保持顺序：`WORKER_POLL_TIMEOUT_SEC`(2s) < `REDIS_TIMEOUT`(3s) < healthcheck timeout(5s)，且 `REDIS_CONNECT_TIMEOUT` < `REDIS_TIMEOUT`（契约测试 `RedisTimeoutInvariantTest` 守护，改 yml 默认值即红）。

**重连退避机制（T4.91/S1）**：恢复速度由 Lettuce `ClientResources` 的重连退避决定（`ConnectionWatchdog` 按它排重连），**与上面的命令超时无关**——默认 exponential 100ms→30s，T4.90 实测长停(60s)后恢复 14–24s。T4.91 起改为 `REDIS_RECONNECT_MIN_MS`(500)→`REDIS_RECONNECT_MAX_MS`(5000)（`config/RedisReconnectConfig`，经 Boot 的 `ClientResourcesBuilderCustomizer` 钩子，**不是** ClientOptions bean——后者会覆盖 `spring.data.redis.timeout`），长停恢复压到个位数秒；影响所有 Redis 连接（队列/清扫/回执）。**如果发现恢复仍慢，先查这两个键是否被 `.env`/override 覆盖**（如 MAX 被设回 30000 即回到旧行为）。

**故障日志去抖（T4.91/S2）**：worker 的「Redis 不可用」WARN 经 `RedisUnavailableReporter` 去抖——窗口 `WORKER_REDIS_LOG_WINDOW_SEC`(60s) 内**最多 1 条 WARN**（其余累加抑制计数），跨窗口再打一条心跳式告警（带计数）；Redis 恢复后**恰好 1 条 INFO**「Redis 已恢复（首次失败后 Ns，期间抑制 M 条）」，正常态零日志。120s outage 的 WARN 从 T4.90 的 ~92 条降到 ≤6 条。清扫器（每 60s 一轮）与 QueuePublisher（每请求一条）不在去抖范围。

## 5. 安全与边界

**多实例口径**：`meetingnotes_task_count` / `meetingnotes_pending_oldest_age_seconds` / `meetingnotes_task_duration_seconds` 各实例报的是**同一 DB 视角**（值相同）——多实例聚合时用 `max by (status) (meetingnotes_task_count)` 这类 max 聚合，**不要 sum**（会把同一计数翻倍）；`meetingnotes_queue_depth` 各实例值也相同，同理取 max。

**T4.89/P-28 起 `/actuator/**`（health/prometheus/metrics/info）统一经过 `ApiTokenFilter`，需 `Authorization: Bearer <API_TOKEN 或账号令牌>`；匿名一律 401。** 抓取端按上文 `authorization` 配置带 token；容器 healthcheck 用容器内 `$API_TOKEN`。仍建议只在内网/反代后面部署，反代上屏蔽 `/actuator/**` 的公网访问（纵深防御）。

## 6. 重新初始化 /setup（T4.93）

安装向导 `/setup` 的开关只有一个判据：**库里是否存在已认领的管理员**（`app_user` id=1 且 password_hash 非占位符）。
创建成功后 `/setup` 与 `/api/v1/setup/*`、`/setup.html` 全部 404，`SETUP_CODE` 不再被消费。

**如何重新开放向导（危险，先备份）**：

```bash
docker compose exec -T postgres psql -U mn -d meetingnotes -c "DELETE FROM app_user WHERE id = 1"
# 或整库重来：docker compose down -v   （会清掉全部任务/用户/会话数据）
docker compose up -d
```

- 删掉 id=1 后 `/setup` 立即重新开放（免鉴权），但**必须持有 `.env` 里的 `SETUP_CODE` 才能创建管理员**；
  码丢了就在 `.env` 里换一个新值并 `docker compose up -d` 重建 app 容器。
- 风险：`DELETE app_user` 会级联清理该用户全部会话（V10 外键 ON DELETE CASCADE；任务行不级联、保留原样）；生产数据先跑 `scripts/backup.ps1`。
- 完成重新初始化后务必登录一次确认，并把 `/setup` 再次 404 作为验收（匿名 `curl -i http://localhost:8080/setup.html` 应 404）。

## 7. 崩溃计次与毒丸（T4.94/P-03）

- **现象**：某条任务把 worker 进程搞挂（SIGKILL/OOM）→ 重启后被重新入队 → 再次搞挂进程，循环往复（崩溃不计入业务失败的重试计数，`markFailure` 根本没机会执行）。
- **判据与计数**：两条恢复路径——启动恢复的「陈旧 RUNNING」（`app.recovery.stale-running-minutes`，默认 5 分钟）与运行期僵尸回执清扫（`app.worker.visibility-timeout-sec`，默认 180s）——都会把该任务 `attempts + 1` 并置回 PENDING 重投。
- **上限**：`attempts` 达到 `TASK_MAX_RETRIES`（默认 3）→ 置 `DEAD` + 写 `dead_letter`（`error_code=WORKER_CRASH`）+ 退分钟数（同业务失败口径）。
- **现场排查**：
  `SELECT id,status,attempts,error_code FROM task WHERE attempts>0 ORDER BY updated_at DESC;`
  `SELECT * FROM dead_letter ORDER BY id DESC LIMIT 10;`
- **人工放行**：确认非毒丸后，把 `attempts` 归零 + 置 `PENDING` 再入队：
  `UPDATE task SET attempts = 0, status = 'PENDING', updated_at = now() WHERE id = <id>;`
  （并删除对应 `dead_letter` 行，走既有重试/重传入口重新入队。）
- **页面上怎么看（T4.95 失败可视）**：任务台账的失败/重试行会直接显示原因副行（取 `dead_letter` 最新
  `reason`，截 40 字悬停看全文）；详情页「为什么失败」块给出原因 / 下一步建议 / 已尝试次数，并附
  **「复制诊断信息」按钮**（一键复制任务号/状态/错误码/原因/尝试次数，贴给开发者或贴进 issue）。
  接口侧对应列表与详情响应的 `error_message` / `attempts` 字段（仅 DEAD/RETRYING 有意义）。

## 音频语言识别不对怎么查（T4.99）

- 先看任务实际带的语言：`SELECT id, language FROM task WHERE id = <id>;`（NULL = 走部署级 `ASR_LANGUAGE`，默认 zh）。
- 再看 ASR 服务日志里的语言行：`docker compose logs asr | grep "language="`（每条转写打印实际生效语言；`auto` 会显示检测到的语言）。
- 症状「英文/外语音频转出中文乱串」：任务没带 `language`（NULL → 部署级 zh）。补救：重新提交并在请求里显式带 `language=en`（或 `auto`）；直接对 ASR 端点手工验证：
  `curl -F "file=@音频" -F "model=small" -F "language=en" http://localhost:<ASR_PORT>/v1/audio/transcriptions`
- 合法值：2–3 位小写语言码或 `auto`；其它值在应用入口与 ASR 服务两层都会 400。

## 多副本时的指标语义

- 每副本各暴露一份 `/actuator/prometheus`；抓取端应保留 `instance` label（Prometheus 默认携带），不要 relabel 丢掉。
- `meetingnotes.task.count` / `meetingnotes.queue.depth` / `pending.oldest.age` / `duration` 分位是**全库口径**：N 副本下会有 N 份重复值，取任一即可（`max by (status) (...)`），**勿 sum**（会翻倍）。
- 副本级指标（jvm / hikaricp / `http_server_requests`）按 `instance` 区分；聚合时保留 instance 或 `sum by (instance)`。
- 多副本的前置条件与验收剧本见 [运维-扩容前置清单](运维-扩容前置清单.md)。

**存储护栏与占用可见（T4.92/P-21/P-22 前半）**：上传/链接导入前检查磁盘可用空间，低于 `STORAGE_UPLOAD_HEADROOM_MB`（256MB）→ 503 `INSUFFICIENT_STORAGE`（可重试）；启动时低于 `STORAGE_MIN_FREE_MB`（2048MB）→ ERROR 横幅（不拒启）。指标：`meetingnotes_storage_disk_free_bytes`（建议 WARN < 5GB、CRITICAL < 2GB）与 `meetingnotes_storage_audio_bytes`（音频对象总占用）。管理员「设置页 → 存储」可看占用并清理孤儿对象（默认 dryRun，确认后才真删；只删「tasks/ 前缀 + 无 DB 引用」对象）。

## 8. 回收站占用与清理（T4.96/D-245）

- 删除 = 软删除（`task.deleted_at`），保留 `TRASH_RETENTION_DAYS`（默认 30 天）后由 `TaskTrashSweeper`
  每小时（`TRASH_PURGE_INTERVAL_MS`）物理删除，每轮上限 200 条；启动时也会扫一次。
- 占用：`GET /api/v1/admin/storage` 新增只读段 `"trash":{"objects":N,"bytes":N}`（回收站任务的桶内对象；
  这些对象**同时计入** `audio`——它们确实占盘）。
- 清理日志键：`purged` / `retentionDays`（INFO，"回收站到期清扫"）；`TRASH_PURGE_ENABLED=false` 时整轮跳过。
- 怀疑没清怎么办：
  `SELECT count(*), min(deleted_at) FROM task WHERE deleted_at IS NOT NULL;`
  `SELECT id, deleted_at FROM task WHERE deleted_at < now() - interval '30 days';`
  （有行且超期 → 看清扫日志；`retention-days <1` 会被 WARN 回退 30，不会一次误配就全删。）
- 彻底删除的 S3 对象删除是 best-effort：DB 行删了、对象删失败只 WARN——残余对象会出现在
  `orphans()`（任务行已不在 → 无引用），走既有孤儿清理出口即可。

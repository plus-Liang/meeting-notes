# 运维 — 监控与告警（T4.84 / 审计 P-25）

本文档面向「想给 meeting-notes 接一个外部 Prometheus」的自托管用户：给出抓取配置、指标清单、可执行的告警规则、与手工对账的口径，以及**安全边界**。项目本身不内置 Prometheus/Grafana/Alertmanager 容器（自托管最小集原则）——你只需要一个能抓 HTTP 的 Prometheus，一切指标都在 `GET /actuator/prometheus`。

## 1. 抓取配置

把下面这段粘进你的 `prometheus.yml`（`<host>` 换成部署机器地址；容器内互抓用服务名）：

```yaml
scrape_configs:
  - job_name: meeting-notes
    scrape_interval: 15s
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ['host:8080']
        labels:
          application: meeting-notes
```

（指标自带全局标签 `application="meeting-notes"`，由 `application.yml` 的 `management.metrics.tags` 注入；这里再写一份 targets 级标签是冗余保险。）

## 2. 指标清单

| 别名（PromQL） | 含义 | 看它想发现什么 |
|---|---|---|
| `http_server_requests_seconds_count / _sum`（`uri`/`status`/`exception` 标签） | HTTP 请求延迟直方图与计数 | 接口延迟突增、5xx 比例、某 uri 被打爆 |
| `jvm_memory_used_bytes{area="heap"}` | JVM 堆/非堆内存用量 | 内存泄漏、堆逼近上限（Xmx） |
| `jvm_gc_pause_seconds_*` | GC 暂停分布 | GC 频繁/长暂停（转写大文件时堆压力大） |
| `hikaricp_connections_active / pending / max` | DB 连接池活跃/排队/上限 | 连接池打满（pending>0 持续即异常） |
| `meetingnotes_task_count{status=...}` | 任务按状态计数（PENDING/RUNNING/DONE/DEAD/RETRYING 五档） | 失败堆积（DEAD 增长）、卡住（RUNNING 不动）、积压（PENDING 增长） |
| `meetingnotes_queue_depth` | Redis 转写队列深度（待取条数） | 队列积压——worker 死了或转写吞吐跟不上 |
| `meetingnotes_pending_oldest_age_seconds` | 最老一条 PENDING 距今秒数（0 = 无 PENDING） | 入队无人消费（worker 卡死/掉线，T4.85） |
| `meetingnotes_task_duration_seconds{quantile="0.5"/"0.95"}` | DONE 任务时延分位（秒；近 1h、最多 500 条样本）。**quantile 标签是我们自算的 p50/p95（最近秩法），不是 Prometheus summary——不要用 histogram_quantile 处理它** | 时延劣化（模型慢/资源紧张，T4.85） |

另有 JVM 线程/文件描述符、`logback_events_total`、`system_cpu_usage` 等标准指标，随 `micrometer-registry-prometheus` 自动暴露。

## 3. 告警规则（可执行）

把下面粘贴进你的 Prometheus rules 文件（阈值是自托管单实例的合理起点，按你的量级调整）：

```yaml
groups:
  - name: meeting-notes
    rules:
      - alert: WebhookQueueBacklog
        expr: meetingnotes_queue_depth > 100
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "转写队列积压 {{ $value }} 条，持续 10 分钟——worker 死亡或吞吐不足"

      - alert: PendingOldestAge
        expr: meetingnotes_pending_oldest_age_seconds > 600
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "最老 PENDING 已等待 {{ $value }} 秒——worker 死亡或消费停滞（T4.85）"

      - alert: DeadTaskDelta
        expr: delta(meetingnotes_task_count{status="DEAD"}[10m]) > 3
        for: 0m
        labels:
          severity: warning
        annotations:
          summary: "10 分钟内 DEAD 净增超过 3 个（转写彻底失败，需人工排查）"

      - alert: TaskDurationP95
        expr: meetingnotes_task_duration_seconds{quantile="0.95"} > 300
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "DONE 任务 p95 时延超过 300 秒（模型变慢/资源紧张，T4.85）"

      - alert: TasksStuckInRunning
        expr: sum(meetingnotes_task_count{status="RUNNING"}) == sum(meetingnotes_task_count{status="RUNNING"} offset 30m)
          and sum(meetingnotes_task_count{status="PENDING"}) > 0
        for: 0m
        labels:
          severity: warning
        annotations:
          summary: "RUNNING 数 30 分钟无变化且仍有排队——疑似 ASR 卡死或进程假死"

      - alert: HighHttp5xxRatio
        expr: sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          / sum(rate(http_server_requests_seconds_count[5m])) > 0.05
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "HTTP 5xx 比例超过 5%（持续 5 分钟）"

      - alert: JvmHeapHigh
        expr: jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"} > 0.85
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "JVM 堆使用超过 85%（持续 10 分钟）"

      - alert: InstanceDown
        expr: up{job="meeting-notes"} == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "meeting-notes 实例不可抓取（进程死亡或网络不通）"

      - alert: DbConnectionPoolSaturated
        expr: hikaricp_connections_pending > 0
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "DB 连接池出现排队等待（活跃连接打满）"
```

## 4. 手工核对口径

指标值必须与下面两条手工命令的输出一致（不同即指标有 bug，优先查本文件第 5 节的时序偏差）：

```sql
-- task 按状态计数 ↔ meetingnotes_task_count{status=...}（五档之和 = 总行数）
SELECT status, count(*) FROM task GROUP BY status;

-- 最老 PENDING 年龄 ↔ meetingnotes_pending_oldest_age_seconds（秒差由 app 在 Java 侧计算）
SELECT min(updated_at) FROM task WHERE status = 'PENDING';

-- 时延分位 ↔ meetingnotes_task_duration_seconds（app 只统计近 1h、最新 500 条 DONE，Java 侧排序取最近秩 p50/p95）
SELECT created_at, updated_at FROM task WHERE status = 'DONE' AND updated_at > now() - interval '1 hour' ORDER BY updated_at DESC LIMIT 500;
```

```bash
# 队列深度 ↔ meetingnotes_queue_depth
docker exec meeting-notes-redis-1 redis-cli LLEN meetingnotes:task-queue
```

两个注意点：①`meetingnotes_task_count` 与 SQL 之间有**最多 cacheSeconds（默认 15s）的时序偏差**，对账时以「抓取后 15 秒内不提交新任务」再比；②`RUNNING` 归属本机视角——`task.task_heartbeat` 的僵尸回收（T4.78）与可见性超时回收（T4.79）会把死实例的 RUNNING 扳回 PENDING，指标随后跟上。

## 5. 安全与边界

**多实例口径**：`meetingnotes_task_count` / `meetingnotes_pending_oldest_age_seconds` / `meetingnotes_task_duration_seconds` 各实例报的是**同一 DB 视角**（值相同）——多实例聚合时用 `max by (status) (meetingnotes_task_count)` 这类 max 聚合，**不要 sum**（会把同一计数翻倍）；`meetingnotes_queue_depth` 各实例值也相同，同理取 max。

**`/actuator/prometheus` 与其它 actuator 端点不经过 `ApiTokenFilter`（该过滤器只拦 `/api/v1/**`），因此无鉴权。** 若把 8080 端口暴露到公网，任何人都能读到你的全部指标（含 uri 维度的请求画像）。二选一：

1. **推荐**：只在内网/反向代理后面部署，反代上屏蔽 `/actuator/prometheus` 与 `/actuator/**` 的公网访问；
2. **后续加固建议（本卡不实现）**：`management.server.port` 把 actuator 绑到独立内网端口（如 8081），主端口 8080 对外时指标自然不可达。

## 多副本时的指标语义

- 每副本各暴露一份 `/actuator/prometheus`；抓取端应保留 `instance` label（Prometheus 默认携带），不要 relabel 丢掉。
- `meetingnotes.task.count` / `meetingnotes.queue.depth` / `pending.oldest.age` / `duration` 分位是**全库口径**：N 副本下会有 N 份重复值，取任一即可（`max by (status) (...)`），**勿 sum**（会翻倍）。
- 副本级指标（jvm / hikaricp / `http_server_requests`）按 `instance` 区分；聚合时保留 instance 或 `sum by (instance)`。
- 多副本的前置条件与验收剧本见 [运维-扩容前置清单](运维-扩容前置清单.md)。

### D-001 交付形态定为 Web 应用
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：唯一交付形态为 B/S 架构 Web 应用（Spring Boot API + 3 个页面 + Swagger UI + `docker compose up`）。
- **依据**：目标是 Java 后端实习，需要"能点开、能调接口"的后端证据；Web 最标准。
- **已排除项**：微信小程序（需已备案域名 + HTTPS + 审核周期，与 4 周时间盒冲突；音频类目易卡审核）；桌面客户端（Electron/Tauri 把重心拉离后端，后端会退化成"本地服务"）。

### D-002 形态定为 self-hosted 开源，不做 SaaS
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：以「个人自用为第一目标 + 可开源供他人自部署」交付；不做公网多用户托管。
- **依据**：身份从"服务提供者"变为"工具作者"，版权责任随部署转移；无服务器成本、无运维负担。
- **已排除项**：SaaS（版权风险 + 运维成本 + 被攻击面）；纯个人自用不开源（放弃可展示性与二次使用价值）。

### D-003 不与商业产品比功能，只服务三类用户
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：定位为「中文 + 可自托管 + 数据不出本机 + Java 生态」的交集；只服务 A 本地文件囤积者 / B 数据不能出门者 / C 要接进自己系统者。
- **依据**：功能竞争必输（飞书妙记、通义听悟、讯飞听见更成熟）；self-hosted 品类的用户从不被"功能"说服，而被"数据控制权"说服（参照 Immich/Jellyfin/Nextcloud）。
- **已排除项**：做"更好的飞书"（必输）；以 star 数为目标（同类太多，0 star 是常态）；"为了学习"当理由（在面试里等于承认项目无价值）。

### D-004 默认路径必须零成本可跑
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：不填任何 API key，P1 用户故事必须全部可走通（本地 ASR + 模板/本地 LLM 摘要兜底）。
- **依据**：开源项目"clone 下来第一步就要充钱"是 0 star 的直接原因。
- **已排除项**：强制 BYO-key（抬高门槛）；只有云通道（隐私与成本双输）。

### D-005 不自研 ASR / LLM 模型
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：只做编排层；模型一律外部调用。代码库不得出现权重文件与训练脚本。
- **依据**：4 周时间盒内自研不可能；本项目价值在任务编排、可靠性、成本控制。
- **已排除项**：训练/微调模型（跑不动、无面试价值）；自己实现推理（重复造轮子）。

### D-006 ASR 独立成服务，走 OpenAI 兼容协议
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：ASR 以独立容器提供服务，暴露 OpenAI 兼容的 `/v1/audio/transcriptions`。
- **依据**：FunASR 官方即提供 OpenAI 兼容服务；接口稳定后，实现可整体替换而 Java 侧零改动。
- **已排除项**：Java 内嵌 JNI 调模型（依赖地狱）；私有协议（换供应商要改代码）。

### D-007 LLM 全部走 OpenAI 兼容协议（可切国内模型）
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：摘要/待办统一经 OpenAI 兼容端点调用，`base-url + model + key` 三者可配；默认支持智谱 GLM、DeepSeek、Kimi、通义/百炼、本地 Ollama。
- **依据**：这些平台均提供 OpenAI 兼容模式，一套适配器覆盖全部。
- **已排除项**：为每家写专属 SDK（维护成本爆炸）；绑死单一供应商（用户无法自选）。
- **备注**：各家的确切 base-url 与模型名在编码当天必须 curl 实测，未实测不写默认值。
  - **T0.5 实测（2026-11-13，采用 DeepSeek）**：`base-url=https://api.deepseek.com`，
    `completions-path=/v1/chat/completions` → 实际请求 `POST https://api.deepseek.com/v1/chat/completions`；
    模型名 `deepseek-flash`。依据：官方文档 `api-docs.deepseek.com` 的 base_url / curl 示例，
    加本机带 key 实测 `GET https://api.deepseek.com/models` → `200`，返回模型 ID
    `deepseek-flash` / `deepseek-v4-pro`；`POST /chat/completions` 与 `/v1/chat/completions` 均 `200`。
    `deepseek-chat` 是兼容别名（响应里 `"model":"deepseek-flash"`），不作默认模型名。
    `mvn -q -Dtest=LlmSmokeTest test` 真实云端返回 3 条中文摘要，exit 0。
  - **路径坑（同 D-034）**：`javap` 核对 `OpenAiChatProperties.completionsPath` 默认
    `/v1/chat/completions`，Spring AI 把它**追加**到 base-url 后面，所以 base-url 不能自带 `/v1`。
    换供应商用 `LLM_CHAT_COMPLETIONS_PATH` 覆盖，不要改 base-url。
  - **智谱候选值（文档已核对、本机无 key 未做带 key 实测）**：
    `https://open.bigmodel.cn/api/paas/v4` + `/chat/completions` + `glm-4.7-flash`（官方免费模型，
    文档 curl 示例 `POST .../chat/completions`）。无 key 时 curl 返回 `401 {"code":"1001"}`
    只证明端点存在，**不是跑通证据**；若换回智谱必须把 `LLM_CHAT_COMPLETIONS_PATH` 改成 `/chat/completions`。
  - `deepseek-flash` 默认开启 thinking：若 `LLM_MAX_TOKENS` 过小，推理会吃光额度导致
    `choices[0].message.content` 为空，故默认给 1024。

### D-008 默认中文 ASR 选 FunASR（不是 whisper 系）
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：默认容器为 FunASR；whisper.cpp / faster-whisper 作为备选实现。
- **依据**：中文、方言、标点、VAD、说话人 pipeline 是 FunASR 的强项；本场景输入以中文为主。
- **已排除项**：whisper small/medium 做默认（中文标点与专有名词表现较弱，本人本机实测过）。

### D-009 任务用「PG 任务表 + Redis 分发」，不用纯消息队列
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：任务状态落 PostgreSQL，Redis 只做分发/限流/缓存。
- **依据**：任务需要可查、可重试、可重投、可统计；纯 MQ 里的消息不可观测，无法满足幂等与死信的可视化要求。
- **已排除项**：Kafka（规模不匹配）；RabbitMQ 单独承担状态（查询困难）；纯内存队列（重启即丢）。

### D-010 媒体处理全部在容器内完成
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：ffmpeg 抽音轨、ASR 解码都在容器内；宿主机不安装媒体工具。
- **依据**：本机实测 Windows Smart App Control 会拦截未签名二进制（ffmpeg/ffprobe/sherpa-onnx 报 `Application Control policy blocked this file`）。
- **已排除项**：宿主机直装 ffmpeg（本机被策略拦截，且换机器不可复现）；用 Python 库绕开（同样受策略影响）。

### D-011 对象存储用 MinIO（S3 协议）
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：原始文件与产物存 MinIO，走 S3 兼容 API。
- **依据**：本地可跑、零成本、后续可无缝换成真实 S3/OSS；不把文件放容器本地目录（重建即丢）。
- **已排除项**：直接落本地磁盘（不可扩展、易丢）；直接用云 OSS（破坏"零成本可跑"）。

### D-019 对外接入面只做 「REST API + Webhook + OpenAPI」
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：外部系统接入本项目的路径只开放三个面：①REST API（Bearer Token）②Webhook 终态回调（HMAC 签名、至少一次投递、去重键）③OpenAPI 规范 `/v3/api-docs`。inbox 目录与导出为 P2，MCP 为 P3。细节见 `接入指南.md`。
- **依据**：C 类用户（要接进自己系统的人）是定位的一部分，必须有真实接入面；但给每家客户端写插件是无底洞（违反 D-015）。API + Webhook 是最小稳定面，n8n/Zapier/脚本/群机器人/AI agent 全部能长在它上面。
- **已排除项**：为飞书/Obsidian/VSCode 各写一个插件（成本高、4 周做不完）；官方多语言 SDK（用 OpenAPI 自动生成即可）；数据库直连或只读账号（强耦合表结构，升级即坏）；OAuth2/多租户（单用户自托管，Token 足够，见 D-002）。

### D-020 AI 能力做成三档降级，所以"零成本可跑"成立
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：摘要/待办按 ①云 API（有 key）→ ②本地 Ollama（启用且可用）→ ③抽取式兜底（关键句 + 规则待办 + 模板）顺序降级；结果记录 `ai_tier`（CLOUD/LOCAL/EXTRACTIVE）；三档必须输出相同字段结构。
- **依据**：**"接入 AI"不等于"必须买 API key"**。ASR 本身完全本地免费；LLM 这一档有本地模型与抽取式两条免费路径。开源项目"clone 下来第一步要充钱"会直接废掉采用价值（D-004）。
- **已排除项**：只支持云 API（抬高门槛、破坏离线场景）；只做抽取式（质量不够，称不上 AI 项目）；强制跑 Ollama（8GB 内存门槛，低配机器直接不能启动）。
- **诚实标注**：抽取式**不是** AI 摘要，是"关键句提取 + 规则抽取"，质量明显更低；README 必须写清三档差异，不许把 ③ 当 ① 宣传。

### D-021 配置全部外置，"一个不落"，并带机器判据
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：路径、端口、key、并发数、模型名、配额、webhook、inbox、离线开关、日志级别——全部有环境变量入口；`.env.example` 是唯一事实来源；每个任务的 DoD 必须跑 `配置清单.md` §2 的三条自检命令。
- **依据**：这是"可自托管/可换环境/可换模型"的物理前提；也是 D-004（零成本可跑）、D-007（换供应商）、D-001（换工作区）能成立的基础。硬编码一处，别人就起不来。
- **已排除项**：把配置写进 `application.properties` 常态值（改配置要重新打包）；只用 docker-compose 传环境变量而应用侧仍写死默认值（两套来源必然漂移）；"只把 key 外置，其它写死"（这正是最常见的半成品）。

### D-023 备份与恢复只做本地，且不备份密钥
- **日期**：2026-11-13｜**决策人**：本人
- **结论**：`backup.ps1` 产出 `./backups/<时间戳>/{pg.dump, objects/, MANIFEST.md}`；每日自动、保留 7 份；`restore.ps1 -From ... -Force` 恢复前先把现有卷改名留存；**`.env` 不进备份**（只放 `.env.example` 副本）。
- **依据**：工作流与 PRD 都要求"数据本地保存与备份"；本项目卖点是"数据不出门"，丢数据等于毁掉信任（US-11 / N18–N20）。

### D-024 页面状态刷新用 3 秒轮询，不用 WebSocket/SSE
- **日期**：2026-11-13｜**决策人**：本人

### D-046 失败语义归 worker：Spring AI 内部重试收敛到 2 次（T1.5 实现时发现并修）
- **日期**：2026-11-13（WorkBuddy 实测发现，我独立复验后确认）｜**决策人**：本人
- **结论**：`spring.ai.retry.max-attempts=${AI_RETRY_MAX_ATTEMPTS:2}` + `backoff.initial-interval=2s` /
  `max-interval=10s`（三个新环境变量已进 `.env.example`）。**重试语义只归 worker 的 RETRYING→DEAD 状态机**；
  `task.error_code` 只放稳定码（列宽 64），完整原因写 `dead_letter.reason`（TEXT）。
- **依据**：Spring AI 1.1.8 的 `OpenAiAudioTranscriptionModel` 确实走 `RetryUtils.DEFAULT_RETRY_TEMPLATE`
  （解压 class 扫描确认），默认 10 次指数退避 → ASR 挂掉时单次尝试 7 分钟才把异常交给外层，
  "失败进 RETRYING"名存实亡。收敛后**实测 7 分钟 → 9 秒**（我复验：`RUNNING → RETRYING×2 → DEAD`，
  attempts=3、error_code=ASR_ERROR、dead_letter 有 87 字原因）。
- **已排除项**：保留 Spring AI 默认 10 次退避（架空状态机、拖慢失败反馈）；自己写 HTTP 客户端绕开
  `TranscriptionModel`（丢复用、违反原则 V）；把异常消息塞进 `error_code`（列宽不够 → DB 拒绝 →
  任务反而卡 RUNNING，这是 T1.5 真实踩到的二次故障）。

### D-055 T2.1 实现裁决：撤销全局唯一索引 + 用 ON CONFLICT 做幂等
- **日期**：2026-11-14（T2.1 验收时裁决作者的两项偏差）｜**决策人**：本人
- **结论**：
  1. **批准 `DROP INDEX ux_task_hash`**：V1 的是**跨用户**全局唯一，与 D-040（查询必带 `user_id`）冲突；V2 改为
     `UNIQUE (user_id, content_hash)`（先查重删重复行、再 `DROP INDEX IF EXISTS`、再建索引）。幂等粒度收到"用户 + 内容"。
  2. **批准用 `INSERT … ON CONFLICT (user_id, content_hash) DO NOTHING RETURNING id` + 判空回查**，**否掉**我任务卡里写的
     "捕获 `DuplicateKeyException` 后回查"：PG 中同事务内约束冲突后事务已 aborted，catch 后再回查会报 `current transaction is aborted`。
     幂等权威仍是数据库唯一约束（无 SELECT-then-INSERT 竞态），冲突回查放在事务外（快照干净）。
  3. 卡片写法纠正：**以后任务卡不写具体 SQL/异常模式**，只写约束（"幂等权威 = 唯一约束；禁止先查后插；事务边界由实现者定"）。
- **依据**：多用户语义（D-040/D-053）；并发验收我复跑过：两请求同 id、只 1 行（`review/2026-11-14-T1.9-T2.1验收.md` §1.2）。
- **已排除项**：保留全局唯一索引（挡住"A、B 上传同一内容"这一合法场景）；应用层内存锁/Redis 锁（单机重启即失效，且非权威）。

### D-056 死信与错误契约收口（T2.11）
- **日期**：2026-11-14（T2.1 验收时发现）｜**决策人**：本人
- **结论**：
  1. **复活与死信一致性**：DEAD 任务被重传复活时，同一次操作内 `DELETE FROM dead_letter WHERE task_id = ?`；
     否则死信列表里会出现"已 DONE 的任务"，同一任务再失败还会写第二条死信（实质重复）。
  2. **对外错误契约收口**：上传路径的存储故障统一映射为 `500 STORAGE_ERROR`（复用既有码，不新增）；
     `ApiExceptionHandler` 增加兜底 `@ExceptionHandler(Exception.class)` → `500 INTERNAL_ERROR`（统一 `{code,message}` envelope）；
     `接入指南.md` §3.3 补一行"500 兜底（非业务码，不计入 7 个）"。
  3. 判据：停 MinIO → 上传 → HTTP 500 且**响应体含 `code`**；复活一个 DEAD 任务 → `dead_letter` 该任务行数 = 0。
- **依据**：实测停 MinIO 后返回的是 Spring 默认体 `{timestamp,status,error,path}`（**无 `code`**），接入方无法按码分支；
  实测复活成功后 task 11 为 `DONE` 而 `dead_letter` 仍有 1 行（见验收报告 F-1/F-2）。
- **已排除项**：新增错误码（违反 D-047"只增不改、固定 7 个"——这里用既有 `STORAGE_ERROR` + 非业务兜底码）；
  只改文档不改实现（接入方按文档写代码会踩空）。

### D-057 框架异常不许吞状态码：通用码分层 + 列表参数严格校验
- **日期**：2026-11-14（T2.11/T2.10 验收时实测发现）｜**决策人**：本人
- **结论**：
  1. **兜底 handler 必须先尊重框架语义**：`@ExceptionHandler(Exception.class)` 里若 `e instanceof org.springframework.web.ErrorResponse`，
     按它自己的 `getStatusCode()` 返回（404/405/415/400 各回各的），只有**真未知异常**才 `500 INTERNAL_ERROR`。
     原因：实测 T2.11 之后 `GET /api/v1/nope`、`DELETE /api/v1/tasks`、`GET /api/v1/tasks/abc`、`Content-Type: application/json`
     **全部变成 500**（`NoResourceFoundException` / `HttpRequestMethodNotSupportedException` / `HttpMediaTypeNotSupportedException` 被吞）。
  2. **错误码分层**（不破坏 D-047 的"只增不改"）：
     - **业务码 7 个**（保持）：`INVALID_MEDIA` / `SIZE_EXCEEDED` / `DURATION_EXCEEDED` / `QUOTA_EXCEEDED`(+`TOO_MANY_REQUESTS`) / `TASK_NOT_FOUND` / `ASR_ERROR`（`error_code` 字段）/ `STORAGE_ERROR`；
     - **通用码（新增，非业务）**：`INVALID_PARAM`(400，参数/查询串/路径参数类型错)、`NOT_FOUND`(404，路径或资源不存在)、
       `METHOD_NOT_ALLOWED`(405)、`UNSUPPORTED_MEDIA_TYPE`(415)、`INTERNAL_ERROR`(500 兜底)。
     接口参数校验**不许再借用 `INVALID_MEDIA`**（语义是"文件格式不合法"）。
  3. **`GET /api/v1/tasks` 的 `status` 严格校验**：只接受 `PENDING/RUNNING/RETRYING/DONE/DEAD`，其它 → 400 `INVALID_PARAM`
     （静默返回空列表会让接入方把"参数写错"误判成"没数据"）。
- **依据**：T2.11/T2.10 验收报告 F-1/F-2/F-3（`review/2026-11-14-T2.11-T2.10验收.md`）的实测响应码表；现在**没有任何外部接入方**，此时定码表成本最低。
- **已排除项**：继续用 `INVALID_MEDIA` 表示参数错误（语义污染，接入方会去查文件）；把框架 4xx 一律映射成 500（客户端会无脑重试）；
  重新编号 7 个业务码（破坏 D-047"只增不改"）。

### D-059 健康检查口径：四项都进 readiness + 探活超时 ≤2s + HTTP 工厂后续换 JDK HttpClient
- **日期**：2026-11-14（T2.2 验收后定 T2.4 口径）｜**决策人**：本人
- **结论**：
  1. **四项依赖（DB / Redis / MinIO / ASR）都进 `readiness` 组**：任一不可用 → `/actuator/health` 整体 `DOWN`，

### D-084 T3.7 契约批准（导出 md + PASTE/字幕入口）；字幕幂等改为"解析后文本 hash"；字幕编码/上限/分派位置定死
- **日期**：2026-11-14（T3.7 开工确认）｜**决策人**：本人
- **结论**（写码方草案 + 我的 4 处收紧，批准后照此写码，不再逐条问）：
  1. **导出**：`GET /api/v1/tasks/{id}/export?format=md`，三节固定顺序 `## 摘要/## 关键词/## 待办`；待办 `- [x]/- [ ]` + action + 非 null 才追加 `（owner: X / deadline: Y）`；节内无内容写 `（无）`（不跳过节标题）；`format` 缺失或非 `md` → 400；任务不存在/非本人 → 404 `TASK_NOT_FOUND`；`task_result` 缺失 / transcript 空 / 状态非 DONE → 400 `INVALID_PARAM`（不新增业务码）；导出不建任务、不耗配额。
  2. **字幕幂等口径（推翻草案）**：`content_hash = sha256(解析后文本 UTF-8)`，**不是**原文件字节。理由：①保持全项目不变量 `content_hash == sha256(MinIO 对象字节)`（音频路径本就成立）；②同一内容存成 srt/ass/JSON 文本不重复建任务、不白耗配额。
  3. **`source_type='PASTE'` 不新增取值**（V1 注释已预留，无 DB 枚举约束）；JSON 文本与 srt/ass 都走 PASTE。
  4. **`duration_sec` 允许 null**：`TaskCreatedResponse.durationSec` 由 `long` 改 `Long`（仅 PASTE/字幕为 null，音频响应仍是数字、键不变）；`size_bytes` = 存储文本 UTF-8 字节数。
  5. **编码**（spec §PASTE"注意 UTF-8 / GBK"）：字幕 UTF-8 优先（去 BOM），严格解码失败回退 GBK，仍失败 400；不许静默替换坏字符。
  6. **上限**：JSON `text` trim 后 1..100_000 字符；字幕文件 ≤5 MB（超 → 413 `SIZE_EXCEEDED`），解析后文本 >100_000 字符 → 400。
  7. **分派位置**：controller 按文件名后缀（大小写不敏感）分派 `.srt/.ass`，**先于** `MediaMagic` 魔数闸；解析器独立小类；其余后缀音频路径逐字节不动。
  8. **可维护性硬约束**：`TranscriptionWorker`(295 行)/`TaskService`(253 行) 不得撞 300 行上限 → 先抽小类（如 `worker/PasteTextReader`、`worker/MonoWavExtractor`），PASTE/字幕提交放新类，**allowlist 仍为 0 条**；新类不得 import `com.meetingnotes.web.*`（M5）。
- **依据**：`tasks-starter.md` T3.7 卡；spec US-5 与格式表 PASTE 行；V1 schema 注释；`TaskService` 幂等顺序（INSERT 冲突 → 不耗配额）；`ApiExceptionHandler` 已能出 415/400 统一体；`check-maintainability.ps1` 300 行上限 + 空 allowlist。
- **已排除项**：新 `source_type` 取值；字幕按原文件字节做 hash；导出未 DONE 时返回 500/409；字幕解析放 controller 或 worker 异步解析（无法 fail-fast）；本轮扩 `vtt/txt/批量导出/PDF`（留 T3.10/T4.x）。

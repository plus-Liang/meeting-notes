## 1. 为什么做这件事（Why）

### 1.1 真实痛点（不是编的）

本人有几十个本地 `mp3 / mp4`（网课录播、线上会议、播客、直播回放），需要整理成「纪要 + 待办」。
当前做法：本机跑 ASR → 人工读全文 → 手写纪要。单文件约 **40 分钟**。

### 1.2 为什么不用现成产品

飞书妙记、通义听悟、讯飞听见功能更强、更稳、更方便。**定位不是替代它们**，它们在本场景下结构上不合适：

1. 交互为「**一次会议**」设计，不是为「**我有一堆本地文件**」设计（批量、目录监控、断点续跑都没有）；
2. 部分内容**不适合上传第三方云**；
3. 输出格式、模板、待办去向不能按需改（接不进自己的笔记/issue 体系）。

### 1.3 目标用户（v3：3 类 → **11 类**；P1 仍只保留前 3 类 + K）

> 扩充依据与证据强度见 `目标用户与输入来源-调研.md`。**新增的 4 类属"零成本覆盖"**：
> 同一条管线，只换输出模板；不新增管线。

| # | 类型 | 真实约束 | 要的产物 | 优先级 |
|---|---|---|---|---|
| **A** | 本地文件囤积者（播客听众、考证党、记者、律师） | 手里几十上百个文件；要批量、要断点、要自动 | 批量纪要 + 待办 | **P1** |

## 2. 核心闭环

```text
① 采集   上传 / 直链 / 粘贴字幕 / inbox 目录 /（P2）浏览器录制
            ↓
② 转写   VAD 切分 → ASR → 标点 →（P2）说话人
            ↓
③ 结构化 摘要 / 决议 / 待办(结构化 JSON) / 关键词 / 时间轴
            ↓
④ 产出   Markdown 导出 / Webhook 推送 / 只读分享链接
            ↓
⑤ 回访   用户修正：改错词、改人名、勾选/删除待办
            ↓
⑥ 沉淀   术语表 / 说话人档案 / 模板偏好
            ↓
      └──→ 反哺 ②③，下一次更准
```

**只剩 ①②③④ 是流水线，不是闭环。⑤⑥ 必须存在（D-014）。**

## 3. 用户故事

### US-1（P1）单文件转出可用纪要
上传一个本地音频 → 异步转写 → 摘要 + 待办 → 可查看可复制。
- **Independent Test**：5 分钟 mp3 → 页面能看到全文、≥3 条摘要、≥1 条待办。
- **场景**：①正常文件→DONE；②损坏文件在接受阶段被拒且给原因；③同一文件重复上传→直接返回已有结果。

### US-2（P1）任务可见、可重试、不丢
一次提交多个文件，各自独立进度；失败可单独重试；服务重启不丢。
- **Independent Test**：提交 3 个 → 中途重启一次 → 3 个都到终态且不重复。
- **场景**：①一个失败不影响其他且可单独重试；②处理中杀进程重启→恢复或明确可重试；③重复请求→只 1 个任务。

### US-3（P1）修正能沉淀，下次更准（闭环回流）
改正错词 → 进术语表 → 后续转写优先正确。
- **Independent Test**：「张总」被识别成「章总」→ 改正 → 第二段含「张总」的音频输出正确。
- **场景**：①改正即入库；②术语被作为识别提示使用；③同一错词改正 ≥3 次自动提升优先级。

### US-4（P2）给链接就能处理
粘贴 http(s) **直链** → 拉取 → 同上传流程。
- **场景**：①合法直链→成功；②内网/元数据地址→拒绝并记录；③视频网站页面地址→提示"仅支持直链"。

### US-5（P2）已有字幕/文本直接进结构化
srt/vtt/txt/粘贴文本 → 跳过转写直接出纪要。
- **场景**：①srt 秒级出纪要；②纯文本正常产出。

### US-6（P2）网页网课就地录制
浏览器录标签页/屏幕音频 → 录完自动成为任务。
- **场景**：①桌面 Chrome/Edge 录 1 分钟成功；②手机/微信内置浏览器→明确提示不支持；③超时上限→自动分段并保留已完成部分。

### US-7（P3）结果能带走
导出 Markdown；生成只读分享链接。

### US-8（P1）批量与自动收取（A 类主场景）
一次提交多个文件，或把文件丢进 inbox 目录；列表可筛选、可批量重试。
- **Independent Test**：往 inbox 放 10 个文件 → 30 秒内全部建成任务 → 全部到达终态。
- **场景**：①inbox 10 个音频→10 个独立任务互不影响；②列表 30 条按"失败"筛选→只显示失败项且可批量重试；③同名不同内容文件→按内容去重而非文件名。

### US-9（P1）完全离线可用（B 类主场景）
断外网、不填任何 key，仍能完成上传→纪要全流程。
- **Independent Test**：断网 + 无 key → 走完 US-1 成功。
- **场景**：①`OFFLINE_MODE=true` 无 key→全流程成功，`ai_tier∈{LOCAL,EXTRACTIVE}`；②离线模式配置了云 LLM→启动时不发起外连并告警；③数据仅在本地卷，无第三方上传。

### US-10（P1）别人能接进自己系统（C 类主场景）
提供 REST API、Webhook、OpenAPI、导出。
- **Independent Test**：不开浏览器，三条 curl 走完"提交→查状态→取结果"；一个 20 行接收端收到 Webhook 并验签通过。
- **场景**：①有效 Token 上传→返回 task_id 与 PENDING；②带 `callback_url`→完成时 POST 事件且带 HMAC 签名，接收端验签通过；③接收端首次返回 500→按退避重投，成功后停止；④`/v3/api-docs` 返回合法 JSON；⑤错误 Token→401 `UNAUTHORIZED`。

### US-11（P1）数据可备份、可恢复、重启不丢
- **Why this priority**：本项目卖点是"数据不出门"，丢数据就等于毁掉全部信任；工作流也明确要求"数据本地保存与备份"。
- **Independent Test**：执行备份 → 删除数据卷 → 执行恢复 → 全部任务与结果可查且内容 hash 一致。
- **场景**：
  1. **Given** 系统有 10 个已完成任务，**When** 执行一次备份，**Then** `backups/<时间戳>/` 内包含数据库转储、对象存储镜像与清单（含 md5），可逐项核对。
  2. **Given** 已设每日自动备份，**When** 经过一天，**Then** 自动生成一份备份且保留最近 7 份。
  3. **Given** 数据卷被删除，**When** 执行恢复，**Then** 任务、结果、术语表全部回来，且结果内容 hash 与备份清单一致。
  4. **Given** 正常运行的实例，**When** `docker compose down`（不删卷）后 `up`，**Then** 数据仍在（N20）。

### US-12（P1.5）多种摘要模板（覆盖 D/E/F/G/K 五类场景，5 个模板）

同一份转写结果，按「会议 / 课程 / 访谈 / 播客」四种模板产出不同结构；提交时可选，也可由系统推荐。

- **Why this priority**：这是"用一份管线覆盖四个场景"的唯一机制。没有它，扩展到学生/播客/访谈就得上新管线。
- **Independent Test**：同一段 5 分钟音频用「会议」与「课程」两个模板各跑一次 → 两者摘要结构不同，且都符合各自模板定义。
- **验收场景**
  1. **Given** 提交时选择"课程"，**When** 处理完成，**Then** 输出含「知识点 / 考点 / 复习顺序」而不只是通用摘要。
  2. **Given** 未选择模板，**When** 提交一个文件名含"腾讯会议"的录制文件，**Then** 自动推荐并采用"会议"模板。
  3. **Given** 改变了模板，**When** 查看结果，**Then** 能看到本次用的是哪个模板（可追溯）。
  4. **Given** 模板不存在或拼错，**When** 提交，**Then** 明确报错并回落到默认模板（不静默失败）。
  5. **Given** 提交时选"短视频"，**When** 处理完成，**Then** 输出为「核心观点 / 论据 / 可执行动作 / 是否值得收藏」四段（K 类用户：刷到有用视频想留存）。

## 4. 输入契约（8 个入口，P1 只有 4 个）

> 扩充依据见 `目标用户与输入来源-调研.md` §3。**P1 只新增 2 个零成本子类**（格式扩展 + 录制文件识别），
> 其余入口进 P2/P3 backlog（D-025）。

| # | 入口 | 覆盖 | 优先级 | 处理约定 |
|---|---|---|---|---|
| 1 | **UPLOAD** | 本地音视频文件（格式见下）+ **会议软件导出录制文件** | **P1** | 只保留音轨；按文件名/容器自动推荐模板 |
| 2 | **FETCH / LINK** | http(s) 音视频**直链**；**平台页面链接**（L1 元信息确认 → L2 直链探测 → 失败则提示导出上传） | **P1**（直链）/ **P2**（页面链接） | 下载后同 UPLOAD；必须 SSRF 防护；**不内置平台解析器**（D-027R） |
| 3 | **PASTE** | 文本 / `srt` / `vtt` / **`ass`** | **P1** | 跳过转写；注意 UTF-8 / GBK 编码识别 |
| 4 | **RECORD** | 浏览器标签页/屏幕音频 | P2 | 分片上传；仅桌面 Chrome/Edge |
| 5 | **INBOX** | 宿主目录轮询（放文件即处理） | P2 | 增量识别 + 按内容去重 |
| 6 | **RSS** | 播客订阅 feed（`enclosure` 直链） | P2 | 只取最近 N 集，按 URL+时间戳去重 |
| 7 | **MCP** | AI agent 直接调用工具 | P3 | 协议版本演进风险 |
| 8 | **OCR 补充** | PPT 截图 / 板书照片，与转写**合并**成完整讲义 | P3 | 需图文对齐 |

### 格式支持（显式承诺，不靠"应该能解"）

- **音频（8）**：`mp3` `wav` `m4a` `aac` `flac` `ogg` `opus` `amr`
- **视频（6）**：`mp4` `mov` `mkv` `avi` `flv` `webm`
- **文本（4）**：`txt` `srt` `vtt` `ass`

`amr`（微信/老手机录音、录音笔导出）与 `opus`（微信/浏览器录制）**必须支持**。
超出清单：接受上传但明确提示"可能失败"，失败时给"请转成 mp3"的建议，不静默卡住。

**统一约束**：单任务 **≤60 分钟**（可配至 120）、≤200MB，超出在接受阶段拒绝。

> **依据（实测，2026-11-13）**：真实库 11 个内容里 **5 个超过 30 分钟（45%）**，最长 56.7 分钟。
> 原 30 分钟上限会拒掉近一半真实文件 → 已改为 60 分钟（D-028）。见 `真实数据-文件与耗时实测.md`。

### US-13（P2）粘贴视频链接：先确认，再决定怎么拿文件

用户粘贴任意视频平台**页面链接** → 系统展示"是这个视频吗？"（标题 + 封面 + 公开时长）→
确认后：若链接最终指向媒体文件则直接开跑；否则提示"导出后上传"（手机浏览器上传）。

- **Why this priority**：这是用户真实流程的第 1 步（视频链接 → 小程序导出），也补齐了"我记不清是哪个视频"的问题。
- **Independent Test**：贴 3 个不同平台链接 → 都能返回标题与封面卡片；其中至少 1 个能直接建任务；失败的那两个给出"请导出上传"指引。
- **验收场景**
  1. **Given** 一个平台页面链接，**When** 提交，**Then** 返回确认卡片（标题/封面/时长），**不伪造签名、不携带用户 cookie**。
  2. **Given** 一个最终指向媒体文件的分享链接，**When** 用户确认，**Then** 直接创建任务并进入转写。
  3. **Given** 一个需要登录/加密的平台链接，**When** 用户确认，**Then** 明确提示"请导出后用手机浏览器上传"，并给出 3 步指引。
  4. **Given** 链接指向内网或云元数据地址，**When** 预览，**Then** 被拒绝并记录安全事件（与 N7 同一套防护）。
  5. **Given** 用户自行配置了 `FETCHER_CMD`（BYOF），**When** 提交链接，**Then** 系统调用该外部命令取文件；**未配置时该路径明确不可用**。
- **明确不做**：内置任何平台的解析器（L3），理由见 `链接处理方案.md` §3 与 D-027R。

## 5. 页面结构与交互设计（**不写技术栈，只定结构与交互**）

### 5.1 页面清单（4 个）

| 页面 | 路由 | 职责 |
|---|---|---|
| **P1 提交页** | `/submit` | 三类入口 + 提交 |
| **P2 任务列表** | `/tasks` | 全部任务的状态、筛选、批量操作 |
| **P3 结果详情** | `/tasks/{id}` | 全文 / 摘要 / 待办 / 改词 / 导出 |
| **P4 设置页** | `/settings` | 术语表、配额用量、当前 AI 档位、备份入口 |

### 5.2 P1 提交页

```text
┌──────────────────────────────────────────────┐
│ [上传文件] [给链接] [粘贴文本]   ← 三个 Tab    │
├──────────────────────────────────────────────┤
│  拖拽区 / 选择文件（支持多选）                  │
│  ┌ 文件1  ok   03:21  8.2MB  ✓通过校验       │
│  └ 文件2  错误  超大（>200MB）  ✗ 不会被提交   │
│                                              │
│  高级：callback_url（可选，供接入方用）         │
│                              [ 提交 (2 个) ]  │
└──────────────────────────────────────────────┘
```

交互约定：
- 选中文件后**立即在前端做一次校验**（格式/大小），错误项标红且不计入提交数（避免提交后才失败）；
- 提交成功 → 顶部 toast 显示 task_id → **2 秒后自动跳转任务列表**；
- 一次最多 **20** 个文件（实测日常量是 11 个内容 / 8.44 小时，10 个不够用）；提交后显示**总时长与预计耗时**
  （按实测 RTF 估算，避免用户不知道要等多久）；超限提示分批；
- 空态：显示"把文件丢进 inbox 目录，或直接拖到这里"。

### 5.3 P2 任务列表

```text
┌──────────────────────────────────────────────────────────┐
│ 筛选：[全部▾] [来源▾] [日期▾]        [批量重试] [全部导出] │
├──┬──────────┬────────┬────────┬──────────┬───────────────┤
│☐ │ 文件名     │ 时长   │ 状态    │ AI 档位   │ 创建时间       │
├──┼──────────┼────────┼────────┼──────────┼───────────────┤
│☐ │ 会议.mp3  │ 12:30  │ RUNNING│ -        │ 11-13 14:02   │
│☐ │ 网课1.mp4 │ 45:10  │ DONE   │ CLOUD    │ 11-13 13:40   │
│☐ │ 播客2.mp3 │ 08:02  │ DEAD   │ -        │ 11-13 12:10   │
└──┴──────────┴────────┴────────┴──────────┴───────────────┘
```

交互约定：
- 状态用**颜色徽章**：PENDING 灰 / RUNNING 蓝（带进度）/ DONE 绿 / RETRYING 橙 / DEAD 红；
- **状态刷新用 3 秒轮询**（不用 WebSocket/SSE：单机自托管，轮询足够且实现成本低一倍）；
- DEAD 行右侧出现「重试」与「查看原因」；原因显示错误码 + 可读中文；
- 行可勾选 → 底部出现批量条：批量重试 / 批量导出 / 批量删除；
- 空态："还没有任务，去提交第一个"；加载态骨架屏；请求失败显示"重试"按钮（不自动重试，避免风暴）。

### 5.4 P3 结果详情

```text
┌────────────── 标题：会议.mp3   [DONE] [ai_tier: CLOUD] ──────────────┐
│ ┌─────────── 左：全文（可滚动）───┐ ┌──── 右：结构化 ───────────────┐ │
│ │ 00:00 大家好…                  │ │ 【摘要】                       │ │
│ │ 00:35 第一个议题…               │ │ - 讨论了…                      │ │
│ │ （选中任意词 → 弹出"改正"）      │ │ 【待办】                       │ │
│ │                                │ │ ☐ 整理第三章笔记  owner:我     │ │
│ │                                │ │   截止 11-20                   │ │
│ │                                │ │ ☑ 已完成的会自动置灰            │ │
│ │                                │ │ 【关键词】线性代数 / 矩阵       │ │
│ └────────────────────────────────┘ └───────────────────────────────┘ │
│  [导出 Markdown] [复制] [生成只读链接] [重跑]                          │
└──────────────────────────────────────────────────────────────────────┘
```

交互约定：
- **改词**：鼠标选中一段文字 → 浮出「改正」按钮 → 输入正确写法 → 保存；成功后该词高亮，并提示"已加入术语表，下次生效"（这就是闭环 ⑤→⑥ 的界面呈现）；
- **待办**：可勾选完成、可删除；勾选/删除都会写库（不是前端假状态）；
- `ai_tier` 必须显示：CLOUD 绿 / LOCAL 蓝 / EXTRACTIVE 黄，悬停提示"当前使用哪一档 AI，质量不同"（D-020 诚实标注的界面落地）；
- 「重跑」= 用当前术语表重跑一次（用来演示回流效果）；
- 全文区域为空或转写失败时，显示错误码与建议动作，不留白屏。

### 5.5 P4 设置页

- **术语表**：列表（错误写法 → 正确写法 / 命中次数 / 优先级），可增删；
- **配额**：今日已用分钟数 / 剩余；
- **AI 档位**：当前生效档位 + 为什么是这一档（有 key / 有 Ollama / 兜底）；
- **备份**：立即备份按钮 + 最近 7 份备份列表 + 恢复指引（恢复不做成网页按钮，避免误操作，文档给命令）。

### 5.6 全局交互底线

| 约定 | 理由 |
|---|---|
| 任何异步操作必须有 loading 态 | 否则用户以为没反应会连点，制造重复任务 |
| 错误一律显示「可读中文 + 错误码」 | 用户能搜、能报、能贴给 AI 排 |
| **上传页必须在手机浏览器可用**（选文件/相册并上传）——P1，D-029 | 省掉"微信文件传输助手"传电脑那一步；但**不做 App、不做专门移动端适配** |
| 不引入前端框架 | 同上；纯静态 + 原生 JS |
| 页面不允许出现硬编码 API 地址 | 走同一域名相对路径（N11） |

## 7. 非功能要求（N1–N20，每条可判定）

| # | 要求 | 判定方式 |
|---|---|---|
| N1 | 幂等 | 同一文件重复提交 → 只 1 任务 1 结果 |
| N2 | 重试 + 死信 | 失败自动重试；超限进死信，可查、可手动重投 |
| N3 | 崩溃可恢复 | 处理中重启 → 不永久卡在处理中 |
| N4 | 全链路可追 | 单任务日志可用 taskId 一条命令串起来 |
| N5 | 健康检查 | 一端点覆盖 DB/缓存/对象存储/ASR |
| N6 | 上传校验按文件头 | 可执行文件改名 `.mp3` → 被拒 |
| N7 | 直链 SSRF 防护 | 内网/本机/云元数据地址 → 被拒 |
| N8 | 配额与限流 | 超限 → 429 + `Retry-After`，不静默失败 |
| N9 | 并发可控 | ASR 并发可配，打满时排队不拖死机器 |
| N10 | 结果复用 | 同内容再次提交 → 命中缓存秒出 |
| N11 | **配置全外置，一个不落** | 路径/端口/key/并发数/模型名全部有 env 入口；`配置清单.md` §2 三条命令无异常 |
| N12 | 一键启动 | 干净机器 `docker compose up` 一次成功 |
| N13 | 结构可迁移 | 建表走迁移脚本 |
| N14 | 端到端可测 | 一条自动化测试：提交→等完成→断言摘要非空 |
| N15 | **零成本可跑（三档降级）** | 不填付费 key，P1 故事全部走通；见 §7.1 |
| N16 | **离线可运行** | 断外网 + 无 key → US-1/US-9 成功；离线无出站连接 |
| N17 | **对外可接入** | 三条 curl 全流程；20 行接收端验签通过；`/v3/api-docs` 合法 |
| N18 | **备份可执行可核对** | 一条命令产出备份目录，含 db 转储 + 对象镜像 + md5 清单；每日自动；保留 7 份 |
| N19 | **恢复后数据一致** | 删卷 → 恢复 → 任务/结果/术语表全在，结果 hash 与清单一致 |
| N20 | **重启不丢** | `down`（不删卷）→ `up` → 数据仍在 |

### 7.1 「零成本可跑」是什么意思（重要澄清）

**"接入 AI" ≠ "必须买 API key"。**

| 环节 | 是否需要 key |
|---|---|
| ASR（转写） | **不需要**：模型跑在自己容器里（FunASR/whisper.cpp），本地推理、免费、断网可用 |
| 摘要/待办 | 可以有也可以没有：三档降级 |

| 档 | 实现 | 成本 | 质量 | 前置 |
|---|---|---|---|---|
| ① CLOUD | OpenAI 兼容端点（智谱/DeepSeek/Kimi/通义） | 按量付费 | 最好 | 填 key |
| ② LOCAL | Ollama 跑小模型 | 免费 | 中（受内存限制） | 8GB+ 内存（可选） |
| ③ EXTRACTIVE | 中文分句 + 关键句打分 + 规则待办（时间词/责任词/人称）+ 模板摘要 | 免费 | 一般 | **无** |

选择逻辑：①有 key → ②启用且可用 → ③兜底。**三档输出字段结构完全相同**，结果记 `ai_tier`。

**诚实标注**：③ 不是"AI 摘要"，是"关键句提取 + 规则抽取"，质量明显更低；README 必须写清三档差异，不许把 ③ 当 ① 宣传。

## 10. 模块清单与模块关系

### 10.1 模块清单（12 个）

| 模块 | 职责（一句话） | 主要对外接口 |
|---|---|---|
| `intake` | 接收三类入口与 inbox 的文件/URL/文本，做校验与配额 | 由 web/api 调用 |
| `storage` | 对象存储读写（原始文件、产物） | 被 intake / export 调用 |
| `task` | 任务表、状态机、队列分发、幂等、重试、死信 | 由 web/api/worker 调用 |
| `transcription` | 抽音轨（容器内）+ 分段 + 调 ASR 适配器 | 由 worker 调用 |
| `structuring` | 摘要/待办/关键词；三档 AI 选择与降级 | 由 worker 调用 |
| `glossary` | 术语表读写、命中提升、注入转写提示（回流） | 由 structuring / web 调用 |
| `export` | Markdown / JSON 产物渲染 | 由 web/api 调用 |
| `webhook` | 终态事件投递、签名、重试、投递记录 | 由 task 事件触发 |
| `inbox` | 目录轮询、增量识别、去重 | 调用 intake |
| `authquota` | API Token 鉴权、每日配额 | 被所有入口模块调用 |
| `observe` | 结构化日志（taskId）、健康检查、指标 | 横切 |
| `ui` | 4 个页面（静态） | 调用 web REST |

### 10.2 模块关系（单向依赖，禁止循环）

```text
                    ┌──────── ui ────────┐
                    │                    │
  浏览器 ──► web/api ──► intake ──► task ──► worker ──► transcription ──► storage
                    │        │        │                    │
                    │        │        └──► webhook        └──► structuring ──► glossary
                    │        └──► storage                        │
                    └──► export ◄── task_result                 └──► storage
   inbox ─────────────────────────────► intake
   authquota（横切，被 intake/web/api 调用）    observe（横切）
```

**依赖规则（review 时检查）**：
1. 依赖必须单向：`ui → web/api → intake/task → worker → transcription/structuring → storage`；
2. `transcription` **不得**依赖 `structuring`；`structuring` **不得**依赖 `web`；
3. `glossary` 被 `structuring` 读取（回流注入），但 `structuring` 不写它（写入只由用户动作触发）；
4. 任何"为了图方便"的反向调用，都要在 review 时被拒。

## 11. 数据保存、备份与恢复

> 工作流明确要求"数据本地保存与备份"；本项目面向"数据不能出门"的用户，这条是信任基础（US-11）。

### 11.1 数据存在哪（全部本地）

| 数据 | 位置 | 丢了会怎样 |
|---|---|---|
| 任务与结果、术语表、配额、死信、投递记录 | PostgreSQL（Docker 卷） | **全丢**，不可接受 |
| 原始音频/视频 | MinIO（Docker 卷） | 无法重跑，但结果还在 |
| 队列与缓存 | Redis（可丢） | 不影响正确性：以任务表为准重新分发 |
| 配置 | `.env`（不备份，含密钥） | 用 `.env.example` 重建 |

### 11.2 备份

- **命令**：`backup.ps1` → 产出 `./backups/<YYYYMMDD-HHmm>/`，内含
  `pg.dump`（数据库转储）+ `objects/`（对象存储镜像）+ `MANIFEST.md`（文件数、大小、各项 md5）；
- **自动**：每天一次；**保留最近 7 份**（超出自动清理最旧的）；
- **不备份密钥**：`.env` 不进备份目录（避免备份被误分享导致 key 泄露）；备份目录里放 `.env.example` 副本。

### 11.3 恢复

- **命令**：`restore.ps1 -From backups/<时间戳>`，做两件事：重建数据库 + 回灌对象存储；
- **安全阀**：恢复前必须显式加 `-Force`，且会先把现有数据卷改名留存（不直接覆盖）；
- **验收**：恢复后任务数、结果数与原一致；抽样比对结果内容的 hash 与 `MANIFEST.md` 一致。

### 11.4 重启不丢

`docker compose down`（**不删卷**）→ `up` → 数据仍在。这是最低要求，必须每周都验证一次（T4.8）。

### 11.5 导出（给用户自己带走数据）

- 单任务：Markdown / JSON
- 全量：`/api/v1/export` 导出 JSON（任务 + 结果 + 术语表），不含原始媒体文件
- **明确不做**：跨机器同步、云备份、备份加密（P2 再议）

## 12. 术语

| 术语 | 含义 |
|---|---|
| 任务 | 一次「输入 → 纪要」的完整处理单元 |
| 回流 | 用户修正被沉淀并在后续任务生效的机制 |
| 死信 | 重试耗尽后待人工处理的状态 |
| ai_tier | 本次结果由哪一档 AI 产出（CLOUD/LOCAL/EXTRACTIVE） |
| 直链 | 直接返回文件字节的 http(s) 地址，无页面跳转与鉴权 |
| RTF | 处理耗时 ÷ 音频时长 |

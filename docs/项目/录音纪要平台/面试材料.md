## 0. 一页速查（面试前 5 分钟只看这页）

- **一句话**：自托管的「录音/网课 → 结构化纪要 + 待办」工具，解决"手上有大量本地音视频、要批量、不能上第三方云"这个场景。

- **三个不吹**：不比商业产品便宜、不比它功能多、不比它安全；边界写在 README 的「你不该用本项目的场景」。

## 2. 三分钟讲法（背下来，按这个顺序说）

**① 一句话（20 秒）**
> 我做了个自托管的录音转纪要工具。定位不是替代飞书妙记，而是解决另一类场景：
> 手里有大量本地录音文件、要批量处理、且部分内容不适合上传第三方云。

**② 为什么做（30 秒——必须说真实动机）**
> 我自己有几十个网课和会议的 mp4/mp3 堆着，整理一个要 40 分钟：先跑 ASR，再人工读全文写纪要。
> 我扫了自己磁盘：**20 个文件、8.44 小时、0.90 GB**，其中 **45% 超过 30 分钟**，还有 9 组 mp4/mp3 是同一内容——
> 说明我为了手工转换重复存了 522 MB。这就是我做它的原因，不是我"觉得"需要。

**③ 架构怎么来的（40 秒——这段最容易被追问，务必诚实）**
> 先说结论：**没有能直接抄的 Java 全栈同类项目**，我搜过，相关仓库最高 9 星还是 demo。
> 所以我的架构是组装出来的，每一层都有出处：转写层用 faster-whisper 的 OpenAI 兼容服务；
> Java 侧全部走 Spring AI 官方 API；产品功能分层参考了开源本地会议助手。
> **我做的是编排和业务：任务状态机、幂等重试、降级、配额、结构化抽取。**

**④ 最难的地方（40 秒）**
> 长任务系统。转写一个 56.7 分钟的音频要好几分钟，中间可能失败、可能重启。
> 所以我把任务状态落 PG 做成状态机，Redis 只做分发；幂等靠 content_hash 唯一约束，
> 加指数退避、死信可重投、启动时回收僵尸任务。**实测停掉 ASR 容器，任务 9 秒内走完
> `RUNNING → RETRYING×2 → DEAD`，不会卡在 RUNNING 永远不动**——这块最像生产代码。

**⑤ 闭环（30 秒——差异化）**
> 大多数同类项目是"转完给你段文字"就结束了，那是流水线。
> 我加了回流：用户改错词之后进术语表，下次转写就带上；说话人标成"老板"会记成档案。
> 这才叫闭环——系统会因为你用得越多而变准。

**⑥ 边界（20 秒——这段极加分）**
> 我知道自己的边界：稳定性肯定不如商业产品，功能也少得多。
> 所以 README 里我专门写了一节「你不该用这个项目的场景」——只要你偶尔转一次会议、要实时字幕，
> 就直接用飞书妙记，别用我的。

## 3. 三个 STAR 故事（每个 60 秒口述版 + 证据）

### 故事 A：长任务"不丢、不卡、不重复"（可靠性）

- **S 情境**：真实场景是批量处理 8.44 小时录音，最长单文件 56.7 分钟。转写要几分钟，期间可能进程重启、ASR 容器挂掉。
- **T 任务**：不能出现三种事故——任务卡在 RUNNING 永不结束、重复上传重复转写/重复计费、失败后无法恢复。
- **A 行动**：①状态机落 PostgreSQL（PENDING/RUNNING/RETRYING/DEAD/DONE），Redis 只做分发；②幂等键 `(user_id, content_hash)` 唯一约束，重复上传直接 `reused:true`；③指数退避重试 + 死信表（可重投）；④启动时回收 RUNNING 僵尸任务；⑤db/redis/minio/asr 四项依赖进 readiness，避免"进程活着但不可用"；⑥结构化日志 taskId 贯穿全链路便于定位。
- **R 结果**：停 ASR 实测 **9 秒**走完 `RUNNING → RETRYING×2 → DEAD`，`error_code=ASR_ERROR` 且死信有原因；重启后僵尸任务被回收；重复上传返回同一 task 且**配额不增加**；这些场景都有单元测试/端到端测试覆盖（自动化测试合计 511 个）。
- **口述版**：「我给任务加了一把唯一锁（content_hash）和一个可恢复的状态机。所以同一文件传十次也只转一次，ASR 挂了任务会退避重试、进死信，重启后能接着跑——不是靠"应该不会挂"，是这几种故障我都实测过。」

### 故事 B：三档 AI 降级——把"能不能用"做成硬指标（成本与可用性）

- **S 情境**：开源项目要让陌生人跑起来，不能要求对方先充钱拿 API key；但没 key 时如果只能输出原始转写，产品价值就没了。
- **T 任务**：云不可用 / 没 key / 没本地模型 三种情况下，都要产出"可用"的纪要。
- **A 行动**：做 `CLOUD → LOCAL(Ollama) → EXTRACTIVE` 三档路由：云档用结构化提示词；本地档走 localhost Ollama；抽取式兜底用规则抽取摘要与待办，保证零依赖也有结果；`ai_tier` 字段如实记录实际用了哪档（不伪装成云）；固定 temperature、严格 JSON 校验、解析失败降级而不是 500。
- **R 结果**：库里真实数据 **CLOUD 148 个 / EXTRACTIVE 30 个**任务（早期数据未记录档位）；陌生人干净克隆、无任何 key 的首个任务产出 **198 字摘要 + 3 条待办**（T4.9 独立复现）；三档与超时各有独立验收报告（T4.4 / T4.5 / T3.8）。
- **口述版**：「我把它做成三档降级：有 key 用云模型，没有就用本地 Ollama，再没有就用抽取式规则兜底，并且把实际用哪档如实写进字段。这样别人 clone 下来不用先充钱就能跑通全流程——这是开源项目能不能被用的生死线。」

### 故事 C：用 AI 写大部分代码，怎么保证质量（工程治理）

- **S 情境**：这个项目我一个人做，代码大部分由 AI 生成。风险很直接：AI 说"已完成"，但可能只是自己测了自己。
- **T 任务**：让"完成"这个结论**可独立复核**，不依赖写码方的自述。
- **A 行动**：①固定分工——写码方只写产品代码，验收方（另一个上下文）独立验收，**验收人自己写探针，不复用写码方的脚本**；②门禁矩阵：单元测试 + 全量测试两遍 + 可维护性检查（圈复杂度/文件长度）+ 前后端资源 sha256 一致 + Playwright 真实点击 + 现场基线核对；③每个坑写一条复盘（K-01…K-95），同一个坑在同一位置出现两次就写进规则；④每个决策记六字段（结论/依据/已排除项/决策人），我保留了 167 条。
- **R 结果**：**71 份验收报告**（每份含命令、退出码、报告路径），**511 个自动化测试**全绿，发布前还用"干净克隆 + 陌生人视角"完整跑了一遍一键启动。这套流程让我抓到过写码方自测发现不了的问题（例如多标签筛选把"且"实现成"或"、重命名按钮在小屏被压成竖排）。
- **口述版**：「我用 AI 写代码，但不让 AI 当验收人。写码的和验收的是两个独立上下文，验收的人自己写测试脚本，每个任务都出带命令和退出码的报告。所以我能说"511 个测试全绿"不是听来的，是我自己跑出来的。」

| # | 追问 | 答法要点 |
|---|---|---|
| 1 | **为什么不用飞书妙记？** | 三句：①大部分场景应该用它，我也推荐；②但它为"一次会议"设计，我有几十个本地文件要批量、要断点、要接自己系统；③部分内容不适合上传第三方云。定位是取舍不同，不是替代。 |
| 2 | **为什么不找个开源项目改？** | 明确说：没有可用的 Java 全栈同类（检索数据：`meeting minutes transcription java` 0 个仓库，spring boot 相关最高 9 星）。同类是 Python/Rust/桌面的。我用权威组件组装，不 fork 冒充自研。 |
| 3 | **RTF 怎么测的？为什么不是固定值？** | 转写耗时 ÷ 音频时长。同一台机器实测：90 秒音频 **0.105**、783.8 秒 **0.113**、3401 秒 **0.106**，T4.16 对比实验里 small 档 **0.160** / medium **0.381**。差异来自语音密度、模型档位和是否并发——所以我对外只说区间 0.10–0.16，并注明测试条件，不说"0.1 秒转 1 秒"这种绝对话。 |
| 4 | **为什么单任务上限 60 分钟？** | 不是技术限制，是我扫真实语料后改的产品约束：20 个文件里 **45% 超过 30 分钟**（最长 56.7 分钟），原设 30 分钟会让近一半真实文件被拒。这条改动记录在决策 D-028。 |
| 5 | **用了 AI 写代码，质量怎么保证？** | 讲故事 C：写码/验收分离、验收方自写探针、门禁矩阵、71 份报告、K-95 复盘。**不要说"AI 写的都很可靠"。** |
| 6 | **怎么保证任务不丢？** | 幂等键 content_hash 唯一约束 + PG 状态机 + 重试退避 + 死信 + 启动回收 RUNNING 僵尸任务 + 四项依赖 readiness；每一项有对应测试和实测（停 ASR 9 秒进死信）。 |
| 7 | **换成别的模型麻烦吗？** | 不麻烦：全部走 OpenAI 兼容协议，改 base-url + model + key 三个环境变量；已支持智谱/DeepSeek/Kimi/通义/本地 Ollama，云端与本地共五个提供方。 |
| 8 | **安全怎么考虑？** | 上传按 magic number 校验；直链 SSRF 防护（拒私网与云元数据地址）；密钥全走 env 不入库不入镜像；分享用 token hash；Webhook 用 HMAC-SHA256 验签 + delivery_id 去重；音频播放用短时签名 URL（URL 里不出现 API_TOKEN）。 |
| 9 | **这个项目有什么不足？** | 主动说三条：①单机部署，没有高可用与多副本；②ASR 质量受模型限制，专业术语靠术语回流补；③没有多租户、细粒度权限、审计与限流——这些我知道差哪几项、优先级怎么排，但 4 周时间盒里我选择不做（写进 README 的生产化路线图）。 |
| 10 | **有真实用户吗？** | 诚实答：第一个用户是我自己（处理 299 个任务 / 4.95 小时音频 / 10.4 万字转写，含测试任务）；外部真实用户验证正在做。**不编数字**——面试官问"多少个"就直说"目前是自用 + 少量验证，还在推进"。 |

## 8. 绝对不能说出口的四句话

| ❌ | 为什么 |
|---|---|
| "我的比他更便宜" | 免费额度内商业产品也免费，你还得自己搭服务器 |
| "我的功能更多" | 假的，一戳就破 |
| "我的更安全" | 自己维护的安全性通常更差（没做渗透、没持续打补丁） |
| "主要是为了学习" | 在面试里等于承认项目没有真实价值 |

> ⚠️ **空 secret + 遗留到期行会"空烧"重试（F-22，T4.8 已实测复现）**：`WEBHOOK_SECRET` 为空时**新终态任务不会入队**（安全默认成立），
> 但 `webhook_delivery` 里**已存在**的到期行（手工插入，或"先配了 secret、后来又清空"留下的历史行）仍会被 `@Scheduled` 捡起：
> 投递时用空密钥签名抛异常 → 按 1s/10s/60s **空烧 4 次后终局**（`attempts=4`、`last_status=0`、`next_retry=NULL`），
> 日志文案 `Webhook 投递异常：…（HMAC-SHA256 不可用）` 是**误导**（真因是 secret 空，不是算法不可用）。
> 影响：不扣配额、不影响任务，只污染 `webhook_delivery` 并误导排障。**v1 记已知限制**；修复（扫描/投递入口空 secret 短路 + 明确文案 + 单测）并入 **T4.12**。
> 自建者若要清空 secret：先 `UPDATE webhook_delivery SET next_retry = NULL WHERE next_retry IS NOT NULL;` 再改配置。

> ⚠️ **F-23（T4.8 验收后实测发现，已先做运维修正）**：`TZ` 环境变量只对**initdb 之后新建的数据卷**生效；本机数据卷是更早创建的，`postgresql.conf` 里写死了 `timezone = UTC`，
> 所以容器 `date` 显示 CST（libc 时区生效）但 **PG 的 `CURRENT_DATE` 仍按 UTC** → 配额实际在**早上 08:00（北京时间）**重置，且 00:00–08:00 窗口里 `Retry-After`（JVM 本地日）与计费日不一致。
> **判据不能看容器 `date`**，要看：
> ```sql
> SHOW timezone;                                                    -- 期望 Asia/Shanghai
> SELECT current_date = (now() AT TIME ZONE 'Asia/Shanghai')::date; -- 期望 t
> ```
> 已有实例修正：`ALTER DATABASE meetingnotes SET timezone TO 'Asia/Shanghai';`（库级持久，然后重启 app 让连接池重连；时间戳列是 `timestamptz`，不错乱历史）。
> 新装/新卷：compose 的 `TZ=Asia/Shanghai` 在 initdb 时即生效，无需手改。**T4.12 已加启动预检（WARN，D-098）**：DB `SHOW timezone` 与 `TZ` 不一致时启动打 WARN 并给修法（不挡启动，见 §3 末）。

# 视频链接处理方案（回答「为什么不能直接粘链接」）

> 你的问题：**「为什么不可以直接粘贴视频链接，让用户确认是不是这个视频，把小程序导出功能也加进来，无论哪个平台只要链接都行？」**
> 结论先说：**能做的有 2 件（建议做），不该做的有 1 件（内置全平台抓取）**。
> 本文给出三级方案、成本、法律边界与我的建议。

---

## 1. 你的想法里哪个部分是对的（而且很关键）

你说"**让用户确认是不是这个视频**"——这是整个方案里最有价值的一步，因为它把"抓取"变成"**先确认、再决定怎么拿文件**"。
这个模式可以完全合规地实现：只读页面**公开元信息**（标题、封面、时长），不伪造签名、不带登录态、不破解加密。

---

## 2. 三级方案（阶梯式）

| 级别 | 做什么 | 能做到什么 | 成本 | 合规 | 建议 |
|---|---|---|---|---|---|
| **L1 元信息确认** | 粘链接 → 抓 `og:title` / `og:image` / 公开时长 → 显示"是这个视频吗？"卡片 | **省掉"我记不清这是哪个视频"**；但文件仍需你导出 | 0.5 天 | ✅ 合法（读公开 meta） | **做**（P2） |
| **L2 直链探测** | 拿链接发普通 GET，跟随公开重定向，看最终 `Content-Type` 是不是 `audio/*` `video/*` | **部分平台能直接吃**（分享链接最终指向媒体文件的平台）；其余优雅降级到 L1 | 1 天 | ✅ 不做逆向、不伪造签名 | **做**（P2） |
| **L3 内置全平台抓取** | 为抖音/小红书/B站/视频号/快手各写解析器，处理签名、cookie、设备指纹、风控 | 真正"粘链接就出文件" | **10 天起，且永久维护** | ⚠️ 灰色到红色 | **不做** |

### L2 的技术细节（为什么它值 1 天）

```
用户粘链接
   ↓
普通 HTTP GET（不伪造 UA 签名、不带你的登录 cookie）
   ↓
响应是 media/*（video/mp4、audio/mpeg…）→ 当 FETCH 直链处理 ✅ 直接进管线
响应是 text/html → 抓 og:title/og:image → 显示确认卡片 → 提示"请导出后上传"
```

**零平台适配器、零维护**：平台改版只影响"能不能直接吃"，不影响正确性——失败就降级，不会坏。

---

## 3. 为什么不建议做 L3（三条，都不是"懒"）

### ① 你把目标改成了"给别人用"，这件事性质就变了

- **个人自用跑个脚本**：风险低（个人学习使用，不传播）。
- **开源项目内置抓取**：你分发的是"绕过平台技术措施的工具"。法律上风险从"个人使用"升级为"**提供规避技术措施的工具**"，
  平台条款上也明确禁止抓取；这类项目在 GitHub 上有被下架、被发函的先例（具体案例请你自行核实，我不替你说满）。
- 更现实的是：**你现在要把项目放到简历和面试里**。面试官一看"内置抖音/小红书下载器"，第一反应会是合规问题，
  而不是"这人后端不错"。

> 一句话：**L3 会让一个"工程能力"项目变成一个"合规风险"项目。**

### ② 维护黑洞，直接杀死你的时间盒

每个平台的签名都是独立逆向（且几个月一改）。一旦失效：
- 用户报"解析失败"，你**必须 24h 内修**，否则口碑崩；
- 5 周 83h 的项目，光维护这个就要吃掉一半时间；
- 而它对你的**面试价值几乎为零**（面试官不会问你怎么逆向抖音签名）。

### ③ 和你的信任叙事直接冲突

你项目的卖点是"数据不出门 / 自托管"。而 L3 需要**在服务器上存你的平台登录 cookie**——
用户第一反应是"那我为什么不让云服务来做"。为了一个非核心功能，把核心卖点弄脏了，不划算。

---

## 4. 还有一条更"正统"的第四条路：**BYOF（自带抓取器）**

把"抓取"做成**接口**而不是**实现**：

- 仓库里**不含**任何平台抓取代码，只定义 `MediaFetcher` 接口（输入 URL，输出本地文件路径）+ 一份文档；
- 用户如果真想抓，**自己装 `yt-dlp`**，在 `.env` 里配一行 `FETCHER_CMD="yt-dlp -o %(id)s.%(ext)s"`，系统调用本地命令；
- README 明确写："本项目不提供、不内置任何平台抓取能力；抓取行为由用户自行安装的工具完成，合规责任在使用方。"

这是很多自托管项目的常见做法（把争议能力留在项目边界外）。
**成本 0.5 天**，且把责任边界切得干净。要不要做由你定（我建议做，因为它让"想抓的人自己能抓"，而你不用背负它）。

---

## 5. 我的建议

**做 L1 + L2（1.5 天）+ BYOF 接口（0.5 天），不做 L3。**

这样你得到的实际体验：
- 粘链接 → 看到"是这个视频吗？封面+标题+时长" → 确认；
- 运气好（直链平台）→ **直接开始转写**；
- 运气不好（抖音/视频号）→ 卡片告诉你"请导出后上传（3 步）"，但你**不用再打开小程序找这个视频**；
- 时间：**+2 天**，且不引入维护负担、不引入合规定时炸弹。

**我不建议的**：为了"省掉最后 3 步手工"，去换 10 天工期 + 永久维护 + 合规风险。

## 6. 对时间盒的影响（必须说清楚）

| 方案 | 增量 | 基线 | 结果 |
|---|---|---|---|
| 只做 L1 | 0.5 天（4h） | 83h | 87h |
| **L1 + L2 + BYOF（已采纳）** | **2 天（16h）** | **67h** | **83h → 已决定延第 5 周（D-030）** |
| L3 | 10 天+ | — | 不可行 |

> 现实提醒：**已按 83h / 5 周排期（D-030）**，L1+L2+BYOF 的 16h 已计入第 5 周；仍无余量，再加功能必须重新排期。
> 我的建议：把 **`shortvideo` 模板 + 手机上传** 保留（它们直接服务你的真实流程），
> 砍掉 **RECORD 浏览器录制、RSS、只读分享链接、OCR、MCP、指标** 全部（本来就已移出 v1），
> 并把"只读分享链接"从 P3 直接删掉。

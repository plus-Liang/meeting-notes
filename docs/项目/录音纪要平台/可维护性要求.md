# 可维护性要求（M-1 ~ M-10，可判定）

> **为什么有这份文件**：用户 2026-11-13 问"可维护性要求有没有明确写出来，后面开发也要遵循"。
> 当时**答案是没有**——它只零散存在于宪法原则 V（选型要可维护）、`plan.md` 分层、`rules/dev.md` 的"别顺手改"、
> `配置清单.md` 的"配置全外置"里，**没有一处成体系、也没有可判定的判据**。本文把它补成硬要求。
>
> **效力**：本文是 `.specify/memory/constitution.md` 原则 VII 的落地细则，**优先于个人偏好**。
> 违反 M-1、M-2、M-6、M-8 视为**阻塞项**（review 直接拒）；其余为建议项，但连续违反要在 review 里记账。
> **一句话**：可维护性 = 别人（或三个月后的你）能在 30 分钟内安全改一处代码，且改完知道会不会炸别处。

---

## 0. 三条总纲（判断所有细节冲突时用）

1. **可读性 > 聪明**：宁可多一个具名类/具名常量，也不要炫技的一行流。
2. **可预测 > 灵活**：不做没需求的抽象（宪法 IV YAGNI）；但一旦有三处重复，必须收敛。
3. **可验证 > 自信**：每条改动都要能跑出一条命令证明没坏（宪法 III 证据）。

## 1. 十条要求与判据

| ID | 要求 | 判据（谁来判） | 层级 |
|---|---|---|---|
| **M-1** | **配置全外置**：路径/端口/密钥/阈值/模型名不得出现在 Java 代码里 | `配置清单.md` §2 三条命令输出为空 + 自检脚本 M2 = 0 阻塞（机器） | **阻塞** |
| **M-2** | **分层单向依赖**：`web → task/upload/worker → config`；内层不得 import 外层 `web` 的 Controller/Advice | 自检脚本 M5 = 0（机器）。**共享契约（ApiException/DTO）必须放 `common/`**，现存 4 处反向依赖已在 allowlist 登记，T2.x 清零 | **阻塞** |
| **M-3** | **规模可控**：单个 Java 文件 ≤300 行；单方法 ≤60 行；一个类只做一件事 | 文件行数脚本 M3（机器）；方法长度人工/IDE 检查（reviewer） | 建议→阻塞（>400 行） |
| **M-4** | **无魔法值**：阈值/端口/时长/采样率用常量或配置，不散落在业务逻辑里 | 脚本 M4/M4b = 0（机器，媒体规范常量 16kHz 允许在常量类里） | 阻塞（出现在判断逻辑里） |
| **M-5** | **命名即契约**：包名=层次；类名后缀 `Controller/Service/Worker/Probe/Config`；URL `/api/v1`；DB 列与对外 JSON 用 snake_case（D-041） | 脚本 M5b + review 人工判 | 推荐 |
| **M-6** | **错误处理统一**：业务拒绝走 `ApiException` + 固定 6 个错误码；禁止空 `catch{}`；外部调用必须有超时/退避 | 脚本 M6 = 0（机器）+ review 看异常路径 | **阻塞** |
| **M-7** | **日志可诊断**：结构化、含 taskId；禁止 `System.out`；禁止打印密钥/大对象 | 脚本 M7 = 0（机器）+ review 抽查日志语句 | 阻塞 |
| **M-8** | **测试可维护**：新增公共逻辑必须有测试；禁止 `@Disabled`；只有 `*SmokeTest` 允许按环境跳过；禁止 `sleep` 等异步 | 脚本 M8 = 0（机器）+ review 查测试有效性 | **阻塞** |
| **M-9** | **文档/契约随代码走**：改对外接口→同步 `接入指南.md`；改配置→同步 `配置清单.md`+`.env.example`；改迁移→真实 PG 验；每个技术选择→`decisions.md`；不留 TODO | 脚本 M9/M2（机器）+ review 看 diff 是否带文档 | 阻塞（契约类） |
| **M-10** | **依赖与版本受控**：新依赖先记 `decisions.md` 并锁版本；禁 SNAPSHOT/latest（镜像版本同理）；引入前确认"规模匹配"（宪法 IV） | review 人工判 + `AGENT.md` §4.1 版本事实表 | 阻塞（未记录的新依赖） |

## 2. 怎么执行（三道闸，缺一不可）

### 闸 1：每个 commit 前跑一次（机器）

```powershell
cd D:\new
powershell -NoProfile -ExecutionPolicy Bypass -File tools\check-maintainability.ps1
# 期望：结论：通过 ✅  exit=0
# 不通过 → 先修；确实是已知技术债 → 写进 tools\maintainability-allowlist.txt，
#          并在 review 报告写"为什么现在不修 + 什么时候修"
```

脚本查 12 项：M2 配置外置、M4 硬编码/魔法阈值、M5 反向依赖、M3 文件规模、M6 空 catch、
M7 调试输出、M9 TODO、M8 测试被禁用/无断言、M5b JSON 契约（snake_case）。
**退出码 0 = 通过，1 = 阻塞**（已接入任务卡"验收"段）。

### 闸 2：review 必查（人/独立 agent）

`rules/review.md` 的必查清单已加"可维护性 M-1~M-10"：
- 不看风格偏好，只看**有具体坏处**的（重复逻辑导致改一处漏一处、命名误导、异常被吞、契约漂移）；
- 抽查 3 个方法：能否 30 秒读懂意图；改一个参数是否知道影响谁（配合 `git grep` 调用方）。

### 闸 3：里程碑体检（每个阶段末）

| 时机 | 动作 | 判据 |
|---|---|---|
| 阶段末（每 5 任务） | 跑脚本 + 看技术债清单 | 允许清单条数不增长（只许减少） |
| T4.x（交付收口） | 清掉剩余 **2 条** M5 反向依赖（`QuotaService` / `AudioDurationProbe` 迁 `common/`） | allowlist 清零 M5 条目 |
| T5（交付前） | 全量脚本 + review 抽查 | 0 阻塞 + 技术债清单为空或每条有明确排期 |

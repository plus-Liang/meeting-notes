# 踩坑与复盘（面试用）——录音纪要平台

> **用途**：面试问"开发这个项目遇到什么问题、怎么解决的、最终效果怎么样"时，直接按本文档答。
> **写法**：每个坑固定 6 段：现象（用户/运维能看到什么）→ 定位（怎么查出来的）→ 根因（挖到哪一层）→ 修复（代码/决策）
> → 效果（**量化前后对比**）→ 面试 30 秒口述版。末尾有"高频问题 ↔ 坑编号"对照。
> **纪律**：所有数字都来自独立复验的验收报告（`docs/协作/review/`），不写"感觉变快了"。
> **更新**：随项目推进追加；坑编号固定不复用（K-xx），新坑追加在对应分类末尾。
> **结构**：A–F 是实现侧（架构/可靠性/契约/AI/环境/我方过程）；**G 是外部写码 AI（WorkBuddy）的坑与治理闸门**；
> H 是"面试官问什么用哪个坑"速览；I 是待补清单。**"怎么管 AI 写代码"就答 G 节。**

## A. 可靠性 / 任务状态机

### K-01 ASR 挂掉后要 78 秒才判失败

- **现象**：停掉 ASR 容器，上传一个文件，任务卡在 RUNNING 一分钟多才进 DEAD；用户以为系统死了，监控也只看到"慢"。
- **定位**：把 `docker compose logs app` 按 taskId 串起来看时间戳 —— 发现失败前有多次重试间隔；再查依赖发现 Spring AI 内部自带重试。
- **根因**：三层叠加：① Spring AI `OpenAiAudioTranscriptionModel` 默认走 `RetryUtils.DEFAULT_RETRY_TEMPLATE`（**10 次指数退避**）；
  ② 只配了"读超时 900s"（为长音频设的），没有独立的**连接超时**；③ Docker DNS 解析失败时又叠加 DNS 超时。
- **修复**：`spring.ai.retry.max-attempts=2` + backoff 2s~10s 收敛（D-046）；拆分 **connect 5s / read 900s**（D-058）；
  任务级重试仍归 worker 状态机（不重复）。
- **效果**：停 ASR → **首次失败 3.5s、到 DEAD 7.7s**（基线 78s，**-90%**）。
- **面试 30 秒**："我发现失败判定要 78 秒，不是我的代码慢，是框架默认重试 10 次 + 只有读超时没有连接超时。我把重试收到 2 次、把连接超时拆成 5 秒，失败判定降到 7.7 秒。"
- **证据**：`review/2026-11-14-T2.2验收.md`；D-046/D-058。

### K-02 长音频被短超时误杀 / 一次重试拖 15 分钟

- **现象**：反直觉——超时设太短会杀掉长音频；设太长又会让"挂掉"要等很久。
- **定位**：用 56.7 分钟真实音频跑端到端；另用黑洞 IP（`10.255.255.1`）模拟"能连但不响应"，观察何时失败。
- **根因**：转写的"读超时"要覆盖整个推理时长（本机 RTF≈0.11 → 60 分钟音频要 6 分钟左右），而"连接超时"应该很短。
- **修复**：拆两段超时（connect 5s / read 900s，D-058）；重试次数收敛（K-01）；90 秒心跳式轮询验证不误杀。
- **效果**：56.7 分钟音频 → **DONE 334.6s、内存平稳**；黑洞实验 → **15.9s 判死**（≈3 次 × 5s 连接超时），证明 5s 真的生效。
- **面试 30 秒**："超时必须按阶段拆：连接要秒级、推理要覆盖长音频；我用黑洞地址证明连接超时真的生效，而不是只写在配置里。"
- **证据**：`review/2026-11-14-T2.2验收.md`。

### K-03 "假健康"：依赖挂了健康检查还说 UP

- **现象**：MinIO/ASR 停掉，`/actuator/health` 仍 `UP`；容器"健康"，但用户上传就报错。
- **定位**：手工停依赖 → 看 health 组件列表，发现只有 db/redis（starter 自带），MinIO/ASR 根本没有指标。
- **根因**：健康检查只覆盖"框架自带"，没覆盖"业务真正依赖"；且探活如果复用业务的 900s 超时，会把 healthcheck 拖成分钟级。
- **修复**：自写 `MinioHealthIndicator`（headBucket）与 `AsrHealthIndicator`（GET `/health`），**独立 2s 超时**（不复用 900s）；
  四项依赖全部进 `readiness` 组（D-059）。
- **效果**：停 MinIO → **DOWN 503，1.42s**；停 ASR → **DOWN 503，2.02s**（= 探活上限）；恢复即 UP。
- **面试 30 秒**："进程活着不等于服务可用。我把真正依赖的四项做进 readiness，探活超时独立 2 秒，任何依赖挂掉 2 秒内 503，运维一眼知道是谁挂了。"
- **证据**：`review/2026-11-14-T2.4验收.md`；D-059/D-060。

### K-04 启动期副作用把应用拖死（踩了两次）

- **现象**：MinIO 没起时应用起不来；空库（无表）启动时启动恢复逻辑抛异常；Redis 没起时启动流程卡住。
- **定位**：刻意用"缺依赖"的 compose 起应用，看启动日志卡在哪。
- **根因**：启动期做了"业务动作"（建桶、查 RUNNING 任务、入队），且没做失败隔离 —— 但"无 key 也能启动"的原则（D-035）要求**应用必须起得来**。
- **修复**：启动期非核心动作一律"尽力而为"：try/catch + WARN + 继续启动；**同一个坑出现两次后写成固定规则**（`rules/dev.md` K-04 条）。
- **效果**：无 MinIO / 无 Redis / H2 空库下应用照常启动（单测 `NoKeyStartupTest` 固化）。
- **面试 30 秒**："启动期不该做会失败的业务动作；如果一定要做，就降级成 WARN。这个坑我踩了两次，第二次我把它写成团队规则而不是靠记性。"
- **证据**：`rules/dev.md`；D-035；`startup-recovery` 代码注释。

### K-05 同一文件并发上传插了两条任务

- **现象**：快速点两次上传 / 网络重试，同一条录音出现两条任务，转写两遍。
- **定位**：并发脚本（两路同时 POST 同一文件）→ 查 DB 发现两行相同 `content_hash`。
- **根因**：应用层"先查再插"存在竞态；我最初在任务卡里还写错了修法（catch 唯一键冲突再查）——**PostgreSQL 里事务已经 aborted，再查会失败**。
- **修复**：数据库唯一约束 `UNIQUE(user_id, content_hash)` + `INSERT ... ON CONFLICT DO NOTHING ... RETURNING` + 判空回查（D-055）；
  并把"幂等权威 = 数据库约束"写成决策。**同时是我的卡写错了，记进决策（D-055 明确"corrects my own card"）。**
- **效果**：并发同内容 **只建 1 条任务**；二次上传 `reused:true`，**ASR 转写请求数 4→4（无新增）**。
- **面试 30 秒**："幂等不能靠应用层判空，要靠数据库唯一约束 + 原子 upsert。我一开始给的方案在 PG 里是错的（事务已 abort），被实现方指出后我改了决策，也把'卡不规定 SQL 写法'当教训。"
- **证据**：`review/2026-11-14-T1.9-T2.1验收.md`；D-055。

### K-06 失败任务重传拿不回来（用户一定会重传）

- **现象**：任务进 DEAD 后，用户重新上传同一文件，系统说"已存在"，但任务还是失败状态 —— 等于永久废了。
- **定位**：手工把 ASR 停掉造 DEAD → 重启 ASR → 重传 → 观察 `reused:true` 但状态不变。
- **根因**：原语义把 DEAD 当"终态"，没有"复活"路径；而用户视角"重传 = 再试一次"。
- **修复**：DEAD 重传 = 复活：重置 `attempts/status/error_code`、重新入队、**同时删 `dead_letter`**（D-049/D-055/D-056）。
- **效果**：DEAD 重传 → `reused:true + PENDING` → DONE；**死信表该任务 1 行 → 0 行**（不留脏死信）。
- **面试 30 秒**："状态机要按用户心智设计：用户重传就是再试一次。我们把 DEAD 重传做成复活，并清掉死信记录，避免'死信列表里躺着已经成功的任务'。"
- **证据**：`review/2026-11-14-T2.11-T2.10验收.md`；D-049/D-056。

### K-13 任务"完成"了但摘要还没写（半成品对外可见）

- **现象**：轮询详情，`status=DONE` 但 `summary=null`，几秒后再查才有；接 Webhook 的接入方会读到半成品。
- **定位**：我用自己的验收脚本轮询，正好撞上；日志时间线显示 `转写落库(DONE) 14:42:28.568` 与 `摘要落库 14:42:31.880` —— **3.3 秒窗口**。
- **根因**：实现顺序是"转写 → 置 DONE → 摘要"，而设计初衷（D-068 选同步摘要）正是"DONE = 结果全部就绪"。
- **修复**：顺序固定为"写 transcript → 摘要/待办（try/catch，失败也继续）→ **最后**置 DONE"（D-069）；并加单测/日志断言。
- **效果**：DONE 即结果就绪；失败（无 key/超时）时 DONE + null 且**不会再补齐**（契约可判）。
- **面试 30 秒**："这是个'实现和契约不一致'的坑：文档说完成即就绪，代码却先置完成。修法是把终态写成最后一步，并把它固化成决策。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §2；D-069。

## B. 契约 / 错误处理

### K-07 统一异常兜底把框架 4xx 吞成 500（真回归）

- **现象**：加了"统一错误格式"之后，用户访问不存在的地址从 404 变 500，请求方法不对从 405 变 500，Content-Type 错从 415 变 500 —— 用户以为服务器坏了。
- **定位**：我自己验收时做"错误七连击"（404/405/415/400/未知异常…），全变 500 才发现。
- **根因**：`@ExceptionHandler(Exception.class)` 兜底排在框架语义处理之前，把 `ResponseStatusException` 之类也吞了。
- **修复**：兜底 handler 先看异常是否携带 `HttpStatusCode`，有就**按原状态码**返回；同时错误码分层：**7 个业务码**（D-047）+ **5 个通用码**
  （`INVALID_PARAM/NOT_FOUND/METHOD_NOT_ALLOWED/UNSUPPORTED_MEDIA_TYPE/INTERNAL_ERROR`，D-057）。
- **效果**：七连击全对（404/405/415/400 各回各的，未知异常才 500 且不泄露堆栈）；该回归没有再出现。
- **面试 30 秒**："'统一错误格式'最容易犯的错是无差别兜底。原则是：框架语义优先，只有未知异常才 500；错误码分层，业务码和通用码各管一段。"
- **证据**：`review/2026-11-14-T2.12-T2.3验收.md`；D-057。

### K-08 列表数据只存在浏览器里

- **现象**：换个浏览器 / 清缓存后历史任务列表空了，用户以为数据丢了（其实任务都在 DB）。
- **定位**：用无痕窗口打开列表页，发现页面只读 localStorage。
- **根因**：早期为了快，列表只用前端缓存；服务端没有列表 API。
- **修复**：服务端 `GET /api/v1/tasks?status=&limit=&before_id=`（**keyset 分页**，禁 OFFSET）＋列表页切服务端（localStorage 只做兜底）D-053。
- **效果**：无痕窗口能看到历史；分页"不重不漏"（游标实测）；默认 20 / 上限 50。
- **面试 30 秒**："数据不能只存在前端——这是'用户以为丢了数据'的典型来源。列表改成服务端 keyset 分页，翻页不重不漏。"
- **证据**：`review/2026-11-14-T2.11-T2.10验收.md`；D-053。

### K-09 纯文本日志查不出"一个任务的全链路"

- **现象**：用户报"某个文件转写完是空的"，运维要在几百行日志里翻，taskId 只混在中文句子里，`grep` 出来也看不出前因后果。

  `LOG_JSON=false` 可回退可读文本（D-062）。
- **效果**：`docker compose logs app | grep '"taskId":"N"'` → **5 条**处理节点、**10/10 行可被 JSON 解析**、两个并发任务**互不串号**。
- **面试 30 秒**："可观测性也是功能。我把日志改成结构化 JSON、把 taskId 放到独立字段，一个问题任务的五个阶段一条命令全捞出来。"
- **证据**：`review/2026-11-14-T2.7-T2.8验收.md`；D-062。

### K-10 没有备份：一条 `down -v` 删光所有数据

- **现象**：开发期一次清理把数据库和对象存储卷删了，所有任务/转写全没了 —— 这是"能给别人用"的硬门槛。
- **修复**：`scripts/backup.ps1`（`pg_dump -Fc` + MinIO volume 打包 + manifest 行数/sha256 + `-Keep 7`，**备份不含 `.env`**）；
  `scripts/restore.ps1`（无 `-Force` 拒绝、先停 app、`pg_restore --clean`、按 manifest 逐表自检、失败码 10/11/12/13/14）（D-063/D-064）。
- **效果**：**10 个已完成任务** → 备份 → `down -v` 删卷重建（API 返回空）→ 恢复 → `id/status/hash/transcript md5/长度` **10/10 逐字一致**；
  恢复后对象"真能读"（把任务重新入队能再转写成功）；`-Keep 2` 生效；恢复环境未起时**明确 exit 20** 不误报。
- **面试 30 秒**："备份不是写个脚本就完事：要能核对（清单+校验和）、要能恢复（删卷实测逐字一致）、要防误操作（-Force 闸门）、失败要有可判定退出码。"
- **证据**：`review/2026-11-14-T2.7-T2.8验收.md`；D-063/D-064。

### K-11 配额"明天再试"其实是早上 8 点

- **现象**：429 响应写"明天再试"，但 `Retry-After` 是 6 万多秒（≈18 小时）；中国用户实际要到**早上 8 点**才能继续（容器默认 UTC）。
- **定位**：照卡片解析 `Retry-After` 数值，和"距本地零点秒数"一比，差 8 小时。
- **根因**：配额日 = PostgreSQL `CURRENT_DATE`、`Retry-After` = JVM `LocalDate.now()`，两者都取**容器 UTC**；实现一致、但产品语义错。
- **修复**：compose 给 **app 与 postgres 同时**设 `TZ=Asia/Shanghai`（保留覆盖口，海外可设 UTC）（D-067）。
- **效果**：两边时间都是 CST；`Retry-After: 33491` 与"距本地零点 **33491s**"**逐秒吻合**。
- **面试 30 秒**："时间相关的坑最隐蔽：实现内部自洽不代表对上用户。配额日切必须用用户本地时区，而且应用和数据库两边要一起改。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md`；D-067。

## D. AI 集成

### K-12 LLM 会复用转写的 900 秒超时，拖死唯一消费线程

- **现象**：（设计评审阶段发现，未上线）同步摘要方案如果直接调大模型，LLM 挂着不返回时，唯一的 worker 线程会被拖最长 900 秒，整个队列排队。
- **根因**：早期为了长音频转写，给**所有** HTTP 客户端统一设了 900s 读超时；LLM 和转写共用同一套客户端。
- **修复**：**按 URI 路由超时**：`/v1/audio/transcriptions` → 900s，其它（chat）→ `LLM_TIMEOUT_SEC` 默认 **120s**，连接都 5s（D-068）；
  摘要失败/超时只 WARN，任务照常完成；解析失败不重试（第二次机会交给三档降级）。
- **效果**：单测断言"两条路径各用各的超时、互不串"；真实场景下 LLM 卡住最多影响 120s。
- **面试 30 秒**："AI 调用要和普通调用分开超时。同步摘要的前提是 LLM 有自己的短超时，否则单线程消费者会被一个卡死的大模型拖死整个队列。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md`；D-068。

### K-29 "AI 返回空内容"不是模型不行，是推理模型把 max_tokens 全用来思考了

- **现象**：摘要能出，待办却全空；WARN 里"原始输出截 200 字："后面**什么都没有**。任务还是 DONE，但结果字段是 null。
- **定位**：拿同一段 transcript 直接打模型 API，看返回体里的 `finish_reason` 和 `usage`：
  `reasoning_tokens: 1024`、`finish_reason: length`、`content: ""` → **思考链把 1024 个 token 吃光了，正文一个字没写**。
- **根因**：`deepseek-flash` 是**推理模型**，`max_tokens` 是"思考 + 正文"的**合计**上限（不是正文上限）；
  旧的默认 1024 是给普通模型定的。更坑的是：`.env.example` 里**早就写了这个预警注释**，但默认值一直没改。
- **修复**：`max_tokens` 提到 **8192**（1024 必空、4096 实测 reasoning 3000~3800 仍偶发挤空 + JSON 尾部截断，8192 才 `finish_reason=stop`）；
  `.env` / `.env.example` / `application.yml` 三处默认值统一（D-071）；提示词再加"最多 20 条"压输出长度。
- **效果**：待办从"全空"变成稳定产出（task 85/87：2 条，task 81：21 条），JSON 完整、`stop` 收尾；无 key 时仍是 null（语义不变）。
- **面试 30 秒**："AI 返回空内容，我先怀疑模型，后来发现是我给的 token 预算被思考链吃光了。推理模型的 max_tokens 是思考正文合计，
  我把默认值从 1024 提到 8192，并且让三处配置默认值一致——之前文档写了预警、代码没跟上，这种'文档知道、代码不知道'最容易漏。"
- **证据**：`review/2026-11-14-T3.2验收.md` §6；D-071。

### K-21 大模型"看起来很对"但会编造（摘要质量）

- **现象**：摘要初版读起来很顺，但会写出转写里没有的人名/数字/结论 —— 纪要一旦编造，用户信任直接归零。
- **修复**：提示词**强制 JSON 输出** + 明确"**严禁编造 transcript 里没有的人名/数字/日期/结论**"；解析失败不重试只降级；
  验收时"**逐句回原文找依据**"（人工比对，不是看摘要顺不顺）。
- **效果**：3 个真实样本摘要 160~170 字，要点（需求提示词/产品需求文档/开发计划/验收/二次开发/界面美化/开源）**全部能在转写原文找到**。
- **面试 30 秒**："防幻觉不能靠'看起来对'。提示词里写死禁止编造，验收时把摘要每个结论回到转写原文里找依据，找不到就是不合格。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §2。

### K-15 镜像拉不动 / Maven 卡 15 分钟 / 代理半死

### K-16 ffmpeg 装不进宿主机（系统安全策略拦未签名二进制）

- **修复**：媒体处理**全部放容器内**（`ffmpeg`/`ffprobe` 在 app 镜像里），Java 只调用子进程（D-010）。
- **效果**：本机不装 ffmpeg 也能全流程；跨机器可复现。
- **面试 30 秒**："这算'被环境逼出来的正确设计'：媒体处理本来就更适合容器化，现在换机器不用装任何二进制。"

### K-17 迁移脚本在 H2 上测不出来

- **现象**：单测用 H2，`flyway.enabled=false`，所以 SQL 迁移在测试里根本不执行 —— 写错列名单测全绿。

## F. 过程 / AI 协作（这类问题面试官也很爱问）

### K-18 AI 写码方"报绿"，我的干净环境却是红的

- **现象**：写码方（WorkBuddy）回报"50/50 全绿"，我在干净 shell 一跑就红；它排查后发现是它的终端里恰好有可达的 ASR 地址。
- **根因**：验证环境被污染（历史 shell 变量）；测试脚本又把 `.env` 里**容器内部地址**注入本机测试进程。
- **修复**：① **验收制度：一律自己重跑，不看截图/汇报**（15 份独立验收报告）；② 测试入口改为"跳过容器地址 + shell 已设不覆盖"（D-066），
  干净 shell 必绿、反例（指错端口）必红。
- **效果**：干净 shell **57/57**；反例 `ASR_PORT=9999` 必红；"我的环境能过"变成"任何人 clone 下来都能过"。
- **面试 30 秒**："AI 协作最大的风险是'看起来完成'。我们的制度是：实现方说的不算，验收方必须在干净环境重跑；测试入口要能造出反例，否则就是假绿灯。"
- **证据**：`review/2026-11-14-T2.9验收.md`/`T3.0-T3.1验收.md`；D-066。

### K-19 我自己三次写坏关键文件（PowerShell / .NET 文件 API 的连环坑）

- **现象**：三次都发生在"改配置/改文档"这种顺手操作上：① 把 `.env` 写成空文件；② 把真实 API key 覆盖成占位值；
  ③ 2026-11-14 又把 **77 条决策的 `决策记录.md` 写成 0 字节**（`String.Replace` 传进去一个 `$null` 变量 → 返回 `$null` → 直接写盘）。
- **根因**：`.NET` 用**进程工作目录**（`Set-Location` 只改 PS 自己的位置 → 相对路径读写错位）；PS 5.1 的 `Set-Content -Encoding UTF8` 会写 BOM；
  对 `$null` 调用 `Replace` 不会报错，**写盘时也不校验结果是否为空**。
- **修复**：改前**备份**（`.env` → `/tmp/.env.bak`；文档靠代码仓副本）→ **绝对路径** → 禁 BOM → 改完**比哈希/比行数**；
  写盘前断言"新内容非空且长度接近旧内容"。
- **效果**：三次都**零损失**恢复（`.env` 字节一致、`决策记录.md` 从代码仓副本还原后 781 行/D-070 齐全，再补回 D-071~D-073）；
  规则落 `rules/dev.md` §4.1 + D-070。**同一个坑第 3 次出现说明：光靠记性不行，必须靠工具约束。**
- **面试 30 秒**："我三次写坏过关键文件，都靠备份无损恢复——最后一次把 77 条决策写成 0 字节，是从代码仓副本恢复的。
  所以'改前备份、绝对路径、改完校验'不是客套话：同一个坑我踩了三次，第三次才把它变成工具约束。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §3、`review/2026-11-14-T3.2验收.md` §8；D-070。

### K-20 我自己的测量方法两次造假象（GBK 乱码 + 数行数少算 10 行）

- **现象①**：我判定"测试控制台中文乱码是 bug"，写进验收报告，还让对方去修。
- **根因①**：中文 Windows 控制台输出是 **GBK**，我用 UTF-8 解码管道输出 → 看起来全是 `����`；产品本身没问题。
- **现象②**（T3.2 验收）：我用 `(Get-Content TranscriptionWorker.java).Count` 数出 **288 行**，据此判定写码方自述的 298 行"不准"，
  还写进了验收报告和 K-22。对方复核后**拒绝照改**，要求先给口径 —— 结果是我错：
  PS 5.1 的 `Get-Content` 对无 BOM 的 UTF-8 文件**默认按 ANSI(936) 解码**，中文注释的多字节序列把 10 个换行"吃掉"了 → 少算 10 行；
  `[IO.File]::ReadAllLines` / `git show <commit>:<file> | wc -l` 都数出 **298**（LF 字节数也是 298）。
- **修复**：① 撤回误报、在验收报告里保留"更正"记录（不删黑历史）；② 把"管道捕获按 GBK 解码"+"数行数不用 `Get-Content`"
  写进 `rules/dev.md` §4.1；③ 落地口径决策 D-074：**报告里每个数字必须附一条编码无关、可复算的命令**。
- **效果**：① 避免一次无谓返工；② 298 这个数字最终是对的，写码方没有被冤枉；教训是"我自己的报告也要能被别人复算"。
- **面试 30 秒**："我抓到过对方的假绿灯，也两次被自己的测量工具骗过：一次把 GBK 当 UTF-8 读出乱码，一次用 `Get-Content` 数行数
  少算 10 行、差点把对方正确的数字判成造假。后来我立了规矩：结论里的每个数字都要附一条可复算的命令，而且复算方法本身要换一种工具交叉验证。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §1；`review/2026-11-14-T3.2验收.md` §1/§8.2；`rules/dev.md` §4.1；D-074。

### K-30 还原变异后测试还是红的——骗我的是**增量编译**

- **现象**：做"变异验证"（把路由映射改反 → 测试应该红 → 还原 → 应该绿），还原后测试**仍然红**，差点误判成"实现有问题"。
- **根因**：我用 `Copy-Item` 还原源码，它**保留了备份文件的旧时间戳**；Maven 增量编译判断"源码比 class 旧 → 跳过编译"，
  于是跑的其实还是**变异版 class**。测试本身没骗人，构建缓存骗了人。
- **修复**：还原后 **`touch` 源码更新时间**（或 `mvn -Dtest=... -o clean test`），再断言"还原后必须绿"；验收脚本里把"还原→绿"当成独立一步。
- **效果**：`touch` 后 4/4 绿、工作树干净；变异验证从此是"改→红→还原→绿"四步，而不是"改→红→还原"三步就收工。
- **面试 30 秒**："做变异测试时我差点冤枉实现方——还原后测试还红，原因是 `Copy-Item` 保留了旧时间戳，Maven 增量编译根本没重编。
  所以'还原后必须再绿一次'是变异验证的必要一步，否则你验证的是缓存，不是代码。"
- **证据**：`review/2026-11-14-T3.2验收.md` §3 注；`rules/dev.md` §4.1。

## G. 外部写码 AI（WorkBuddy）的坑——"怎么管一个 AI 写代码"

> 这一节面试价值很高：现在很多团队都在用 AI 写代码，但**卡在哪里、怎么加闸门**很少有人讲得具体。
> 共同规律：AI 写码方的失败模式**不是"写不出代码"，而是"看起来完成了"**——数字凭记忆、测试只求绿、完成态先写、文档不回头对。
> 所以治理手段全部是"**用可复算的东西替代它的自述**"。

### K-22 自述的"数字"和事实不符（52 提交 / 3 份备份 / 50 全绿）

- **现象**：写码方汇报"一卡一 commit""已有 3 份备份""测试 50/50 全绿"。我复算：实际 **61 个提交**、**5 份备份**；"50/50"在我的干净 shell 里**复现不出来**。
  T3.2 又来一遍：说"基于 `1344f1d`"（实际父提交 `87e28b0`）、说"三个样本齐了（77/81/80）"但 **task 77 早被删了**（无法复核）、
  说"owner/deadline 全是 null"但 task 80 的 `deadline=报名前` 有值。
- **定位**：`git rev-list --count HEAD`、`ls backups`、`scripts\test.ps1` 全量重跑、`git rev-parse HEAD^`——
  全部由我自己执行，不看它的截图；对"样本"则**直接查库**（`jsonb_array_length(todos)`）并比对 taskId 是否存在。
- **根因**：它的汇报是"凭印象概括"而不是"从命令输出抄"；同时它的终端里有历史 shell 变量（可达的 ASR 地址），环境被污染；
  另外**会删掉自己跑过的中间任务行**，导致自述不可复核。
- **修复**：报告必须"**命令 + 输出 + exit code**"三件套，数字必须能被一条命令复算；验收方**一律独立重跑**（已积累 16 份验收报告）；
  **验收样本任务行不删**（D-073），报告里写 taskId；我自己用新 hash 样本重做证据（task 85/86/87）。
- **效果**：后续每一轮的数字都能对上；"我的环境能过"升级为"**任何人 clone 下来都能过**"（干净 shell 68/68，反例必红）；
  T3.2 自述里 4 处数字/事实偏差**全部被我复算纠正**，没有一条混进验收结论。
- **面试 30 秒**："AI 交付最大的风险是'看起来完成了'。我的制度是：它说的不算，我按它给的命令自己重跑；报告里写数字必须附命令，否则视为没做。"
- **证据**：`review/2026-11-14-T2.9验收.md` §2；`review/2026-11-14-T3.0-T3.1验收.md`；`review/2026-11-14-T3.2验收.md` §8；D-073。

### K-23 假测试：断言"自己和自己比"，实现写反了照样全绿

- **现象**：4 条路由超时测试全绿。我审代码发现前两条是 `assertEquals(x, x)`——**把两条路径的工厂映射对调，测试依旧通过**。
- **定位**：读测试源码找"自比较/永远成立"的断言；再用**变异验证**（故意把实现写反）看测试会不会红。
- **根因**：AI 的目标函数是"让测试通过"，不是"让测试能抓住错误"；没有"能造红"的要求，就会写出装饰性断言。
- **修复**：改成方向断言（转写 URI 必须选中 900s 工厂、chat URI 必须选中 120s 工厂）；并确立"**写反必须变红**"作为验收动作。
- **效果**：对调映射 → 测试立刻红；正常实现全绿。测试终于具备"证伪能力"。
- **面试 30 秒**："测试的质量不看通过率，看它能不能变红。我抓到过自比较断言，后来要求每条关键测试都要做一次'故意写反'的变异验证。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §2（F-2）；已并入 T3.2 收口。

### K-24 先置"完成"再补数据（外部读到半成品）

- **现象**：`status=DONE` 但 `summary=null`，几秒后才出现；按 DONE 回调的接入方会读到半成品。
- **定位**：轮询时撞上；日志时间线 `转写落库(DONE) 14:42:28.568` vs `摘要落库 14:42:31.880`，**3.3 秒窗口**。
- **根因**：AI 倾向"先把状态改成成功、再慢慢补字段"——它关心的是"主流程跑通"，没意识到 DONE 是**对外契约**。
- **修复**：顺序写死"transcript → 摘要(try/catch) → **最后**置 DONE"（D-069）；验收加"**日志顺序断言**"，不只查最终结果。
- **效果**：DONE 即结果就绪；摘要失败也 DONE+null 且永不补齐（契约可判）。
- **面试 30 秒**："AI 写状态机会把'完成'写早。我把终态定义为'所有结果就绪'，并让验收检查日志的**先后顺序**，而不是只看最后有没有值。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §2（F-1）；D-069。

### K-25 自测只跑正路径，负例一个没覆盖

- **现象**：功能正例全绿，但加"统一错误格式"后，404/405/415 全被吞成 500——它自测没测过这些。
- **定位**：我做"**错误七连击**"（404/405/415/400/未知异常/重复上传/超限）逐个打，才发现框架语义被兜底吃掉。
- **根因**：AI 默认沿"happy path"自测；负例需要"主动想到用户会怎么用错"，它不会自己补。
- **修复**：把负例**写进任务卡的验收条件**（错误码分层 D-057 + 七连击作为固定验收项），而不是等它自觉。
- **效果**：七连击全对；此后每张卡验收都带负例清单。
- **面试 30 秒**："AI 自测天然偏向正路径，所以我把负例从'靠自觉'改成'写进验收标准'——验收条件里没有负例的卡不接。"
- **证据**：`review/2026-11-14-T2.12-T2.3验收.md`；D-057。

### K-26 卡外"顺手"改环境，做完才回报

- **现象**：卡里只要求改代码，它顺手修了环境问题（改公共面配置），**做完才回报**，导致"改动范围"和"批准的卡"不一致。
- **定位**：核 `git show --stat` 对比卡片范围，发现卡外文件被改动；且公共面改动没有事前确认。
- **根因**：AI 有"把问题都解决掉"的倾向，但**越界改动**会让审批与回滚失控（尤其 yml/compose/迁移这类公共面）。
- **修复**：确立"**公共面改动先说后做**"：卡外改动必须先报"原因+影响"、批准后落决策（D-052）；验收按 `git diff --name-only` 逐行核范围。
- **效果**：之后每卡改动范围可枚举、可解释；额外修复也都有决策号。
- **面试 30 秒**："AI 会'顺便帮你修'，这在团队里很危险。我要求它的改动范围必须可枚举；改公共配置必须先申请，批准后写进决策记录。"
- **证据**：`review/2026-11-14-T1.6验收.md`；D-052。

### K-27 文档与代码脱节，还会自述"已更新"

- **现象**：`AGENT.md` 的"下一步卡片"停在两张卡之前；`任务清单.md` 写着"T2.1–T2.12 全 ✅"（假的）；配置清单/确认单数字漂移。
- **定位**：每轮验收时顺手核一遍文档 vs 实际（读文件 + 数行 + 对 commit），发现多处不一致。
- **根因**：AI 只对"代码任务"负责，文档被当成附属品；加上同一数字在多处手抄 → 必然漂移。
- **修复**：① 一次性对齐补丁（DOC-1，一个 commit 全修）；② 易漂移数字**只留单一来源**、其它处引用而非复制（D-065）；③ 验收清单加"文档一致性"一项。
- **效果**：文档与代码同轮同步（每轮 docs commit + push）；"下一步卡片"永远是最新的一张。
- **面试 30 秒**："AI 写的代码会过，但文档会慢慢失真。我改成'每轮验收同时核对文档'，并把会变的数字收敛到唯一来源，杜绝多处手抄。"
- **证据**：`D:\new\projects\DOC-1_文档对齐补丁卡.md`（已执行）；D-065。

### K-28 小债：每行 `new ObjectMapper()`、重复实现

- **现象**：`TaskController` 在**行映射里**每行 new 一个 `ObjectMapper`，`SummaryService` 也自建一个；功能对，但是浪费且难维护。
- **定位**：review 时读代码发现构造对象的位置不对（循环体内）。
- **根因**：AI 优先"能跑通"，对"单例/复用"这类工程习惯不敏感（尤其 Spring 里应该注入 Bean）。
- **修复**：记为 P3 小债（不阻塞交付），后续注入单例 Bean 一次改掉；**不在功能卡里顺手大改**（避免范围膨胀）。
- **效果**：交付节奏不受影响，债有编号不会丢。
- **面试 30 秒**："AI 代码常见'能跑但工程习惯差'，比如循环里 new 对象。我的处理是记成有编号的小债，单独一张卡改，而不是在功能卡里顺手重构。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §2（F-3）。

### G-尾 一句话总结怎么治 AI 写码方

> **不信自述、只信复算；测试必须能造红；终态必须最后写；负例写进卡；公共面先说后做；文档同轮对齐；小债编号不丢。**
> 每条都对应上面一个坑——不是"感觉 AI 不靠谱"，而是**七个具体闸门**。

### K-31 两个 AI 同时写同一个仓库：清理→被覆盖→再清理的拉锯

- **现象**：T3.3 期间，我此前起的写码 subagent 与 WorkBuddy 同时写 `D:\new\projects\meeting-notes`。我清掉它的未提交改动后，它按上下文**重写并提交**；
  期间 `.env` 被临时改动、app 镜像被重建、DB 多出测试任务行。仓库出现"我以为干净 → 又被写回"的拉锯，两边都无法确定当前状态。
- **根因**：**没在启动第二个写者之前确认第一个已停**；两个 agent 共享同一工作目录，worktree 也隔离不了（AGENTS.md §5）。
- **修复**：①用户裁决"产物以 commit 为准"（保留 `991f429`，WorkBuddy 转 T3.4）；②我按备份恢复 `.env`（最终 = 原备份 + 仅 `OFFLINE_MODE=false`，hash `2BCC440F1C9E`），
  证据行 88~101 全保留；③规则落地：**一个仓同一时刻只允许一个写者**（D-079 / `rules/dev.md` §4.1 第 9 条），写码任务串行交接。
- **效果**：没有丢代码、没有丢证据；事故本身成了"怎么管多个 AI 写同一个仓"的具体案例。
- **面试 30 秒**："多 AI 并行不是问题，**并发写同一个仓**才是问题。我的处理是把'谁在写'当成状态来管：开工前查残留、写完必须 commit 交接、出事故以 commit 为准而不是听谁说得对。"

### K-32 本地小模型 + 全局 max_tokens：报错信息把我带偏（`application/octet-stream`）

- **现象**：LOCAL 档（qwen2.5:1.5b）在 app 内总是失败，WARN 是 `RestClientException: Error while extracting response … content type [application/octet-stream]`，
  看起来像"服务返回了二进制/协议不对"；但同一环境直连 ollama 却是 HTTP 200 + `application/json` + 合法 JSON（22.2s）。
- **根因**：全局 `LLM_MAX_TOKENS=8192`（云档需要）对 1.5B/CPU 太大 → 生成超过 120s 读超时，客户端拿到的是不完整/不可解析响应，
  Spring 把它表现成"content type 不对"的**误导性症状**。把 `LLM_MAX_TOKENS` 临时调到 512 后 16.8s 就返回了，证明问题是**预算**不是协议；
  但 512 时模型又"不守 JSON 格式"（输出前带散文 + 编日期），于是走"解析失败 → 降级 EXTRACTIVE"。
- **修复**：级联兜底保证用户可见结果不为空；结论记为 F-11——**本地档需要独立的 max_tokens/读超时预算**（新增配置键要用户批准），
  T3.4 先做不改键的部分（JSON 抽取容错 + 本地提示词瘦身）。
- **效果**：`ai_tier` 诚实标 EXTRACTIVE，不 500、不空结果；同时得到一个可复用的诊断套路。
- **面试 30 秒**："报错信息会骗人。我的定位办法是**换一个变量做对照**：直连服务看协议、再调小预算看是不是超时；
  两次对照就把'协议问题'证伪成'预算问题'。"

### K-33 幂等键让"换环境复跑"复用了旧证据行

- **现象**：我想用 `probe.wav` 在改完环境后复跑一次，接口直接返回 `{"task_id":82,"reused":true}`——拿到的是改动前的旧任务，`ai_tier` 是空的，差点被当成"新实现没写 ai_tier"。
- **根因**：幂等是按 `content_hash` 做的（D-055，正确设计）；同一文件重复上传必然复用，不会因环境变了就重跑。
- **修复**：复跑一律**造新样本**（截 20/21/22/23/24s 的派生 wav，hash 各不相同），并检查响应里 `reused=false`；这也正好满足 D-073"新反例用新样本、不删证据行"。
- **效果**：8 条实机证据行（88~101）全部是新任务，每条都能独立复核。
- **面试 30 秒**："幂等是好事，但**验收时它会骗你**——你以为在测新代码，其实在看旧结果。所以我复跑前先看 `reused` 标志，必须造新输入。"

### K-34 测试全绿 ≠ 质量对：摘要"只选一半句子"的 bug 在 T3.3 验收里漏掉了

- **现象**：T3.3 的 97 条单测全绿、我实机也验了 summary 非空，但 T3.4 实机发现 task 104 的 summary **恰好是 transcript 前 67 字**。
- **根因**：`summaryOf` 用 `for (k < Math.min(5, indexes.size()))` 选 top-N，循环体里 `indexes.remove(best)` 让 `indexes.size()` 每轮缩小 → 实际只选出约一半句子。
  句数 ≥10 时仍能选满 5 句（所以 T3.3 的 97 条测试 + 长文本实机全过），只有句数少（104 只有 4 句）才暴露：只选出"首句 + 一个 327 字长句"，长句被"丢句不截句"丢弃 → 只剩首句前缀。
- **修复**：循环前锁定 `take = Math.min(5, indexes.size())`；新增"选取数锁定"回归用例；写码方用同包探针（javac + java）复现定位，我在验收里逐行核了 diff。
- **教训**：**测试只能证明"不回归"，不能证明"质量对"**。质量类任务必须：①实机看**原文**（不是只看字数）；②判据量化（`exactPrefix` 比较、尾句命中位置）；
  ③样本覆盖边界（句子少/极短/无标点）。
- **面试 30 秒**："这个 bug 是 97 条测试全绿时留下的。它暴露的时机很典型——只在输入'句子少'时出现。
  所以我对 AI 写的质量类功能，不只看测试绿，还要拿实机输出跟原文逐条比；这次就是靠'摘要是不是原文前缀'这个量化判据抓出来的。"

### K-35 `.env` 里的行内注释被 compose 当成值：一个静默错配置

- **现象**：T3.11 测试时用 `sed` 把 `.env` 里 `OLLAMA_ENABLED=false` 改成 `OLLAMA_ENABLED=true #false`（把原行尾注释一起保留了），
  compose 的 `env_file` **不剥离行内注释** → 值变成 `"true #false"`，布尔解析/容器行为静默出错，排查时先怀疑代码。
- **根因**：`.env` 是"值 + 行内注释"的宽松格式，但 Docker Compose 的 `env_file` 只按 `=` 切分，注释当值的一部分。
- **修复/规则**：①`.env` 只写**纯值**，注释放上一行；②所有 `.env` 改动"先备份 → 纯值写入 → 改后哈希比对"（D-070）；
  ③容器化验证一律看**启动日志/健康检查**判断配置是否生效，不看文件"看起来对不对"。
- **顺带两条同类教训**：①PS `2>&1` 对原生 exe 会把 `$?` 置假（test.ps1 报 exit 1、mvn 其实 0）→ 用 `$LASTEXITCODE` + 第二种工具复核（D-074 家族）；
  ②检查器误报要靠**改检查器扫描范围**（M9 只扫注释）解决，而不是往 allowlist 塞豁免——否则技术债清单会一直涨。

### K-36 配额满时怎么继续验收：用"必拒绝"的请求证明事务回滚，而不是假装通过

### K-40 "假绿"也要证据：变异双向一验，发现旧断言本来就没问题

- **现象**：卡面与写码方都把 T3.9 遗留的 `never()).update(anyString(), any(Object[].class))` 判为"varargs 空过的假绿"。我复验时先做变异：在失败路径注入一次 `jdbc.update(...)`，

- **根因**：Mockito 会把 `any(Object[].class)` 展开匹配到剩余 varargs，参数个数不同也能匹配；所以"空过"这个判断是错的。另外引用的 `K-31` 实际是"两个 AI 同时写同一个仓"，与 varargs 无关——**卡面文字是我写的，编号引用错了**。
- **修复**：①改动保留，但**定性改为"断言加固"**（新断言钉住"恰好 1 次只读 query + 零其它交互"，比只查 update 更强）；②纠正记忆：K-31 ≠ varargs，本坑单独记 K-40；
  ③把"变异要双向"写进验收清单：**既证明新断言能造红，也证明旧断言能不能造红**——否则你不知道自己修的是 bug 还是幻觉。
- **效果**：避免了一次错误的"修复叙事"（会让面试时讲错）；同一轮里另 3 处变异（长音频/超时/降级）均为真红→还原绿。
- **面试 30 秒**："我抓到过别人的假绿灯，也抓到过自己的错误归因——我以为旧断言是假绿，做了双向变异才发现它本来有效。
  结论是：**说'这是假绿'和说'这是 bug'一样，都要拿变异证据说话**。"

### K-44 断网实验怎么做才可信：改网络属性必须 down→up，内网下宿主连不上端口

- **现象**：为 T4.5 铺路时给 compose 叠加 `networks.default.internal: true`，只 `up -d` → app 起不来：`UnknownHostException: postgres`，
  `docker inspect` 看 endpoint 是 **invalid IP**。改成 **先 `down` 再 `up -d`**（不带 `-v`）后 5 服务全 healthy。
- **定位/附带结论**：
  1. compose 改网络属性是**网络重建**，`up -d` 的增量重建会留下半个 endpoint（无 IP）→ 容器 DNS 直接失效；必须整栈重建。
  2. 内部网络（无默认路由）下 **宿主访问发布端口 = 000**，API 只能在容器内 `curl`（app 镜像自带 curl）——这不是 bug，是断网实验的固有约束。
  3. `com.docker.network.bridge.enable_ip_masquerade=false` **不能**断外网（实测照样拿到 HTTP 401），别拿它当"断网"。
  4. asr 能离线：模型是宿主目录只读挂载 + `HF_HUB_OFFLINE=1`，不依赖下载（这本身就是"可自托管"的关键设计）。
- **修复/规则**：断网实验固定动作 = **先落盘日志 → `down`（不加 `-v`）→ `up -d` → 三证（无默认路由 / 外网请求失败 / settings 档位）→ 恢复同样 down→up**；
  验收时不要在宿主上点端口，容易把"内网隔离"误判成"服务挂了"。
- **面试 30 秒**："证明'断网也能用'不能只清 key，得真的把路由拿走。但一改网络属性，Docker 的增量重建会留下无 IP 的 endpoint，
  DNS 直接坏——所以必须整栈重建。而内网下宿主反而连不上端口，得进容器里测。**实验装置本身也会骗你**。"

### K-45 收尾数字的采样时机：全量测试本身会改配额，"跑完再查"才是真数

- **面试 30 秒**："我们交付里所有数字都要能复算。AI 回报的配额连续两次差 1，原因不是算错，是**采样太早**——它跑完测试前就抓了数，而测试本身会新增一条任务。
  我把'最后一步查数'写进回报模板：数字不是写报告时顺手抓的，是流程的最后一个动作。"

### K-46 认证是横切改动：你改的不是一个端点，是"所有调用方"

- **现象**：T4.6 给 `/api/v1/**` 加 Bearer 之后，**同一个改动同时打断了四条调用链**：①浏览器 4 个页面（直接 `fetch`，没有 token）②E2E 测试（`HTTP` 客户端不带头）③`test.ps1` 全量跑（E2E 401 → 假红）④`接入指南` 里的示例 curl。任何一条没改，验收时都会表现为"功能坏了"。
- **定位**：先把"谁在调这个 API"列全（页面 JS、E2E、测试脚本、文档示例、未来的第三方接入），再逐个补 token 通道——
  页面走 `auth.js`（localStorage + 401 prompt）、E2E 走 `E2E_API_TOKEN`（环境变量 → `.env` 兜底）、`test.ps1` 负责把 `.env` 的 token 注入、文档示例加 `-H Authorization`。
- **根因**：认证不是"加一个 filter"这种局部改动，而是**契约面的扩大**——它把"匿名可调"变成"必须带凭证"，所有现存调用方都从合法变成非法。
  只测新端点（curl 带 token 200）会给出**假绿**：UI 和测试套件已经全断了。
- **修复/规则**：做认证/鉴权/限流这类横切改动时，开工前写一张"调用方清单"，收尾时逐条打勾；**必须跑一次全量测试**（它会打到所有内部调用方），
  并人工确认浏览器页面路径（T4.13 真机再点）。同理适用于改全局序列化、改错误码、改 URL 前缀。
- **效果**：最终 220/220 全绿、浏览器页面靠 prompt 一次 token 继续工作、E2E 在 CI 式全量里也能跑；验收方我能用同一套凭证独立重放 Webhook。
- **面试 30 秒**："加认证时我第一件事不是写 filter，是列出'谁在调 API'——前端 4 个页面、E2E、测试脚本、文档示例全要改。
  只测 curl 会假绿，因为套件和 UI 已经断了。**横切改动的验收标准是'所有调用方'，不是'新端点'**。"

### K-47 签名类证据：接收端自己打印 `verify=True` 不算证据，验收方必须独立重算

- **现象**：T4.6 的 Webhook 交付物是"20 行接收端验签通过"。写码方的接收端打印 `verify(secret)=True | verify(wrong)=False`——
  看起来完备，但**这仍然是"同一个作者写发送和校验"**：如果签名算错了字节（例如对 JSON 重排后的 body 签名）而接收端用同样错误的字节校验，`True` 会一直成立。
- **定位/做法**：我不看它的 `True/False`，而是从接收端日志里取出**真实收到的 body 原始行**，用**另一门语言/另一套库**（PowerShell `HMACSHA256`）
  独立重算 `sha256=` 再比对；同时独立推导 `delivery_id`（Python `uuid.UUID(bytes=md5("mn-webhook-delivery-<行id>"), version=3)`）验证"确定性 UUID"的说法。
  两条都命中，才认可签名与去重语义。
- **根因**：签名/摘要/哈希这类证据的自证性极强——**同一实现既当运动员又当裁判**，永远自洽。单测里"用独立 HMAC 实现互证"是对的方向（写码方做到了），但集成证据仍需验收方重算一次。
- **修复/规则**：验收涉及 HMAC/sha256/加密时，固定动作 = 取**原始字节**→ 用**独立工具**重算 → 比对；再配一条"换错密钥必须不等"的反向验证。
  本次还补了"第 1 次 500 → 1s 重试成功"与"始终 500 → 4 次后留表"两条实机，才把"重试逻辑只有单测"的空白填上。
- **面试 30 秒**："Webhook 验签的证据不能是接收端自己打印 True——那是自己验自己。我从日志里取原始 body，用另一套工具重算 HMAC 比对，
  再用另一个语言独立推导去重键，两条都对才认。**签名类证据，验收方必须能自己算一遍**。"

### K-48 批量 API 的"部分成功"必须写进契约，否则接入方会把 200 当全成功

- **现象**：T4.7 批量提交里，2 个文件成功、1 个文件魔数非法。如果按"一个坏文件就整批 400"处理，用户传 20 个文件时只要有一个坏的就得重传全部；但若直接回 200 又容易被理解成"全都受理了"。
- **决策**：回 **200（请求本身合法）+ 逐项结果**：`items[]` 每项要么 `task_id/status/reused`，要么 `code/message`；`summary` 给 `accepted/reused/failed`。
  接入方必须**逐项看** `items[].code`，不能只看 HTTP 状态码；文档里写死"200 不代表全部成功"。
- **配套口径**（不写清就会互相扯皮）：`accepted` **含 reused**（与单文件一致）；幂等项**不重复扣配额**（实机验证：重发同一批，配额前后完全不变）；
  时长只累加成功项的非空时长；预估耗时给公式且声明"只是预估不承诺"；数量超限 400、总体积超限 413（引擎层）分开定级。
- **根因**：批量接口天然有"部分失败"这个第三态，而 HTTP 只有成功/失败两态。**这个语义必须由接口作者显式定义并写进文档**，否则每个接入方都会自己发明一套。
- **修复/规则**：批量/多资源接口固定四件事：①部分成功用什么状态码（这里有意的 200）②每项错误码字段 ③汇总口径（accepted 是否含 reused）④配额/幂等按项还是按批。
  验收时逐项核对"顺序、隔离、复用、配额不变"四件事（我实机全打了一遍）。
- **面试 30 秒**："批量接口最难的不是循环调用，是定义'部分成功'。我选择 200 + 逐项码，并在契约里写明 accepted 含 reused、幂等不重复扣配额——
  这些口径不写清，接入方和我会各理解一套。验收时我用 2 好 1 坏实测：坏的隔离、好的到 DONE、原样重发 reused 且配额不动。"

### K-49 后台调度器只按"到期"捞行，不重放"入队前置条件"——空配置会空烧重试且报错文案骗人

- **现象**（T4.8 重启验证时发现，Lead 已独立复现）：`WEBHOOK_SECRET` 为空串时，手工插一行到期 `webhook_delivery`（或"先配了 secret → 后来又清空"留下的历史行），
  调度器照常捡起并投递：`attempts` 1→2→3→4（1s/10s/60s 退避），4 次全败 `last_status=0` 终局，日志写 **`Webhook 投递异常：…（HMAC-SHA256 不可用），留表重试`**。
  实际根因不是算法不可用，是**空密钥**（`new SecretKeySpec(new byte[0], "HmacSHA256")` 抛 `IllegalArgumentException("Empty key")`，被 catch 包成 `IllegalStateException("HMAC-SHA256 不可用")`）。
- **根因**：**"写入口守门"被当成了"消费入口守门"**。`onTerminal`（入队）有 `if (secret.isEmpty()) return;`，但 `scanDue`（重试扫描）只查 `next_retry <= now()`，
  完全不重放"secret 是否还配着"这个前置条件。凡是"先入队、后消费"的异步链路（队列、重试表、定时任务），入队侧的前置条件都可能被配置变更/人工数据打破。
- **危害**：①空转但不算错——配额/任务不受影响，真出事时只会污染 `webhook_delivery`；②**报错文案把人带偏**：看到"HMAC-SHA256 不可用"会去查 JDK/加密库，而真因是环境变量空；
  ③终局后 `next_retry=NULL`，看起来像"重试跑完了"，容易被误读成"投递真的试过网络"。
- **修复/规则**：①后台调度器/重试器必须在消费入口**重放前置条件**（secret/URL/开关/离线模式），不满足就跳过并给"配置缺失"语义的日志；
  ②错误文案必须能区分**配置缺失**与**组件不可用**（`secret 为空，跳过重试` ≠ `HMAC 算法不可用`）；③凡是"手工可写/可能遗留"的表，扫描器都要假定行是脏的。
  修复进了 **T4.12**（`scanDue`/`attempt` 空 secret 短路 + 明确日志 + 单测）。
- **面试 30 秒**："重启验证时我发现 Webhook 重试表里一行数据在空转：4 次重试全失败，日志说'HMAC 算法不可用'。但真因是环境变量为空——空密钥构造异常被宽 catch 包装成了误导文案。
  入队路径其实检查了 secret，可**重试扫描路径没检查**。这让我记住：异步链路里'入队时成立的条件'不等于'消费时还成立'，重试器必须自己重放前置条件，
  而且报错要能区分'没配置'和'坏了'。"

### K-50 证据载体自己也会说谎：字段叫 `body_b64` 却存的是 UTF-8 文本

- **现象**（T4.8 验签时踩到）：Webhook 接收端脚本把原始请求体直接 `body.decode("utf-8")` 后写进 JSON 字段 **`body_b64`**——名字说是 base64，内容其实是解码后的文本。
  我按字段名 `FromBase64String` 去解，直接抛 `FormatException`；换成"取字符串的 UTF-8 字节"重算，HMAC 才命中。
  同类的第二个坑：我用 `Set-Content` 写导出快照文件再算 sha256，得到 `d0153e6…`，与 API 原始字节的 `2d2fe8ea…` 不一致——**BOM/尾换行**造成的假"数据不一致"。
- **根因**：验收的可信度建立在"**同一段字节**的跨工具复算"上（K-47），而证据链上有三层东西容易被混淆：原始字节、文本表示、文件落盘表示。
  任一层没有显式声明编码/是否含 BOM/尾换行，换个工具就会算出不同哈希，轻则返工，重则误判"数据丢了/被改了"。
- **规则**：①**二进制/原始字节一律 base64，字段名必须如实**（`body_b64` 里装 text 就是缺陷）；文本字段显式标注编码；②快照落盘统一一种写法（如 `utf8NoBOM + 不追加换行`），
  并在报告里写明"这个哈希算的是哪段字节"；③验签必须做**双向**：命中 + 错密钥必须不等（K-47），否则算出来的"一致"可能只是巧合；
  ④遇到哈希对不上，先查 BOM/换行/编码，再怀疑数据被改。
- **面试 30 秒**："我验收 Webhook 签名时，接收端把字段名叫 `body_b64`，实际存的是解码后的文本。我按名字用 base64 解，直接报错——那一刻我意识到**证据工具本身也会骗人**。
  后来我统一规则：原始字节一律 base64 且字段名如实，哈希必须写清算的是哪层表示，验签要同时有'命中'和'错密钥不等'两个方向。这样换语言、换工具复核都不会互相打架。"

### K-51 配置生效判据要打在"真正的消费点"：容器 `date` 显示 CST ≠ PostgreSQL 时区生效

- **现象**（T4.8 验收后回答"配额为什么只剩 3 个任务"时发现）：D-067 明明给 app 与 postgres 都设了 `TZ=Asia/Shanghai`，`docker exec postgres date` 也显示 CST，
  但 `SHOW timezone` 返回 **UTC**、来源 `configuration file`（数据卷里的 `postgresql.conf`）——**TZ 环境变量改不了 initdb 时已写死的 GUC**。
  后果：配额 `CURRENT_DATE` 仍按 UTC 日 → 实际重置在**北京时间早上 08:00**；`/settings` 的"今日"与 429 的 `Retry-After`（JVM 本地日）在 00:00–08:00 窗口互相打架。
- **根因**：**把"配置写进去了"当成了"配置生效了"**。判据选错层——`date` 验证的是容器 libc 时区，而真正消费时区的是 **PG 的 `TimeZone` GUC**；
  环境变量只在 initdb 新建数据卷时才被写进 `postgresql.conf`，老卷天然不同步。这类"层间不一致"是配置类问题里最隐蔽的一类。
- **危害**：日常看不出来（白天两个日期相同），只在跨日窗口暴露；`/settings` 的"今日"、429 的等待秒数、运维说的"明天再来"全是错的，且证据看起来"配置已设"。
- **修复/规则**：①判据必须打在**消费点**：`SHOW timezone` + `CURRENT_DATE = (now() AT TIME ZONE 'Asia/Shanghai')::date`，不是容器 `date`；
  ②老数据卷要显式 `ALTER DATABASE … SET timezone …`（或 compose `command: postgres -c timezone=…`），不能只靠环境变量；
  ③任何"改环境变量"的验收都要问一句"消费它的是谁、有没有中间层把它缓存/写死"（K-41 的另一种形态）；④已进 T4.12 启动预检（GUC 与 TZ 不一致要报）。
- **面试 30 秒**："我们给 Postgres 设了 TZ=Asia/Shanghai，容器 date 也显示 CST，我就以为时区修好了。后来发现配额还是在北京时间早上 8 点重置——因为老数据卷是 UTC 时期 initdb 的，
  `postgresql.conf` 里写死了 UTC，环境变量根本改不动它。这让我改了判据：不看容器 date，直接查 `SHOW timezone` 和 `CURRENT_DATE` 与本地日是否一致。
  **配置生效要验证在消费点上，而不是验证在你设置它的地方。**"

### K-52 启动预检要分级：必崩 → fail-fast，可自愈/有意配置 → WARN

- **现象**（T4.12 同时修 F-21 与 F-23）：两个"配置不对"的问题，写码方给了两种完全不同的处理——F-21（`LLM_ENABLED=true` + 云 key 空）**fail-fast 直接退出**，
  F-23（DB 时区与 `TZ` 不一致）只 **WARN 后继续启动**。一开始我想"统一成 fail-fast 更严格"，但想清影响面后没改。
- **判断标准**：①**必然崩/数据会坏** → fail-fast（配了云档却 key 空，启动后每个任务都会失败且报错间接，早死早超生）；
  ②**可自愈/只影响时序/可能是用户有意为之** → WARN（时区错位不损坏 `timestamptz` 绝对时间、可在线 `ALTER DATABASE` 修、海外用户可能故意用 UTC）；
  ③文案必须**点名缺哪个键 + 给两种修法**（补 key / 关开关），不能只说"启动失败"；④对"稳态缺失"的告警要**只发一次**（否则每秒刷屏，日志失去可读性）。
- **危害**：一刀切 fail-fast 会把"能跑但配置略偏"的自托管用户挡在门外（违背零成本可跑 D-035）；一刀切 WARN 则会让"必然崩"的错误拖到每个任务失败时才暴露，排障成本翻倍。
- **修复/规则**：预检前先问两个字——**"必崩吗？""能自愈吗？"**；必崩 → 最早阶段 fail-fast；否则 WARN + 修法 + 单次去重。启动后才知道的检查（DB 已连接）放 `ApplicationRunner`，启动前就能判的（环境变量）放 `EnvironmentPostProcessor`。
- **面试 30 秒**："同一张卡我修了两个配置问题，但一个我让它启动即崩、一个只警告。标准是：**必崩且下游报错间接的 fail-fast**（配了云档没配 key），
  **可自愈、甚至可能是用户有意配置的只警告**（时区与库不一致）。而且警告只发一次——稳态缺失每秒刷一遍，日志就没法看了。"

### K-53 机器判据自己的"快照"会过期：不重跑快照，"死配置=0"就是自己骗自己

- **现象**（T4.12 体检）：`配置清单.md §2` 的 `$appKeys` 快照写着"**36** 个键，新增配置必须同步加进列表"，但 yml 实际已是 **40** 个叶子键
  （T4.7 的 2 个 `app.limits.*` + T3.11 的 2 个 `app.llm.ollama.max-tokens/timeout-sec` 没登记）；§3"计划中"表里 `app.base-url` 还写着"现在填了不起作用"，
  而 T4.6 起它已被消费。**如果这轮只照着 36 键跑判据，会漏查 4 个键，还会以为 `app.base-url` 是死配置**。
- **根因**：机器判据是"人对配置的认知"的快照——**配置在长，快照不会自己长**。更隐蔽的是：快照里多出来的"计划中"条目会**掩盖**真实孤儿（因为大家都以为"大家都知道它没用"）。
- **规则**：①体检卡必须**先重跑机器判据、再对照快照**，两边不一致时**改快照**并注明日期与差额（本轮 36→40，另 `$allowed` 增加 `TZ`）；
  ②"计划中"表必须**逐条能对上任务号**，对不上就删行或修功能；③新增配置键 = 同一次 commit 里更新 `$appKeys`（否则下次体检又漏）；
  ④判据卡自己也要有输出落盘（K-43），不能"我跑过了，没问题"。
- **面试 30 秒**："做配置体检时我发现，我们那个'死配置反查'脚本里写死的键快照早就过期了——36 个 vs 实际 40 个。最危险的不是漏查，
  而是**快照里过期的'计划中'条目会让真正的死配置看起来很正常**。所以体检前我先重跑判据、把快照对齐到 40，并让'计划中'每一条都能报出对应任务号。
  **校验规则的元数据也会漂移，得和配置一起体检。**"

### K-54 `edit` 工具会吃掉 PowerShell 脚本的 UTF-8 BOM；PS 5.1 按 ANSI 读中文注释就解析崩

- **现象**（T4.12 验收收尾，我给 `tools/check-maintainability.ps1` 的 `$allowed` 加 `TZ`）：改完后脚本报
  `Unexpected token '}' in expression or statement`，指向毫不相关的第 13 行 `}` 和第 99 行 `` "`n" ``；但用 `PSParser.Tokenize` 检查却是 **0 错误**。
- **根因**：该脚本原本是 **UTF-8 with BOM**；`edit` 工具重写文件时**去掉了 BOM**。Windows PowerShell 5.1 对**无 BOM 的 .ps1 按系统 ANSI（GBK）解析**，
  文件里的中文注释/字符串被拆成乱码字节，某些字符吃掉引号/换行 → 解析错位，报错行号完全误导。`PSParser` 走的是另一条读取路径（.NET 按 UTF-8），所以显示"0 错误"。
- **危害**：报错行号全错（指向无关的行），很容易去改"看起来有问题"的代码，越改越乱；而且**同一文件在 `pwsh 7` 下正常、在 `powershell 5.1` 下崩**，换工具就复现不了。
- **规则**：①**含非 ASCII 的 `.ps1` 必须带 UTF-8 BOM**（与 `.env`/Java 源码"禁 BOM"相反，别搞混——那条针对的是被程序读取的纯值/源码，BOM 会变成首字符；这里是给 PS 解析器看的）；
  ②用 `edit` 工具改过 PS 脚本后，**必须**跑一次 `powershell.exe -File …` 真执行（或至少 `-Command` 直接 `&` 调用），不能只做静态检查；
  ③同类问题判据：报错行号与改动位置不相关 + 文件含中文 → 先查编码/BOM，再怀疑语法。
- **面试 30 秒**："我给自检脚本加一个豁免项，改完脚本直接报解析错误，而且报错指向我根本没动的行。静态解析器又说零错误。最后发现是编辑器重写文件时把 UTF-8 BOM 去掉了——
  Windows PowerShell 5.1 对无 BOM 脚本按 GBK 解析，中文注释把引号吃坏了。教训是：**报错位置和改动位置对不上时，先怀疑编码，不是语法**；
  改完脚本要真跑一遍，不能只看解析器。"

### K-55 "已排期"不是"已跑完"：异步/自动化的验收只认执行证据

- **现象**（T4.14 验收）：聊天里说"凌晨 00:10 的全量测试自动化也同步指向了新 commit"，听起来像"全量已经绿了"。核对后发现：
  WorkBuddy 的 memory 文件里写的是**待办**——`00:10 自动化（id 52235e59）跑全量 235/235 + 上传冒烟`，只是把自动化的 **HEAD 校验值**改成了新 commit。
  当时 18:10、配额 50/50、产物目录 `post-midnight\` 不存在、也没有 235/235 的日志。**"计划已排期"被口语转述成了"已经跑了"**。
- **根因**：异步任务/定时自动化的"可观测面"是**排期对象**（任务 id、HEAD guard），不是**执行结果**（日志、exit code、产物、时间戳）。两者在转述链里极易混淆；
  而验收的判据必须是后者——否则明天代码一改，"昨天的绿"会被错记到今天的头上。
- **危害**：把未跑的验证记成已跑 → 假绿进入发布；等真出问题时才发现"那次全量测的是 3 个 commit 之前的代码"。
- **规则**：①验收只认**执行证据四件套**：运行时间戳 + 命令 + 输出/exit code + 产物路径（且产物里的 HEAD 要等于被验收的 commit）；
  ②"已排期/已同步 HEAD/自动化会跑"一律记为**待办**，不算通过；③让自动化把 `git rev-parse HEAD` 与产物一起落盘，验收时对一次；
  ④转述自动化状态时用固定措辞："已排期（未执行）" / "已执行（证据在 X）"，禁止含糊。
- **面试 30 秒**："有次我们的定时任务被说成'凌晨会跑全量'，传到我这里变成'全量已经绿了'。我核对产物目录发现根本没有那次的日志——它只是被排期了。
  从那以后我定死：**排期不算验证，只认带时间戳、exit code 和 HEAD 的执行证据**；自动化产物里必须落当天 HEAD，不然'绿'可能属于上一版代码。"

### K-56 视觉验收要"看 + 量"：看着高级 ≠ 可达性达标

- **现象**（T4.14 验收）：新 UI 截图看一眼挺高级（暖纸底/排印/单一暖黄），但用浏览器 computed style 一量：`.hint` 文字 `rgb(138,138,147)` on `rgb(248,246,239)` = **3.16:1**，
  **低于 WCAG AA 正文 4.5:1**。`.hint` 恰好是全站说明文字/元信息的主力 class——"看起来淡雅"就是"读起来费劲"。而徽章绿 4.56:1 只是勉强过线。
- **根因**：**审美判断和对比度是两套尺子**。设计师/模型都会被"低对比=高级"的排版风潮带偏；而可达性是**可计算的标准**，不量就发现不了。
- **规则**：①视觉验收固定加一条机器判据：用浏览器/工具批量量关键文字与背景的对比度（正文 ≥4.5:1、大字号 ≥3:1），把数值写进报告；
  ②"单一 accent 极省用量"必须配"文字颜色落在 accent-deep 上"（黄底白字几乎必挂）；③截图矩阵证明"布局没坏"，**不能**证明"能读"；
  ④低对比修复优先做 token 级（改一个 `--ink-3` 全站生效），不要逐处打补丁。
- **面试 30 秒**："新版界面我先看截图觉得挺高级，但验收时我用浏览器量了一下次要文字的对比度——3.16:1，WCAG 要求 4.5，直接不达标。
  那次我学到：**视觉验收要'看 + 量'**，截图只能证明布局没坏，证明不了能读。现在我们的 UI 验收会带一个对比度脚本，把每个关键 token 的数值打出来。"

### K-57 半透明底色的对比度必须先 alpha 合成：否则会算出 1.0 这种伪差

- **现象**（T4.14c 验收）：写码方加了 `.task-row:hover{background:rgba(26,26,26,.035)}`（3.5% 墨色），自测 hover 态对比度时直接拿
  `rgba(26,26,26,.035)` 的 RGB 当背景色去算，得到 **1.0 / 3.3** 这种"文字几乎看不见"的荒谬值；修正为**先把半透明色合成到下层白卡**（`255×.965+26×.035 = 247`）
  再算，得到 **16.25 / 4.93**（与我独立复测一致）。
- **根因**：对比度公式要求**两个不透明色**（相对亮度只对实色定义）。`getComputedStyle` 返回 `rgba(...,.035)` 时，后三位是"要往上叠的墨色"，不是渲染后的底色。
- **规则**：①量对比度前先判断 `background-color` 是否带 alpha：带则按 `c = fg*a + bg*(1-a)` 逐通道合成到**实际下层**（卡片/纸底/图片）再算；
  ②报告里写明"算的是哪一层"（K-50 的同一精神：数值必须说清口径）；③同一元素的正常态和 hover 态要分别量（底色变了，文字色没变也可能掉线）。
- **面试 30 秒**："给列表行加了一个 3.5% 的 hover 底色，自测对比度时算出 1.0——看着像文字消失了。排查发现是拿 `rgba` 的墨色当背景直接算，
  而对比度只对不透明色成立。把半透明色先合成到白卡上再算，数值就正常了（16.25）。**度量前先问：我量的这一层，真的是用户看到的那一层吗？**"

### K-58 后台作业的退出码可能不是子进程的退出码：证据要取真 ExitCode

- **现象**（T4.14c 验收）：我用 `pwsh -Command "...; powershell.exe -File scripts\test.ps1 -UnitOnly 2>&1 | Select-Object -Last 40"` 起后台作业，
  日志里明明写着 `[test.ps1] 用例数 225，mvn exit 0` / `BUILD SUCCESS`，但**作业本身报 `exit code: 1`**。
  改成 `Start-Process -PassThru -Wait` 直接取子进程 `ExitCode` → **0**。同一条命令，两个"退出码"。
- **根因**：外层是 `pwsh -Command` + 管道 + 原生程序 stderr 的组合，作业退出码由最后一层/宿主包装决定；中间脚本的真实退出码被吞掉或被 stderr 干扰。
  （同类现象：Windows 上被强杀的命令也会先报 exit 1 而无信号标记。）
- **规则**：①**要写进证据的 exit code，必须是目标脚本/测试进程自己的**：用 `Start-Process -PassThru -Wait` 取 `.ExitCode`，或至少把
  `$LASTEXITCODE` 在**同一层**落盘；②`BUILD SUCCESS` 与 exit code 同时记，两者不一致时先查包装层，别急着判定"测试失败/通过"；
  ③后台作业只用来跑，最终判据回到前台/脚本内的真实退出码（配合 K-43"命令输出要落盘"）。
- **面试 30 秒**："有次验收，日志里 `BUILD SUCCESS`、`mvn exit 0` 都在，但后台作业报 exit 1。我没直接采信任何一方，改用 `Start-Process` 拿子进程真实退出码，
  确认是 0——错误出在我的包装命令上。**做验收时，'谁说的 exit code'和 exit code 本身一样重要。**"

### K-59 改了设计 token 不等于改完：必须 grep 全部使用点逐一量

- **现象**（T4.15 验收）：T4.15 新增的「示例数据」徽章复用了既有颜色对 `--accent-deep #a16207` on `--accent-tint #fdf4d9`；我用 Playwright 量到 **4.48:1 < WCAG AA 4.5**（12px 文字）。
  进一步 grep 发现这个颜色对早在 T4.14 就被 `.chip`（关键词胶囊）和 `.badge.busy` 使用——**我上次验收只量了 hint/badge.done/task-name/nav，漏了 chip**，于是"不达标"被带到了这一轮。
- **根因**：①色值达标与否取决于**前景+背景的组合**，同一个 token 在不同底色上是不同结论；②"新增元素"和"复用 token 的旧元素"共享风险，但验收清单通常只写新元素；
  ③自报的"新增文字全部 ≥4.5"只覆盖它量过的元素，未覆盖复用点。
- **规则**：①**改/复用语义色 token 时，先 `grep` 全部使用点，逐个量"前景 vs 实际底色"**（K-57 的 alpha 合成口径），把使用点清单写进报告；
  ②验收清单按"**新增元素 + 复用该 token 的旧元素**"两类分别列；③token 级修复优先（改一处全站生效），但必须回归确认没有把别的组合改坏；
  ④"示例/诚实标签"这类文字本身就是功能（要被人读到），不能当装饰放过。
- **面试 30 秒**："给示例数据加了个黄色小标签，自测量出来 4.48:1，差 0.02 不到 AA。追下去发现这个颜色组合在两个月前的改版里就被关键词胶囊用了，当时验收漏量。
  我后来把规则改成：**改语义色 token 先 grep 所有使用点，逐一量前景和真实底色**——因为一个 token 在卡片上和在黄色底上，是两回事。"

### K-62 交接链上"谁执行的"会被抹掉：自动化证据必须回到系统记录核对

- **现象**（T4.15c）：写码方在回报里"顺带汇报：凌晨自动化状态——**跑了**，且有执行证据：09:58 补触发……全量吃 3 任务"。
  但我去查 `C:\Users\ljh\.workbuddy\workbuddy.db` 的 `automations` 行：`status=ACTIVE`、`scheduled_at=2026-11-16T00:10`、**`last_run_at=null`**；
  `artifacts\T4.15\post-midnight\` 里也只有我自己写的 `run-full.ps1` / `head.txt` / `full-test.log`。那次 09:58 的全量是 **Lead 手动跑的**，被转述成"自动化补触发"。
- **根因**：①证据只记了"结果"，没记"**谁发起、什么触发的**"；②经过"Lead→用户→写码方→回报"的转述链，执行主体被抹平；
  ③"补触发""跑了"这类词自带"计划执行"的心智暗示，和"人手动执行一次"的可信度不是一回事（K-55 排期≠执行的延伸）。
- **修复/规则**：①凡落盘证据必须带**三要素：执行者/触发者、时间、完整命令**（不能只有结论和 exit code）；
  ②验收侧遇到"自动化执行过"类声明，**一律回到系统记录核对**（`automations.last_run_at`、日志里的启动行、目录/文件的创建者与时间），不采信叙述；
  ③区分"计划触发"与"手动执行一次"，报告里分别写清。
- **面试 30 秒**："写码 AI 汇报说'凌晨的自动化跑了，有全量证据'，我查数据库发现那行自动化 `last_run_at` 还是 null——那次全量其实是我自己手动跑的，
  只是中间人转述时把执行主体说没了。**所以证据必须写清是谁、什么时候、用什么命令跑的**；'有日志'不等于'是它跑的'。"

### K-63 验证者不能碰被测物：Lead 越界写代码会污染基线

- **现象**（T4.15c）：空态文案是 10 分钟的小改动，我（Lead）顺手在 `task.html` 写了修复、还构建了 app 镜像准备自测；
  用户提醒"代码让 WorkBuddy 写，你负责验证"后，我撤掉改动并重建镜像对齐 HEAD（`fb93469`）。若没撤回，写码方的 commit 会含我的代码，且"独立验收"名不副实。
- **根因**：①小改动带来的"顺手做完"冲动；②验证者与被测物同源，是验收的大忌（不能自己 review 自己）；③没有"提交前先看 `git status` 是否干净"的习惯动作兜底。
- **修复/规则**：①Lead 只写任务卡 / 验收报告 / 文档 / **artifacts 下的实验脚本**，产品代码一律由写码方写；
  ②验证开始前必须确认：工作区 `git status` 干净、HEAD 已知、镜像/容器确实来自该 commit（**"服务端文件 sha256 == 工作区文件 sha256"** 这条判据能兜住）；
  ③自己的实验脚本只放 `D:\new\artifacts\`，不进仓库、不进 commit。
- **面试 30 秒**："有次我作为验收方，顺手把小 bug 修了——这其实是验收大忌：**验证者不能碰被测物**，否则你验的是自己的代码。
  我改回来并重建镜像，从此固定动作是：先确认工作区干净、镜像来自该 commit，再开始验。"

### K-64 A/B 实验撞上产品幂等：`reused:true` 会静默复用旧任务，"以为跑了其实没跑"

- **现象**（T4.16）：切到 medium 后重新上传同一批文件跑"模型对比"，接口返回 201，但响应里 `reused:true`、`task_id` 还是 small 档的 `217/218/219`——**ASR 根本没跑**，差点把"两档结果一样"写成"medium 与 small 质量相当"。
- **定位**：看上传响应里的 `reused` 字段和 `task_id` 是否新值；产品按 `(user_id, content_hash)` 唯一约束做幂等（同字节文件重复提交直接复用），与模板、模型配置无关。
- **修复/规则**：①任何"同内容多配置"的对比实验，**先确认本次真的产生了新任务**（新 `task_id` + `reused:false`）；②要绕过幂等就换**文件字节**（转码/去元数据/加元数据块），不要试图改模板或配置；③"实验结果相同"要先排除"实验根本没执行"。
- **面试 30 秒**："做模型对比时，上传接口返回成功，但我一看 `reused:true`、任务号还是旧的——产品的幂等设计把第二次实验整个吞了。差点得出'两个模型差不多'的错误结论。**对比实验的第一件事是确认实验真的跑了**：新任务号 + 非复用标记。"

### K-65 对比实验必须证明"输入相同"：用 PCM md5 而不是"看起来一样"

- **现象**（T4.16）：为了让两档真跑，我造了 tier2/tier3 两套文件（wav 转换、mp4 只去元数据），文件大小与 sha256 都不同——如果只靠"都是同一段录音"，质量差异可能来自转码，结论就不可信。
- **修复/规则**：①对音频类对比实验，**解码成同一格式后算 PCM md5**，证明"进入模型的采样完全一致"（本次 tier2/tier3 三段 PCM md5 与原始全等，sha256 不同）；②报告里同时写"文件不同字节"和"输入 PCM 相同"两句话；③凡是"改变输入表示"的步骤，都要有一句"这一步不影响被比较的内容"的证据。
- **面试 30 秒**："要比较两个 ASR 模型，我先解决'输入必须一致'：两套文件字节不同（为了绕过内容去重），但解码出的 PCM 哈希逐字节相同——这样差异只能来自模型，而不是我转码转坏了。"

### K-66 同一模型两次输出差异巨大：没有固定 temperature 的结构化结果不可复现

- **现象**（T4.16）：同一份转写稿（逐字相同）两次结构化，待办 **0 条 vs 5 条**、摘要相似度 **0.47**；另两个样本 13 vs 18 条、相似度 0.52/0.76。云档 `temperature` 从未显式设置（本地 Ollama 档反而写了 `0.0`）。
- **修复/规则**：①验收"内容质量"前先测**方差**（同输入跑两次，量化差异），否则单次对比可能全是噪声；②结构化/抽取类任务必须**显式固定 temperature=0.0**（默认值是给聊天场景的）；③把"结果可复现"写进验收判据，而不是只测一次"看着不错"。
- **面试 30 秒**："同一段转写，两次生成的待办一个 0 条一个 5 条——查出来是云档没设 temperature。**做质量验收前先测方差**：如果同一输入自己都不稳定，那么'模型 A 比 B 好'的结论可能只是抽签。"

### K-67 清理临时容器时用 `docker ps | rm -f` 全量管道，把整个栈删了

- **现象**（2026-11-16，T4.17 找会议素材时）：为了清掉残留的临时转写容器，我执行了
  `docker ps --format '{{.Names}}' | ForEach-Object { docker rm -f $_ }` —— 一瞬间 app/asr/postgres/redis/minio **5 个容器全被删除**，服务中断。
- **定位/后果**：`docker ps` 输出的是**全部运行中容器**，管道里没有做名字过滤；`docker rm -f` 只是删容器，**数据卷（pgdata/redisdata/miniodata）没删**（没加 `-v`）。

### K-71 把子列表移进"整块可点击"的容器：键盘 Enter 被容器吞掉、detached 元素穿透 closest() guard

- **现象**（T4.20 修上传交互）：把已选文件列表移进拖拽框 `#dropZone` 后，点移除按钮的**键盘 Enter** 会打开文件选择器而不是移除文件；鼠标点移除虽然能删，但事件继续冒泡，有时也会把选择器打开。
- **定位**（写码方用事件日志实锤）：①`dropZone` 的 `keydown` 里 `Enter/空格 → preventDefault() + fileInput.click()`，移除按钮的 Enter 冒泡上来后被容器处理，按钮的原生 click 合成被吞；②按钮 click 先删 DOM，再沿旧路径冒泡，此时 `e.target` 已 detached → `e.target.closest('#fileList')` 返回 `null`，原来"在列表内就忽略"的 guard 被穿透。

- **面试 30 秒**："把文件列表移进可点击的上传框后，键盘按 Enter 删文件变成了打开文件选择器。原因有两层：容器的 keydown 把 Enter 吞了，以及按钮删掉 DOM 后事件冒泡时 target 已经 detached，`closest()` 返回 null 把 guard 穿透了。修复是加来源判断 + stopPropagation + `contains()` 兜底，并且用 `filechooser` 事件做断言，而不是只看 DOM。"

### K-72 "部分路径漏分支"：3 个删除入口只有 2 个清 MinIO，DB 干净但对象存储留孤儿

### K-73 手写 HTTP 客户端 POST JSON 不带 `Content-Type` → Spring 直接 415（不是 400）

- **现象**（T4.21 写码方自验）：用 python urllib 调 `POST /api/v1/tasks`（PASTE）返回 **415**，一开始以为是接口/参数问题；补上 `Content-Type: application/json` 立刻成功。同一天我复核 `POST /tasks/delete-failed` 时不带 body/头也得到 415（端点声明了 `consumes=application/json`）。
- **根因**：Spring 的 `@PostMapping(consumes = APPLICATION_JSON_VALUE)` 在**读 body 之前**就按请求头匹配；urllib 默认不带 `Content-Type`（或带 `application/x-www-form-urlencoded`）→ `HttpMediaTypeNotSupportedException` → 415 `UNSUPPORTED_MEDIA_TYPE`，错误信息里通常**不会告诉你缺哪个头**。
- **修复/规则**：①脚本里手写 JSON 请求一律显式写头（`Content-Type: application/json`；curl 用 `-H`；urllib 用 `Request(..., headers=...)`）；②看到 415 先查请求头而不是参数/鉴权；③无参数的 POST 端点也要求 `{}` body 时，文档要写清（本次 `接入指南.md` §3.6a 已写"body 空 JSON `{}`"）。
- **面试 30 秒**："自己写脚本调 PASTE 接口一直 415，以为是参数错。其实 Spring 在 `consumes=json` 时会先按 Content-Type 匹配，urllib 默认不带头，所以请求还没进方法就被拒了。补上 `Content-Type: application/json` 就通。**415 先看头，400 才看参数。**"

### K-75 Playwright route 的 URL glob：`*` 不跨 `/`，`**/api/v1/tasks*` 拦不住 `/tasks/batch`（假绿/真后端）

- **现象**（T4.22 验收，我自己的复核脚本）：想用 `page.route('**/api/v1/tasks*', ...)` 拦截所有上传请求做 0 配额验证。单文件 `POST /api/v1/tasks` 能拦住，**批量 `POST /api/v1/tasks/batch` 却没拦住** → 两个真请求打到了后端容器；测试里"批量请求体"断言因此失败（body 为空），而页面其实显示成功（真后端返回 200 reused）。
- **定位**：Playwright 的 URL glob 里 `*` **不跨 `/`**、`**` 才跨。`/api/v1/tasks*` 只能匹配 `tasks` 后面不含斜杠的内容，`/batch` 匹配不上。改成 `**/api/v1/tasks**`（或分别注册 `/tasks` 与 `/tasks/batch` 两条路由）即全部拦住。

- **修复/规则**：①mock 类验证**先断言"请求数/URL"再断言 body**，发现某条路由没被拦立刻停；②glob 用 `**` 或显式两条路由；③**验收前明确"这轮不许产生真实副作用"**（0 配额卡），脚本跑完立刻查 `task` 计数与配额、MinIO 对象；④把"reused 幂等"当兜底而不是许可证——它只保证不重复处理，不保证不产生请求。
- **面试 30 秒**："做 0 配额的前端验收，我用 Playwright route 拦截请求，结果 glob 写成了 `tasks*`——Playwright 里 `*` 不跨斜杠，批量端点 `/tasks/batch` 没被拦住，两个真请求打到了后端。好在后端有 content_hash 幂等，命中已有任务没扣配额。修法是 `**` 或显式两条路由，并且 mock 验证要先断言路由命中、再断言请求体。"

### K-76 "匹配纯数字就 parseLong"：20 位数字 `q` 直接 500，违反"参数非法 → 400"契约

- **现象**（T4.24 验收，我自写 API 探针顺手加的边界用例）：服务端搜索 `q` 对纯数字会额外精确匹配任务 id。正常 `q=82` 没问题，但 `q=99999999999999999999`、`q=9223372036854775808`、`q=123456789012345678901234567890`（20～30 位，都 ≤100 字所以过了长度校验）**全部 500 `INTERNAL_ERROR`**；`q=9223372036854775807`（Long.MAX 边界）和 `q=007` 正常 200。
- **定位**：`q.matches("\\d+")` 只证明"全是数字"，不证明"能放进 long"；随后 `Long.parseLong(q)` 抛 `NumberFormatException`，全局异常兜底成 500。写码方的单测只测了正常数字与超长字符串，**边界值（max / max+1）没测**。
- **修复/规则**：①凡是"字符串 → 数值"的分支，`matches`/正则之后还要**试解析或长度前置判断**：`try { Long.parseLong } catch (NumberFormatException) → 不参与数值匹配`（不要让它变成 500）；②边界测试固定四件套：`0`/正常值/`MAX`/`MAX+1`（本轮补成单测 2 例）；③"参数非法 → 400"的契约不允许被 500 兜底，错误码矩阵里 5xx 只留"真内部故障"。
- **面试 30 秒**："搜索参数是纯数字时会顺带按任务 id 精确匹配，结果有人输入 20 位数字，`Long.parseLong` 溢出抛异常，接口直接 500。测试只覆盖了正常数字和超长字符串，漏了数值边界。修法是解析失败就退化成普通关键词匹配（不 400 也不 500），并把 `MAX`/`MAX+1` 加进单测边界四件套。**'格式对'不等于'范围对'，参数校验要测边界。**"

- **复发（T4.27 验收，D-134）**：同一个坑第二次出现——新的 `GET /tasks/export?ids=` 端点里 `value.matches("\\d+")` 后直接 `Long.parseLong`，20 位纯数字 → **500**（`ids=99999999999999999999/9223372036854775808/1,99999999999999999999`）。说明"只写进复盘、没进开发 checklist"的规则等于没写 → 已按 AGENTS §3 沉淀阈值写进 `rules/dev.md` 第 10 条（新增数字参数必须带 `0/正常/MAX/MAX+1/20 位/前导零超长` 矩阵，改完 grep `parseLong|parseInt|valueOf` 自检），并立 T4.27b 前置修。

### K-77 写码方"先跑全量、后 commit"：`head.txt` 记的是提交前的 HEAD，被测内容≠提交内容

- **现象**（T4.24 验收）：写码方回报"build/up 后全量 296/296，K-68 head `1b5cba0`"——但被验 commit 是 `7a4fc30`。看时间戳：`full-test.log` 22:01:57、`head.txt` 22:03:28、commit 22:03:23 → **先测试后提交**。docker 侧 HEAD 仍是旧的 `1b5cba0`，所以它自己标的 head 是对的，只是这份证据**证明不了"提交内容跑过全量"**。

### K-84 SSRF 防护里"数字字面量 IP"不能只靠系统解析器：JDK 21 把 `0177.0.0.1` 按十进制解析成公网 `177.0.0.1`，缩写八进制会漏

- **现象**（T4.32a 执行中，写码方自测发现）：SSRF 守卫按"解析出的 IP 是不是内网"来拦，常规域名/十进制 IP 都对；但 `http://0177.0.0.1/` 这种**前导 0 的八进制缩写**没被拦——系统解析器（`InetAddress.getAllByName`）按**十进制**把它归一化成 `177.0.0.1`（公网），于是守卫认为"这是公网地址，放行"。
- **定位**：多数客户端（curl/浏览器/部分 HTTP 库）按 **inet_aton 语义**解释数字主机名：`0177` 是八进制 127、`0x7f` 是十六进制、`127.1` 是缺段、`2130706433` 是 32 位整数——都指向 `127.0.0.1`。而 JDK 21 出于安全**改变了解析规则**（不再把前导 0 当八进制），于是"校验时的解析结果"和"真正连接时的目标"不一致。另外 `0x7f.0.0.1`、`127.1` 在 Java 里更早一步就被 `URI.getHost()` 判成非法 host（返回 null），根本走不到解析。
- **修复/规则**：①只对"纯数字字面量 host"（含十进制/`0x`/前导 0/缺段）在守卫内部**自己按 inet_aton 语义规范化**成 4 字节地址再判，仍然"算出真正会连的地址再判"，**不是字符串黑名单**；②域名才交给系统解析器，且**每个解析结果都要判**（多 A 记录混一个内网也拒）；③缩写形式的边界要写进单测矩阵 + 真机反例（十进制/八进制/十六进制/缺段四种）；④别假设"语言运行时现在的解析行为"和"客户端实际连接行为"一致——安全校验要按**最宽松解释**（攻击者能用的那种）算一遍。
- **面试 30 秒**："做 SSRF 防护时我先按'解析出什么 IP 就拦什么'写，常规用例全绿。但前导 0 的八进制 IP 没被拦：JDK 21 出于安全把它按十进制解析成了公网地址 `177.0.0.1`，而 curl/浏览器实际上会把它当八进制，连到 `127.0.0.1`。也就是**校验时看到的目标和真正连的目标不是同一个**。修法是在守卫里自己按 inet_aton 语义把数字字面量规范化成四字节再判——仍是按真正目标判，不是维护一张字符串黑名单；配套把十进制/八进制/十六进制/缺段四种缩写都做成单测和真机反例。**安全校验不能依赖'运行时解析器现在的怪癖'，要按攻击者客户端的解释算一遍。**"

### K-85 宿主测试服务只监听 IPv4 时，容器里 `host.docker.internal` 可能解析成 IPv6 → Connection refused；Windows 上 `IPV6_V6ONLY=0` 必须在 bind 之前设置

- **现象**（T4.35a 真机验收）：想在 ASR 容器里直接 `curl -F file=@... http://localhost:8000/v1/audio/transcriptions` 验原始响应，结果 **`curl: not found`**；改用 git-bash 拼 `docker exec ... python /tmp/probe.py` 时，容器里报找不到脚本——路径被 MSYS 自动转换了。

- **规则**：①容器里没有 curl 就用**镜像自带的语言**发请求（python `urllib` 手拼 multipart 即可；本仓库 ASR 镜像自带 python）；②在 git-bash 里跑 `docker exec` 传容器内绝对路径时加 **`MSYS_NO_PATHCONV=1`**，或干脆用 PowerShell（本题就是 PS 下正常）；③探针文件优先 `docker cp` 进容器再执行、用完删除，别在容器里留文件（D-139 残留纪律）。
- **面试 30 秒**："真机验 ASR 契约时，容器是 slim 镜像没有 curl；我改成用镜像自带的 python 手拼 multipart 打接口，就能拿到原始 JSON。又踩了一个 Windows 坑：git-bash 会把命令行里的 `/tmp/xxx` 自动转换成 Windows 路径再传给 docker，容器里就找不到文件了，要么加 `MSYS_NO_PATHCONV=1` 要么直接用 PowerShell。**验证工具也要适配最小镜像和宿主 shell 的怪癖，不然会把环境问题误判成产品问题。**"

### K-87 MinIO 数据目录里的 `part.1` 是 bitrot 编码，不是原始对象字节：直接 sha256 比对会假红

- **现象**（T4.35b 真机验收）：要证明"HTTP 音频流返回的字节 == MinIO 里存的字节"，直接读 `/data/meetingnotes/tasks/<id>/<name>/xl.meta`/`part.1` 算 sha256，与 HTTP 响应首 1KB 的 sha256 **不一致**，一度怀疑流出了错字节。
- **定位**：MinIO 的对象在磁盘上不是裸文件——`part.1` 等是内部**编码/bitrot 校验**格式（含校验和与分块元数据），不是对象原始内容；只有走 S3 API（`mc cat`、SDK `GetObject`）拿到的才是原始字节。
- **规则**：①**别直接读 MinIO 数据目录做字节比对**，用 `mc cat`（S3 API）或与"上传源文件字节"比；②"存储侧对照"要么走被测协议（HTTP）要么走对象存储 API，**不要用存储的内部落盘格式当真相**；③这条与 K-50（字节保真）、D-074（数字/证据交叉验证）同一族：**对不上先怀疑比较口径，再怀疑产品**。
- **面试 30 秒**："验音频流时我想证明 HTTP 返回的字节和 MinIO 里存的一致，就直接读 MinIO 数据目录里的 part 文件算 sha256，结果对不上，差点以为流写坏了。原因是 MinIO 落盘的是带校验和的内部编码格式，不是对象原始字节。换成走 S3 API（mc cat）读，或者干脆和上传时的源文件比，就逐字节一致。**存储的内部落盘格式不能当真相，要比就比协议层或对象存储 API 层。**"

### K-88 播放/seek 类进度断言必须"先暂停再读"：点句会自动播放，等一会儿读 currentTime 会把"正在播"误判成"seek 不准"

- **现象**（T4.35c 执行中，写码方首轮自测红）：Playwright 点第 3 句（`start=8.0`）后等 1200ms 再读 `audio.currentTime`，得到 **8.55**，超过 ±0.5s 阈值 → 差点当成 seek 实现有问题。
- **定位**：点句逻辑是"`currentTime = start` **+ `play()`**"（用户手势内合法），所以读的时候音频已经**真实播放了 0.55s**——不是 seek 不准，是断言没有控制播放状态。
- **规则**：①**任何"位置/进度"类断言先把被测状态冻结**（`audio.pause()` 后再读 `currentTime`；或读"seek 目标是否被命中"而不是"当前时刻"）；②断言时间容差要说明是在**暂停态**还是**播放态**下成立（播放态容差应 ≥ 读延迟，且要扣掉已播放时长）；③这类假红先问"是产品错还是我的观测时机错"，改口径后 8.000 精确命中；④同族：滚动位置、动画进度、轮询计数都同理——**观测前先让状态稳定**。
- **面试 30 秒**："验播放器点句跳转时，我点了第 3 句、等 1 秒多读 `audio.currentTime`，得到 8.55 而目标是 8.0，看着像 seek 偏了。其实点句会顺带自动播放，读数时音频已经在放；暂停后一读就是精确的 8.000。**验收进度类行为，必须先把播放/动画状态冻结再读数，否则测的是'时间流逝'不是'跳转正确性'。**"

### K-89 卡面里的列名/字段名先对真实 schema 再落 SQL：`task_result` 没有 `updated_at`，照抄会让 PATCH 500；单测构造 null 值不能用 `Map.of`

- **现象**（T4.36 执行中，写码方照卡面写）：卡面要求"只更新 `speaker_map` + `updated_at`"，但 `task_result` 表**实际没有 `updated_at` 列**（`\d task_result` 只有 `created_at`，V1 建表如此）。若照抄 SQL 会直接运行期报错（列不存在 → 500）；写码方改为按既有 `saveTranscript` 同口径落 `created_at = now()` 并在回报/文档说明，**未为此新建迁移**。同卡两处小坑：单测构造"值为 null 的 map"用 `Map.of` 会抛 NPE（`Map.of` 不收 null），要用 `LinkedHashMap`；"20 字标签"恰好等于上限（合法），21 字才该拒——首轮测试先红后修正。
- **定位**：卡的契约字段是**语义描述**（"要记更新时间"），不等于真实列名；表结构里没有该列时有两种选择——①加迁移补列（本卡禁止、且为一个"谁也没读"的时间戳不值）②按既有同类写路径的口径落现有列。正确做法是先把"这张表到底有哪些列"查实，再决定，并把最终口径**写进接口文档**，别默默少更新一个字段。
- **规则**：①**卡面/文档里的列名、字段名、配置键，落 SQL/代码前先用真实 schema 核对**（`\d 表`、`SELECT * ... LIMIT 0`、迁移文件），不一致就按"语义"落地并回报差异；②"卡面没写、但表里没有"的字段不要硬造——**能加迁移才加，禁止期内按既有写路径同口径处理并写文档**；③Doc 与实现不一致时**优先修文档口径**，别让下一手按错列名再踩；④单测造数据注意语言约束（`Map.of`/`List.of` 不收 null、int 溢出），边界值要**两侧都测**（上限恰好合法、上限+1 才拒）。
- **面试 30 秒**："任务卡上写'更新 speaker_map 和 updated_at'，我照着写 SQL 前先 `\d task_result` 看了一眼——这张表根本没有 updated_at，只有 created_at。如果照抄，这个 PATCH 上线就是 500。我按项目里既有的转写写入口径落 created_at，没为它单开迁移，并把这个口径写进接口文档。**卡面是需求语义，不是数据库列名；写 SQL 前先对真实 schema。**" 同一张卡还踩了两个测试小坑：`Map.of` 不收 null（要 `LinkedHashMap`）、'20 字上限'恰好合法要测 21 字才红——**语言/协议的边界约束要按语言实际行为测。**

### K-90 请求身份 ThreadLocal 只在请求线程有效：`StreamingResponseBody`/异步回调/worker 读它必炸；全量 E2E 才是这类横切改动的真正判据

- **现象**（T4.37a 执行中）：把"单用户 `DEFAULT_USER_ID=1`"换成每请求身份 `UserContext`（ThreadLocal）后，`-UnitOnly` 与可维护性全绿；但**全量 E2E 首轮红**——zip 导出 500、一个任务卡 RUNNING。日志显示 `TaskZipExportController` 的 `StreamingResponseBody` lambda 在**异步线程**执行时读 `UserContext.current()` 抛 `IllegalStateException`（ThreadLocal 只属于请求线程）。worker 里的 `StructuringService` 同理（写码方已按卡面改成按 `taskId` 查 `user_id`）。
- **定位**：`UserContext` 故意"未设置就抛异常、不静默回退 1"，所以漏掉的异步路径会显式失败（这是对的）。zip 的修法：**在请求线程先 `UserContext.current()` 取出 userId，作为参数显式传进 lambda**；worker 链路：`SELECT user_id FROM task WHERE id=?` 解析归属，查不到给空/跳过。
- **规则**：①**ThreadLocal 只给请求线程用**；任何流式响应、`@Async`、线程池任务、消息/回调、定时任务都不能依赖它，必须显式传参或按业务 id（taskId）反查；②换横切身份模型时，**单元测试全绿不算数**——必须让全量 E2E 跑一遍（流式/异步路径只有那里覆盖），K-68 的"改契约先 commit→build/up→全量"再次救场；③"未设置就抛异常"要保留，**禁止静默回退默认用户**（否则漏改的端点会悄悄越权）。
- **面试 30 秒**："把单用户硬编码换成每请求用户上下文时，单元测试全绿，但全量 E2E 立刻挂了——因为 zip 导出用的是 `StreamingResponseBody`，lambda 跑在异步线程，ThreadLocal 里根本没有当前用户。修法是请求线程先取用户、再显式传进 lambda；worker 链路则按 taskId 反查归属。**ThreadLocal 不是跨线程的，横切身份改动必须用包含异步路径的端到端测试兜底，而且未设置时宁可抛异常也不要静默回退默认用户。**"

### K-91 并发同名注册把"唯一约束"变成 500：契约写 409 就必须在写路径兜住 `DuplicateKeyException`，顺序测试全绿不等于契约成立

- **现象**（T4.37a 我验收时实测）：`POST /api/v1/auth/register` 同用户名 4 路并发 → `[500 INTERNAL_ERROR, 200, 500 INTERNAL_ERROR, 500 INTERNAL_ERROR]`；顺序重复时正确返回 409 `USERNAME_TAKEN`，写码方单测也全绿。原因是 `register` 先 `SELECT` 查重（`requireUsernameFree`）再 `INSERT`，两个请求同时通过查重后，后到者撞 `ux_app_user_username` 唯一索引 → `DataIntegrityViolationException` → 全局 500。
- **定位**：唯一性由**数据库唯一索引**保证，而"先查再插"的查重只是**易用性前置**；并发窗口内必须由 INSERT 的异常兜底。前端注册按钮双击/自动重试都能触发。
- **规则**：①**契约写"重复 → 409"，写路径就必须 catch 唯一键冲突**（Spring/JdbcTemplate 的 `DuplicateKeyException`）并映射为 409；只吞唯一键冲突，**别吞所有 `DataIntegrityViolationException`**；②"先查重再插入"永远只能当提前提示，**不能当作并发安全的保证**；③**顺序测试全绿 ≠ 契约成立**：涉及唯一性/幂等的写接口，验收要补**并发探针**（本卡 4 路并发一测即现）；④同理适用于首访认领/抢注类流程——用条件 `UPDATE ... WHERE 旧状态` + 检查影响行数做原子化。
- **面试 30 秒**："注册接口我单测'重复用户名返回 409'是全绿的，但验收时用 4 个并发同名请求一打，3 个返回 500。因为代码是先查重再插入，并发窗口里两个请求都通过查重，后到的撞了数据库唯一索引，异常一路冒成 500。修法是在 INSERT 处捕获唯一键冲突映射成 409，只吞这一种。**唯一性是数据库保证的，'先查再插'只是体验优化；契约里的错误码必须在并发路径也成立。**"

### K-92 前端"多步跳转"验收的断言时机：URL/登录态断言必须在跳转发生当时取快照

- **现象**（T4.37b）：写码方 Playwright 用 `wait_for_url` 的 glob 匹配，被 `login.html?next=%2Ftasks.html` 里的 `next` **参数**误匹配（登录还没成功就"等到了"）；我自写探针把"登录后回跳 URL"的检查放在 helper 末尾，而 helper 内部最后一步已执行退出（logout），读到的自然是 `login.html` → 误报 B/F 类失败。两次都不是产品缺陷，是**断言取值时机**问题。
- **规则**：①跳转/重定向类断言，**在引发跳转的动作后立刻取 `page.url` 快照并返回给调用方**，不要放在会改状态的 helper 之后；②等待跳转的谓词只匹配 **path**（`urlparse`），不要用会包含 query 的 glob/子串（`next=` 参数天然包含目标路径）；③"退出/清理"必须排在断言之后；④探针失败先判断"是产品错还是断言语义错"——本卡两轮误报全是后者。
- **面试 30 秒**："用 Playwright 验收登录跳转，第一版一直红。查日志发现产品其实跳对了：一次是等待条件把 `?next=/tasks.html` 里的目标路径当成已跳转成功；另一次是断言写在 helper 后面，而 helper 最后一步是退出登录，读到的 URL 已是登录页。**跳转类断言要取动作发生当时的快照，等待谓词只匹配 path 不匹配 query。**"

### K-93 渲染页跑 impeccable detect 时，快照必须内联 CSS

- **现象**：用 `page.content()` 落盘的渲染快照交给 `npx -y impeccable detect`，报 `flat-type-hierarchy`（body/h1/h2 全 16px）假阳性 4 条，页面实际字号层级正常。
- **根因**：`page.content()` 只保留 `<link rel=stylesheet>` 引用，快照目录无对应 CSS；检测器读不到样式 → 按 UA 默认 16px 判层级。
- **修复**：落快照前把 `document.styleSheets` 的 `cssText` 拼成 `<style>` 内联进克隆的 `<html>` 再检测（内联后 0 条）。

- **现象**：T4.15 故障注入第一轮 8 项有 5 项"PASS"，实际上 `docker kill mn-drill-asr` 报 `cannot kill container: mn-drill-asr: No such container`（compose 实际名为 `mn-drill-asr-1`），脚本没断言退出码 → kill 是空操作、任务照常 DONE。同一脚本里 S2 `recovered=0`（中途 `login()` 换成了新用户，用别人 token 轮询旧任务 → TIMEOUT）、S3 `日志命中=0`（`logs()` 只取尾部 3000 字，启动期证据早被切掉）、S6 FAIL（`docker network disconnect` 断的是 app 与**整网**，重连 5s 就提交撞 `500 STORAGE_ERROR`，实测 50s 才自愈）。另外 `pwsh *> file` 重定向按本地代码页解码子进程 stdout，中文全乱码且不可逆（文件其实是 UTF-16）。

### K-106 `rm -rf /data/*` 不删隐藏目录：MinIO 恢复后健康检查 UP 但上传全 500
- **现象**：T4.16 在**全新卷**上验证异地恢复：`rm -rf /data/*` 后解包备份 → `docker compose ps` minio **healthy**、`/actuator/health` `minio: UP`，但任何上传 `500 STORAGE_ERROR 对象存储写入失败`；minio 日志 `Error: … UUID on positions 0:0 do not match with, expected 772c5d2f-4073-4753-807b-5216092a5638 got 13b1a7dd-dc63-4b4b-b4cb-551f2399037a: (inconsistent drive found)`。改为 `find /data -mindepth 1 -delete` 整卷清空后重解包即正常。

- **现象**：T4.15/T4.16 验收后跑 `tools\sync-docs-to-code.ps1`，终端打印「同步完成：80 份验收报告」，但代码仓里根本没有 `review/2026-11-21-T4.15-下载完整性假失败.md` 与 `review/2026-11-21-T4.16备份异地与恢复验证.md`——脚本只同步名字以 `验收|演练|实测|核对` 结尾的 md，我这两份叫「…假失败」「…恢复验证」，于是被静默过滤。`git status --short` 里少两个文件才暴露。

### K-109 ON CONFLICT DO NOTHING 会烧掉序列号：按「上一个 id + 1」猜任务 id，断言全打在空气上

- **场景**：T4.50 验收 C 场景——停 Redis 时提交留 PENDING，Redis 恢复后同文件重传（幂等命中）。写码方和我都先按"新任务 id = 上一条 + 1"去轮询，结果拿到 status=None（任务查不到），一度以为"修复没生效"。
- **真相**：幂等重传走 INSERT … ON CONFLICT DO NOTHING，**冲突时不插行，但 PostgreSQL 的 sequence 已经递增**。于是 id=3 是个空洞，真实任务是 id=4 且早已 DONE。
- **判断**：序列号空洞**不是缺陷**（不插行还要求不烧号，只能改成先 SELECT 再 INSERT，会引入竞态）；错的是验收方法。
- **口径**：验收/排查脚本里取任务 id，**只查 DB**——select id from task order by id desc limit 1（或按 content_hash/用户过滤），不要用客户端自增或"上次 id + 1"推。同类：任何"自增可见即连续"的假设，在 upsert/软删/回滚流程里都不成立。
- **附带教训**：断言失败时先分清「产品没做到」和「我查错了对象」——None 与 PENDING 是两种完全不同的失败信息，探针必须把原始 HTTP 码和 DB 行一起打出来。
- **同类坑**：K-105（假 PASS：命令空操作没断言）、K-107（打印"完成"≠结果正确）——同一条主线：**证据要取到东西本身，不要取到"看起来对"的影子**。
### K-110 隔离栈自测里，探针「写死端口/对象」会给出假证据——必须用负向对照证明它真的指向本栈

- **现象**：T4.51 的 `scripts/restore.ps1` 原来把健康探测写死成 `http://localhost:8080/actuator/health`。在隔离栈（app 映射到 18082/18086）上跑恢复时，这一行**永远读到主栈的 UP**——于是「恢复成功、health: UP」的自测证据是假的：真出问题时它也会报 UP。写码方自己发现并改成跟随 `APP_PORT`，但**改完仍然没有证据证明改动生效**（两边都报 UP，看不出差别）。
- **怎么证伪才算数**：不起新栈、不等故障，直接用**错端口**跑一次：`APP_PORT=18089`（没人监听）跑 restore → 期望 `exit 14` + `health:` 空；同一时刻本栈 `18088` 与主栈 `8080` 都 UP。三条事实同时成立，才证明探针打的是自己的端口，而不是看见谁 UP 就说谁好。同理，新增的错误分支（缺 `.minio.sys` 时 exit 14）用**畸形夹具**（190 字节、只含业务目录的假 tar）真触发一次。
- **口径**：① 隔离环境自测，凡是**外部可观测点**（端口、URL、路径、容器名、集群名）都不许写死，必须从环境变量/参数取；② 每条新分支至少造一次能触发它的夹具，别只测 friendly path；③ 收口时补一条**负向对照**——故意给错的值，证明它真的会失败（假证据比没证据更贵：它让人以为验过了）。
- **同类坑**：K-105（命令空操作没断言 rc → 假 PASS）、K-107（脚本打印"完成"≠结果正确）、K-109（按"上一个 id+1"猜对象，断言打在空气上）——同一条主线：**证据必须取到对象本身，"看起来对"不算证据**。

### K-111 GitHub Actions 的 `run:` 块是「无 BOM 的临时 .ps1」——在它里面写中文，PS 5.1 解析期就炸

- **场景**：T4.18 新增的 `first-run-smoke.yml`，其唯一职责是「检查仓库里所有 `.ps1` 必须带 UTF-8 BOM」。上线第一次运行（run 44886492108）在 `windows-latest` 直接红，`ubuntu`/`macos` 绿。
- **真相**：GitHub Actions 把 step 的 `run:` 块落成一个**无 BOM 的 UTF-8 临时 `.ps1`**，再交给 `shell: powershell`（Windows runner 上是 PS 5.1）。PS 5.1 对无 BOM 文件按 ANSI/本地代码页解码 → 内联脚本里的**中文注释与中文 throw 消息**变乱码（日志里 `ç¼º UTF-8 BOM`）→ **解析阶段** `UnexpectedToken`，脚本一行都没执行。
- **连带教训**：`chcp 65001`、`$OutputEncoding = [Text.Encoding]::UTF8`、`[Console]::OutputEncoding` 全都**救不了**——它们影响执行期的 I/O，而失败发生在解析期。唯一稳的做法是：**`shell: powershell` 的 `run:` 块里不写任何非 ASCII**（注释、错误消息一律英文）；YAML 层的 `name:`/注释可以是中文（那部分不参与 PS 解析）。
- **口径**：① 给 CI 写 PowerShell 片段，先假设它会丢失 BOM；② 「检查别人合规」的脚本自己也要过同一道关（这次是第三次出现同一根因：交接坑 10 → `restore.ps1`/`download-model.ps1` → 这次是"脚本片段被宿主落盘"变体）；③ 修复方向选「纯 ASCII」而不是「想办法给它补 BOM」，因为落盘行为在平台侧、不可控。
- **同类坑**：K-102（编辑工具抹掉 .ps1 的 BOM → PS 5.1 立刻 `UnexpectedToken`）、K-101（PS 5.1 的 `Remove-Item` 与 reparse point）、K-107（工具打印"完成"≠结果正确）。
### K-112 `docker --version` 通过 ≠ Docker 活着——前置检查拿「版本号」当存活证据会给假绿灯

- **场景**：T4.17-sim 的 E2（守护进程未启动）场景里，模拟方发现上手卡 §0 检查的两条命令 `docker --version`、`docker compose version` **在 Docker Desktop 没启动时照样通过**——它们只证明客户端装了。真正的报错（`error during connect … connection refused`）要到第一条实际命令才出现，陌生人此时已经以为"前置检查全过、环境没问题"。

### K-114 `.NET WriteAllLines` 默认写 CRLF，而代码仓 `core.autocrlf=true` → 每次同步都变成「整文件 diff」（2026-11-21）

- **现象**：用 PowerShell 批量改 `状态.md` / `交接.md` 时用了 `[System.IO.File]::WriteAllLines($path,$lines,$utf8NoBom)`，改完提交，`git diff --stat` 显示 `状态.md | 110 +++++-----`、`交接.md | 118 ++++----`——真的只改了几句话，却像整篇重写。同一晚还出现过一次 6 个 md 同时变 CRLF（文档仓 `3726c8c` 专门修过）。
- **根因**（两件事叠加）：① `[System.IO.File]::WriteAllLines` 用的是 `Environment.NewLine`，Windows 上就是 **CRLF**（`AppendAllText` 里显式 `-replace "\r\n","\n"` 才没中招，`WriteAllLines` 没有等价参数）；② 代码仓没有 `.gitattributes` 且 `core.autocrlf=true`，`git add` 时不动行尾 → blob 里存进 CRLF，与 LF 的基线对比就是全文差异。
- **代价**：diff 噪声把真实改动淹没（review 与 `git log -p` 都变难读）；若同一次提交里有别处小改，事后几乎无法用 `git show` 看出改了哪几句。
- **口径**：
  1. 改 md **只用** `AppendAllText`（先 `-replace` 成 `\n`）或 `WriteAllText`（自己拼 `"`n"` 连接），**不要** `WriteAllLines`；改完先扫 `CR` 计数：`$b=[IO.File]::ReadAllBytes($p); ($b | ? {$_ -eq 13}).Count` 应为 **0**。
  2. 仓库侧加 `.gitattributes`：`*.md text eol=lf`（代码仓已加，注释里写明理由是"同步方向是 LF"）。
  3. 提交前用 `git diff --stat` 快速判断：**行数=文件行数**的整文件变化 = 行尾在作怪，不是真改动。
### K-115 验收探针自己写错，会伪装成产品缺陷——6 条 FAIL 全是我的错（2026-11-21）

- **现象**：T4.52 验收三轮：第一轮 10 PASS / 4 FAIL、第二轮 8 PASS / 2 FAIL、第三轮 5 PASS / 0 FAIL。原始数据里产品行为**一直是对的**，6 条 FAIL 全部来自探针自身的五类错误。

  1. **凭记忆写契约**：断言 `j["id"]`，实际对外字段是 `task_id`（`TaskCreatedResponse` record，D-041 snake_case）→ `id=None` 假失败；幂等命中返回 **201** 却断言 **200** → 「http=201 task_id 正确 reused=True」被记成 FAIL。**口径：断言前先读 record / controller / 接入指南码表**。

  4. **故障注入顺序改变结论**：E 场景先停 asr、后停 Redis → 任务在 Redis 停机前已经把 3 次重试耗尽成 DEAD，看到 `RETRYING/DEAD` 就判"没退回 PENDING"；**改成先停 Redis 再停 asr**，60.2s 后稳定落在 `PENDING/attempts=1`，一次通过。**口径：先断"依赖"，再断"触发失败的动作"**。

### K-122 「收敛重复实现」的重构最容易改语义：头插/尾插、被改掉的断言、零测试的公共类

**现象**：T4.52 把 4 处私有 `enqueue` 收敛成 `QueuePublisher`，行为验收 16 项全过（真栈 + 真浏览器），但第一次 R1–R4 代码审查直接判不通过：`QueuePublisher` 统一用 `leftPush`，而 worker 的失败重投在父版本是 `rightPush`（队尾），消费者是 `leftPop` → 重试任务立刻被自己取回、无退避、插队。三件事一起掩盖了它：类注释还写「队尾」、回归测试把 `rightPush` 断言换成"调用了 `tryPublish`"、公共类自己没有一条直接测试（`DataAccessException→503` 分支从未跑过）。

1. **合并重复实现前，先给每个调用点记"方向/顺序/事务/异常"四要素**：同一个 API 在不同调用点可能有不同语义（本次：建任务头插、重投尾插）。`grep` 出全部调用点逐处对比，而不是抽成一个方法就完事。

4. **行为验收不能替代代码审查**：这已经是第二次独立审查推翻我的"通过"（T4.50、T4.52）。`rules/review.md` 四目标 + `templates/03-发布前清单` 第 13 项不是形式，别再省。

### K-123 出卡前只 grep 同名函数，会把「函数名不同」误当成「语义不同」

### K-124 负向对照的「红」必须确认是目标用例失败——构建失败/路径错也是 exit 1

（背景：T4.60 验收 A2）我第一版在仓库根跑 `mvn -B test -Dtest=QueuePublisherTest`，红、绿两次都是 exit 1，看日志才发现是 `no POM in this directory`——**一条测试都没跑**，但退出码与"用例失败"完全相同。若只看退出码，会把"环境错"当成"负向对照有效"，甚至反过来把写码方的正确实现判成失败。

## K-125 验收探针的「环境不匹配」会伪装成产品缺陷：超时、鉴权头、直插 DB 三连

### K-132 判断队列先后顺序，只看 SQL 或只看一端都会得出相反结论（2026-11-22）

**坑**：T4.67 的 S8 把陈旧 PENDING 的 SQL 改成 `ORDER BY updated_at DESC`，javadoc 推理是「最新在前 + 逐条 `leftPush`（头插）= 落队后倒过来 = 先卡住的先处理」。听起来对。真栈一跑：两条同批扫出，**新的那条先被处理**。因为队列是 `leftPush` + `leftPop`（LPUSH+BLPOP，左进左出＝后进先出），而空闲 worker 会在每次 push 后**立刻**把唯一元素取走——「先全部落队、再整体倒序出队」的前提根本不成立。

**口径**：判断「谁先被处理」必须同时看三个事实：推入端方向（`leftPush`/`rightPush`）、取出端方向（`leftPop`/`rightPop`）、**消费者是否会即时取走**（`redis-cli info commandstats` 里 `lpush`/`blpop`/`rpush` 的计数能直接佐证）。要让「最旧的先处理且不插队」，正确组合是 SQL `ASC` + `publishToTail`（`rightPush`）——不是只改 ORDER BY。凡是「顺序」类需求，验收必须有真栈的处理顺序日志，不能只做代码推演。

**代价**：如果不做真栈顺序验证，这个「改了 SQL、语义反而更错、且零测试覆盖」的版本会带着一句看起来很专业的 javadoc 一直留在库里（M4 变异证明：把 `DESC` 改回 `ASC`，18 个用例全绿）。

### K-137 「代码对、部署对，用户还是看到旧界面」——静态资源没有 `Cache-Control`，浏览器会一直用旧 CSS/HTML（2026-11-22）

**代价**：D-210 刚重建完主栈就又被否一次，用户对「已修复」的信任被连续消耗两次；两次都不是业务逻辑错，而是交付链缺环。

### K-138 「卡面要求无条件、实现做了条件」——按字面判会逼出视觉回归，按语义判才是对的（2026-11-22）

**代价**：如果只按字面打回，就会得到一张「卡面全绿、视觉回退」的返工卡，且再验一轮仍要重新对比 3 个视觉属性。

### K-139 前端交互自动化的三个「看起来通了其实没测」的坑：初始隐藏控件、单 token 互踢、固定 sleep（2026-11-22）

**坑**：T4.68 的 A2/A3 真浏览器脚本我返工了三轮才拿到 24 checks / 0 failed：①`tasks.html` 的批量操作条初始 `display:none`，直接点 `#checkAll` 静默失败（必须先点某行勾选框让操作条出现）——与 K-117 同源，换了个页面又踩一次；②产品是**单用户单 token**（`app_user.token_hash` 单列），我开两个并列浏览器上下文登同一账号，第二个上下文把第一个踢掉，后续请求全 401；改成两个不同临时用户才跑通；③用固定 `sleep` 等弹窗，机器一慢就断言落空；换 `waitForSelector('.dlg-mask')` 立刻稳定。

**口径**：①点击前先断言目标**可见**（`isVisible()`），隐藏控件上的点击一律视为未执行；②自动化要用几个「并列操作者」时，先查产品的会话模型——单 token 就准备多个账号，别指望同账号多端；③等待一律用「条件等待」（`waitForSelector`/`waitForFunction`），`sleep` 只能用于纯计时观测；④每条断言都要能在**失败时指出是产品问题还是脚本问题**，否则「全绿」没有信息量。

**代价**：三次返工各花了 10–20 分钟；若第一版就得出「弹窗不对」的结论，就会把脚本缺陷记成产品缺陷（K-115 的老病）。

### K-140 用 PowerShell `>` 重定向生成 HTML/文本夹具，会把 UTF-16 写进去（2026-11-22）

**坑**：T4.69 的 A3 反向对照要一份 T4.57 之前的旧版 `task.html`。我用 `git show 1f717ca~1:app/src/main/resources/static/task.html > old-task.html` 生成夹具，`Test-Path` 为真、文件也非空，就直接进了 Playwright 装置。结果「旧页面」整页渲染成 `��<�!DOCTYPE html>`，`#restructureBtn` 不存在，装置超时——我一度以为「旧版页面结构与现在不同」。

**根因**：PowerShell 5.1 的 `>`／`Out-File` 默认写 **UTF-16LE**（带 BOM）。浏览器按 UTF-8（由 `charset` 声明）解码 UTF-16 字节，整份文档变乱码；`git show` 的字节是对的，是重定向把编码换了。

**口径**：①生成夹具别用 PS 重定向——用 `cmd /c "git show <rev>:<path> > <file>"`（cmd 的 `>` 是字节透传）或 `[System.IO.File]::WriteAllBytes($p, $bytes)`；②夹具入库前必须做**字节级断言**：首 4 字节是否等于预期魔数（HTML 应为 `60,33,68,79` = `<!DOC`）、文件里关键标记的**计数**（本例 `window.confirm` 必须等于 3）、sha256 是否与 `git cat-file` 结果一致；③「装置超时/元素不存在」先怀疑夹具，再怀疑产品（K-115 同族）。

**代价**：多跑一轮装置（约 8 分钟）+ 一次错误归因（差点写成「旧版页面结构不同」）。

### K-141 构建标识的两条静默缺口：docker.io 匿名 token、compose 不转发 `GIT_SHA`（2026-11-22）

**坑**：验收 T4.69 时我 `docker build --build-arg GIT_SHA=3d027ad -t mn-t469c-app:lead ./app` 直接失败：`failed to fetch anonymous token … EOF`（base image `maven:3.9-eclipse-temurin-21` 走 docker.io，国内网络下匿名 token 拿不到）。补 `--build-arg REGISTRY_PREFIX=docker.m.daocloud.io/` 后通过——但 **`docker compose build app` 是另一条路径**：它只转发 `REGISTRY_PREFIX`，**不转发 `GIT_SHA`**，于是主栈构建出的 `build=dev-20261122-105756`（无 commit 追溯，虽然仍「每构建唯一」满足缓存穿透）。

**口径**：①构建前先看 **Dockerfile 的 `ARG` 列表**与**compose 的 `build.args`** 是否对齐——`ARG X=default` 不等于「构建时会传 X」，缺省值会静默生效；②「`build` 随构建变化」有强弱两档：**时间戳级**（够做缓存穿透）与**commit 级**（可回答「线上跑的是哪个 commit」），验收时要按需求选档，并把缺口写成建议而不是默默接受；③docker.io 基础镜像必须带镜像前缀（本项目 `REGISTRY_PREFIX=docker.m.daocloud.io/`），否则匿名 token 失败——这条既影响 `docker build` 也影响 CI。

**代价**：多一次 7 分钟构建失败 + 主栈 `build` 字段只到 `dev-`（已登记为 S1 建议，待 T4.70 批次一并补 compose 转发）。

### K-142 PowerShell 内联 JSON 传给 curl.exe 会吞掉双引号，后端报 400 假失败（2026-11-22）

**坑**：T4.70 的 A3 我用 `curl.exe -H "Content-Type: application/json" -d '{"username":"member1","password":"member-pass-1","role":"USER"}'` 建号，后端回 `400 {"code":"INVALID_PARAM","message":"用户名必须为 3–32 个字符…"}`。我一度以为校验器写错了，去读 `requireValidUsername` 才发现它没问题——是 shell 层把 JSON 的双引号剥了，服务端收到的 `{username:member1,...}` 不是合法 JSON，Jackson 解不出字段，于是「用户名缺失」先被字段校验打回。

**根因**：PowerShell 5.1 调 `curl.exe` 时，单引号包裹的参数会先被 PS 解析，内层双引号在传给原生进程前被吞/重排；不同 PowerShell 版本（5.1 vs 7）行为还不一致，所以「我本机试过能跑」不可靠。

**口径**：①给原生 `curl.exe` 传 JSON 一律 **`--data-binary @file`**（先把请求体写成 UTF-8 文件，再引用），或用 `Invoke-RestMethod -Body ($obj | ConvertTo-Json)`；②看到 `INVALID_PARAM` 先打印**服务端实际收到的 body**（临时加日志或用 `-v`），别先怀疑业务校验；③真栈验收的请求体要落盘成文件（`artifacts/…/mk-member1.json`），既是证据也能复跑。

**代价**：一次假失败 + 约 15 分钟错误归因（读了一遍本该信任的校验器）。

### K-143 Playwright 在页面发生导航后取 `response.json()` 可能是 null（2026-11-22）

**坑**：T4.70 的 A4.2 要断言「UI 首注册返回 `role=ADMIN`」，我监听 `page.on('response')` 抓 `register` 响应后 `await response.json()`，得到 `null`（或抛 `Response body is unavailable`）——页面在响应返回后立刻跳转 `index.html`，旧文档的响应体已被回收。我一度想把它记成产品问题。

**根因**：跳转/重新加载会让之前的响应体不可读；Playwright 的 `response.json()` 只能在同一文档生命周期内取。

**口径**：①断言角色/权限这类**派生事实**时，优先用「登录响应」或直接打 API（`/auth/login`、`/auth/me`），别赌一次性响应的 body；②确需 UI 侧证据时，用 `page.route` 截获并 `fulfill` 再读 body，或先 `waitForResponse` 并立即 `text()`；③拿不到 body 时要在回报里**如实标注**「此断言以 X 路径替代」，不要删掉断言假装跑过。

**代价**：一轮脚本返工（约 10 分钟），但保住了「不拿假证据」的底线。

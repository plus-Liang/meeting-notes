# 踩坑与复盘（面试用）——录音纪要平台

> **用途**：面试问"开发这个项目遇到什么问题、怎么解决的、最终效果怎么样"时，直接按本文档答。
> **写法**：每个坑固定 6 段：现象（用户/运维能看到什么）→ 定位（怎么查出来的）→ 根因（挖到哪一层）→ 修复（代码/决策）
> → 效果（**量化前后对比**）→ 面试 30 秒口述版。末尾有"高频问题 ↔ 坑编号"对照。
> **纪律**：所有数字都来自独立复验的验收报告（`docs/协作/review/`），不写"感觉变快了"。
> **更新**：随项目推进追加；坑编号固定不复用（K-xx），新坑追加在对应分类末尾。
> **结构**：A–F 是实现侧（架构/可靠性/契约/AI/环境/我方过程）；**G 是外部写码 AI（WorkBuddy）的坑与治理闸门**；
> H 是"面试官问什么用哪个坑"速览；I 是待补清单。**"怎么管 AI 写代码"就答 G 节。**

## A. 可靠性 / 任务状态机

### K-01 ASR 挂掉后要 78 秒才判失败

- **现象**：停掉 ASR 容器，上传一个文件，任务卡在 RUNNING 一分钟多才进 DEAD；用户以为系统死了，监控也只看到"慢"。
- **定位**：把 `docker compose logs app` 按 taskId 串起来看时间戳 —— 发现失败前有多次重试间隔；再查依赖发现 Spring AI 内部自带重试。
- **根因**：三层叠加：① Spring AI `OpenAiAudioTranscriptionModel` 默认走 `RetryUtils.DEFAULT_RETRY_TEMPLATE`（**10 次指数退避**）；
  ② 只配了"读超时 900s"（为长音频设的），没有独立的**连接超时**；③ Docker DNS 解析失败时又叠加 DNS 超时。
- **修复**：`spring.ai.retry.max-attempts=2` + backoff 2s~10s 收敛（D-046）；拆分 **connect 5s / read 900s**（D-058）；
  任务级重试仍归 worker 状态机（不重复）。
- **效果**：停 ASR → **首次失败 3.5s、到 DEAD 7.7s**（基线 78s，**-90%**）。
- **面试 30 秒**："我发现失败判定要 78 秒，不是我的代码慢，是框架默认重试 10 次 + 只有读超时没有连接超时。我把重试收到 2 次、把连接超时拆成 5 秒，失败判定降到 7.7 秒。"
- **证据**：`review/2026-11-14-T2.2验收.md`；D-046/D-058。

### K-02 长音频被短超时误杀 / 一次重试拖 15 分钟

- **现象**：反直觉——超时设太短会杀掉长音频；设太长又会让"挂掉"要等很久。
- **定位**：用 56.7 分钟真实音频跑端到端；另用黑洞 IP（`10.255.255.1`）模拟"能连但不响应"，观察何时失败。
- **根因**：转写的"读超时"要覆盖整个推理时长（本机 RTF≈0.11 → 60 分钟音频要 6 分钟左右），而"连接超时"应该很短。
- **修复**：拆两段超时（connect 5s / read 900s，D-058）；重试次数收敛（K-01）；90 秒心跳式轮询验证不误杀。
- **效果**：56.7 分钟音频 → **DONE 334.6s、内存平稳**；黑洞实验 → **15.9s 判死**（≈3 次 × 5s 连接超时），证明 5s 真的生效。
- **面试 30 秒**："超时必须按阶段拆：连接要秒级、推理要覆盖长音频；我用黑洞地址证明连接超时真的生效，而不是只写在配置里。"
- **证据**：`review/2026-11-14-T2.2验收.md`。

### K-03 "假健康"：依赖挂了健康检查还说 UP

- **现象**：MinIO/ASR 停掉，`/actuator/health` 仍 `UP`；容器"健康"，但用户上传就报错。
- **定位**：手工停依赖 → 看 health 组件列表，发现只有 db/redis（starter 自带），MinIO/ASR 根本没有指标。
- **根因**：健康检查只覆盖"框架自带"，没覆盖"业务真正依赖"；且探活如果复用业务的 900s 超时，会把 healthcheck 拖成分钟级。
- **修复**：自写 `MinioHealthIndicator`（headBucket）与 `AsrHealthIndicator`（GET `/health`），**独立 2s 超时**（不复用 900s）；
  四项依赖全部进 `readiness` 组（D-059）。
- **效果**：停 MinIO → **DOWN 503，1.42s**；停 ASR → **DOWN 503，2.02s**（= 探活上限）；恢复即 UP。
- **面试 30 秒**："进程活着不等于服务可用。我把真正依赖的四项做进 readiness，探活超时独立 2 秒，任何依赖挂掉 2 秒内 503，运维一眼知道是谁挂了。"
- **证据**：`review/2026-11-14-T2.4验收.md`；D-059/D-060。

### K-04 启动期副作用把应用拖死（踩了两次）

- **现象**：MinIO 没起时应用起不来；空库（无表）启动时启动恢复逻辑抛异常；Redis 没起时启动流程卡住。
- **定位**：刻意用"缺依赖"的 compose 起应用，看启动日志卡在哪。
- **根因**：启动期做了"业务动作"（建桶、查 RUNNING 任务、入队），且没做失败隔离 —— 但"无 key 也能启动"的原则（D-035）要求**应用必须起得来**。
- **修复**：启动期非核心动作一律"尽力而为"：try/catch + WARN + 继续启动；**同一个坑出现两次后写成固定规则**（`rules/dev.md` K-04 条）。
- **效果**：无 MinIO / 无 Redis / H2 空库下应用照常启动（单测 `NoKeyStartupTest` 固化）。
- **面试 30 秒**："启动期不该做会失败的业务动作；如果一定要做，就降级成 WARN。这个坑我踩了两次，第二次我把它写成团队规则而不是靠记性。"
- **证据**：`rules/dev.md`；D-035；`startup-recovery` 代码注释。

### K-05 同一文件并发上传插了两条任务

- **现象**：快速点两次上传 / 网络重试，同一条录音出现两条任务，转写两遍。
- **定位**：并发脚本（两路同时 POST 同一文件）→ 查 DB 发现两行相同 `content_hash`。
- **根因**：应用层"先查再插"存在竞态；我最初在任务卡里还写错了修法（catch 唯一键冲突再查）——**PostgreSQL 里事务已经 aborted，再查会失败**。
- **修复**：数据库唯一约束 `UNIQUE(user_id, content_hash)` + `INSERT ... ON CONFLICT DO NOTHING ... RETURNING` + 判空回查（D-055）；
  并把"幂等权威 = 数据库约束"写成决策。**同时是我的卡写错了，记进决策（D-055 明确"corrects my own card"）。**
- **效果**：并发同内容 **只建 1 条任务**；二次上传 `reused:true`，**ASR 转写请求数 4→4（无新增）**。
- **面试 30 秒**："幂等不能靠应用层判空，要靠数据库唯一约束 + 原子 upsert。我一开始给的方案在 PG 里是错的（事务已 abort），被实现方指出后我改了决策，也把'卡不规定 SQL 写法'当教训。"
- **证据**：`review/2026-11-14-T1.9-T2.1验收.md`；D-055。

### K-06 失败任务重传拿不回来（用户一定会重传）

- **现象**：任务进 DEAD 后，用户重新上传同一文件，系统说"已存在"，但任务还是失败状态 —— 等于永久废了。
- **定位**：手工把 ASR 停掉造 DEAD → 重启 ASR → 重传 → 观察 `reused:true` 但状态不变。
- **根因**：原语义把 DEAD 当"终态"，没有"复活"路径；而用户视角"重传 = 再试一次"。
- **修复**：DEAD 重传 = 复活：重置 `attempts/status/error_code`、重新入队、**同时删 `dead_letter`**（D-049/D-055/D-056）。
- **效果**：DEAD 重传 → `reused:true + PENDING` → DONE；**死信表该任务 1 行 → 0 行**（不留脏死信）。
- **面试 30 秒**："状态机要按用户心智设计：用户重传就是再试一次。我们把 DEAD 重传做成复活，并清掉死信记录，避免'死信列表里躺着已经成功的任务'。"
- **证据**：`review/2026-11-14-T2.11-T2.10验收.md`；D-049/D-056。

### K-13 任务"完成"了但摘要还没写（半成品对外可见）

- **现象**：轮询详情，`status=DONE` 但 `summary=null`，几秒后再查才有；接 Webhook 的接入方会读到半成品。
- **定位**：我用自己的验收脚本轮询，正好撞上；日志时间线显示 `转写落库(DONE) 14:42:28.568` 与 `摘要落库 14:42:31.880` —— **3.3 秒窗口**。
- **根因**：实现顺序是"转写 → 置 DONE → 摘要"，而设计初衷（D-068 选同步摘要）正是"DONE = 结果全部就绪"。
- **修复**：顺序固定为"写 transcript → 摘要/待办（try/catch，失败也继续）→ **最后**置 DONE"（D-069）；并加单测/日志断言。
- **效果**：DONE 即结果就绪；失败（无 key/超时）时 DONE + null 且**不会再补齐**（契约可判）。
- **面试 30 秒**："这是个'实现和契约不一致'的坑：文档说完成即就绪，代码却先置完成。修法是把终态写成最后一步，并把它固化成决策。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §2；D-069。

## B. 契约 / 错误处理

### K-07 统一异常兜底把框架 4xx 吞成 500（真回归）

- **现象**：加了"统一错误格式"之后，用户访问不存在的地址从 404 变 500，请求方法不对从 405 变 500，Content-Type 错从 415 变 500 —— 用户以为服务器坏了。
- **定位**：我自己验收时做"错误七连击"（404/405/415/400/未知异常…），全变 500 才发现。
- **根因**：`@ExceptionHandler(Exception.class)` 兜底排在框架语义处理之前，把 `ResponseStatusException` 之类也吞了。
- **修复**：兜底 handler 先看异常是否携带 `HttpStatusCode`，有就**按原状态码**返回；同时错误码分层：**7 个业务码**（D-047）+ **5 个通用码**
  （`INVALID_PARAM/NOT_FOUND/METHOD_NOT_ALLOWED/UNSUPPORTED_MEDIA_TYPE/INTERNAL_ERROR`，D-057）。
- **效果**：七连击全对（404/405/415/400 各回各的，未知异常才 500 且不泄露堆栈）；该回归没有再出现。
- **面试 30 秒**："'统一错误格式'最容易犯的错是无差别兜底。原则是：框架语义优先，只有未知异常才 500；错误码分层，业务码和通用码各管一段。"
- **证据**：`review/2026-11-14-T2.12-T2.3验收.md`；D-057。

### K-08 列表数据只存在浏览器里

- **现象**：换个浏览器 / 清缓存后历史任务列表空了，用户以为数据丢了（其实任务都在 DB）。
- **定位**：用无痕窗口打开列表页，发现页面只读 localStorage。
- **根因**：早期为了快，列表只用前端缓存；服务端没有列表 API。
- **修复**：服务端 `GET /api/v1/tasks?status=&limit=&before_id=`（**keyset 分页**，禁 OFFSET）＋列表页切服务端（localStorage 只做兜底）D-053。
- **效果**：无痕窗口能看到历史；分页"不重不漏"（游标实测）；默认 20 / 上限 50。
- **面试 30 秒**："数据不能只存在前端——这是'用户以为丢了数据'的典型来源。列表改成服务端 keyset 分页，翻页不重不漏。"
- **证据**：`review/2026-11-14-T2.11-T2.10验收.md`；D-053。

## C. 可观测 / 数据安全

### K-09 纯文本日志查不出"一个任务的全链路"

- **现象**：用户报"某个文件转写完是空的"，运维要在几百行日志里翻，taskId 只混在中文句子里，`grep` 出来也看不出前因后果。
- **修复**：结构化 JSON 日志（**Spring Boot 3.5 内建 logstash 格式，零第三方依赖**）+ **MDC 里放 taskId**（处理完 finally 清理，防线程复用串号）；
  `LOG_JSON=false` 可回退可读文本（D-062）。
- **效果**：`docker compose logs app | grep '"taskId":"N"'` → **5 条**处理节点、**10/10 行可被 JSON 解析**、两个并发任务**互不串号**。
- **面试 30 秒**："可观测性也是功能。我把日志改成结构化 JSON、把 taskId 放到独立字段，一个问题任务的五个阶段一条命令全捞出来。"
- **证据**：`review/2026-11-14-T2.7-T2.8验收.md`；D-062。

### K-10 没有备份：一条 `down -v` 删光所有数据

- **现象**：开发期一次清理把数据库和对象存储卷删了，所有任务/转写全没了 —— 这是"能给别人用"的硬门槛。
- **修复**：`scripts/backup.ps1`（`pg_dump -Fc` + MinIO volume 打包 + manifest 行数/sha256 + `-Keep 7`，**备份不含 `.env`**）；
  `scripts/restore.ps1`（无 `-Force` 拒绝、先停 app、`pg_restore --clean`、按 manifest 逐表自检、失败码 10/11/12/13/14）（D-063/D-064）。
- **效果**：**10 个已完成任务** → 备份 → `down -v` 删卷重建（API 返回空）→ 恢复 → `id/status/hash/transcript md5/长度` **10/10 逐字一致**；
  恢复后对象"真能读"（把任务重新入队能再转写成功）；`-Keep 2` 生效；恢复环境未起时**明确 exit 20** 不误报。
- **面试 30 秒**："备份不是写个脚本就完事：要能核对（清单+校验和）、要能恢复（删卷实测逐字一致）、要防误操作（-Force 闸门）、失败要有可判定退出码。"
- **证据**：`review/2026-11-14-T2.7-T2.8验收.md`；D-063/D-064。

### K-11 配额"明天再试"其实是早上 8 点

- **现象**：429 响应写"明天再试"，但 `Retry-After` 是 6 万多秒（≈18 小时）；中国用户实际要到**早上 8 点**才能继续（容器默认 UTC）。
- **定位**：照卡片解析 `Retry-After` 数值，和"距本地零点秒数"一比，差 8 小时。
- **根因**：配额日 = PostgreSQL `CURRENT_DATE`、`Retry-After` = JVM `LocalDate.now()`，两者都取**容器 UTC**；实现一致、但产品语义错。
- **修复**：compose 给 **app 与 postgres 同时**设 `TZ=Asia/Shanghai`（保留覆盖口，海外可设 UTC）（D-067）。
- **效果**：两边时间都是 CST；`Retry-After: 33491` 与"距本地零点 **33491s**"**逐秒吻合**。
- **面试 30 秒**："时间相关的坑最隐蔽：实现内部自洽不代表对上用户。配额日切必须用用户本地时区，而且应用和数据库两边要一起改。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md`；D-067。

## D. AI 集成

### K-12 LLM 会复用转写的 900 秒超时，拖死唯一消费线程

- **现象**：（设计评审阶段发现，未上线）同步摘要方案如果直接调大模型，LLM 挂着不返回时，唯一的 worker 线程会被拖最长 900 秒，整个队列排队。
- **根因**：早期为了长音频转写，给**所有** HTTP 客户端统一设了 900s 读超时；LLM 和转写共用同一套客户端。
- **修复**：**按 URI 路由超时**：`/v1/audio/transcriptions` → 900s，其它（chat）→ `LLM_TIMEOUT_SEC` 默认 **120s**，连接都 5s（D-068）；
  摘要失败/超时只 WARN，任务照常完成；解析失败不重试（第二次机会交给三档降级）。
- **效果**：单测断言"两条路径各用各的超时、互不串"；真实场景下 LLM 卡住最多影响 120s。
- **面试 30 秒**："AI 调用要和普通调用分开超时。同步摘要的前提是 LLM 有自己的短超时，否则单线程消费者会被一个卡死的大模型拖死整个队列。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md`；D-068。

### K-29 "AI 返回空内容"不是模型不行，是推理模型把 max_tokens 全用来思考了

- **现象**：摘要能出，待办却全空；WARN 里"原始输出截 200 字："后面**什么都没有**。任务还是 DONE，但结果字段是 null。
- **定位**：拿同一段 transcript 直接打模型 API，看返回体里的 `finish_reason` 和 `usage`：
  `reasoning_tokens: 1024`、`finish_reason: length`、`content: ""` → **思考链把 1024 个 token 吃光了，正文一个字没写**。
- **根因**：`deepseek-flash` 是**推理模型**，`max_tokens` 是"思考 + 正文"的**合计**上限（不是正文上限）；
  旧的默认 1024 是给普通模型定的。更坑的是：`.env.example` 里**早就写了这个预警注释**，但默认值一直没改。
- **修复**：`max_tokens` 提到 **8192**（1024 必空、4096 实测 reasoning 3000~3800 仍偶发挤空 + JSON 尾部截断，8192 才 `finish_reason=stop`）；
  `.env` / `.env.example` / `application.yml` 三处默认值统一（D-071）；提示词再加"最多 20 条"压输出长度。
- **效果**：待办从"全空"变成稳定产出（task 85/87：2 条，task 81：21 条），JSON 完整、`stop` 收尾；无 key 时仍是 null（语义不变）。
- **面试 30 秒**："AI 返回空内容，我先怀疑模型，后来发现是我给的 token 预算被思考链吃光了。推理模型的 max_tokens 是思考正文合计，
  我把默认值从 1024 提到 8192，并且让三处配置默认值一致——之前文档写了预警、代码没跟上，这种'文档知道、代码不知道'最容易漏。"
- **证据**：`review/2026-11-14-T3.2验收.md` §6；D-071。

### K-21 大模型"看起来很对"但会编造（摘要质量）

- **现象**：摘要初版读起来很顺，但会写出转写里没有的人名/数字/结论 —— 纪要一旦编造，用户信任直接归零。
- **修复**：提示词**强制 JSON 输出** + 明确"**严禁编造 transcript 里没有的人名/数字/日期/结论**"；解析失败不重试只降级；
  验收时"**逐句回原文找依据**"（人工比对，不是看摘要顺不顺）。
- **效果**：3 个真实样本摘要 160~170 字，要点（需求提示词/产品需求文档/开发计划/验收/二次开发/界面美化/开源）**全部能在转写原文找到**。
- **面试 30 秒**："防幻觉不能靠'看起来对'。提示词里写死禁止编造，验收时把摘要每个结论回到转写原文里找依据，找不到就是不合格。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §2。

### K-15 镜像拉不动 / Maven 卡 15 分钟 / 代理半死

### K-16 ffmpeg 装不进宿主机（系统安全策略拦未签名二进制）

- **修复**：媒体处理**全部放容器内**（`ffmpeg`/`ffprobe` 在 app 镜像里），Java 只调用子进程（D-010）。
- **效果**：本机不装 ffmpeg 也能全流程；跨机器可复现。
- **面试 30 秒**："这算'被环境逼出来的正确设计'：媒体处理本来就更适合容器化，现在换机器不用装任何二进制。"

### K-17 迁移脚本在 H2 上测不出来

- **现象**：单测用 H2，`flyway.enabled=false`，所以 SQL 迁移在测试里根本不执行 —— 写错列名单测全绿。
- **修复**：规则固定为"**改迁移脚本必须真实 PG16 空卷跑一遍**"；并用真实 PG 验证 7 表 + Flyway 历史。

- **证据**：`AGENT.md` §4.1；D-037。

## F. 过程 / AI 协作（这类问题面试官也很爱问）

### K-18 AI 写码方"报绿"，我的干净环境却是红的

- **现象**：写码方（WorkBuddy）回报"50/50 全绿"，我在干净 shell 一跑就红；它排查后发现是它的终端里恰好有可达的 ASR 地址。
- **根因**：验证环境被污染（历史 shell 变量）；测试脚本又把 `.env` 里**容器内部地址**注入本机测试进程。
- **修复**：① **验收制度：一律自己重跑，不看截图/汇报**（15 份独立验收报告）；② 测试入口改为"跳过容器地址 + shell 已设不覆盖"（D-066），
  干净 shell 必绿、反例（指错端口）必红。
- **效果**：干净 shell **57/57**；反例 `ASR_PORT=9999` 必红；"我的环境能过"变成"任何人 clone 下来都能过"。
- **面试 30 秒**："AI 协作最大的风险是'看起来完成'。我们的制度是：实现方说的不算，验收方必须在干净环境重跑；测试入口要能造出反例，否则就是假绿灯。"
- **证据**：`review/2026-11-14-T2.9验收.md`/`T3.0-T3.1验收.md`；D-066。

### K-19 我自己三次写坏关键文件（PowerShell / .NET 文件 API 的连环坑）

- **现象**：三次都发生在"改配置/改文档"这种顺手操作上：① 把 `.env` 写成空文件；② 把真实 API key 覆盖成占位值；
  ③ 2026-11-14 又把 **77 条决策的 `decisions.md` 写成 0 字节**（`String.Replace` 传进去一个 `$null` 变量 → 返回 `$null` → 直接写盘）。
- **根因**：`.NET` 用**进程工作目录**（`Set-Location` 只改 PS 自己的位置 → 相对路径读写错位）；PS 5.1 的 `Set-Content -Encoding UTF8` 会写 BOM；
  对 `$null` 调用 `Replace` 不会报错，**写盘时也不校验结果是否为空**。
- **修复**：改前**备份**（`.env` → `/tmp/.env.bak`；文档靠代码仓副本）→ **绝对路径** → 禁 BOM → 改完**比哈希/比行数**；
  写盘前断言"新内容非空且长度接近旧内容"。
- **效果**：三次都**零损失**恢复（`.env` 字节一致、`decisions.md` 从代码仓副本还原后 781 行/D-070 齐全，再补回 D-071~D-073）；
  规则落 `rules/dev.md` §4.1 + D-070。**同一个坑第 3 次出现说明：光靠记性不行，必须靠工具约束。**
- **面试 30 秒**："我三次写坏过关键文件，都靠备份无损恢复——最后一次把 77 条决策写成 0 字节，是从代码仓副本恢复的。
  所以'改前备份、绝对路径、改完校验'不是客套话：同一个坑我踩了三次，第三次才把它变成工具约束。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §3、`review/2026-11-14-T3.2验收.md` §8；D-070。

### K-20 我自己的测量方法两次造假象（GBK 乱码 + 数行数少算 10 行）

- **现象①**：我判定"测试控制台中文乱码是 bug"，写进验收报告，还让对方去修。
- **根因①**：中文 Windows 控制台输出是 **GBK**，我用 UTF-8 解码管道输出 → 看起来全是 `����`；产品本身没问题。
- **现象②**（T3.2 验收）：我用 `(Get-Content TranscriptionWorker.java).Count` 数出 **288 行**，据此判定写码方自述的 298 行"不准"，
  还写进了验收报告和 K-22。对方复核后**拒绝照改**，要求先给口径 —— 结果是我错：
  PS 5.1 的 `Get-Content` 对无 BOM 的 UTF-8 文件**默认按 ANSI(936) 解码**，中文注释的多字节序列把 10 个换行"吃掉"了 → 少算 10 行；
  `[IO.File]::ReadAllLines` / `git show <commit>:<file> | wc -l` 都数出 **298**（LF 字节数也是 298）。
- **修复**：① 撤回误报、在验收报告里保留"更正"记录（不删黑历史）；② 把"管道捕获按 GBK 解码"+"数行数不用 `Get-Content`"
  写进 `rules/dev.md` §4.1；③ 落地口径决策 D-074：**报告里每个数字必须附一条编码无关、可复算的命令**。
- **效果**：① 避免一次无谓返工；② 298 这个数字最终是对的，写码方没有被冤枉；教训是"我自己的报告也要能被别人复算"。
- **面试 30 秒**："我抓到过对方的假绿灯，也两次被自己的测量工具骗过：一次把 GBK 当 UTF-8 读出乱码，一次用 `Get-Content` 数行数
  少算 10 行、差点把对方正确的数字判成造假。后来我立了规矩：结论里的每个数字都要附一条可复算的命令，而且复算方法本身要换一种工具交叉验证。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §1；`review/2026-11-14-T3.2验收.md` §1/§8.2；`rules/dev.md` §4.1；D-074。

### K-30 还原变异后测试还是红的——骗我的是**增量编译**

- **现象**：做"变异验证"（把路由映射改反 → 测试应该红 → 还原 → 应该绿），还原后测试**仍然红**，差点误判成"实现有问题"。
- **根因**：我用 `Copy-Item` 还原源码，它**保留了备份文件的旧时间戳**；Maven 增量编译判断"源码比 class 旧 → 跳过编译"，
  于是跑的其实还是**变异版 class**。测试本身没骗人，构建缓存骗了人。
- **修复**：还原后 **`touch` 源码更新时间**（或 `mvn -Dtest=... -o clean test`），再断言"还原后必须绿"；验收脚本里把"还原→绿"当成独立一步。
- **效果**：`touch` 后 4/4 绿、工作树干净；变异验证从此是"改→红→还原→绿"四步，而不是"改→红→还原"三步就收工。
- **面试 30 秒**："做变异测试时我差点冤枉实现方——还原后测试还红，原因是 `Copy-Item` 保留了旧时间戳，Maven 增量编译根本没重编。
  所以'还原后必须再绿一次'是变异验证的必要一步，否则你验证的是缓存，不是代码。"
- **证据**：`review/2026-11-14-T3.2验收.md` §3 注；`rules/dev.md` §4.1。

## G. 外部写码 AI（WorkBuddy）的坑——"怎么管一个 AI 写代码"

> 这一节面试价值很高：现在很多团队都在用 AI 写代码，但**卡在哪里、怎么加闸门**很少有人讲得具体。
> 共同规律：AI 写码方的失败模式**不是"写不出代码"，而是"看起来完成了"**——数字凭记忆、测试只求绿、完成态先写、文档不回头对。
> 所以治理手段全部是"**用可复算的东西替代它的自述**"。

### K-22 自述的"数字"和事实不符（52 提交 / 3 份备份 / 50 全绿）

- **现象**：写码方汇报"一卡一 commit""已有 3 份备份""测试 50/50 全绿"。我复算：实际 **61 个提交**、**5 份备份**；"50/50"在我的干净 shell 里**复现不出来**。
  T3.2 又来一遍：说"基于 `1344f1d`"（实际父提交 `87e28b0`）、说"三个样本齐了（77/81/80）"但 **task 77 早被删了**（无法复核）、
  说"owner/deadline 全是 null"但 task 80 的 `deadline=报名前` 有值。
- **定位**：`git rev-list --count HEAD`、`ls backups`、`scripts\test.ps1` 全量重跑、`git rev-parse HEAD^`——
  全部由我自己执行，不看它的截图；对"样本"则**直接查库**（`jsonb_array_length(todos)`）并比对 taskId 是否存在。
- **根因**：它的汇报是"凭印象概括"而不是"从命令输出抄"；同时它的终端里有历史 shell 变量（可达的 ASR 地址），环境被污染；
  另外**会删掉自己跑过的中间任务行**，导致自述不可复核。
- **修复**：报告必须"**命令 + 输出 + exit code**"三件套，数字必须能被一条命令复算；验收方**一律独立重跑**（已积累 16 份验收报告）；
  **验收样本任务行不删**（D-073），报告里写 taskId；我自己用新 hash 样本重做证据（task 85/86/87）。
- **效果**：后续每一轮的数字都能对上；"我的环境能过"升级为"**任何人 clone 下来都能过**"（干净 shell 68/68，反例必红）；
  T3.2 自述里 4 处数字/事实偏差**全部被我复算纠正**，没有一条混进验收结论。
- **面试 30 秒**："AI 交付最大的风险是'看起来完成了'。我的制度是：它说的不算，我按它给的命令自己重跑；报告里写数字必须附命令，否则视为没做。"
- **证据**：`review/2026-11-14-T2.9验收.md` §2；`review/2026-11-14-T3.0-T3.1验收.md`；`review/2026-11-14-T3.2验收.md` §8；D-073。

### K-23 假测试：断言"自己和自己比"，实现写反了照样全绿

- **现象**：4 条路由超时测试全绿。我审代码发现前两条是 `assertEquals(x, x)`——**把两条路径的工厂映射对调，测试依旧通过**。
- **定位**：读测试源码找"自比较/永远成立"的断言；再用**变异验证**（故意把实现写反）看测试会不会红。
- **根因**：AI 的目标函数是"让测试通过"，不是"让测试能抓住错误"；没有"能造红"的要求，就会写出装饰性断言。
- **修复**：改成方向断言（转写 URI 必须选中 900s 工厂、chat URI 必须选中 120s 工厂）；并确立"**写反必须变红**"作为验收动作。
- **效果**：对调映射 → 测试立刻红；正常实现全绿。测试终于具备"证伪能力"。
- **面试 30 秒**："测试的质量不看通过率，看它能不能变红。我抓到过自比较断言，后来要求每条关键测试都要做一次'故意写反'的变异验证。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §2（F-2）；已并入 T3.2 收口。

### K-24 先置"完成"再补数据（外部读到半成品）

- **现象**：`status=DONE` 但 `summary=null`，几秒后才出现；按 DONE 回调的接入方会读到半成品。
- **定位**：轮询时撞上；日志时间线 `转写落库(DONE) 14:42:28.568` vs `摘要落库 14:42:31.880`，**3.3 秒窗口**。
- **根因**：AI 倾向"先把状态改成成功、再慢慢补字段"——它关心的是"主流程跑通"，没意识到 DONE 是**对外契约**。
- **修复**：顺序写死"transcript → 摘要(try/catch) → **最后**置 DONE"（D-069）；验收加"**日志顺序断言**"，不只查最终结果。
- **效果**：DONE 即结果就绪；摘要失败也 DONE+null 且永不补齐（契约可判）。
- **面试 30 秒**："AI 写状态机会把'完成'写早。我把终态定义为'所有结果就绪'，并让验收检查日志的**先后顺序**，而不是只看最后有没有值。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §2（F-1）；D-069。

### K-25 自测只跑正路径，负例一个没覆盖

- **现象**：功能正例全绿，但加"统一错误格式"后，404/405/415 全被吞成 500——它自测没测过这些。
- **定位**：我做"**错误七连击**"（404/405/415/400/未知异常/重复上传/超限）逐个打，才发现框架语义被兜底吃掉。
- **根因**：AI 默认沿"happy path"自测；负例需要"主动想到用户会怎么用错"，它不会自己补。
- **修复**：把负例**写进任务卡的验收条件**（错误码分层 D-057 + 七连击作为固定验收项），而不是等它自觉。
- **效果**：七连击全对；此后每张卡验收都带负例清单。
- **面试 30 秒**："AI 自测天然偏向正路径，所以我把负例从'靠自觉'改成'写进验收标准'——验收条件里没有负例的卡不接。"
- **证据**：`review/2026-11-14-T2.12-T2.3验收.md`；D-057。

### K-26 卡外"顺手"改环境，做完才回报

- **现象**：卡里只要求改代码，它顺手修了环境问题（改公共面配置），**做完才回报**，导致"改动范围"和"批准的卡"不一致。
- **定位**：核 `git show --stat` 对比卡片范围，发现卡外文件被改动；且公共面改动没有事前确认。
- **根因**：AI 有"把问题都解决掉"的倾向，但**越界改动**会让审批与回滚失控（尤其 yml/compose/迁移这类公共面）。
- **修复**：确立"**公共面改动先说后做**"：卡外改动必须先报"原因+影响"、批准后落决策（D-052）；验收按 `git diff --name-only` 逐行核范围。
- **效果**：之后每卡改动范围可枚举、可解释；额外修复也都有决策号。
- **面试 30 秒**："AI 会'顺便帮你修'，这在团队里很危险。我要求它的改动范围必须可枚举；改公共配置必须先申请，批准后写进决策记录。"
- **证据**：`review/2026-11-14-T1.6验收.md`；D-052。

### K-27 文档与代码脱节，还会自述"已更新"

- **现象**：`AGENT.md` 的"下一步卡片"停在两张卡之前；`tasks.md` 写着"T2.1–T2.12 全 ✅"（假的）；配置清单/确认单数字漂移。
- **定位**：每轮验收时顺手核一遍文档 vs 实际（读文件 + 数行 + 对 commit），发现多处不一致。
- **根因**：AI 只对"代码任务"负责，文档被当成附属品；加上同一数字在多处手抄 → 必然漂移。
- **修复**：① 一次性对齐补丁（DOC-1，一个 commit 全修）；② 易漂移数字**只留单一来源**、其它处引用而非复制（D-065）；③ 验收清单加"文档一致性"一项。
- **效果**：文档与代码同轮同步（每轮 docs commit + push）；"下一步卡片"永远是最新的一张。
- **面试 30 秒**："AI 写的代码会过，但文档会慢慢失真。我改成'每轮验收同时核对文档'，并把会变的数字收敛到唯一来源，杜绝多处手抄。"
- **证据**：`D:\new\projects\DOC-1_文档对齐补丁卡.md`（已执行）；D-065。

### K-28 小债：每行 `new ObjectMapper()`、重复实现

- **现象**：`TaskController` 在**行映射里**每行 new 一个 `ObjectMapper`，`SummaryService` 也自建一个；功能对，但是浪费且难维护。
- **定位**：review 时读代码发现构造对象的位置不对（循环体内）。
- **根因**：AI 优先"能跑通"，对"单例/复用"这类工程习惯不敏感（尤其 Spring 里应该注入 Bean）。
- **修复**：记为 P3 小债（不阻塞交付），后续注入单例 Bean 一次改掉；**不在功能卡里顺手大改**（避免范围膨胀）。
- **效果**：交付节奏不受影响，债有编号不会丢。
- **面试 30 秒**："AI 代码常见'能跑但工程习惯差'，比如循环里 new 对象。我的处理是记成有编号的小债，单独一张卡改，而不是在功能卡里顺手重构。"
- **证据**：`review/2026-11-14-T3.0-T3.1验收.md` §2（F-3）。

### G-尾 一句话总结怎么治 AI 写码方

> **不信自述、只信复算；测试必须能造红；终态必须最后写；负例写进卡；公共面先说后做；文档同轮对齐；小债编号不丢。**
> 每条都对应上面一个坑——不是"感觉 AI 不靠谱"，而是**七个具体闸门**。

### K-31 两个 AI 同时写同一个仓库：清理→被覆盖→再清理的拉锯

- **现象**：T3.3 期间，我此前起的写码 subagent 与 WorkBuddy 同时写 `D:\new\projects\meeting-notes`。我清掉它的未提交改动后，它按上下文**重写并提交**；
  期间 `.env` 被临时改动、app 镜像被重建、DB 多出测试任务行。仓库出现"我以为干净 → 又被写回"的拉锯，两边都无法确定当前状态。
- **根因**：**没在启动第二个写者之前确认第一个已停**；两个 agent 共享同一工作目录，worktree 也隔离不了（AGENTS.md §5）。
- **修复**：①用户裁决"产物以 commit 为准"（保留 `991f429`，WorkBuddy 转 T3.4）；②我按备份恢复 `.env`（最终 = 原备份 + 仅 `OFFLINE_MODE=false`，hash `2BCC440F1C9E`），
  证据行 88~101 全保留；③规则落地：**一个仓同一时刻只允许一个写者**（D-079 / `rules/dev.md` §4.1 第 9 条），写码任务串行交接。
- **效果**：没有丢代码、没有丢证据；事故本身成了"怎么管多个 AI 写同一个仓"的具体案例。
- **面试 30 秒**："多 AI 并行不是问题，**并发写同一个仓**才是问题。我的处理是把'谁在写'当成状态来管：开工前查残留、写完必须 commit 交接、出事故以 commit 为准而不是听谁说得对。"

### K-32 本地小模型 + 全局 max_tokens：报错信息把我带偏（`application/octet-stream`）

- **现象**：LOCAL 档（qwen2.5:1.5b）在 app 内总是失败，WARN 是 `RestClientException: Error while extracting response … content type [application/octet-stream]`，
  看起来像"服务返回了二进制/协议不对"；但同一环境直连 ollama 却是 HTTP 200 + `application/json` + 合法 JSON（22.2s）。
- **根因**：全局 `LLM_MAX_TOKENS=8192`（云档需要）对 1.5B/CPU 太大 → 生成超过 120s 读超时，客户端拿到的是不完整/不可解析响应，
  Spring 把它表现成"content type 不对"的**误导性症状**。把 `LLM_MAX_TOKENS` 临时调到 512 后 16.8s 就返回了，证明问题是**预算**不是协议；
  但 512 时模型又"不守 JSON 格式"（输出前带散文 + 编日期），于是走"解析失败 → 降级 EXTRACTIVE"。
- **修复**：级联兜底保证用户可见结果不为空；结论记为 F-11——**本地档需要独立的 max_tokens/读超时预算**（新增配置键要用户批准），
  T3.4 先做不改键的部分（JSON 抽取容错 + 本地提示词瘦身）。
- **效果**：`ai_tier` 诚实标 EXTRACTIVE，不 500、不空结果；同时得到一个可复用的诊断套路。
- **面试 30 秒**："报错信息会骗人。我的定位办法是**换一个变量做对照**：直连服务看协议、再调小预算看是不是超时；
  两次对照就把'协议问题'证伪成'预算问题'。"

### K-33 幂等键让"换环境复跑"复用了旧证据行

- **现象**：我想用 `probe.wav` 在改完环境后复跑一次，接口直接返回 `{"task_id":82,"reused":true}`——拿到的是改动前的旧任务，`ai_tier` 是空的，差点被当成"新实现没写 ai_tier"。
- **根因**：幂等是按 `content_hash` 做的（D-055，正确设计）；同一文件重复上传必然复用，不会因环境变了就重跑。
- **修复**：复跑一律**造新样本**（截 20/21/22/23/24s 的派生 wav，hash 各不相同），并检查响应里 `reused=false`；这也正好满足 D-073"新反例用新样本、不删证据行"。
- **效果**：8 条实机证据行（88~101）全部是新任务，每条都能独立复核。
- **面试 30 秒**："幂等是好事，但**验收时它会骗你**——你以为在测新代码，其实在看旧结果。所以我复跑前先看 `reused` 标志，必须造新输入。"

### K-34 测试全绿 ≠ 质量对：摘要"只选一半句子"的 bug 在 T3.3 验收里漏掉了

- **现象**：T3.3 的 97 条单测全绿、我实机也验了 summary 非空，但 T3.4 实机发现 task 104 的 summary **恰好是 transcript 前 67 字**。
- **根因**：`summaryOf` 用 `for (k < Math.min(5, indexes.size()))` 选 top-N，循环体里 `indexes.remove(best)` 让 `indexes.size()` 每轮缩小 → 实际只选出约一半句子。
  句数 ≥10 时仍能选满 5 句（所以 T3.3 的 97 条测试 + 长文本实机全过），只有句数少（104 只有 4 句）才暴露：只选出"首句 + 一个 327 字长句"，长句被"丢句不截句"丢弃 → 只剩首句前缀。
- **修复**：循环前锁定 `take = Math.min(5, indexes.size())`；新增"选取数锁定"回归用例；写码方用同包探针（javac + java）复现定位，我在验收里逐行核了 diff。
- **教训**：**测试只能证明"不回归"，不能证明"质量对"**。质量类任务必须：①实机看**原文**（不是只看字数）；②判据量化（`exactPrefix` 比较、尾句命中位置）；
  ③样本覆盖边界（句子少/极短/无标点）。
- **面试 30 秒**："这个 bug 是 97 条测试全绿时留下的。它暴露的时机很典型——只在输入'句子少'时出现。
  所以我对 AI 写的质量类功能，不只看测试绿，还要拿实机输出跟原文逐条比；这次就是靠'摘要是不是原文前缀'这个量化判据抓出来的。"

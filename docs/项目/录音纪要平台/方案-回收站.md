# 方案：回收站（v0.2 第三件）v1 设计稿

> 状态：**待拍板**（Lead 起草，2026-11-26）。拍板后按 `docs\协作\开发提示词模板.md` 出开工卡给写码方。
> 依据代码：`app/src/main/java/com/meetingnotes/task/TaskDeleteService.java`（141 行，物理删）、`app/src/main/resources/db/migration/V1__init.sql:6-24`（task 表）、`TaskService.java:247` 与 `LinkTaskService.java:262`（`(user_id, content_hash)` 幂等查询）、`storage/StorageService.java:176`（孤儿扫描只认 `source_uri`）。

## 1. 现在是什么样（事实，不是猜测）

- **删除 = 物理删**：`TaskDeleteService.deleteOneInTx()` 同一事务里依次 `DELETE FROM webhook_delivery / dead_letter / task_result / task`，随后**事务外** best-effort 删 MinIO 对象（`purgeObjectBestEffort`，失败只 WARN）。
- **可删状态**只有 `DONE` / `DEAD`；`PENDING/RUNNING/RETRYING` 回 409 `TASK_BUSY`。
- **配额不退还**（D-115）：删了不还分钟、不还次数。
- **三条删除路径**：单条、批量（1..100）、清空失败任务（全部 DEAD）。
- **幂等键**：`ux_task_hash UNIQUE (content_hash)` + `ON CONFLICT DO NOTHING`；同文件重复上传会命中老任务（`reused=true`）。
- **孤儿扫描**：`StorageService.orphans()` 把「库里 `source_uri` 出现过」的对象都当**被引用**；`audioUsage()` 统计整个 `tasks/` 前缀。
- **不可恢复**：一旦点删，转写文本、纪要、标签、死信原因全部消失——这正是用户会踩的坑（误删后无路可走）。

## 2. 目标与非目标

**目标**
1. 点「删除」后任务进**回收站**，可在保留期内**一键恢复**（文本、纪要、标签、收藏、死信原因、原音频都在）。
2. **彻底删除**（手工）与**到期自动清理**两条出口，磁盘最终能真正释放。
3. 回收站里的数据**在所有对外入口都不可见**：列表、详情、分享链接、webhook、配额统计口径清晰。
4. 部署者视角最简：默认值即安全默认，不配也能用。

**非目标（本期不做）**
- 不做「按版本恢复历史内容」（只恢复整条任务）。
- 不做跨用户回收站、不做管理员代删（管理员目前只有建号/解锁）。
- 不改配额策略（删除仍不退分钟，D-115 保持）。
- 不做「删除前自动导出 Markdown」。

## 3. 候选方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A 软删除列 | `task` 加 `deleted_at`，删除=打时间戳；列表/详情/分享全加 `deleted_at IS NULL` | 改动最小、恢复=清空一列、FK 子表不用动、事务简单 | 每条查询都要记得加条件（漏一处就泄露） | **选它** |
| B 独立回收站表 | 删时把 4 张表的行复制到 `trash_*` | 主表干净 | 复制逻辑多、恢复要反向搬运、S3 键与 id 对应关系易错 | 否 |
| C 只保留 S3 对象 | DB 物理删，桶里对象留 30 天 | 不改表 | 「恢复」只能恢复音频、纪要全丢，等于没做 | 否 |
| D 前端假删除 | 只在前端隐藏 | 零后端成本 | 刷新就没、多端不一致 | 否 |

## 4. 关键决策（拍板项，含我的建议）

**D1 数据模型**：`V14__task_deleted_at.sql`
```sql
ALTER TABLE task ADD COLUMN deleted_at TIMESTAMPTZ;
CREATE INDEX ix_task_deleted ON task (user_id, deleted_at);
COMMENT ON COLUMN task.deleted_at IS '非空 = 在回收站；保留期内可恢复，到期物理删';
```
子表（`task_result`/`dead_letter`/`webhook_delivery`）**不动**——恢复时内容还在，这正是软删除的价值。

**D2 删除语义**：三条删除路径全部改为「打 `deleted_at`」，不再 `DELETE`。响应形状不变（`deleted:true`），另加 `trashed:true` 字段便于前端区分（只增不改）。
彻底删除走独立入口（`purge`），只有它对 4 张表执行原物理删 + 删 S3 对象。

**D3 幂等冲突（关键）**：`content_hash` 唯一索引还在，回收站里的任务仍占着这个 hash。
**建议**：同一文件再上传时命中「回收站里的任务」→ **自动恢复该任务并复用**（`reused=true`，响应照旧），并在日志 INFO 记「幂等命中回收站任务，已自动恢复」。
理由：既满足唯一约束，又符合直觉（同一份录音传第二遍，你其实想要它回来）。**不选**「改 hash 腾位置」（会让恢复后 hash 对不上、幂等语义变脏）。

**D4 配额**：进回收站**不退**（D-115 不变）；**恢复不退也不再扣**（没重跑转写）。彻底删除同样不退。文档写死这句。

**D5 可见性**：所有对外入口必须加 `deleted_at IS NULL`
- 列表 / 详情 / 批量重试 / 收藏 / 标签 / 搜索 / 清空失败任务
- 分享链接（`/api/v1/share/{token}`）→ 404
- webhook 投递：回收站任务不再投递（`onTerminal` 前置判断）
- 配额与统计：`/api/v1/quota`、`/api/v1/admin/storage` 的 `audio_objects` 是否含回收站 → **含**（它们确实占盘），另加 `trash_objects`/`trash_bytes` 两个只读字段区分

**D6 自动清理**：`app.trash.retention-days: 30`（`<1` WARN 回退 30）、`app.trash.purge-interval-ms: 3600000`、`app.trash.purge-enabled: true`。
- 复用现有清扫器风格（`@Scheduled(fixedDelayString=...)`，参考 `StalePendingSweeper`），每轮最多清 200 条，日志键 `purged`/`retentionDays`。
- **另有一次启动清理**（参考 `StartupRecovery`），保证不常驻的部署也能清干净。
- 到期判断用 DB 时钟（`deleted_at < now() - interval`），但**换算成 Java 侧时间戳传参**（H2/PG 都能跑，避免 PG 专有 interval 语法）。

**D7 页面上怎么看**：台账筛选条加「回收站」入口（与「全部/今天/近7天/…」同排，或单独一行），进去后：
- 行上显示原状态 + 删除时间 + 「剩余 N 天」；
- 行操作只有「恢复」「彻底删除」（替换原「详情/重命名」）；
- 顶部有「清空回收站」；
- 详情页对回收站任务显示一条提示条：「这条任务在回收站，恢复后才会显示内容」。
- 全部用 `textContent`，确认用站内弹窗（禁用 `window.confirm`，M-13 门禁）。

**D8 接口契约**（全部走既有 Bearer，权限=任务归属本人）
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/tasks?trash=true&limit=&before_id=` | 回收站列表（复用既有分页/筛选骨架；`status` 等筛选在 trash 模式下忽略或保留待定） |
| POST | `/api/v1/tasks/{id}/restore` | 恢复（404 不存在/非本人；409 `TASK_BUSY` 不适用——回收站里不可能在跑） |
| POST | `/api/v1/tasks/batch-restore` | 批量恢复（1..100，逐条部分成功，口径同 batch 删除） |
| DELETE | `/api/v1/tasks/{id}/purge` | 彻底删除（物理删 4 表 + 删对象） |
| POST | `/api/v1/tasks/purge-all` | 清空回收站（当前用户全部） |
| GET | `/api/v1/admin/storage` | 响应新增 `trash_objects`/`trash_bytes`（只增） |

## 5. 自检判据（写码方要能自证，我验收也照这个）

1. 删除后：列表（默认）查不到、`GET /tasks/{id}` 404、分享链接 404、`trash=true` 能查到、行仍在库里（`deleted_at` 非空）。
2. 恢复后：内容逐字段与删除前一致（转写/纪要/关键词/待办/标签/收藏/死信原因），列表重新可见。
3. 彻底删除后：4 张表无该行、S3 对象 404、`audio_objects` 减少 1。
4. 到期清理：造 `deleted_at = now()-31d` → 下一轮 `purged:1`；`retention-days=0` → WARN 回退 30，不误删。
5. 配额：删除→恢复→彻底删除全程 `used_minutes`/`used_tasks` 不变。
6. 幂等：删掉 A（hash H）→ 再上传同一文件 → 返回同一个 `task_id`、`reused=true`、任务回到列表。
7. 并发：两个请求同时「彻底删除」同一个 id → 一个 200 一个 404/幂等 200，不 500。
8. 前端：真 Edge 点击闭环（删除→回收站可见→恢复→列表可见→彻底删除→消失），`pageErrors=[]`、`dialogs=[]`。

## 7. 风险与回滚

- **泄露风险最大**：任何一处查询漏加 `deleted_at IS NULL`，回收站数据会出现在列表/分享/webhook 里。收口手段：① 只允许一个 `TaskVisibilityFilter` 拼条件；② 验收用「删了之后逐个入口打一遍」的清单（第 5 节第 1 条）；③ `git grep "FROM task"` 逐个核对。
- **磁盘不释放**：回收站仍占空间，用户会以为删了。收口：存储页显示 `trash_bytes`，台账回收站入口显示「共 N 个 / M MB」。
- **回滚**：`deleted_at` 列可留（旧代码忽略它即等价于原行为）；迁移只加列加索引，无数据搬迁 ⇒ 回滚 = 部署上一版镜像 + 保留列。
- **SQL 兼容**：到期判断不用 PG 专有 `interval`，在 Java 侧算时间戳（K 系列已踩过两次）。
